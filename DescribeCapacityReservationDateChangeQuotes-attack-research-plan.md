# EC2 DescribeCapacityReservationDateChangeQuotes — Attack Research Plan

Source of leads: online API reference `API_DescribeCapacityReservationDateChangeQuotes.html` (+ `API_CapacityReservationModificationQuote.html`, `API_ModificationQuoteCurrentConfiguration`, `API_ModificationTerms`); local IAM mirror `/work/list_ec2.md` (stale — see doc-gap). Sibling plan: `/work/ec2-CreateCapacityReservationDateChangeQuote-attack-research-plan.md`. Status: documentation-derived hypotheses only; nothing tested against a live account.

## 0. How to use this document
- Each lead: Claim → Mechanism (doc evidence) → Confirm/Refute oracle → Preconditions → Cost → Severity → Stop condition. Work in priority order; look left and right for adjacent bugs.
- This is the **read-only Describe leg** of the Capacity-Reservation date-change-quote family. The *mutating* legs (`CreateCapacityReservationDateChangeQuote` = quote-gen; `ModifyCapacityReservation` = paid apply) are covered in the sibling plan. The prize here is a **cross-tenant disclosure oracle**, not state change.
- HARD STOP: the moment evidence shows an identity/credential/ARN/account belonging to AWS's own service plane (or AWS billing/commerce plane), stop, preserve evidence, flag for AWS-Security disclosure. Reading a *quote* is read-only; do NOT proceed to the paid `ModifyCapacityReservation` apply.

## 1. Pentest Objectives
1. **Read a date-change quote (`crmq-…`) that belongs to another AWS account/tenant** by naming its ID directly — recovering its `currentConfiguration` (instanceCount, originalStartDate, reservationState, startDate) and `modificationTerms` (newStartDate, newCommitmentEndDate, newCommitmentDuration). This is the cross-tenant *capacity/commitment-posture* disclosure oracle.
2. Determine whether the API scopes results by the **caller's account** or merely by **existence** of the quote id.
3. Establish whether `crmq-…` ids are **fabricable/enumerable** (entropy, embedded checksum) so that #1 is reachable without first knowing a victim id.
4. Determine whether a **RAM-shared Capacity Reservation** lets a consumer account read quotes generated by the owner (or vice-versa).
5. Enumerate the `Filter.N` names the API accepts and whether any filter widens visibility or forms an enumeration oracle.
6. Confirm IAM authorization surface: resource-level scoping, condition keys, and whether the Describe can be denied independently of the Create/Modify legs.

## 2. Components, Assets, and Design

**Interface.** EC2 Query/SigV4 API `DescribeCapacityReservationDateChangeQuotes` (API version 2016-11-15), reachable at `https://ec2.<region>.amazonaws.com/`. SDK-surfaced (CLI v2, all SDKs listed). Read-only (`Describe*`). Paginated.

**What it reads.** "Capacity Reservation date change quotes that you generated by using the `CreateCapacityReservationDateChangeQuote` operation." A quote is a short-lived (24h TTL) `crmq-…` object pricing a push-out of the **start date of a future-dated Capacity Reservation not yet delivered**; a push-out extends the commitment (= cost). The apply leg is the separate `ModifyCapacityReservation`.

**Asset disclosed per quote** (`CapacityReservationModificationQuote`):
- `capacityReservationId` (`cr-…`) — links quote → the owner's CR.
- `capacityReservationModificationQuoteId` (`crmq-…`).
- `createTime`, `expirationTime`, `quoteState` (`active | expired`).
- `currentConfiguration` (`ModificationQuoteCurrentConfiguration`): **instanceCount, reservationState, startDate, originalStartDate** — a snapshot of the owner's reserved-capacity posture and scheduling.
- `modificationTerms` (`ModificationTerms` → `reservationUpdate`): **newStartDate, newCommitmentEndDate, newCommitmentDuration** — the extended commitment window (financial terms).
- `TagSet.N` — tags on the quote (may carry customer-authored labels).

**Request inputs.** `CapacityReservationModificationQuoteId.N` (array, 0–1000, **optional**), `Filter.N` (array of `Filter`, optional), `MaxResults` (1–1000), `NextToken`, `DryRun`.

**Identifier shape.** Example id `crmq-123456789abcdefgh` → `crmq-` + 17 lowercase base-32/hex-ish chars (same shape family as `cr-…`, `eni-…`, etc.). Entropy and any embedded checksum are **unverified from docs** — a Step-4 Lens-A question.

```
Caller (account A, SigV4) ──Describe(crmqIds/Filter)──▶ EC2 CR control plane
                                                          │  looks up crmq object
                                                          ▼
                              returns CapacityReservationModificationQuote[]
                              (currentConfiguration + modificationTerms + tags)
   ?? scoped by caller account  — OR —  scoped only by crmq existence ??   ← the whole question
```

## 5. Recommended Areas of Focus

### Area 1 — Cross-tenant quote read by direct id (Lens A — IDOR) — PRIORITY 1
**Background.** The API accepts `CapacityReservationModificationQuoteId.N` as an array of ids. A quote object leaks the owner's reserved-capacity posture (`instanceCount`, `originalStartDate`, `reservationState`, `startDate`) and the extended commitment terms. Nothing in the doc states the lookup binds the quote's owner account to the caller.
**Security Concern.** If the service resolves a `crmq-…` id by existence and returns it without checking that the caller owns (or is RAM-shared) the underlying CR, any account can read another tenant's capacity/commitment posture — a competitive-intelligence / capacity-planning disclosure oracle.
**High-level Test Scenarios.**
- Claim: *Calling Describe with a `crmq-…` id generated by account B, from account A, returns B's quote.* → Oracle: account A receives a `capacityReservationModificationQuoteSet` item with B's `capacityReservationId`/`currentConfiguration` (refute = `InvalidCapacityReservationModificationQuoteId.NotFound` / empty set / `AccessDenied`).
- Claim: *The API validates existence but not ownership* → compare the error/latency for (a) a well-formed id that exists in another account vs (b) a well-formed id that exists nowhere. A **NotFound-vs-AccessDenied / 400-vs-200-empty** differential is itself an existence oracle across the tenant boundary (Lens A oracle variant).
- Claim: *`DryRunOperation` is a caller-IAM-only signal, NOT ownership* — do not treat a DryRun success as proof the foreign quote is readable (it is evaluated before resource resolution; a false-positive trap).
**Doc evidence.** Request param `CapacityReservationModificationQuoteId.N`; response `currentConfiguration`/`modificationTerms`; prose "quotes that *you* generated." **Severity-if-true:** cross-account disclosure = **High** (Critical if it also exposes AWS-plane identifiers — HARD STOP).

### Area 2 — `crmq-…` id fabricability / enumeration (Lens A oracle variant) — PRIORITY 2
**Background.** Reaching Area 1 without a leaked id requires fabricating or guessing a valid `crmq-…`. Example id `crmq-` + 17 chars.
**Security Concern.** If ids are low-entropy, sequential, or lack an embedded checksum, an attacker can enumerate the namespace and harvest quotes (combined with Area 1's existence oracle). Many EC2 resource ids carry a checksum so a *foreign* id cannot even be fabricated — if so, Area 1 is only reachable via a genuinely leaked id (a real mitigation to document).
**High-level Test Scenarios.**
- Claim: *`crmq-` ids embed a checksum that rejects fabricated ids before resource lookup.* → Oracle: a syntactically valid but random `crmq-…` returns a *malformed/invalid-id* error distinct from the *NotFound* returned for a well-formed-but-absent id. Two distinct error classes ⇒ checksum present ⇒ enumeration bounded.
- Claim: *Ids are monotonic/time-correlated* → generate several quotes in a controlled account, inspect ordering/structure; estimate guess cost.
**Doc evidence.** Example id in the reference. **Severity-if-true:** enumerable ids feeding Area 1 = raises Area 1 to **High**; checksum-bounded = Area 1 degrades to "needs a leaked id" (Low likelihood).

### Area 3 — RAM-shared CR → cross-account quote visibility (Lens A / Lens AA) — PRIORITY 2
**Background.** Capacity Reservations are RAM-shareable; the quote is a child of a `cr-…`. The sibling plan's "Fire A" flags cross-account CR quote/apply as the Critical path.
**Security Concern.** When a CR is shared, is the *child quote* namespace also exposed to the consumer (so a consumer reads owner-generated commitment terms), and conversely can the owner enumerate consumer-generated quotes? Share-scope for a parent resource silently extending to a derived financial object is an isolation gap.
**High-level Test Scenarios.**
- Claim: *A RAM-share consumer of `cr-X` can Describe a `crmq-…` the owner generated against `cr-X`.* → Oracle: consumer receives the owner's quote terms.
- Claim: *Revoking the RAM share does not stop the consumer reading previously-visible quotes* (Lens AA revocation completeness) → unshare, then Describe the same `crmq-…`.
**Doc evidence.** CR RAM-shareability (CR service docs) + quote's `capacityReservationId` linkage. **Severity-if-true:** cross-account commitment-terms disclosure = **High–Critical**.

### Area 4 — IAM authorization surface & condition-key coverage (Lens S / Lens R / doc-gap) — PRIORITY 2
**Background.** `/work/list_ec2.md` has **no action definition** for `DescribeCapacityReservationDateChangeQuotes` (only the Create twin appears, at L417, and only inside a tag-on-create table). There is **no `capacity-reservation-modification-quote` / `date-change-quote` resource type** in the local mirror. Online Service Authorization Reference is JS-rendered (WebFetch returns empty).
**Security Concern.** If the Describe has no resource-level scoping and no condition keys, (a) it cannot be carved off from the Create/Modify legs (separation-of-duties collapse mirrors the sibling's `ModifyCapacityReservation` ZERO-condition-key finding), and (b) a grant of a broad `ec2:DescribeCapacityReservation*` likely authorizes reading all quotes the account can resolve — relevant to Area 1 if resolution is existence-based.
**High-level Test Scenarios.**
- Claim: *No condition key (`ec2:Region`, `aws:ResourceTag`, an `ec2:CapacityReservation*` key) can restrict which quotes a principal may Describe.* → Oracle: pull the live action definition via `iam:SimulatePrincipalPolicy` / policy-sim / console JSON; confirm empty condition-key set and `Resource:"*"`-only.
- Claim: *The Describe cannot be denied independently of Create/Modify* → attempt a scoped policy allowing Modify but denying Describe (or vice-versa); confirm whether the service honors it.
- Claim: *`TagSet` on quotes is not usable for ABAC* (no `aws:ResourceTag` condition on the Describe) → so tags are decorative, not an access control.
**Doc evidence.** Local mirror absence (doc-gap); response `TagSet.N`. **Severity-if-true:** separation-of-duties / least-privilege inexpressibility = **Medium** (mirrors sibling CROWN; AWS-owned IAM-expressiveness gap).

### Area 5 — `Filter.N` enumeration & widening (Lens A / Lens U) — PRIORITY 3
**Background.** `Filter.N` is accepted but the reference does **not enumerate valid filter names** for this action ("Filter names and values are case-sensitive").
**Security Concern.** Undocumented filter names are a console-hidden knob (Step 3 discipline). A filter such as `capacity-reservation-id`, `state`, or an owner/account filter could (a) let a caller pivot from a known `cr-…` to its quotes, or (b) if an `owner`/`account` filter exists, widen cross-tenant visibility.
**High-level Test Scenarios.**
- Claim: *An undocumented filter (e.g. `capacity-reservation-id`) lets me list all quotes for a CR id I supply, including a foreign `cr-…`.* → Oracle: Describe with `Filter.1.Name=capacity-reservation-id&Filter.1.Value.1=<foreign cr>` returns quotes.
- Claim: *Case-sensitivity of filter names is a validator differential* — a mis-cased filter name is silently ignored (returns unfiltered = all visible quotes) rather than erroring. → Oracle: compare result count for `State` vs `state`.
**Doc evidence.** `Filter.N` param, "case-sensitive," no enumerated names. **Severity-if-true:** filter-driven cross-tenant pivot = **High**; silently-ignored-filter fail-open = Low–Medium (info/over-return).

### Area 6 — Audit / disclosure-oracle hygiene (Lens O) — PRIORITY 3
**Background.** Read API returning financial/commitment terms.
**Security Concern.** Is `DescribeCapacityReservationDateChangeQuotes` recorded in CloudTrail with the queried ids, so a victim could detect enumeration of their quotes? The family memory notes no CloudTrail docs for commitment/quote events (family-wide gap).
**High-level Test Scenarios.**
- Claim: *Enumerating quotes produces no per-id CloudTrail record, defeating victim-side detection.* → Oracle: inspect CloudTrail event for a Describe call; check whether `requestParameters` includes the queried `crmq`/`cr` ids.
**Doc evidence.** Family CloudTrail doc gap. **Severity-if-true:** **Low / Informational** (enabler for Area 1–3).
