## 1. Lens W — Attestation-conditioned authorization (Nitro Enclaves + NitroTPM)

### Background: what the target page implies vs. what gates it
`ec2-nitro-instances.md` describes the **Nitro security chip** ("integrated into the motherboard") and the **Nitro hypervisor** ("manages memory and CPU allocation") as the hardware roots that make bare-metal/virtualized isolation possible. Those same primitives are what NitroTPM measured-boot and Nitro Enclaves cryptographic attestation are built on (`nitrotpm.md`, `enclaves/latest/user/set-up-attestation.md`). The page itself names only the hardware; the *authorization* consequence — that AWS KMS can gate `Decrypt`/`GenerateDataKey`/etc. on measurements from that hardware via `kms:RecipientAttestation:*` condition keys — lives in the KMS developer guide and is the surface this section tests.

### W-1 — Absent-attestation request: does the gate fail open? **REFUTED by doc text, both mechanisms — record as confirmed-closed, not a finding**
- **Claim:** a `Decrypt`/`GenerateDataKey`/etc. request with no `Recipient` attestation document still satisfies a KMS key policy that conditions on `kms:RecipientAttestation:*`.
- **Mechanism:** `kms/latest/developerguide/conditions-nitro-enclave.md`: *"If the request does not include a valid attestation document from an AWS Nitro enclave, permission is denied because this condition is not satisfied."* `conditions-nitro-tpm.md`: identical sentence for NitroTPM. `enclaves/latest/user/kms.md`: *"If the request doesn't include an attestation document, the role doesn't have permission to call the operation because this condition cannot be satisfied."*
- **Oracle:** call `kms:Decrypt` without `Recipient` against a key whose *only* Allow statement for the caller's principal carries a `kms:RecipientAttestation:*` condition → expect `AccessDeniedException`.
- **Preconditions:** none; this is a direct doc statement.
- **Severity:** N/A — doc explicitly claims fail-closed for *this specific condition* when it is the only grant. Not a lead to spend time on. The real fail-open surface is architectural, not this condition's own evaluation — see W-2.

### W-2 — Fail-open by **policy composition**, not by the condition itself (the real "fail open" risk) ⭐
- **Claim:** an attestation-gated KMS key is nonetheless reachable *without* attestation, because IAM/KMS policy evaluation is **additive-Allow / explicit-Deny**: a `kms:RecipientAttestation:*` condition only constrains the *statement it appears on*. If the key policy, or any identity-based policy for the same principal, contains a **second** `Allow kms:Decrypt` statement without the condition (e.g. the default key policy's account-root "full access" grant, a broad `kms:*` grant to an admin role, or a separately-authored Allow for the same action), that second statement independently satisfies the request — the attestation requirement is bypassed entirely, with no error, because evaluation never has to touch the gated statement.
- **Mechanism:** `kms/latest/developerguide/conditions-attestation.md` itself flags the precondition for this: *"If you don't provide a key policy when you create an AWS KMS key, AWS creates one for you. This default key policy grants the AWS accounts that own the KMS key full access to the key... This policy allows all actions like Decrypt."* The same page's only mitigation offered is informational: *"You can also restrict access by modifying the KMS key policy action for `kms:*` to `NotAction:kms:Decrypt`."* No sample in `conditions-nitro-enclave.md`, `conditions-nitro-tpm.md`, `kms.md`, or `require-attestation-for-kms-key.md` shows a companion explicit-`Deny`-without-attestation statement; every published sample is a single bare `Allow + Condition`, which is a *grant*, not an *exclusivity guarantee*. The customer must independently know to either (a) start from a key policy that denies `kms:*` by default (`NotAction`) or (b) add an explicit `Deny kms:Decrypt unless RecipientAttestation matches` — the docs never say this is required, only that it is possible.
- **Confirm/Refute oracle:** author a key policy with Statement 1 = the AWS-sample Allow+attestation-condition, and Statement 2 = the AWS-default "account root full access" Allow (unmodified). Call `Decrypt` as the account root (or any principal covered by Statement 2) **without** a `Recipient` attestation document. If it succeeds, the gate is confirmed bypassable by composition — this is the predictable, falsifiable "fail open," and it is a **customer policy-authoring footgun that AWS's own sample encourages by omission** (none of the four KMS/enclaves pages instruct the reader to remove or restrict the default full-access statement before adding the attestation Allow).
- **Preconditions:** customer accepts the default key policy, or otherwise leaves a second unconditioned Allow for the same action/principal — a very common state since AWS auto-creates it.
- **Severity:** **High** if confirmed — defeats the entire purpose of attestation-gating (data meant to be readable only by a specific measured enclave/instance becomes readable by any principal covered by the un-gated statement) — but it is a **customer-policy-authoring gap enabled by an AWS-authored doc omission**, not a KMS enforcement bug (the condition itself still evaluates correctly in isolation). File as Lens U (doc-vs-practice) + customer footgun, route the "AWS sample never warns about this" slice to `aws-security` as a doc-completeness defect, same shape as the sibling plan's AF-3.

### W-3 — `PutKeyPolicy` value-acceptance: does authoring-time validation catch bad PCR values? (shared dependency with sibling plans' AF-3/AF-4, extended to Enclaves)
- **Claim:** `kms:PutKeyPolicy` accepts, with no error, a policy document containing: (a) a non-existent PCR id (`kms:RecipientAttestation:PCR99`, `NitroTPMPCR255`); (b) a value that is not valid lower-case hex, or not of plausible SHA-384-length (`conditions-nitro-enclave.md`/`conditions-nitro-tpm.md`: *"The PCR value must be a lower-case hexadecimal string of up to 96 bytes"* — stated as **guidance**, not as a schema the API is documented to enforce); (c) a `StringLike` operator with a wildcard/prefix value instead of the sample's `StringEqualsIgnoreCase` exact match.
- **Mechanism:** IAM/KMS resource policies are opaque JSON to the policy-authoring API; `reference_policies_elements_condition_operators.md` documents `StringLike` (with `*`/`?` wildcards) as a generally valid operator for any **String**-type condition key, and nothing on `conditions-nitro-enclave.md` / `conditions-nitro-tpm.md` restricts the key's `Condition Type: String` to only `StringEquals`-family operators or states that `PutKeyPolicy`/`PutKeyPolicy`-equivalent validates PCR-id numeric range or hex length/format at authoring time. (By contrast, IAM/KMS *do* validate JSON policy grammar; they do not generally validate whether a service-defined context key name is "real" or whether its value matches a service-specific format — that is evaluated only at request time, when the key is populated from the request.)
- **Confirm/Refute oracle:**
  1. **Typo/garbage condition key:** `PutKeyPolicy` with `kms:RecipientAttestation:PCR99` (no such enclave measurement exists) or a 10-character non-hex value → expect **200 OK, accepted**, because policy authoring doesn't validate semantic correctness of condition key names/values. Then confirm the statement is simply inert (`Decrypt` under it never succeeds for anyone, since the context key is never populated to that bogus value) — this is a **silent authoring footgun**: a typo'd Allow-with-condition "fails closed by accident" (never grants, but the author believes it is live) and, far more dangerously, a typo'd **Deny**-with-condition "fails open by accident" (a Deny meant to block non-attested access never fires, because the malformed key never matches, silently voiding the intended protection).
  2. **Wildcard operator:** `PutKeyPolicy` with `"StringLike": {"kms:RecipientAttestation:PCR0": "7f*"}` → expect acceptance (no documented operator restriction). If KMS honors `StringLike` at evaluation time the same as any IAM context key, this converts an intended full 48-byte SHA-384 image-hash pin into a short-prefix match — weakening the binding from "this exact enclave image" to "any image whose PCR0 happens to share this hex prefix." Given PCR0 is a cryptographic hash, a short literal prefix is not attacker-forgeable by preimage search at reasonable prefix lengths, but it **is** a realistic risk if an author (reasonably, by analogy to S3 `s3:prefix` `StringLike` patterns shown elsewhere in AWS's own IAM docs) writes a short pattern believing it is "starts with," not realizing the full hash length still has to be reasoned about — mis-sized wildcards (e.g., truncating a copy-pasted 96-byte hex value and appending `*`) silently broaden the grant with no error at authoring time.
- **Preconditions:** none beyond normal `kms:PutKeyPolicy` permission; purely a documentation-vs-API-behavior question, answerable without touching the Nitro Hypervisor.
- **Severity:** **Medium–High.** A Deny-based protection silently voided by a typo'd/malformed condition key is the dangerous case (fail-open with no error signal); an Allow-based grant silently broadened by an unvalidated wildcard is the second. Both are AWS-API-behavior questions (does `PutKeyPolicy` validate), not Nitro-hardware questions, so **in scope** and not a hard-stop.
- **Scope:** in-scope, customer-facing (policy-authoring surface); the underlying "does the API validate condition-key semantics" question is itself testable via `iam:SimulateCustomPolicy` or a live `PutKeyPolicy` call — no enclave/instance required to establish the primitive, same as the sibling SEV-SNP plan's Area 1 methodology.

### W-4 — Under-binding: which single PCR is "enough," and does the docs' own guidance invite weak policies? (Enclaves-specific; NitroTPM side owned by sibling AF-1/AF-3)
- **Claim:** a KMS key policy pinned to only **one** of the six enclave measurements grants far more broadly than a reader would assume from the phrase "attestation-gated."
- **Mechanism — exact measurement semantics from `enclaves/latest/user/set-up-attestation.md`:**
  - **PCR0** = enclave image file hash ("what code"). **PCR1** = kernel+bootstrap. **PCR2** = application. **PCR3** = SHA-384 of the **IAM role ARN** of the *parent instance* ("ensures... the parent instance has the correct IAM role" — binds *where*, not *what*). **PCR4** = SHA-384 of the parent instance ID ("ensures... a specific instance ID" — binds *which exact instance*, not *what code*). **PCR8** = signing-certificate hash ("ensures... booted from an enclave image file signed by a specific certificate").
  - The doc's own worked example in `conditions-nitro-enclave.md` pins **only PCR1** (kernel/bootstrap hash) in its illustrative policy. The `prescriptive-guidance` best-practice sample (`require-attestation-for-kms-key.md`) pins PCR0,1,2,3,4,8 together — i.e. AWS's *own* best-practice doc implicitly concedes that a smaller set (as shown in the KMS reference-page example one click away) is insufficient, but neither page cross-links the other to say so explicitly.
  - `set-up-attestation.md` explicitly recommends combining **PCR3+PCR8** ("We recommend that you use PCR3 and PCR8 together for the best flexibility") — but PCR3+PCR8 together bind *role* + *signing cert*, and **conspicuously never bind PCR0** (the actual code hash). A policy built exactly to this recommendation authorizes **any image signed by the right cert, run under the right role** — including a different, attacker-modified application (different PCR2) as long as it's rebuilt with the same signing key, which the signing key's owner (presumably the same customer, but also anyone who obtains that private key — a supply-chain/key-custody question entirely outside AWS's control) can always produce.
- **Confirm/Refute oracle:** author a policy pinned only to PCR3+PCR8 (per the doc's own recommended pairing); build two enclave images — "trusted" and "malicious" — signed by the same certificate and launched under the same parent-instance IAM role, with different PCR0/1/2 (different code). Confirm **both** satisfy the condition and both successfully `Decrypt`. If so, the AWS-recommended "best flexibility" pairing is confirmed to not bind code identity at all — which the doc text already implies by omission (it talks about role/cert flexibility, never claims code-integrity coverage for that pairing) but never states as a limitation in a security-relevant way (no "Warning: PCR3+PCR8 alone do not verify which application is running" callout exists on the page).
- **Preconditions:** attacker needs the signing private key and the ability to run something under the pinned IAM role — i.e. this is a **privilege a legitimate holder of the signing key/role already has**, not a cross-tenant bypass. The finding is "the recommended minimal pairing is weaker than its name ('best flexibility') suggests," a Lens-U doc-expectation gap, not an unauthorized-access bug.
- **Severity:** **Medium** (doc-completeness / guidance gap — AWS's own "best flexibility" recommendation can be followed exactly and still not deliver code-attestation if the reader assumed PCR3+PCR8 implies PCR0 coverage).
- **Scope:** in-scope, documentation-completeness.

### W-5 — Debug-mode all-zero PCRs: confirm fail-closed, not fail-open
- **Claim:** enclaves launched with `--debug-mode`/`--attach-console` produce attestation documents with all-zero PCRs. If any key policy's condition value happens to be (or is weakly pinned toward) all-zeros, a debug enclave would satisfy it.
- **Mechanism:** `set-up-attestation.md`: *"Enclaves launched using the `--debug-mode` or `--attach-console` options generate attestation documents with PCR values made up entirely of zeroes... These attestation documents can't be used for cryptographic attestation."* The doc asserts this as a hard rule but does not state *which component* enforces it — whether KMS specifically special-cases all-zero PCRs and rejects them regardless of policy content, or whether the "can't be used" claim is purely a matter of no legitimate reference measurement ever being zero (i.e., enforcement is incidental, not special-cased).
- **Confirm/Refute oracle:** (a) does KMS documentation anywhere state it special-case-rejects all-zero attestation documents independent of policy match? (current read: **no** — the enforcement appears to rely entirely on no real reference measurement being zero, which is a property of the *policy author's* input, not a platform guarantee). (b) If a policy author ever pins a condition to an all-zero value (e.g., by copy-paste error, or because a never-extended/optional PCR legitimately reads as zero for a given build — this is exactly the open question the sibling NitroTPM plan raises for PCR12-all-zeros in `prepare-attestation-service.md`'s own sample), a debug-mode enclave would satisfy that specific condition. This mirrors the sibling plan's AF-3 PCR12-all-zeros finding, extended here to Enclaves PCR values generally.
- **Preconditions:** a policy author pins (deliberately or by error) an all-zero reference value for some PCR.
- **Severity:** **Medium** — contingent, not a universal fail-open; the enforcement appears to be "no legitimate image ever hashes to zero," which is sound in practice but is a property the docs assert rather than something KMS is documented to independently verify.
- **Scope:** in-scope, doc-completeness; chains with W-3/W-4.

### W-6 — Capability-reporting ground truth: which instance types can even reach this surface?
- **Claim/finding (confirmed from docs, not a vulnerability — scoping fact for the whole Lens-W section):** `NitroEnclavesSupport` and `NitroTpmSupport` (`API_InstanceTypeInfo.md`: `unsupported | supported`) are the authoritative capability flags (`aws ec2 describe-instance-types --query 'InstanceTypes[].[InstanceType,NitroEnclavesSupport,NitroTpmSupport]'`). Cross-referencing `enclaves/latest/user/nitro-enclave.md`'s "Parent instance requirements" table against `ec2-nitro-instances.md`'s bare-metal lists:
  - **Bare-metal (`.metal*`) instance types are excluded from Nitro Enclaves support** across every family shown (e.g. `m5.metal`, `c5.metal`, `r5.metal`, and every later-generation `.metal-24xl`/`.metal-48xl`/`.metal-96xl` size listed under "except"). The smallest size in nearly every family (`.large`/`.medium`) is also excluded.
  - **Mechanism tie-in:** `nitro-enclave.md` states enclaves are created by "partitioning memory and vCPUs from a Nitro-based parent instance" via the **Nitro Hypervisor**. `ec2-nitro-instances.md` describes bare metal as giving "full access to host hardware" and eliminating "virtualization overhead" — i.e., the Nitro Hypervisor's memory/CPU-partitioning role that enclaves depend on is exactly the layer bare metal is designed to bypass. The exclusion is therefore a direct, documented, mechanism-consistent consequence, not an arbitrary restriction — useful as a **falsifiable scoping check** (`DescribeInstanceTypes` should show `nitroEnclavesSupport=unsupported` for every `.metal*` type) rather than a security finding.
  - **NitroTPM** has a narrower *allow-list* of virtualized types (`enable-nitrotpm-prerequisites.md`) that excludes some Nitro-System instance families entirely (e.g. no `G4ad`, `DL1`, `Trn1`/`Trn1n`, several storage-optimized Nitro-v3 types) even though those families appear in `ec2-nitro-instances.md`'s Nitro-System tables — confirming "built on Nitro" (the target page's framing) is **not** equivalent to "NitroTPM/Enclaves-capable," and a customer threat-modeling from the Nitro-instances page alone would over-assume attestation coverage.
- **Oracle:** `describe-instance-types --filters Name=bare-metal,Values=true --query 'InstanceTypes[].NitroEnclavesSupport'` should return all `unsupported`; `describe-instance-types --filters Name=nitro-enclaves-support,Values=supported` intersected with the NitroTPM allow-list in `enable-nitrotpm-prerequisites.md` should reproduce the family exclusions by hand-diff.
- **Severity:** Informational — a scoping/capability-reporting fact, not a vulnerability. Feeds every other W-lead's "preconditions" field (attestation leads only apply to the supported subset).
- **Scope:** in-scope, trivially confirmable from the API reference alone, no live account required beyond a read-only `DescribeInstanceTypes` call.

## 2. Lens V/D — Isolation boundary (bare metal, Nitro hypervisor, Nitro security chip)

### Background
`ec2-nitro-instances.md`: *"The Nitro System provides bare metal capabilities that eliminate virtualization overhead and support workloads that require full access to host hardware."* Nitro components list: *"Nitro security chip, integrated into the motherboard"*; *"Nitro hypervisor — A lightweight hypervisor that manages memory and CPU allocation and delivers performance that is indistinguishable from bare metal for most workloads."*

### V/D-1 — The documented isolation guarantee vs. its enforcement is an AWS hardware/firmware property — **HARD STOP, do not probe**
- **Claim framing (Lens-U shaped, not a hunting target):** the page's implicit guarantee is that bare-metal "full access to host hardware" is *tenant-scoped* host hardware — i.e., giving a customer unmediated hardware access does not also give them a path to another tenant's co-resident workload or to the Nitro control plane, because the Nitro **security chip** (described elsewhere, e.g. the AWS Nitro System whitepaper linked from this very page, as handling the root-of-trust/attestation functions "below" the host OS, independent of what the host CPU can see) sits outside what "full access to host hardware" grants.
- **Mechanism:** the page links out to `https://aws.amazon.com/ec2/nitro/` for the full architecture; the sibling `isolate-data-operators` plan already documents the canonical AWS claim (sourced from the Nitro security whitepaper): *"no mechanism for any AWS system or person to log in to Nitro hosts, access instance memory, or access customer data..."* — this is the same B1/HARD-STOP boundary that plan already identifies, extended here to the bare-metal-specific question of whether unmediated hardware access (vs. a virtualized guest) changes the answer.
- **Decision:** **Do not probe.** Whether the Nitro security chip's isolation between a bare-metal tenant and (a) the Nitro control plane or (b) a different tenant's co-resident allocation actually holds is a hardware/firmware property of AWS's own fleet. Any evidence suggesting it does *not* hold is a **critical AWS-service-plane finding requiring immediate disclosure**, not a documentation-research deliverable to keep investigating. State the boundary explicitly (done) and stop.
- **Severity:** N/A / out-of-scope by design. Recorded as an explicit null per task instructions, not silence.

### V/D-2 — The useful in-scope angle: documented guarantee vs. what the capability-reporting API actually promises (Lens U)
- **Claim:** the page's prose ("full access to host hardware", "indistinguishable from bare metal") is a *performance* claim dressed in security-adjacent language; it does not itself claim an isolation SLA, and no condition key or API field lets a customer *require* or *verify* bare-metal tenancy exclusivity (contrast with Dedicated Hosts/Dedicated Instances, which **do** have an explicit, documented, billable, API-visible single-tenancy guarantee via `ec2:Tenancy`/`dedicatedHostsSupported`).
- **Mechanism:** `API_InstanceTypeInfo.md` exposes `bareMetal` (boolean) and `dedicatedHostsSupported` (boolean) as independent, orthogonal fields — a bare-metal instance type is not inherently a *Dedicated Host*; "bare metal" describes the hypervisor-bypass performance characteristic, "dedicated" describes the billing/tenancy-exclusivity guarantee. A customer who conflates "bare metal = my hardware alone, nobody else's workload ever runs here" with the documented meaning is building a false assumption the page's wording invites but never corrects — the page never states "a bare-metal instance type is run on a host otherwise shared with other tenants/instances only via standard On-Demand allocation, exactly like a virtualized instance, unless you also use Dedicated Host."
- **Confirm/Refute oracle:** doc review only — search `ec2-nitro-instances.md`, `instance-types.md`, and the Dedicated Hosts/Tenancy docs for any sentence equating "bare metal" with tenancy exclusivity. Current read: **absent** — bare metal and Dedicated Host/Tenancy are documented as separate, independently selectable properties (`dedicatedHostsSupported` field exists precisely because not every bare-metal type implies host-level exclusivity by default, and conversely Dedicated Hosts support plenty of non-bare-metal types too).
- **Severity:** **Low/Informational** — doc-completeness gap, customer-footgun shaped (a compliance narrative built on "I chose bare metal so no one else is on this hardware" is wrong unless Dedicated Host/Tenancy was *also* chosen). Worth flagging to `aws-security` as a Tier-2 clarity gap given how security-adjacent the "full access to host hardware" phrasing reads out of context.
- **Scope:** in-scope, customer-facing, doc-only (no live testing needed — this is confirmable by reading the Tenancy/Dedicated Host docs for the explicit boundary and finding it absent from the nitro-instances page specifically).

### V/D-3 — Boot-time integrity check as an inadvertent timing/DoS surface on bare metal
- **Claim:** `ec2-nitro-instances.md`: *"In most cases, when you launch a bare metal instance, the underlying server goes through its boot process, during which it verifies all hardware and firmware components. This means that it can take up to 20 minutes or more from the time the instance enters the running state until it becomes available over the network."* This is a documented **availability** characteristic (long, variable launch latency) rather than a confidentiality/integrity issue.
- **Mechanism/Oracle:** confirm whether this 20-minute(+) window is uniform across bare-metal families or variable enough that a customer's auto-scaling/failover logic (sized against virtualized-instance launch latency assumptions) could treat a healthy-but-still-booting bare-metal replacement as failed, causing self-inflicted flapping — a **single-tenant availability footgun**, not a cross-tenant issue.
- **Severity:** Informational — single-tenant self-availability consideration; **out of scope** as a security finding (no cross-tenant or AWS-plane angle), noted only because the task asked to frame the bare-metal boundary completely.
- **Scope:** out of scope / low-value; recorded for completeness per the task's instruction to state the boundary explicitly.

## 3. Lens Y — Transport trust ("Encryption in transit", Nitro v3+)

### Background
`ec2-nitro-instances.md`, Nitro v3 bullet: *"Encryption in transit."* No further detail on that page — the mechanism is defined in `AWSEC2/latest/UserGuide/data-protection.md#encryption-transit`.

### Y-1 — "Automatic" encryption is default-on **only inside a narrow, silently-exited envelope** ⭐ (the crown lead for this lens)
- **Claim:** a customer who reads "some instance types... automatically encrypt in-transit traffic between instances... There is no impact on network performance" and the Nitro v3+ "Encryption in transit" bullet, and concludes "traffic between my [Nitro v3+] instances is encrypted," is building a compliance claim on a guarantee that **silently stops applying** the moment any one of three conditions is violated — with **no runtime signal, metric, log field, or API** telling the customer encryption did not occur for a given flow.
- **Mechanism — exact requirements from `data-protection.md`:**
  > "To support this additional in-transit traffic encryption between instances, the following requirements must be met: + The instances use the following instance types: [specific list] + The instances are in the same Region. + The instances are in the same VPC or peered VPCs, **and the traffic does not pass through a virtual network device or service, such as a load balancer or a transit gateway.**"
  - **(a) Instance-type pairing:** both ends must be on the supported-type list (`network-info.encryption-in-transit-supported=true`). The list is large but **not universal** — e.g., it excludes most burstable T-family types, many `.large`/base sizes, and numerous older/general compute families. Mixed-type traffic (one supported, one not) is not addressed by the doc at all — the reasonable reading is that encryption requires **both** ends to support it, meaning a single unsupported peer silently drops the whole flow back to the baseline (physical-layer-only, intra-AZ-unencrypted-at-this-layer) protection with no error.
  - **(b) Same Region.**
  - **(c) Same VPC or peered VPCs, **and** no intervening virtual network device/service** — explicitly including Load Balancers and Transit Gateways. This is the sharpest cliff edge: introducing an ALB/NLB, a Transit Gateway, or (by extension/ambiguity — doc doesn't explicitly list every device) likely a NAT Gateway or AWS PrivateLink endpoint between two otherwise-qualifying instances **silently disables** this layer of encryption, while the architecture diagram and the "automatic" framing give no visual or API indication that the property was lost.
- **Verification gap:** the only customer-facing lever is `describe-instance-types --filters Name=network-info.encryption-in-transit-supported,Values=true` — a **static, per-type capability flag**. It answers "can this instance type ever do this," never "did this specific flow, right now, between these two specific instances, actually get encrypted." There is no IAM condition key, no VPC Flow Logs field, no CloudWatch metric, and no KMS-style attestation mechanism (contrast directly with Lens W's `kms:RecipientAttestation:*`, which *does* let a customer **require and verify** a cryptographic property before a request succeeds) that lets a customer condition on, deny on, or retroactively audit whether in-transit encryption actually applied to given traffic. Unlike attestation, which fails closed and loudly (`AccessDeniedException`), this transport property fails open and silently (packets simply flow, unencrypted at this extra layer, indistinguishable on the wire/API from the encrypted case).
- **Confirm/Refute oracle (documentation-only, falsifiable):**
  1. Search `data-protection.md`, `ena-express.md`, and the EC2 API reference for any **per-flow** observability signal (flow log field, CloudWatch metric, VPC Reachability Analyzer check) that reports whether a specific connection was encrypted by this mechanism. Current read: **absent** — only the static type-capability filter exists.

Search for any IAM/SCP/VPC mechanism to **require** this encryption (e.g., deny `ec2:RunInstances` for unsupported types, or deny traffic egress through a disqualifying device) — i.e., can an org *enforce* the compliance property it might want to claim, rather than merely enable it opportunistically? ### Y-2 — Layered-encryption language could mask the absence of the inner layer

## 4. Lens L — Shared-host cross-tenant contention (equal-share, CPU credits, Flex burst)

### Background
`ec2/latest/instancetypes/instance-types.md`: *"Amazon EC2 dedicates some resources of the host computer, such as CPU, memory, and instance storage, to a particular instance. Amazon EC2 shares other resources of the host computer, such as the network and the disk subsystem, among instances. If each instance on a host computer tries to use as much of one of these shared resources as possible, each receives an equal share of that resource. However, when a resource is underused, an instance can consume a higher share of that resource while it's available."*

### L-1 — The "equal share" guarantee has no customer-visible enforcement mechanism, denominator, or SLA ⭐
- **Claim:** the "equal share" sentence is the *entire* documented guarantee against noisy-neighbor degradation of shared resources (network, disk subsystem) on a multi-tenant host — and it specifies **no** denominator (equal share of how many co-tenants — 2? 20? is there a cap on co-tenancy density per host that would bound the worst case?), **no** time horizon (equal share measured over what window?), **no** enforcement mechanism (is this QoS-ticketed/weighted-fair-queued in the Nitro card's networking hardware, or a best-effort statistical outcome?), and **no** customer-facing metric that distinguishes "I am getting my equal share and that share is simply small because many tenants are active" from "I am being starved below my equal share by misbehavior or a platform bug."
- **Mechanism:** the sentence itself, plus the Nitro-card bullet list on the target page (`ec2-nitro-instances.md`): *"Nitro card: Local NVMe storage volumes, Networking hardware support, Management, Monitoring, Security"* — i.e., the Nitro card is named as the place network/storage hardware support and monitoring live, but the page never connects that hardware to the "equal share" fairness mechanism, nor cites any CloudWatch metric that would let a tenant observe their own slice versus the host-wide contention level.
- **Confirm/Refute oracle (doc-only):** search `ec2-instance-network-bandwidth.md`, EBS performance docs, and CloudWatch EC2 metrics reference for (a) any metric that reports "your share of a shared resource is currently reduced due to co-tenant demand" vs. generic "your own instance's throughput right now" (which conflates self-caused and neighbor-caused reduction indistinguishably), and (b) any documented per-host co-tenancy density cap. Current read: EC2 exposes only *your own* instance-level network/disk metrics (e.g. `NetworkIn/Out`, EBS `VolumeQueueLength`), not a host-level fairness/contention indicator — a tenant cannot distinguish "the network is fine, I'm just not using much" from "I'm being throttled to my fair share because 50 noisy neighbors are maxed out" from "I'm being throttled below my fair share, which would be a platform bug," from the metrics alone.
- **Severity:** **Medium as a visibility gap, informational-to-High as a hypothesis depending on confirmation path.** The claim that is actually testable *without* touching AWS's fleet is narrower: **can a tenant on a shared host, using only their own documented resource allocation, construct a workload that denies a measurable share of shared network/disk bandwidth to a co-resident tenant beyond the "equal share" the doc promises** — this requires a live multi-tenant placement under the researcher's control (two accounts' instances confirmed co-resident on the same physical host), which is **not establishable from documentation alone** and is exactly the kind of claim that, if demonstrated, is a cross-tenant resource-isolation finding against AWS's hypervisor/network-card fair-queueing implementation — i.e. **High severity if ever confirmed, but the confirmation step itself reaches into AWS's own fleet behavior (hypervisor-level QoS enforcement) and must be flagged for disclosure rather than pursued as an independent "bug," per the HARD STOP rule.** The documentation-only, safely in-scope deliverable here is the **gap itself**: no SLA, no fairness-violation-distinguishing metric, no density cap disclosed.
- **Scope:** **split scope.** (i) The doc-completeness/visibility gap (no metric to tell fair-queueing-working from fair-queueing-violated) is in-scope and fully confirmable from docs alone — record it as a finding. (ii) Any attempt to actually *demonstrate* one tenant degrading another beyond "equal share" requires reaching into the Nitro hypervisor/network-card's real-world QoS enforcement on shared fleet hardware — **flag as HARD STOP / route to AWS-Security disclosure if evidence is ever obtained**, do not pursue as a standalone customer-side test.

### L-2 — CPU-credit accounting: self-DoS and billing-edge framing, not cross-tenant (mostly out of scope, with one in-scope sliver)
- **Claim A (out of scope):** can a T-instance's own CPU-credit exhaustion ("gradual reduction to baseline CPU utilization... cannot burst above baseline until it accrues more credits" — `burstable-credits-baseline-concepts.md`) be weaponized? This is **single-tenant self-DoS** (a tenant can only exhaust *their own* credit balance) — explicitly out of scope per the task framing and per the mechanism: credits are tracked per-instance, not shared or borrowable across tenants, and nothing in `burstable-credits-baseline-concepts.md` or `burstable-performance-instances-unlimited-mode.md` describes a cross-instance or cross-tenant credit interaction.
- **Claim B (in-scope, Low severity, billing/metering-adjacent):** Unlimited mode's billing model — *"the hourly instance price automatically covers all CPU usage spikes if the average CPU utilization... is at or below the baseline over a rolling 24-hour period... If the instance runs at higher CPU utilization for a prolonged period, it can do so for a flat additional rate per vCPU-hour"* — creates an averaging window a cost-conscious customer could try to game (burst hard for a short period, then force idle to pull the 24h rolling average back under baseline before the window closes) to get sustained-high-throughput work done while minimizing the additional per-vCPU-hour surcharge. This is a **customer optimizing their own bill**, not an attack on anyone else — recorded only because the task asked whether CPU-credit accounting is "manipulable for billing/perf abuse"; the honest answer is: manipulable for **the account's own billing optimization**, not for abusing AWS or any other tenant, so it is **not a security finding**, just a noted null result.
- **Severity:** N/A / Low-informational, non-security (billing optimization is legitimate customer behavior, not abuse, absent a ToS violation question which is outside this plan's remit).
- **Scope:** out of scope (self-DoS, legitimate billing optimization); recorded as an explicit null per task instructions.

### L-3 — Flex instances' "95% of the time" clause: a documented, bounded exception window
- **Claim:** `instance-types.md`: Flex instances "deliver... up to 100 percent CPU performance for **95 percent of the time** over a 24-hour window" and "running at a high CPU utilization that is consistently above the baseline for long periods of time might see **a gradual reduction** in the maximum burst CPU throughput." This is a documented, bounded, **self-targeting** degradation (the instance's own sustained high usage reduces its own future burst ceiling) — the doc does not frame the remaining "5% of the time" or the "gradual reduction" as a function of co-tenant demand, so on its face this reads as a per-instance throttling algorithm (akin to T-instance credits) rather than a shared-resource contention effect.
- **Confirm/Refute oracle (doc-only):** does any Flex-instance doc attribute the reduction to *host-level* contention (shared-resource Lens-L mechanism) vs. a *per-instance* algorithmic cap (self-contained, like CPU credits)? Current read: the doc's wording ("instances running at a high CPU utilization... might see a gradual reduction") attributes the cause to the instance's **own** utilization pattern, not to co-tenants — so this reads as the same self-contained category as L-2's CPU credits, not a Lens-L cross-tenant mechanism. Recorded as a **null result**: Flex "95%" framing does not, on current doc evidence, describe a noisy-neighbor-exposed mechanism; it describes a self-throttling one.
- **Severity:** Informational / null.
- **Scope:** out of scope as cross-tenant; in-scope only as a doc-completeness question (does AWS ever disclose whether the undocumented 5%/throttle threshold varies with host-wide load — current read: no, and that absence is itself unremarkable since the doc frames it as self-caused).
