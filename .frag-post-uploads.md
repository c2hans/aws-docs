## 1. Cluster summary

This cluster is AWS's SigV2 and SigV4 mechanism for **unauthenticated browsers** to `PUT`-equivalent objects directly into S3 via `multipart/form-data` HTTP POST, authorized by a **caller-constructed, server-validated JSON "POST policy"** (base64'd, signed by the bucket owner's secret key, handed to the untrusted browser as an opaque blob). The trust model is unusual for AWS: the signer (site operator) is trusted, but the **browser is the party that assembles and submits the actual field values** that get checked against the policy's `conditions` array. The security of the whole mechanism rests entirely on:
1. the operator writing a policy whose conditions are **tight** (exact-match or narrow `starts-with`), and
2. S3's server-side policy evaluator enforcing those conditions **exactly as documented** (no condition = no restriction).

Both SigV2 (`UsingHTTPPOST.md`, `HTTPPOSTForms.md`, `HTTPPOSTExamples.md`, `HTTPPOSTFlash.md`, `postVersions.md`) and SigV4 (`sigv4-*.md`) variants share the identical policy-condition grammar (`eq` / `starts-with` / `content-length-range`), the identical rule that "**any field present in the form but absent from `conditions` is NOT constrained**", and the identical mass-assignable field set: `acl`, `success_action_redirect`/`redirect`, `Content-Type`, `Content-Disposition`, `x-amz-meta-*`, `x-amz-website-redirect-location`, `x-amz-storage-class`. This is a textbook mass-assignment surface (Lens Q/mass-assignment) layered under a signature mechanism that only covers what the *policy author chose to cover* — the attack surface is "what did the operator forget to pin," not "can I forge the signature."

## 3. Ranked, lens-mapped falsifiable leads

### Lead 1 — Mass-assignment of `acl` via POST policy omission (Lens Q / mass-assignment / Lens S)
**Claim:** If a site operator's POST policy conditions array omits an `acl` condition entirely, the browser can set `acl=public-read-write` (or `public-read`) on any uploaded object, even though the operator never intended objects to be publicly accessible.
**Mechanism (doc evidence):** HTTPPOSTForms.md L141: "Each form field that you specify in the form (**except** AWSAccessKeyId, signature, file, policy, and field names that have an x-ignore- prefix) **must be included** in the list of conditions" — implying the server does *validate* presence-in-conditions for fields present in the form, BUT this is a client-authoring discipline, not a server-enforced invariant on fields NOT present in the form declaration at authoring time. More directly: every one of AWS's own worked examples (HTTPPOSTExamples.md L31 `{"acl": "public-read"}`; sigv4-post-example.md L34 same) pins `acl` to exactly one value — demonstrating AWS's own guidance is "pin acl or get burned." The condition-matching table (HTTPPOSTForms.md L151, sigv4-HTTPPOSTConstructPolicy.md L73) explicitly supports `starts-with` for `acl`, meaning an operator could (and some real-world policies do) write `["starts-with","$acl",""]` — "Matching Any Content" (HTTPPOSTForms.md L172) — which, per the docs, "allow[s] any content within a field." If applied to `acl`, this is a documented, self-inflicted mass-assignment of ACL = any value including `public-read-write`.
**Confirm/Refute oracle:** Construct a policy whose conditions array has no `acl` entry at all (not even starts-with) alongside a form that still submits `acl=public-read-write`; per the "must appear in conditions" rule a strict implementation should 400/403 this request (condition violation: field present, not in conditions) — confirm whether S3 actually enforces that invariant, or whether (per common real-world misconfig) a policy using `starts-with $acl ""` is what operators actually ship, which the docs affirmatively teach as the "Matching Any Content" pattern.
**Preconditions:** Operator-authored policy that includes `acl` only via an empty-prefix `starts-with` (a pattern AWS's own doc explicitly demonstrates as reusable for `success_action_redirect` and does not warn against reusing for `acl`).
**Severity-if-true:** Medium–High (self-inflicted public-bucket-content exposure; falls under Lens U — doc teaches a pattern whose generalization to a sensitive field is never flagged as dangerous).

### Lead 2 — Unpinned `key` via empty-prefix `starts-with` → arbitrary key / overwrite outside intended prefix (Lens Q, path-traversal variant)
**Claim:** A POST policy using `["starts-with","$key",""]` (the documented "Matching Any Content" idiom, HTTPPOSTForms.md L172 / sigv4-HTTPPOSTConstructPolicy.md L50) permits the browser to write to **any key in the bucket**, including overwriting objects outside the intended per-user prefix (e.g., `../other-user/file`, or just directly naming another tenant's existing key), because `starts-with` with an empty value is, per the docs, unconditional.
**Mechanism (doc evidence):** The `key` condition "Supports exact matching and starts-with" (HTTPPOSTForms.md L154); the canonical, repeatedly-shown-safe pattern is `["starts-with","$key","user/eric/"]` (HTTPPOSTExamples.md L30, sigv4-post-example.md L33) — a non-empty prefix. The docs never state that S3 performs path-canonicalization or segment validation on `key` beyond prefix string-matching; `key` is treated as an opaque string match, not a path. There is no documented restriction preventing a key value of e.g. `user/eric/../../victim/secret.html` from satisfying a `starts-with "user/eric/"` string condition, since string `starts-with` does not collapse `..` segments the way a filesystem would, but S3 object keys are flat strings (not resolved as paths), so a key literally containing `../` is still a distinct, valid key starting with the required prefix — meaning the uploaded content lands at a literal key named `.../../victim/secret.html`, not actually at `victim/secret.html`. This downgrades the traversal variant to Low (S3 keys are not path-resolved) but the **empty-prefix mass-assignment of `key` remains the live issue**: an operator who uses `starts-with $key ""` (same empty-value idiom AWS documents for `success_action_redirect`) grants the browser write access to any key in the bucket, overwriting arbitrary existing objects (including ones outside any per-user prefix, such as site assets, other users' uploads, or `crossdomain.xml`).
**Confirm/Refute oracle:** Policy with `["starts-with","$key",""]` plus `acl` pinned; submit `key=crossdomain.xml` (or any attacker-chosen existing object key) and observe whether the overwrite is accepted — a true positive is any successful overwrite of a key the operator did not intend to expose to anonymous POST.
**Preconditions:** Operator reuses the documented empty-prefix idiom for `key` (plausible exactly because AWS's own docs demonstrate the idiom generically under "Matching Any Content" without scoping the warning to `success_action_redirect` only).
**Severity-if-true:** Medium (overwrite primitive, not read; severity rises to High if the overwritten key is `crossdomain.xml`, a website-hosting index/error page, or another tenant's object — chains into Lead 5/Lead 6).

### Lead 3 — `success_action_redirect` / `redirect`: documented open-redirect, with bucket/key/etag reflected into the target URL (Lens CC / open-redirect / Lens G)
**Claim:** `success_action_redirect` is a browser-supplied, policy-constrained redirect target that S3 itself issues (HTTP 303) after a successful anonymous or policy-authenticated upload, and S3 appends `bucket`, `key`, and `etag` as query-string parameters to **whatever URL the browser supplied** — turning any upload into an S3-origin-triggered redirect to an attacker-chosen URL carrying attacker-influenced content (the key name) in the query string, if the policy's condition on this field is `starts-with ""` (any value) as AWS's own doc explicitly demonstrates.
**Mechanism (doc evidence):** HTTPPOSTForms.md L92 / L212: "The URL to which the client is redirected upon successful upload. Amazon S3 appends the bucket, key, and etag values as query string parameters to the URL... If Amazon S3 cannot interpret the URL, it ignores the field." No allowlist, no same-origin requirement, no host validation is documented — the only check described is syntactic URL-parseability. The condition-matching table's **own canonical example** for "Matching Any Content" is literally `["starts-with", "$success_action_redirect", ""]` (HTTPPOSTForms.md L172, sigv4-HTTPPOSTConstructPolicy.md L50) — i.e., AWS's documentation teaches, as the flagship example of unconstrained matching, exactly the pattern that creates an open redirect from the `*.s3.amazonaws.com` origin to an arbitrary attacker-chosen URL. HTTPPOSTExamples.md's sample response (L163) shows the actual `Location:` header construction: `https://.../successful_upload.html?bucket=...&key=user/eric/MyPicture.jpg&etag=...` — demonstrating the reflected-parameter mechanics plainly.
**Confirm/Refute oracle:** Submit a POST with a policy containing `["starts-with","$success_action_redirect",""]` and `success_action_redirect=https://evil.example/phish`; confirm S3 issues `303 Location: https://evil.example/phish?bucket=...&key=...&etag=...` for a successful upload. This is an open redirect originating from a trusted `*.amazonaws.com` host — classic phishing/SSRF-pivot primitive (Lens CC) and, since the key/etag are attacker-influenced reflected values, a potential injection point into the target site if that site trusts the query string.
**Preconditions:** Operator uses the exact "Matching Any Content" idiom AWS documents for this field (the only field for which this idiom is explicitly worked through in the docs) — i.e., AWS's own canonical example is the vulnerable configuration.
**Severity-if-true:** High (open redirect from an AWS-trusted origin, explicitly taught by AWS's own sample as the way to allow "any" redirect target; no documented host/scheme allowlist mechanism exists for this field at all, even for operators who want one).

### Lead 4 — `success_action_redirect`/`redirect` field-name duplication / deprecation ambiguity (Lens S — condition-key semantics)
**Claim:** Both `success_action_redirect` and the deprecated `redirect` field name map to the **same** policy condition element name (`success_action_redirect, redirect` is listed as one combined row, HTTPPOSTForms.md L155, L196; RESTObjectPOST.md L112, L196), raising the question of whether a policy pinning `success_action_redirect` to an exact value also implicitly fails to constrain a request that instead supplies the legacy `redirect` field name — i.e., a condition written against one field name might not be evaluated against its synonym, giving an unconstrained-redirect bypass of an otherwise-correct exact-match policy.
**Mechanism (doc evidence):** HTTPPOSTForms.md L92: "The redirect field name is deprecated and support for the redirect field name will be removed in the future" — implying both names are *currently* live and both resolve to redirect behavior, but the docs never clarify whether a policy's condition keyed on `$success_action_redirect` is cross-checked against a form submission that uses `redirect` instead.
**Confirm/Refute oracle:** Build a policy with `{"success_action_redirect": "https://good.example/ok"}` (exact match) but submit the form with `redirect=https://evil.example/phish` instead of `success_action_redirect`. If S3 enforces the condition only by the exact field name `success_action_redirect` and treats `redirect` as a different, unconstrained field (which per policy-condition rules — "each form field... must be included in list of conditions" — would mean the request should be *rejected* for having an unconstrained field present), confirm whether rejection actually happens, versus the alternate failure mode where S3 silently accepts `redirect` as an alias with no condition cross-check (bypass).
**Preconditions:** Operator policy written only against the modern field name; attacker uses the legacy alias.
**Severity-if-true:** Medium–High if confirmed as a bypass (this is the Lens X "legacy-alias twin" shape — an action with a documented control that has a legacy alias potentially not enforcing the same condition).

### Lead 5 — Flash `crossdomain.xml`: publicly-writable-by-the-same-mechanism cross-origin trust artifact (Lens Q + Lens J, legacy)
**Claim:** The documented `crossdomain.xml` sample (`<allow-access-from domain="*" secure="false" />`) is itself commonly uploaded to the bucket **using this same POST mechanism**, and if the operator's POST policy for the bucket uses a broad/empty `key` prefix (Lead 2) or the bucket itself is publicly writable (Lead 7), an attacker can overwrite `crossdomain.xml` with a malicious version or create one in a bucket that lacked it, changing cross-origin trust for any legacy Flash content still served from that bucket.
**Mechanism (doc evidence):** HTTPPOSTFlash.md L15: "you must upload a publicly readable crossdomain.xml file to the bucket" — the doc gives the wildcard `domain="*"` sample as the normal/expected configuration, with the caveat (L28) that it "does not grant access to the actual Amazon S3 bucket" via Flash itself. But it does not address what happens if the attacker can overwrite/plant `crossdomain.xml` via the key-mass-assignment path (Lead 2) in a bucket that also hosts other sensitive content reachable by Flash cross-domain policy.
**Confirm/Refute oracle:** Documentation-only; this is a chain hypothesis — "can an attacker reach the key needed to write/overwrite crossdomain.xml via a POST policy with an under-scoped key condition" (ties to Lead 2's oracle). No live testing performed.
**Preconditions:** Legacy SWF content still served from the bucket; bucket's POST policy has an under-scoped `key` condition.
**Severity-if-true:** Low–Medium today (Flash is EOL; relevance is primarily to legacy buckets that still serve old SWF content) — flag as a null-hypothesis-leaning lead; AWS likely considers this out-of-scope / historical, but documentation-wise it is still a live, present-tense instruction in the current guide (no deprecation notice on HTTPPOSTFlash.md itself, unlike the explicit SOAP EOL notice elsewhere).

### Lead 6 — Content-Type mass-assignment → stored-"active-content" / MIME-sniffing chain into website-hosting XSS (Lens Q, output/render-side variant)
**Claim:** `Content-Type` is a browser-supplied form field (HTTPPOSTForms.md L89/97; sigv4-HTTPPOSTForms.md L69) that, if the policy's condition is a broad `starts-with` (AWS's own example: `["starts-with","$Content-Type","image/"]`, HTTPPOSTExamples.md L33, sigv4-post-example.md L36) or omitted/empty-prefixed, lets the browser store any file (including HTML/SVG/JS) under a `Content-Type` the browser also controls (e.g., `text/html`, `image/svg+xml`) — meaning the *declared* MIME type and the *actual* file bytes need never match (there is no documented true-type validation anywhere in these pages). If that bucket is also configured for static website hosting (a configuration this cluster's docs don't themselves cover but reference adjacently via `x-amz-website-redirect-location`, RESTObjectPOST.md L119), an uploaded "image" with attacker-chosen `Content-Type: text/html` and HTML/JS payload bytes becomes a same-origin stored-XSS payload when later fetched.
**Mechanism (doc evidence):** No field in HTTPPOSTForms.md, sigv4-HTTPPOSTForms.md, or RESTObjectPOST.md's form-field tables documents any content-sniffing, magic-byte validation, or enforcement that uploaded bytes match the declared `Content-Type`. The `Content-Type` starts-with comma-list matching rule (sigv4-HTTPPOSTConstructPolicy.md L49, "Matching Content-Types in a Comma-Separated List") is purely a string-prefix check against the declared header value, not the payload.
**Confirm/Refute oracle:** This is a chained, cross-cluster lead — the actual rendering/sniffing behavior lives in the website-hosting docs (out of this cluster's assigned page set), so mark as **doc-gap requiring cross-cluster confirmation**: does the website-hosting cluster's docs state Content-Type is honored verbatim on GET with no sniffing override? If yes, this upload path is the stored-XSS delivery vector into that surface.
**Preconditions:** Target bucket has static website hosting enabled; POST policy's `Content-Type` condition is `starts-with` with a broad prefix or absent.
**Severity-if-true:** High if confirmed (stored XSS equivalent on an S3-website origin) — flagged for cross-referencing with the website-hosting cluster's researcher.

### Lead 7 — Anonymous/no-policy POST path: "succeeds only on publicly writable buckets" — fully unconstrained mass-assignment (Lens Q / Lens U)
**Claim:** When no `policy` field is present, S3 treats the request as fully anonymous; the docs state this "will succeed only on publicly writable buckets" (HTTPPOSTForms.md L91; RESTObjectPOST.md L111) — on such a bucket, **every** field (`acl`, `key`, `Content-Type`, `x-amz-meta-*`, `success_action_redirect`, etc.) is attacker-controlled with zero server-side condition checking, since the entire policy-condition enforcement mechanism (Section/Lead 1-4 above) is bypassed by construction. This is not a bug in the mechanism — it's the documented, intended fallback — but it means every mass-assignment concern above is maximized (not just "under-scoped policy" but "zero policy") whenever a bucket is publicly writable, and the docs' own emphatic warning ("we highly recommend [a policy] over making a bucket publicly writable," HTTPPOSTForms.md L111) confirms AWS is aware this fallback is the worst case.
**Mechanism (doc evidence):** HTTPPOSTForms.md L91, L111; sigv4-HTTPPOSTConstructPolicy.md L19 ("If you make the bucket publicly writable, you have no control at all over which users can write to your bucket").
**Confirm/Refute oracle:** N/A for live testing (requires an actually-public bucket, which is an operator misconfiguration, not an S3 enforcement gap) — this is a **null-hypothesis-leaning** lead: the mechanism works exactly as documented and exactly as warned against. Record as confirmed-by-documentation-design, not a defect.
**Preconditions:** Bucket ACL/bucket-policy is public-write (operator misconfiguration, heavily and explicitly warned against in-doc).
**Severity-if-true:** Out of scope as an S3 defect (customer-footgun, explicitly and repeatedly warned against in the exact pages describing it) — included here only to make the escalation path explicit when combined with Leads 1-6.

### Lead 8 — SigV4 POST signature coverage: does the signature actually bind the fields it doesn't need to re-derive? (Lens Y)
**Claim:** The SigV4 POST "StringToSign" is the **base64-encoded policy document itself** (sigv4-UsingHTTPPOST.md L46-69; sigv4-authentication-HTTPPOST.md L40-57), not a hash over the actual multipart form body. This means the signature cryptographically binds only the `conditions` array's *literal text* — any field present in the form that is *also* unconstrained by `conditions` (per Leads 1-7) is **entirely outside the cryptographic signature's protection**, even though the request as a whole is "signed." The signature guarantees "the operator approved this exact policy text," not "the operator approved this exact request" — the two diverge precisely at every under-scoped condition.
**Mechanism (doc evidence):** sigv4-authentication-HTTPPOST.md L40: "For signature calculation the POST policy is the string to sign" — confirms the signature covers the policy document bytes only, not the submitted form-field values directly (those are checked against the policy post-hoc by the condition evaluator, a separate mechanism from signature verification).
**Confirm/Refute oracle:** Documentation-only structural observation — this is the root cause explaining why Leads 1-6 are possible at all despite the request being "signed": signature validity (Lens Y) and condition enforcement (Lens S) are two different checks, and the signature says nothing about fields the policy author forgot to constrain. No further live confirmation needed beyond what's stated; flag as the unifying mechanism note for the whole cluster.
**Preconditions:** N/A — structural property of the protocol as documented.
**Severity-if-true:** Informational/structural — explains why this entire cluster's severity rests on policy-authoring discipline rather than any cryptographic weakness.

### Lead 9 — POST Object restore (`RESTObjectPOSTrestore`) SELECT output location: caller-specified `OutputLocation.S3` bucket/ACL/grantee/KMS on an authenticated (non-anonymous) path (Lens A / Lens H, adjacent surface)
**Claim:** Distinct from the form/policy mechanism, `RESTObjectPOSTrestore.md`'s SELECT-type restore request lets an authenticated caller specify an arbitrary `OutputLocation.S3.BucketName`, `CannedACL`, `AccessControlList` (grantee by email/ID/URI), `Encryption.KMSKeyId`, and `Prefix` for where SQL-query results land (L165-202, L245-276) — the only documented constraint is "must be in the same AWS Region as the bucket that contains the input archive object" (L23) and that "the AWS account that initiates the job must have permissions to write to the S3 bucket" (L23). This is IAM-gated, not policy-condition-gated, so it is a different trust boundary than Leads 1-8, but it is adjacent surface worth flagging: does S3 verify the caller's `s3:PutObject` permission on the **output** bucket before or after accepting the job, and can `CannedACL`/`AccessControlList` grant unintended external parties (by email/URI) access to the query output regardless of the output bucket's own policy?
**Mechanism (doc evidence):** RESTObjectPOSTrestore.md L23, L165-202, L245-276.
**Confirm/Refute oracle:** Doc-gap — the permission-check *ordering* (validate output-bucket write access vs. after query execution) and whether `AccessControlList`/`CannedACL` on output objects can bypass bucket-level public-access-block settings are not stated in this page; mark as doc-gap requiring the S3 Select / Glacier Select querying-archives page (out of this cluster's assigned set) for confirmation.
**Preconditions:** Caller has `s3:RestoreObject`/`s3:GetObject` on the source but the real question is permission validation on an arbitrary *destination* bucket named in the request body.
**Severity-if-true:** Medium (IAM-gated at the destination, but ACL-grant-by-email/URI is a documented mechanism that could leak query results beyond the destination bucket's intended audience if ACLs aren't blocked at the account level) — lower priority than Leads 1-8 since it requires valid IAM credentials already.

## 4. Null hypotheses / doc gaps (pages checked)

- **Replay / stale-policy reuse:** No page in this assigned set (`UsingHTTPPOST.md`, `HTTPPOSTForms.md`, `sigv4-HTTPPOSTConstructPolicy.md`, `sigv4-authentication-HTTPPOST.md`, `sigv4-post-example.md`) states a nonce, single-use token, or any anti-replay mechanism beyond the `expiration` timestamp and (SigV4) `x-amz-date`. The only enforced temporal control is "policy is not valid after midnight UTC on `<date>`" (HTTPPOSTForms.md L136; sigv4-HTTPPOSTConstructPolicy.md L38). **Within its expiration window, nothing in these pages states a policy+signature pair cannot be submitted multiple times** (replayed for repeated uploads to the same constrained key/prefix). This is likely intended behavior (a policy is meant to be reusable "per user" or "for all uploads" per HTTPPOSTForms.md L108/L21), so flagging as a doc-confirmed design choice, not a gap — but worth noting no doc states a server-side single-use enforcement exists, so an operator who assumes "signed = one-time" is relying on an undocumented (and seemingly false) assumption.
- **Server-side true file-type / content-sniffing validation:** checked `HTTPPOSTForms.md`, `sigv4-HTTPPOSTForms.md`, `RESTObjectPOST.md` form-field tables in full — no field or sentence anywhere describes magic-byte checking, SVG sanitization, or decompression/zip-bomb handling for the `file` field. Treated as a **doc-gap, not confirmed-absent** — these pages simply don't discuss it either way (the mechanism may exist in a different page, e.g. a malware-scanning feature page, not assigned to this cluster).
- **SSRF via `success_action_redirect`:** the field is a client-followed redirect (browser receives 303 and follows it, or doesn't) — it is **not** a server-side fetch by S3's own fleet identity (S3 does not dereference the URL itself; it only emits a `Location:` header). Checked HTTPPOSTForms.md L204-221 and RESTObjectPOST.md L112/196 explicitly for any server-side fetch language — none found. **Confirmed null for classic SSRF (Lens G)** — this is an open-redirect/phishing primitive (Lens CC), not an SSRF-from-AWS-fleet-identity primitive. Downgrade any framing of this as "SSRF" accordingly; it is client-side-followed redirect only.
- **x-amz-meta-* injection/validation:** HTTPPOSTForms.md L96 and RESTObjectPOST.md L116 both explicitly state "Amazon S3 does not validate or use this data" — confirms by design there is no server-side interpretation of these values (so no injection into S3 behavior is possible via this field; downstream application-level risk only if the operator's own site later renders metadata unsanitized — out of scope for this cluster, in scope for whichever cluster covers object metadata/GetObject response rendering).
- **DevPay `x-amz-security-token` dual-token mechanism:** present in both SigV2 and SigV4 docs (HTTPPOSTForms.md L95/157; sigv4-HTTPPOSTConstructPolicy.md L83) but Amazon DevPay is a long-retired program; not pursued as live surface — informational/legacy only.
- **AWS Amplify sample (`browser-based-uploads-aws-amplify.md`):** the page is a thin, dated wrapper example (uses `aws-amplify` v1-era API, Cognito Identity/User Pool config) and contains no POST-policy, no ACL, no bucket-policy guidance at all — it defers all authorization entirely to Cognito-scoped IAM credentials, which this page does not detail. **Doc-gap**: the sample's `Storage.put('test.txt', 'Hello')` (default/public level) vs `level: 'private'` example never states what IAM/Cognito role scoping backs the "public" vs "private" level distinction, nor whether a misconfigured Identity Pool could let `level: 'public'` writes escalate beyond the intended prefix (Amplify's actual implementation scopes `public/`, `protected/`, `private/{identity_id}/` prefixes via Cognito-generated IAM policy — not documented on this page at all). Flagged as doc-gap — confirm surface via Amplify/Cognito-specific documentation, out of this cluster's assigned page set.
- **Versioning (`postVersions.md`):** reviewed in full; purely a data-integrity/concurrency note (`x-amz-version-id`, suspended-versioning `null` ID). No access-control implication found. **Null — confirmed, no lens fires.**
- **HTTP 100-Continue note (RESTObjectPOST.md L18):** informational only, no security relevance found.
