Inspector AMI (machine-image) scanning cross-account snapshot-content read (plan _run1008b H2, run 2026-10-08-1, [[env-sessions]] accts A=183174222929 / B=289531347876). Full results: `/work/aws-docs/_run1008b/results/security-services.md`.

**H2 = REFUTED at two independent layers — the "B's Inspector reads A's snapshot" break is structurally unreachable:**
1. **EC2 ownership gate at RegisterImage:** `register_image(BlockDeviceMappings=[{Ebs:{SnapshotId: <A-owned, shared via createVolumePermission>}}])` from B => **400 InvalidParameterValue "Snapshot does not belong to <B-acct>"**. A `createVolumePermission` share grants volume-creation ONLY, not AMI registration. B cannot mint an AMI backed by a foreign-owned snapshot. (B CAN `describe_snapshots` the shared A-owned snap and see owner=A — visibility != registerability.)
2. **CopyImage makes B-owned copies:** A shares AMI via launchPermission; B `copy_image` => new AMI backed by a NEW **B-owned** snapshot copy (verified owner=B). Inspector scanning B's copy reads B's own snapshot, never A's.
3. **AMI SLR KMS decrypt is account-scoped:** created SLR `AWSServiceRoleForAmazonInspector2Ami` (create_service_linked_role for `ami.inspector2.amazonaws.com` SUCCEEDS in a plain member — service principal registered). Live attached policy = **`AmazonInspector2AmiScanServiceRolePolicy`** (NOTE: live name != plan/docs' `AmazonInspector2AmiServiceRolePolicy`). `kms:Decrypt` on `key/*` is conditioned **`StringEquals{aws:ResourceAccount: ${aws:PrincipalAccount}}`** + `kms:ViaService:ec2.*` + ebs encryption-context → can only decrypt CMKs in its OWN account. Cannot decrypt A's key. ebs:GetSnapshotBlock/ListSnapshotBlocks on `snapshot/*` is service-account-access-gated.
   - Left/right: a 2nd statement grants ebs-read+kms:Decrypt on resources tagged `aws:ResourceTag/InspectorEc2Exclusion=true` WITHOUT the ResourceAccount cond — but cross-account KMS still needs A's key policy to grant B (two-party authz, A controls) → no break. Observation only.

**Live API gap (botocore 1.43.109):** inspector2 exposes NO machine-image/on-demand surface — no `StartOnDemandScan`/`GetOnDemandScanStatus`/`ListOnDemandScans`; `UpdateConfiguration` input = ec2Configuration(activateVMScanner,scanMode)+ecrConfiguration only, **no amiConfiguration**. The Sept-8-2026-documented AMI feature's data plane is NOT yet served. DOC-GAP — the on-demand AMI scan verbs can't be exercised. ListCoverage filterCriteria resourceType is an unconstrained string (no AMI enum).

**Managed-policy breadth (Lens R, intra-account, AWS-authored):** `AmazonInspector2FullAccess_v2` carries a CURATED org set (EnableAWSServiceAccess, RegisterDelegatedAdministrator, ListDelegatedAdministrators, DescribeOrganization/Account/OU, ListPolicies, Describe{Resource,Effective}Policy) — **NOT** blanket `organizations:*` (plan overstated it). RegisterDelegatedAdministrator/EnableAWSServiceAccess are org-mgmt-account-gated → no member self-escalation to DA. `AWSInspector2OrganizationsAccess` NOT present as standalone managed policy (NoSuchEntity). Not a boundary breach.

**Teardown gotcha — AMI SLR is NON-DELETABLE (run 2026-10-08-1):** `create_service_linked_role(ami.inspector2.amazonaws.com)` succeeds, but `delete_service_linked_role` then `get_service_linked_role_deletion_status` returns **FAILED "Cannot delete the role due to internal errors"** with EMPTY RoleUsageList, repeatably (6+ attempts / 25 min). Role is unused (RoleLastUsed={}), harmless (account-scoped grants, data plane not live). Reaper failure is AWS-side — likely the AMI-scanning backend the SLR-deletion reaper calls isn't deployed yet (matches missing data-plane verbs). **DO NOT create this SLR unless needed** — you can't clean it up during the run; it becomes a residual requiring operator retry after the feature GAs. (Right-after-submit the status endpoint can also return NoSuchEntity "Cannot find deletion status" — a separate consistency quirk.) Snapshot/AMI cheap substrate: 1 GiB gp3 vol → create_snapshot (no instance needed if only testing ownership primitives; empty snap has no packages so can't prove content-enum, but ownership gate fires before that matters).
