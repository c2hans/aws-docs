Kinesis Data Streams **data-delivery / channel** feature (StreamsDataDelivery plan) is LIVE in both in-scope accounts, us-east-1. SDK botocore 1.43.95 models CreateChannel/DeleteChannel/DescribeChannel/ListChannels/UpdateChannel natively (no hand-crafted SigV4 needed). Run 2026-10-02-1 outcome: every priority lead REFUTED or low-sev doc weak-default. The feature is well-defended.

**Why / what was tested & observed (so future runs skip re-proving):**
- **Lead 1 PassRole: REFUTED — ENFORCED.** CreateChannel synchronously checks `iam:PassRole` on `ServiceExecutionRoleARN`. Scoped principal lacking PassRole → `AccessDeniedException: not authorized to perform: iam:PassRole ... because no identity-based policy allows`. The documented IAM "lifecycle" table omitting PassRole is a doc gap only.
- **Lead 2 confused deputy: REFUTED.** Cross-account pass role blocked outright: `AccessDeniedException: Cross-account pass role is not allowed.` AND `aws:SourceArn` IS genuinely stamped — a role whose trust pins a *specific* (non-matching) channel ARN fails `ValidationException: Unable to assume the service execution role` at create. So specific-channel trust binds. Only the AWS **sample** trust uses `channel/*` (any channel in acct) which contradicts the best-practices.md L31 promise "only your specific delivery can assume the role" — a Lens R/U weak-default in an AWS-authored sample, but practically bounded by PassRole gating. Low/informational.
- **Lead 3 cross-account S3 exfil: REFUTED — consent-gated.** CreateChannel validates destination bucket access at create time using the passed role. B→A bucket WITHOUT A's bucket policy → `ValidationException: Unable to access the S3 bucket`. ADD A's bucket policy granting B's role → channel creates + reaches ACTIVE (advertised cross-account feature works only with bucket-owner consent). `ExpectedBucketOwner` enforced at create: wrong owner (999999999999) → `ValidationException: expected bucket owner matches the actual bucket owner`.
- **Lead 4 key-template traversal: REFUTED.** ChannelName rejects consecutive periods ("must not contain consecutive periods") and `/` (regex). OutputKeyTemplate rejects `..`/period-only-segment/leading-`/`. Stream names DO allow `..` (e.g. `vh..dot` created fine) and `!{stream-name}` is a supported template var — but S3 keys are opaque strings (no fs traversal) and IAM resource prefix matching is literal, so `..` in a key yields no real prefix escape. Non-exploitable.
- **Lead 5.7 KMS `StringEqualsIfExists` vacuous-allow: CONFIRMED (low, AWS-sample weak-default).** The shipped `KMSForCreateTimeValidation` statement (data-delivery-iam.md ~L144) grants kms:Decrypt+GenerateDataKey conditioned only on `StringEqualsIfExists kms:ViaService`. SimulateCustomPolicy: ViaService ABSENT → **allowed** (direct non-Kinesis KMS use), ViaService=s3 → implicitDeny. No `kms:EncryptionContext` pin (unlike the sibling KMSForDecryptSourceStreamRecords which IS bound). Defense-in-depth gap; role only assumable by kinesis.amazonaws.com so impact limited. Routing: account-operator / doc fix.
- **Left/right REFUTED:** cross-account DescribeChannel → `AccessDeniedException` "no resource-based policy allows" (own-acct missing channel gives `ResourceNotFoundException` instead — clean 403/404 discriminator, boundary IAM-enforced before lookup). Cross-account RegisterStreamConsumer (EFO) → `AccessDeniedException`.

**Operational gotchas:** CreateChannel S3 StorageConfiguration requires `CompressionType` (NONE/GZIP/ZSTD...). ChannelId is a ~17-char lowercase-alnum token (e.g. `78y09tumh9bq0u5mi`), NOT the UUID the plan assumed. Limit ~1 channel per stream per destination-type (`LimitExceededException`). DescribeChannel takes `ChannelARN` (not ChannelName). Default OutputKeyTemplate = `kinesis-channel/!{channel-name}/!{channel-id}/!{yyyy}/!{MM}/!{dd}/!{HH}/...`. DataFreshness min 300s so delivery is slow — don't wait for objects to prove create/consent logic (all enforced synchronously at CreateChannel). Delete channels before streams (ResourceInUse). See [[aws-env-setup]].
