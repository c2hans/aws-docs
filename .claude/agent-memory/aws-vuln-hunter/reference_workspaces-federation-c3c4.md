**WorkSpaces directory federation (RegisterWorkspaceDirectory / ModifyCertificateBasedAuthProperties) — all SDK-reachable in botocore 1.43.x.**
Register validation gauntlet ORDER (each gates the next, so cheap bogus probes stall early): DirectoryId-or-identity-combo -> WorkspaceDirectoryName (IdC path) -> SubnetIds (2, same VPC) -> AZ-ID must be in {use1-az4,use1-az6,use1-az2} -> workspace-type/identity-type combo -> Tenancy -> **secret-ARN account check**. Map subnets by `AvailabilityZoneId` not AZ name.
- Identity-type combos: `AWS_IAM_IDENTITY_CENTER` needs WorkspaceDirectoryName, only PERSONAL (not POOLS), Entra DomainJoin needs Tenancy=DEDICATED which needs **BYOL account entitlement** (unmeetable in test accts -> Entra ApplicationConfigSecretArn path blocked before secret validation). `CUSTOMER_MANAGED`+ActiveDirectoryConfig works only with WorkspaceType=POOLS, needs `workspaces_DefaultRole` IAM role to exist (cheap to create: trust workspaces.amazonaws.com + AmazonWorkSpacesServiceAccess/SelfServiceAccess).
- **WS-SECRET = REFUTED (same-account enforced at config-validation):** AD-path `ActiveDirectoryConfig.ServiceAccountSecretArn` pointing at a B-account secret -> `InvalidParameterValuesException "Please verify that the AwsAccountIds of your calling account and SecretArn match."` vs own-A secret -> different error "verify the ARN exists and WorkSpaces has access to it". The two distinct messages ARE the oracle: cross-account rejected on account-mismatch BEFORE any dereference. No confused-deputy, no fleet-identity read.
- **WS-CBA = BLOCKED:precondition:** ModifyCertificateBasedAuthProperties validates `ResourceId` (a real directory) FIRST — bogus ResourceId -> identical `ResourceNotFoundException "Unable to find domain"` for foreign-B and own-A CA ARNs. CA-ARN account unreachable without a fully-provisioned MicrosoftAD/self-managed-AD directory (costly). Inference: same same-account guard as WS-SECRET. Don't stand up a directory for this.
- **WS-IDC = REFUTED-by-design:** IdC instance ARNs are account-less (`arn:aws:sso:::instance/...`). Both accounts see the SAME org instance `ssoins-7223cfab9178db6f` / identity store `d-9067d20885` (org o-pf2hyvtase). No foreign-instance ARN variant is constructible, so no cross-account oracle exists.
- WS-SAML = client-side redirect only (SSRF refuted by design, not tested).

**AgentCore AgentRegistry (agent-registry-control):**
- **AR-ORG = REFUTED:** `create_registry(autoDetectionConfiguration={scope:ORGANIZATION,enabled:True})` from a member account -> `ValidationException "The caller's AWS Organization is not onboarded to auto-detection. Enable trusted access for the AWS Agent Registry service..."`. Org-scoped auto-detection gated behind org trusted-access (mgmt-account action; organizations:* is SCP-denied here). Member account cannot silently enable cross-account discovery.
- AR-KMS (I4): see prior note — same-account KMS "guarantee" is advisory not enforced, but exploitation needs B to grant the agent-registry service principal; encryption-context `aws:agent-registry:registry-arn` embeds owner account (working defense); aws:SourceAccount inert (guidance gap). Boundary-dependent.

**AgentCore Evaluators (bedrock-agentcore-control CreateEvaluator) — BAC-DERIVE = REFUTED:**
Derived evaluator `evaluatorConfig.derived.baseEvaluatorId` can ONLY reference `Builtin.*`/`ThirdParty.*` ids. A custom account-owned evaluator id (format `name-xxxxxxxxxx`) is categorically rejected: `ValidationException "baseEvaluatorId '...' is not a known base evaluator. It must be a registered Builtin.* or ThirdParty.* evaluator ID."` — IDENTICAL for A->B foreign id AND A->A-own id; `Builtin.Correctness` succeeds. The CFN pattern that appears to allow a custom-id-shaped baseEvaluatorId is not enforced that way server-side (model-vs-enforcement delta, safe direction). No cross-tenant custom-evaluator reference path. (Eval create quirks: instructions need single-brace placeholders e.g. `{context}` for TRACE level; model must be available in-region — `amazon.nova-micro-v1:0` works, claude-3-haiku ids rejected as unavailable.)

**App Signals InstrumentationConfig (application-signals CreateInstrumentationConfiguration) — E5 = BLOCKED:precondition + structural refute of cross-tenant/egress interpretation:**
No caller-specified sink/destination in the Create input (sink is service-determined, NOT attacker-choosable); `Service`/`Environment` are account-scoped names. So there is NO primitive to redirect another tenant's capture anywhere the caller chooses -> cross-tenant SSRF-style egress refuted structurally. There is no snapshot/capture-read API in application-signals (capture lands in a service CloudWatch/App-Signals store). Residual risk is INTRA-account privilege separation only (applicationsignals:Create* without code-read capturing runtime secrets) — requires a running instrumented workload to demonstrate; out of cross-tenant scope. Don't stand up an instrumented service for it.

**NSM service-linked role `NetworkSecurityManagerServiceRolePolicy` (Tier-2 doc audit) = REFUTED:**
ZERO `*:*` wildcard-action statements. Granular/resource-scoped: WAFv2 webacl/rulegroup mutation scoped to wafv2 ARNs; ELB/CloudFront/APIGW/Cognito/AppRunner/AppSync/Amplify/VerifiedAccess SetWebACL remediation; Shield; Config recorder; READ-ONLY organizations (Describe/List); `iam:CreateServiceLinkedRole` scoped to specific service SLR paths (shield/config/wafv2). No PutRolePolicy/PassRole/privesc primitive. The `s3:PutBucketPolicy` grant is scoped to `aws-waf-logs-*` buckets (owner's own WAF-log buckets). The doc-claimed wildcard is absent.
