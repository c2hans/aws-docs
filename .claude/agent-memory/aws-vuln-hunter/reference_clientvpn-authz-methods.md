Client VPN authorization-policy trio: `ec2:{Get,Modify,Delete}ClientVpnEndpointAuthorizationPolicy` (boto3 1.43.108). Tested sweep-3 2026-10-06 (vh-run-id=20261006-cvpnauthz). See [[agentcore-env]] for accounts.

**No-endpoint IAM oracle (key technique):** For these EC2 ops the IAM permission check PRECEDES resource validation — DryRun on a syntactically-valid but non-existent endpoint id (`cvpn-endpoint-<17hex>`) returns `DryRunOperation` (412) if authorized, `UnauthorizedOperation` if not. So the ENTIRE IAM-granularity analysis needs NO provisioned endpoint. All three require only `ClientVpnEndpointId`; all support `DryRun`.

**Authoritative action-name discovery:** assume a scoped role with NO ec2 perms, DryRun → `UnauthorizedOperation` whose message carries `Encoded authorization failure message:`; `sts:decode_authorization_message` → `context.action`/`context.resource` = the exact IAM action string + ARN the service checks. Admin has DecodeAuthorizationMessage.

**L1 verdict (REFUTED, high-confidence):** each API is gated by its OWN dedicated action (not generic `ec2:ModifyClientVpnEndpoint`), resource-type `client-vpn-endpoint` (ARN-scopable: SimulateCustomPolicy ARN-match=allowed, mismatch=implicitDeny). Get/Modify/Delete independently gated (read ≠ write). The actions are ABSENT from `list_ec2.md` = documentation gap ONLY. Prior report M-2 claim "Cedar policy requires its own action" = VERIFIED CORRECT.

**L2/L3/L4/L7 = intended-behavior, not AWS defects:**
- L4: malformed Cedar REJECTED synchronously (`InvalidParameterValue` "provide a valid Cedar policy document"), prior doc unchanged — fail-CLOSED; never saw status=failed. Over-broad `permit(principal,action,resource);` accepted = customer footgun.
- L3: `Modify ShadowMode=enabled` with NO PolicyDocument = partial update; `Get` shows ShadowMode=enabled but PolicyDocument intact → auditor reading only the doc misses that enforcement is off. Operator caution, documented feature.
- L2: Delete → status=deleting, removes gate in one call. Documented feature, gated.
- L7: unauthorized principal gets `UnauthorizedOperation` regardless of existence (no leak, auth precedes lookup); authorized+nonexistent → `InvalidClientVpnEndpointId.NotFound`.

**Endpoint provisioning recipe (minimal cost):** cert-auth, ClientCidrBlock=/22, ConnectionLogOptions Enabled=false, NO target-network associations (associations are what incur hourly charge; bare endpoint ~free). Server cert CN MUST be a FQDN domain (ACM import else create_client_vpn_endpoint fails "does not have a domain"). Import server cert + CA(as client-root) to ACM. Teardown order: delete endpoint → wait gone → delete ACM certs (ResourceInUse until endpoint gone) → delete IAM role policies+roles. Clean tenant isolation: awsbb2 never needed (no cross-account path; endpoint is account-scoped).

**SWEEP-5 device-posture / trust-provider (run 2026-10-07-1).** botocore 1.43.108 has the shapes: `Create/ModifyClientVpnEndpoint.DevicePostureOptions{Enabled, TrustProviders[]}`; each `ClientVpnTrustProviderRequest{TrustProviderType(enum crowdstrike|jamf|jumpcloud), TenantId, PublicSigningKeyUrl}`. ShadowMode is a STRING enum `enabled|disabled` (not bool). GetAuthzPolicy output = {PolicyDocument, Description, ShadowMode, Status}.

- **CV1 (publicSigningKeyUrl SSRF/fetch) = REFUTED at control plane + DOC-GAP at connect-time.** Collector = APIGW-v2 HTTP API→Lambda (Function URLs SCP-blocked). Set `publicSigningKeyUrl` to in-account collector via create AND modify → **ZERO server-side fetch** at config time (watched ~90s, async too). The URL is stored verbatim; it is only dereferenced at CONNECT time by the service (needs live VPN client + real 3P posture token + target-network assoc = not reachable in 2-acct sandbox → DOC-GAP, NOT exploitable here). **No IMDS reached — HARD STOP never triggered.** Config-time URL validation is ROBUST: `must be a valid https URL` (rejects http/file/non-URL), `must reference a public hostname, not localhost or an IP address` (explicitly blocks 169.254.169.254). BUT accepts internal DNS hostnames like `https://internal-fleet.ec2.internal/key` (public-hostname-FORMAT, not internal check) — only a weak signal since no config-time fetch. Also: `PublicSigningKeyUrl` only valid for `crowdstrike` type; jamf/jumpcloud → `InvalidParameterValue "PublicSigningKeyUrl is not supported for the jamf trust provider type"`.
- **CV2 (Cedar unavailable-namespace fail-open) = config-plane PRECONDITION CONFIRMED, enforcement DOC-GAP.** `ModifyClientVpnEndpointAuthorizationPolicy` silently ACCEPTS a syntactically-valid `forbid` keyed on a namespace whose trust provider is NOT configured (e.g. `forbid when {context.jamf.diskEncryptionEnabled==true}` with only crowdstrike set), on a totally bogus namespace (`context.bogusvendor.x`), and a permit-only-on-unavailable-ns — all with NO error, NO warning. Stronger: can `ModifyClientVpnEndpoint(DevicePostureOptions.Enabled=False)` to REMOVE the provider underneath an active crowdstrike-referencing forbid; policy is RETAINED (doc intact, no warning) → the forbid's namespace is now unavailable → inert. Per docs ("namespace available only when provider configured") + Cedar forbid-skip-on-error, the deny goes silently dead. New beyond sweep-3 (which only had malformed=fail-closed + overbroad-permit footgun). Full "denied client admitted" oracle needs live connect = DOC-GAP.
- **CV3 (ShadowMode reporting) = CONFIRMED but documented/intended (= sweep-3 L3).** After settle, `Get` shows `Status: active` while `ShadowMode: enabled` (enforcement OFF). Status field reports attached-ness, NOT enforcement — operator reading only Status is deceived. Documented (shadowMode field distinct). Not a new finding.
- **CV4 (foreign tenantId) = acceptance-only CONFIRMED, attestation DOC-GAP.** Arbitrary/foreign `TenantId` strings ("vh5-foreign-99999" etc.) stored verbatim, no ownership/format validation. Honored-cross-tenant-attestation needs a live 3P tenant → DOC-GAP (no 3P in 2-acct scope).
