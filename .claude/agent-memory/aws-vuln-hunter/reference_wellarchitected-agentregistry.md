**Well-Architected Agent (`wellarchitected`, 2020-03-31 preview) — LIVE both accounts (ListAgentProfiles 200):**
- SDK model has 23 `*Agent*` ops (CreateAgentProfile, Start/List/Get AgentRecommendation*, AgentContext/Goal). NO `PutAgentProfilePolicy`/`GetAgentProfilePolicy`, NO Basic-profile, NO Organizational ops. Raw SigV4 `PUT /api/v1/agent-profiles/{arn}/policy` => HTTP 400 `{"message":"Unknown Operation"}` = route not served. So **WA2/WA3 (profile resource-policy) = DOC-GAP: op absent from the preview, not callable.**
- `CreateAgentProfile` requires name, pillars (enum COST_OPTIMIZATION|SECURITY|RESILIENCE|PERFORMANCE|OPERATIONAL_EXCELLENCE, UPPERCASE), executionRoleArn, aggregationConfiguration[].{accountId,regions,accessRoleArn}.
- **HARD PREVIEW GATE: `profiles-per-account` service quota = 0.0 in BOTH accounts** (service-quotas ServiceCode `wellarchitected`). Any create => `ServiceQuotaExceededException "Quota 'profiles-per-account' is not available for this account"`. Cannot create a profile => StartAgentRecommendationGeneration / role-chain / ExternalId-stamping (WA1 generation-time breach) all **blocked = DOC-GAP** with that exact blocker.
- **WA1 observable sub-result (REFUTED): accessRoleArn.account == accountId IS enforced** at CreateAgentProfile input validation (before quota): mismatch => `ValidationException "Invalid accessRoleArn '<arn>': it belongs to account X but is configured for account Y."` Validation order: accessRoleArn/accountId binding -> quota. accountId=foreign (B) is NOT rejected at input stage (passes to quota) but caller-ownership-of-accountId can't be tested (quota blocks). executionRoleArn/role-trust NOT validated at create (nonexistent role still reached quota).

**AgentRegistry — control plane `agent-registry-control`, discovery plane `agent-registry`. Both member-reachable, both accounts (ListRegistries/ListAgentProfiles 200).**
- control ops: Create/Get/Update/Delete Registry + RegistryRecord, SubmitRegistryRecordForApproval, UpdateRegistryRecordStatus, Tag*. **NO InvokeRegistryMcp op anywhere in botocore** => the CUSTOM_JWT MCP-consumer invoke/forged-JWT sub-path is **DOC-GAP (not SDK-reachable)**.
- discovery ops (`agent-registry` client): Search/List/BatchGetDiscoverableRegistryRecord only (SigV4/IAM-auth).
- Registry: CreateRegistry(name, discoveryConfiguration{authorizerType CUSTOM_JWT|AWS_IAM, authorizerConfiguration}, approvalConfiguration{autoApprovalRules:[APPROVE_ALL]}, autoDetectionConfiguration). Create is async (status CREATING ~45-60s -> READY; must be READY before CreateRegistryRecord else ConflictException).
- Record lifecycle: create => DRAFT (async CREATING first); `SubmitRegistryRecordForApproval(registryId,recordId)` => PENDING_APPROVAL; owner `UpdateRegistryRecordStatus(status=APPROVED)` => APPROVED (discoverable). DRAFT->APPROVED direct is rejected. recordType enum MCP|AGENT|CUSTOM|SKILL|GATEWAY. **MCP inline `data` needs an unknown supported `dataSchemaVersion` (2025-11-25/2024-11-05/1.0 all rejected "not supported"); use recordType=CUSTOM `descriptors.custom.data` (no schema version) for a cheap healthy discoverable record.**
- CUSTOM_JWT registry: authorizerConfiguration key is `customJWTAuthorizer{discoveryUrl(req), allowedAudience, allowedClients, allowedScopes, customClaims}`. DiscoveryUrl is **validated pre-fetch** — example.com and nip.io both => `ValidationException "Invalid authorizer configuration"`, NO fetch reached in-account collector. Would need a valid in-account OIDC endpoint to stand one up.

**AR1 (cross-tenant discovery) — REFUTED, clean isolation:** owner (A) Search/List returns its APPROVED record; victim B calling SearchDiscoverableRegistryRecords(registryIds=[A's id]) / ListDiscoverableRegistryRecords(registryId=A's id) => `ResourceNotFoundException "Registry not found: <id>"` (identical to bogus id, no existence leak). SigV4 discovery plane is strictly caller-account-scoped regardless of AuthorizerType.

**AR2 (descriptor SSRF / SigV4 signing) — server-side fetch CONFIRMED, dangerous vectors REFUTED, NO hard stop:**
- `descriptors.{mcpServer|a2aAgentCard|http|agui|...}.source.fromUrl.url` IS dereferenced server-side: record goes CREATING, service connects to the URL as an **MCP client** (collector saw `user-agent: Apache-HttpAsyncClient/5.6.1 (Java/25.0.4.1)`, header `mcp-protocol-version: 2025-11-25`, POST JSON-RPC initialize + event-stream GET), then CREATE_FAILED "Failed to initialize MCP connection" for a non-MCP collector.
- **SSRF guard holds (resolve-time):** url regex is https-only (`http://`,`file://` rejected by regex). IP literal => "fromUrl must use a hostname, not an IP address". localhost / instance-data / metadata.google.internal / `169-254-169-254.nip.io` (DNS-rebind to link-local) ALL => `ValidationException "fromUrl is invalid"` — the service resolves the hostname and blocks link-local/private. Public hostnames (incl sts/ecr.amazonaws.com) accepted and connected to. No link-local reach, no fleet creds.
- **SigV4 signing confused-deputy REFUTED:** `source.fromUrl.credentialProviderConfigurations[].credentialProvider.iamCredentialProvider.{roleArn,service,region}`. Same-account roleArn: service DOES SigV4-sign the outbound fetch as that role (collector saw `Authorization: AWS4-HMAC-SHA256 Credential=ASIA...<caller-account>/.../execute-api/...` + x-amz-security-token) = caller's OWN role, caller-chosen service scope. Cross-account roleArn (in B) => `AccessDeniedException "iam:PassRole ... a cross-account role cannot be used with..."` at CreateRegistryRecord = PassRole bound to caller account. So signing is bounded to caller's own identity to a caller-chosen public host — not cross-boundary.

**RcsAgent (`pinpoint-sms-voice-v2`, service name `smsvoice`=False) — REFUTED:** `CreateRcsAgent` (no role fields) creates cheaply/instantly (Status CREATED, no carrier onboarding). The confused-deputy fields (`TwoWayMediaS3Role`, `TwoWayMediaS3BucketName`, `TwoWayChannelRole`) are on `UpdateRcsAgent` only (NOT Create — plan assumed CFN `AWS::SMSVOICE::RcsAgent`). Cross-account TwoWayMediaS3Role => `AccessDeniedException "Cross-account pass role is not allowed."` Same-account role => ValidationException RESOURCE_NOT_ACCESSIBLE (role must trust sms-voice + bucket reachable). Cross-account confused deputy blocked at config time — same guard as EI/securityagent/eventbridgev2.

**Pattern reconfirmed:** every service in these accounts enforces same-account PassRole on caller-named roles at the control plane ("Cross-account pass role is not allowed"); cross-tenant control/discovery reads return ResourceNotFoundException (no existence leak). Confused-deputy-via-caller-named-role is consistently REFUTED here.
