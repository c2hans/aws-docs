## 1. Pentest Objectives
1. Confirm the **irreversibility guarantee is absolute at the control plane** — that there is **no API action** (no `DisableNitroTpm`, no `ModifyInstanceAttribute` TPM attribute) by which NitroTPM can be turned off after launch — and determine whether that immutability is a *security* property (tamper-resistance) or merely an *availability* footgun with an assurance side effect.
2. Determine whether the documented **"stop using NitroTPM" guest-OS action** (disable the TPM 2.0 driver via `tpm-tools` / `tpm.msc`) produces **any control-plane-visible signal** — specifically whether `DescribeInstances.TpmSupport` still reports `"v2.0"` after the guest driver is disabled, creating a **split-brain** where a compliance/attestation consumer trusting the control-plane attribute believes NitroTPM is in active use when the guest has stopped using it.
3. Determine the **blast radius and authorization** of the guest-side "stop using" action — i.e. that any principal with **guest OS administrator/root** (an insider, or an attacker post-compromise) can silently void every in-instance NitroTPM-dependent control (BitLocker drive unlock, measured-boot runtime PCR extension, any workload reading the vTPM) with **no EC2 control-plane event**, and whether that interacts with the KMS attestation gate (does disabling the guest driver change the PCR values the Nitro layer attests — a doc-gap to route to the attestation sibling).

## 2. Components, Assets, and Design

**What this page is.** `nitrotpm-instance.html` ("Enable or stop using NitroTPM on an Amazon EC2 instance") has exactly two sections: **Launch an instance with NitroTPM enabled** (points at `enable-nitrotpm-prerequisites.md`; "NitroTPM is automatically enabled" when prerequisites are met; "You can enable NitroTPM on an instance only at launch") and **Stop using NitroTPM on an instance** ("After launching an instance with NitroTPM enabled, you can't disable NitroTPM for the instance. However, you can configure the operating system to stop using NitroTPM by disabling the TPM 2.0 device driver" — Linux `tpm-tools`, Windows `tpm.msc`). It introduces **no new API, no new IAM action, no new field** — it describes the *lifecycle* of the launch-only, immutable NitroTPM attribute set elsewhere.

**Key design facts (confirmed this pass from docs/IAM/API):**
- **No control-plane disable path exists.** A full grep of `list_ec2.md` for `DisableNitroTpm` / `ModifyNitroTpm` / `StopNitro` / `tpmSupport`(as an action or Modify attribute) / `DisableTpm` returns **ZERO** matches. `ModifyInstanceAttribute` (`list_ec2.md:10051`) carries `ec2:InstanceType`, `ec2:InstanceProfile`, auto-recovery, metadata-tags, etc. — but **no TPM/`tpmSupport` attribute**. `tpmSupport` is a **launch-only, AMI-inherited, immutable** instance attribute (`API_Instance.md` `tpmSupport`; set via `RunInstances` from a `RegisterImage --tpm-support v2.0` AMI — enablement path owned by the enable-on-ami + prereq siblings). ⇒ the doc's "you can't disable it" is literally true: **AWS exposes no action to do so.**
- **The only off-switch is a guest-OS action, invisible to the control plane.** "Stop using" = disable the guest TPM 2.0 CRB driver (`tpm-tools` on Linux, `tpm.msc` on Windows). This changes **guest state only**; it does not call any EC2 API and leaves `TpmSupport="v2.0"` on the instance.
- **The control-plane verification path reports launch-time state, not current guest usage.** `verify-nitrotpm-support-on-instance.md:5` — "If NitroTPM support is enabled on the instance, the command returns `"v2.0"`. Otherwise, the `TpmSupport` field is not present" — via `describe-instances --query ...TpmSupport`. This attribute reflects **whether the instance was launched NitroTPM-enabled**, which is immutable; it has **no coupling to whether the guest driver is currently enabled**. The console does not display `TpmSupport` at all (`:7`).
- **Windows has a guest-side signal the control plane lacks.** `verify-nitrotpm-support-on-instance.md:33-49` — `tpm.msc` → **TPM Manufacturer Information** shows the NitroTPM manufacturer/version *when the TPM is accessible to Windows*. So on Windows the **same tool** (`tpm.msc`) is BOTH the documented "stop using" switch (target page) AND the "verify access" check (verify page) — a guest admin who runs the stop-using procedure makes the guest-side signal flip while the control-plane `TpmSupport` stays `"v2.0"`.

**ASCII — the two state machines and where they diverge:**
```
CONTROL-PLANE state (immutable after launch)        GUEST-OS state (mutable by any OS admin)
┌─────────────────────────────────────┐            ┌──────────────────────────────────────┐
│ RunInstances (NitroTPM AMI + type)   │            │ TPM 2.0 CRB driver: enabled            │
│   -> tpmSupport = "v2.0"  [LAUNCH]   │            │   BitLocker seal active, PCRs extended │
│   NO DisableNitroTpm / ModifyAttr    │            │                                        │
│   -> value is PERMANENT              │            │   "stop using":                        │
│                                      │            │   tpm-tools (Linux) / tpm.msc (Win)    │
│ Read: describe-instances             │            │   -> driver DISABLED                   │
│   --query ...TpmSupport => "v2.0"    │  <<< SPLIT  │   -> guest no longer uses the vTPM     │
│   (console: never shown)             │   BRAIN >>> │   (tpm.msc Manufacturer Info: gone/err)│
└─────────────────────────────────────┘            └──────────────────────────────────────┘
   A compliance/attestation CONSUMER reading the control-plane attribute still sees "v2.0"
   = NitroTPM "enabled" — but the guest has stopped using it, with NO EC2 API event. (Area 1/2)
```

## 5. Recommended Areas of Focus

### Area 1 — Irreversibility is absolute at the control plane; the ONLY off-switch is a guest-OS action [HEADLINE; Lens U/O/AA]
**Background:** the target page states "After an instance is enabled for NitroTPM, you can't disable it … you must configure the operating system to stop using it." This is the page's defining property.
**Security Concern:** confirmed by a full grep of `list_ec2.md` — there is **no `DisableNitroTpm`, no `ModifyInstanceAttribute` TPM attribute, no `StopNitroTpm`** action anywhere. The control-plane NitroTPM state is **genuinely immutable** after launch. Two consequences worth filing:
- **(a) Positive-control confirmation (good hygiene, worth recording):** immutability means an attacker who compromises the EC2 control-plane API **cannot** forge a "NitroTPM-disabled" state or tamper the attribute to defeat an attestation posture — the attribute is launch-bound and permanent. This is the *intended* security value; it is a boundary that **holds** and should be recorded as a null-breach (contrast with mutable attributes that an attacker could flip).
- **(b) The assurance gap this creates (the real lead → Area 2):** because the control-plane state can *only* say "was launched NitroTPM-enabled" and can *never* be turned off or reflect disablement, the **only** way to actually stop using NitroTPM is the guest-OS action — which the control plane cannot see. So the immutable attribute **over-reports**: it is a reliable signal of *launch configuration* but **not** of *current usage*. Any control built on "`TpmSupport=v2.0` ⇒ NitroTPM is protecting this instance" is unsound.
**High-level Test Scenarios:**
1. Grep/confirm (done) `list_ec2.md` exposes no disable/modify-TPM action; `iam:SimulateCustomPolicy` is not even applicable (no action to scope) — **oracle: the absence itself**, documenting that immutability is enforced by *there being no API*, not by a condition.
2. Confirm `ModifyInstanceAttribute` rejects any attempt to set a TPM attribute (`API_ModifyInstanceAttribute.md` attribute list has no TPM member) — isolates that even the general mutate action cannot touch it.
**Doc evidence:** target page §"Stop using NitroTPM"; `list_ec2.md:10051` (ModifyInstanceAttribute attribute set); confirmed-absent grep; `API_Instance.md` `tpmSupport`.
**Severity-if-true:** Informational for (a) (a control that holds); **Low–Medium** for (b) as the assurance over-reporting that Area 2 develops. AWS-owned. **Stop** once the absence is confirmed — no live resource needed.

### Area 2 — Control-plane ↔ guest-OS split-brain: "stop using" leaves `TpmSupport="v2.0"` with no control-plane signal [NET-NEW; Lens U/O]
**Background:** the page's "stop using" procedure disables the guest TPM 2.0 driver. `verify-nitrotpm-support-on-instance.md:5` defines the control-plane verification as `describe-instances --query ...TpmSupport` returning `"v2.0"` iff the instance was *launched* NitroTPM-enabled — an immutable, launch-bound attribute (Area 1).
**Security Concern:** the control-plane attribute and the guest driver state are **decoupled**. After an operator (or attacker with guest admin) runs the documented stop-using procedure, `DescribeInstances.TpmSupport` **still returns `"v2.0"`** — the attribute has no coupling to current guest usage and no API can change it. Therefore:
- A **compliance/attestation consumer** (a Config rule, a custom auditor, an "only attestable instances" gate) that reads `TpmSupport="v2.0"` as "NitroTPM is in active use" gets a **false positive**: NitroTPM may have been fully stopped inside the guest, voiding BitLocker and any vTPM-dependent control, while the control-plane audit says "healthy / attestable."
- There is **no CloudTrail / EC2 event** for the guest-side stop (it is an in-OS driver action, not an API call) → the downgrade is **undetectable from the control plane** (compounds the prereq plan's Area 5 console blind spot — the field isn't even in the console, and even the API field can't see this).
- On **Windows**, a *guest-side* signal does exist and does flip: `tpm.msc` → **TPM Manufacturer Information** (the verify-page check, `:33-49`) becomes unavailable once the driver is disabled — but reaching that signal requires in-guest access (SSM Run Command / an agent), not the standard control-plane audit path. On **Linux** the only check is likewise guest-side (`tpm-tools`). So detection of "stopped using" is **guest-only**, defender-expensive, and absent from the attribute defenders actually query.
**High-level Test Scenarios (needs a live canary — the stop-using step mutates guest state; `DescribeInstances` read is non-mutating):**
1. Launch a NitroTPM-enabled instance; confirm `describe-instances --query ...TpmSupport` = `"v2.0"`. In-guest, run the documented stop-using procedure (`tpm-tools` disable on Linux / `tpm.msc` on Windows). Re-run `describe-instances` — **oracle: `TpmSupport` is STILL `"v2.0"`** (expected per the immutability of Area 1), proving the control-plane attribute cannot reflect the guest stop → the split-brain is confirmed.
2. On Windows, confirm the `tpm.msc` Manufacturer-Information signal is gone/errored post-disable (the only observation that *does* flip) — documents that detection is guest-only.
3. Confirm no CloudTrail management/data event is produced by the guest driver-disable (it is not an EC2 API call) — documents the control-plane blind spot.
**Doc evidence:** target page §"Stop using NitroTPM"; `verify-nitrotpm-support-on-instance.md:5`, `:7` (console omits field), `:33-49` (Windows `tpm.msc` guest signal); `list_ec2.md` (no disable action, Area 1).
**Severity-if-true:** **Low–Medium** (assurance / detection gap: a security control built on the attribute silently over-reports; AWS-owned documentation/signal gap, not a cross-tenant breach). Worth filing because a customer could build an attestation/compliance control on the false equivalence `TpmSupport=v2.0 ⇒ in use`. **Stop** once scenario 1 confirms the attribute is unchanged post-stop.

### Area 3 — Guest-admin "stop using" as an unsignalled integrity downgrade + the KMS-attestation interaction [Lens U/O; chains to attestation sibling]
**Background:** the stop-using action is a *guest-OS* operation available to any principal with OS administrator/root — a legitimate operator, an insider, or an attacker who has already achieved in-guest privilege. It voids BitLocker sealing (keys sealed to NitroTPM PCRs become unusable once the OS stops using the TPM) and halts runtime PCR extension.
**Security Concern:** two angles, both page-local and honest about their boundary:
- **(a) Who can downgrade & with what signal:** disabling the TPM driver is **not** a privileged EC2 action — it needs no IAM, no `ec2:*`, only guest admin. So the set of principals who can void an instance's NitroTPM-dependent protections is "anyone with OS admin," which is **strictly larger** than "anyone with EC2 control-plane permission on the instance," and the action is invisible to the control plane (Area 2). For a defender who assumed "NitroTPM instances are tamper-evident at the platform layer," the tamper is in-guest and un-evented. This is primarily a **customer threat-model clarification** (NitroTPM protects data *for* the guest; it does not protect *against* the guest), in scope here only as the assurance framing, not as an AWS boundary breach.
- **(b) The KMS-attestation interaction (DOC-GAP → route to the attestation sibling):** does disabling the guest TPM driver change the PCR values the **Nitro layer** attests for a `kms:RecipientAttestation:NitroTPMPCR<N>`-gated `Decrypt`? If the attested measured-boot PCRs (indices 4/7/8/9/16/23 per the attestation plan) are produced **below** the guest and are independent of the guest driver state, the KMS gate **still passes** after the guest has "stopped using" NitroTPM — i.e. the attestation attests *boot measurement*, not *ongoing usage* (consistent with the attestation plan's "attestation = measurement-not-identity" theme). If instead some index reflects guest-driver runtime state, the gate could fail-closed. **This plan does not resolve it** — it is the one net-new *question* the lifecycle page raises for the attestation surface; carry it into `nitrotpm-attestation-attack-research-plan.md` as a scenario.
**High-level Test Scenarios:**
1. (Customer-framing, doc-only) Confirm from `nitrotpm.md` that the sealing/attestation threat model excludes a malicious guest admin — record that stop-using-by-guest-admin is **by design**, so the finding is the *doc/assurance clarity*, not a breakable control.
2. (Attestation interaction — defer execution to the sibling plan's canary) After the guest stop-using step, attempt a `Decrypt` under a `kms:RecipientAttestation:NitroTPMPCR<N>` policy — **oracle: gate still ALLOW (boot-measurement-independent of guest usage) vs DENY (runtime-coupled)**. Document the result for the attestation plan.
**Doc evidence:** target page §"Stop using NitroTPM"; `nitrotpm.md:12` (PCR seal / BitLocker binding); cross-ref `nitrotpm-attestation-attack-research-plan.md` (PCR index set, measurement-not-identity).
**Severity-if-true:** Informational–Low for (a) (by-design threat-model clarification); the (b) interaction inherits the attestation gate's severity **only if** it fails open in a way a customer would not expect — resolved in the sibling, not here. **Stop** after recording (a) and handing (b) to the attestation plan.
