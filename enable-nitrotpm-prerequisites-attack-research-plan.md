## 1. Pentest Objectives
1. Determine whether the three documented launch **requirements** — the AMI's `TpmSupport="v2.0"`, UEFI boot mode, and the specific instance-type allow-list — can be **enforced by an EC2 IAM/SCP policy** at `RunInstances`/`ModifyInstanceAttribute`/`RegisterImage` time, or whether "you must meet the following requirements" is enforced only by EC2 control-plane runtime validation with **no condition key an org can author** (so a "require confidential/attestable compute" mandate is not expressible).
2. Determine whether the **hard-coded ~250-name instance-type list** on the page diverges from the authoritative live API (`DescribeInstanceTypes` filter `nitro-tpm-support`), i.e. whether any guardrail/compliance tool that copies the doc list silently drifts (false-negative on new NitroTPM types, false-positive on retired ones).
3. Determine the **failure mode** of the "if you change the instance type, the new type must also support NitroTPM" consideration — does a type-change to an unsupported type **hard-error**, or **silently succeed and drop** the instance's NitroTPM state (voiding any attestation/BitLocker control built on it) — and whether `ec2:InstanceType` on `ModifyInstanceAttribute` evaluates the *requested new* value or the *current* value.
4. Determine whether a **BitLocker volume sealed to a NitroTPM-based key** that is cloned via EBS snapshot or VM Import/Export is (a) a permanent **data-loss footgun** (key unrecoverable, undocumented) and/or (b) a **silent security downgrade** (restored AMI/instance silently lacks `TpmSupport`, so the "original instance only"/sealing guarantee silently doesn't apply) — and confirm the per-instance NitroTPM EK is **not** a cross-tenant disclosure oracle.
5. Determine whether AWS's own **`Update-EC2SecureBootCertificate.ps1`** runbook (download over plain S3 HTTPS → run as Administrator, no integrity check) is a copy-verbatim supply-chain gap.

## 2. Components, Assets, and Design

**What this page is.** `enable-nitrotpm-prerequisites.html` ("Requirements for using NitroTPM") is a three-section requirements/considerations page: **AMIs** (the AMI must have `TpmSupport` enabled + a TPM 2.0 CRB-driver OS + UEFI boot mode; Linux has no prebuilt AMI — you build your own; Windows has AWS-prebuilt AMIs), **Instance types** (a hard-coded allow-list of ~250 virtualized type names across 6 families), and **Considerations** (type-change must stay on a supporting type; BitLocker sealed-key is original-instance-only; state not shown in console / not in EBS snapshots / not in VM Import-Export; not supported on Outposts/Local Zones/Wavelength). It introduces **no new API** — it gates the ordinary `RunInstances`/`ModifyInstanceAttribute`/`RegisterImage`/`CreateImage` flow.

**Key design facts (confirmed from docs/IAM/API this pass):**
- **NitroTPM is launch-only and immutable:** `nitrotpm-instance.md` — "You can enable an Amazon EC2 instance for NitroTPM only at launch. After an instance is enabled for NitroTPM, you can't disable it." To stop using it you disable the guest TPM 2.0 driver (Linux `tpm-tools`; Windows `tpm.msc`) — a guest-OS action, invisible to the control plane.
- **`TpmSupport="v2.0"`** is an AMI/instance attribute set once (at `RegisterImage` for the AMI; inherited at launch) and read via `DescribeImages`/`describe-image-attribute --attribute tpmSupport` / `DescribeInstances` (`API_Instance.md:308` `tpmSupport` field). **Not shown in the console** (stated on the prereq page and both verify-* pages).
- **Type-level NitroTPM capability is live-queryable:** `API_InstanceTypeInfo.md:116` `nitroTpmInfo` (→ `API_NitroTpmInfo.md`, sole field `SupportedVersions.N`) and `:121` `nitroTpmSupport` (`supported|unsupported`); `API_DescribeInstanceTypes.md:61-63` exposes filters `nitro-tpm-support` and `nitro-tpm-info.supported-versions`, plus `supported-boot-mode` (`legacy-bios|uefi`).
- **IAM condition-key coverage for TPM/boot is essentially empty** (grep of all 10,190 lines of `list_ec2.md`): `TpmSupport`/`NitroTpm`/`UefiData` → ZERO condition keys (only action names `GetInstanceTpmEkPub`/`GetInstanceUefiData`). The ONLY boot key is **`ec2:BootModeOverride`** (`list_ec2.md:10059`), present only on `CreateImage`/`image` (`:5144`, `:9945`) — **absent from `RunInstances`, `ModifyInstanceAttribute`, `RegisterImage`, `CopyImage`**.
- **BitLocker binding mechanism** (`nitrotpm.md:12`): keys are *sealed* to a PCR value, "can never be accessed if the value of the PCR, and thus the instance integrity, changes" — BitLocker seals its drive key so "the drive can only be decrypted when the operating system has booted correctly and is in a known good state." (Whether the per-instance EK is also part of the non-portability binding is **doc-silent** — see Area 4.)

**ASCII — where the "requirements" are (not) enforced:**

   |                                        "instance type supports NitroTPM" (no dynamic key)
   v
[EC2 control-plane runtime validation]  <-- the ONLY enforcer of the 3 "requirements";
   |                                         error behavior for a type-change to an
   |                                         unsupported type is UNDOCUMENTED (Area 3)
   v
[Instance with NitroTPM]  --tpmSupport--> readable only via API/CLI, NEVER the console (Area 5)
   |

## 5. Recommended Areas of Focus

### Area 1 — The three NitroTPM "requirements" are NOT IAM-expressible [headline; Lens U/S]
**Background:** the page opens "To launch an instance with NitroTPM enabled, you must meet the following requirements" and lists (1) AMI with `TpmSupport` enabled, (2) UEFI boot mode, (3) a supported instance type. The whole value of NitroTPM downstream — the attestation KMS gate (sibling plan Area 1) and BitLocker sealing — depends on these being true. A security org will want to *mandate* them.
**Security Concern:** a full grep of `list_ec2.md` (10,190 lines) finds **ZERO** condition keys for `TpmSupport`/`NitroTpm`/`UefiData`, and the only boot-mode key `ec2:BootModeOverride` (`:10059`) is present **only** on `CreateImage`/`image` (`:5144`, `:9945`) — **absent from `RunInstances`, `ModifyInstanceAttribute`, `RegisterImage`, `CopyImage`**. `RunInstances` carries `ec2:InstanceType` but **nothing that pins the AMI's `TpmSupport`** nor "the type supports NitroTPM." ⇒ an org **cannot author an EC2 IAM/SCP condition** that says "only launch NitroTPM-attestable (UEFI + TpmSupport=v2.0 + capable type) instances." The requirements are enforced **solely by EC2 control-plane runtime validation**, which the customer cannot extend, scope, or make mandatory per-principal. This is the launch-time analogue of the sibling data-protection plan's R6 "`ec2:AmdSevSnp` Deny fails open" finding and the attestation plan's Area 8 "zero condition keys on RegisterImage."
**High-level Test Scenarios:**
1. `iam:SimulateCustomPolicy` with a policy `Deny RunInstances unless ec2:TpmSupport = v2.0` (and a UEFI variant) — **oracle: the condition key is unknown/inert**, the Deny never fires, confirming the mandate is vacuous.
2. Confirm `ec2:BootModeOverride` is accepted on `CreateImage` but rejected/ignored on `RunInstances` (simulate both) — isolates that even the one boot key doesn't reach the launch path.
3. Confirm the only expressible lever is a hand-maintained `ec2:InstanceType` StringEquals allow-list (chains to Area 2 — that list is exactly the thing that drifts).
**Doc evidence:** page §AMIs/§Instance types; `list_ec2.md:9585-9611` (RunInstances), `:8806-8810` (ModifyInstanceAttribute), `:9317-9321` (RegisterImage), `:10059`/`:5144`/`:9945` (BootModeOverride).
**Severity-if-true:** Medium (defense-in-depth / compliance-expressibility gap; AWS-owned absence). **Not** cross-tenant. Reportable as a Lens-U/S enforcement gap, not a product bug. **Stop** once simulation confirms the key is absent/inert — no live launch needed.

### Area 2 — Hard-coded instance-type allow-list vs live `DescribeInstanceTypes` [Lens U doc-vs-API drift]
**Background:** §Instance types enumerates ~250 type names across 6 families as a static list. `API_DescribeInstanceTypes.md:61-63` exposes filters `nitro-tpm-support` (`supported|unsupported`) and `nitro-tpm-info.supported-versions`, backed by `InstanceTypeInfo.nitroTpmInfo` (`API_NitroTpmInfo.md`, `SupportedVersions.N`) and `nitroTpmSupport` (`API_InstanceTypeInfo.md:116-122`).
**Security Concern:** the doc hard-codes a list that an **authoritative live API already exposes**. Any guardrail/compliance tool (or the hand-maintained `ec2:InstanceType` allow-list from Area 1 scenario 3) that **copies the doc list instead of calling `DescribeInstanceTypes nitro-tpm-support=supported`** will silently drift: a NitroTPM-capable type added after the doc snapshot is a **false negative** (wrongly denied / wrongly treated as non-attestable), and a retired name is a **false positive**. Same structural defect as the data-protection plan's **T1** (encryption-in-transit static ~130-type list vs the live `network-info.encryption-in-transit-supported` filter) — a reusable "AWS doc freezes a capability list the API serves live" pattern.
**High-level Test Scenarios:**
1. `aws ec2 describe-instance-types --filters Name=nitro-tpm-support,Values=supported --query 'InstanceTypes[].InstanceType'` and diff against the page's list — **oracle: any non-empty symmetric difference** proves drift (expect the API superset to already exceed the doc).
2. Confirm `supported-boot-mode=uefi` as the companion live check for the UEFI requirement (the page's §AMIs UEFI requirement has the same static-prose-vs-live-filter shape).
**Doc evidence:** page §Instance types; `API_DescribeInstanceTypes.md:61-63`; `API_InstanceTypeInfo.md:116-122`; `API_NitroTpmInfo.md`.
**Severity-if-true:** Low–Medium (compliance/assurance; AWS-owned). A customer building a NitroTPM/attestation guardrail on the frozen list inherits silent coverage gaps. **Stop** once the diff is captured.

### Area 3 — Instance-type-change: "new type must also support NitroTPM" has no distinct enforcement/signal [Lens U/S]
**Background:** §Considerations — "After you launch an instance using an AMI with NitroTPM enabled, if you want to change the instance type, the new instance type that you choose must also support NitroTPM." `resize-limitations.md:39-40` restates the rule. NitroTPM is launch-only and un-disable-able (`nitrotpm-instance.md`).
**Security Concern:** `ModifyInstanceAttribute` carries `ec2:InstanceType` (`list_ec2.md:8806-8810`), but (a) the IAM reference's one-line definition of `ec2:InstanceType` (`:10097` "Filters access by the type of instance") **does not disambiguate whether it evaluates the requested-new value or the instance's current value** on a Modify action — a load-bearing semantics gap for any policy trying to pin the target type; and (b) **no doc anywhere states the control-plane failure mode** if you change to an unsupported type: does it **hard-error**, or **silently succeed and drop NitroTPM state** (since state is launch-only and never shown in the console)? If silent, an attestation KMS gate or a BitLocker seal that assumed NitroTPM is in force is **voided with no operator signal** — and Area 5's console blind spot means it's undetectable without an API call.
**High-level Test Scenarios (needs a live canary — Modify is state-changing; DryRun is caller-IAM-only, cannot answer runtime validation):**
1. Launch a NitroTPM instance; stop it; `ModifyInstanceAttribute --instance-type <non-NitroTPM type>` — **oracle: hard error (fail-closed, good) vs success**. If success, immediately `DescribeInstances --query ...TpmSupport` — if `TpmSupport` is now absent, the state was silently dropped (the breach-shaped outcome).
2. `iam:SimulateCustomPolicy` for `ModifyInstanceAttribute` with `ec2:InstanceType` StringEquals on the *new* type to probe whether the key binds the requested value (settles the (a) semantics gap without resizing).
**Doc evidence:** page §Considerations; `resize-limitations.md:39-40`; `list_ec2.md:8806-8810`, `:10097`; `nitrotpm-instance.md`.
**Severity-if-true:** Medium (silent voiding of an attestation/BitLocker control). **Stop** at the first type-change result + `TpmSupport` read; do not iterate types.

### Area 4 — BitLocker "original instance only" + state-not-in-snapshot/VM-Import [Lens U/AA/L]
**Background:** §Considerations — "BitLocker volumes that are encrypted with NitroTPM-based keys can only be used on the original instance"; "The NitroTPM state is not included in Amazon EBS snapshots"; "…not included in VM Import/Export images." `nitrotpm.md:12` describes PCR-based sealing. `enable-nitrotpm-support-on-ami.md:12` adds "You can't use the Amazon EC2 console or VM Import/Export" to create a NitroTPM AMI.
**Security Concern:** two shapes, both doc-silent on consequence:
- **(a) Availability footgun (Lens L/AA):** a BitLocker-sealed volume cloned via snapshot or VM Import/Export carries no NitroTPM state → the sealed drive key becomes **permanently unrecoverable** on the restored/imported instance. Grep of the whole mirror (`bitlocker`/`sealing`/`unseal`/`endorsement`) finds **no statement of this data-loss consequence** — the "original instance only" guarantee is asserted without naming the failure.
- **(b) Silent security downgrade (Lens U):** an AMI/instance derived from a snapshot or a VM-import **silently lacks `TpmSupport`** (confirmed non-carriable), so any attestation KMS gate or BitLocker/sealing control a customer layered on the *original* image **silently does not apply** to the clone — and the console (Area 5) won't reveal it. A customer who "re-deploys from the golden snapshot" believes attestation is in force when it is not.
- The confidentiality *guarantee* "can only be used on the original instance" is worth tracing to its mechanism: `nitrotpm.md:12` attributes it to the **PCR seal**, but whether the **per-instance EK** also binds non-portability is **doc-silent** (inference gap). The deeper "could a reproduced/cloned boot state unseal on a *different* instance" question is the BitLocker-flavored twin of the attestation plan's **Area 1 reproducible-measurement** concern — **cross-ref it, do not re-derive here**.
**High-level Test Scenarios:**
1. Snapshot a NitroTPM instance's BitLocker-sealed volume, restore to a new instance, attempt to unlock — **oracle: key unrecoverable** (confirms (a); documents the undocumented failure).
2. `RegisterImage` from such a snapshot (or VM-import an image) and `describe-image-attribute --attribute tpmSupport` — **oracle: `TpmSupport` absent** on the derived AMI (confirms (b) silent downgrade).
3. **EK-oracle sub-lead = NULL:** `GetInstanceTpmEkPub` is `instance*`-resource-scoped (`list_ec2.md:8330`), requires `ec2:GetInstanceTpmEkPub` on the instance ARN; `retrieve-ekpub.md`/`API_GetInstanceTpmEkPub.md` assert no uniqueness and expose no cross-tenant path. Record as null, not a lead.
**Doc evidence:** page §Considerations; `nitrotpm.md:12`; `enable-nitrotpm-support-on-ami.md:12`; `retrieve-ekpub.md`; `list_ec2.md:8330`.
**Severity-if-true:** Low–Medium (customer availability footgun + assurance gap; the non-portability guarantee itself appears to hold — the confidentiality concern reduces to the attestation plan's Area 1). **Stop** once the restored clone's `TpmSupport`-absence is observed.

### Area 5 — NitroTPM state not surfaced in the console [Lens O/U — POINTER + compounding]
**Background:** page §Considerations "The NitroTPM state is not displayed in the Amazon EC2 console"; corroborated verbatim in `verify-nitrotpm-support-on-instance.md:10` and `verify-nitrotpm-support-on-ami.md:10` ("The Amazon EC2 console does not display `TpmSupport`").
**Security Concern:** this is the **same verifiability blind spot already owned by `nitrotpm-attestation-attack-research-plan.md` Area 7** — not re-scored here. Its page-local value is as the **compounding enabler** for Areas 2/3/4: every silent-drift / silent-drop / silent-downgrade outcome above is undetectable via the default console workflow and requires `DescribeInstances`/`DescribeImages`/`describe-image-attribute`. (Windows has a partial guest-side check: `tpm.msc` → TPM Manufacturer Information, `verify-nitrotpm-support-on-instance.md:37-49` — guest-side only, not control-plane.)
**Doc evidence:** the three verbatim sentences above.
**Severity-if-true:** Low/Informational standalone; raises Areas 2/3/4. **Stop** — doc-confirmed; this agent does not touch the console. If AWS has since added console visibility, that is resolved drift to report.

### Area 6 — AWS-authored `Update-EC2SecureBootCertificate.ps1` runbook: unverified download, run as Administrator [Lens R/Q/Y]
**Background:** `ami-windows-tpm.md:83-105` ("Update Secure Boot certificates on Windows instances"): the Microsoft 2011 Secure Boot certs expire from **June 2026**; instances from Windows AMIs dated **2026.01.14 or earlier** must update (2026.02.11+ need no action). The runbook: ":95 Download the following PowerShell script … `https://s3.amazonaws.com/ec2-downloads-windows/Scripts/Update-EC2SecureBootCertificate.ps1`"; ":97 Open a PowerShell command prompt as an Administrator, and run the downloaded PowerShell script."
**Security Concern:** the AWS-published runbook ships **no hash, checksum, code-signature, or signed-URL** step anywhere in the section (confirmed by full read of `:83-105`) — it goes straight from a **plain path-style `s3.amazonaws.com` URL** to "run as Administrator." A reader cannot verify the script's integrity or the bucket's ownership. If the `ec2-downloads-windows` S3 object were tampered, the URL MITM'd/downgraded, or the bucket mis-resolved, the operator runs attacker code **as Administrator**. This is the **Secure-Boot-cert twin of the EC2 Windows credential-guard child's finding** (`ec2-windows-credential-guard-...` — `Invoke-WebRequest` + `msiexec` with no hash/sig) — cross-ref it; same AWS-authored copy-verbatim supply-chain shape, in scope per the Lens-R carve-out (AWS-published runbook the customer executes as-is).
