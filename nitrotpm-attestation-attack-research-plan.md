## 0. How to use this document
- Each lead: Claim → Mechanism (doc evidence) → Confirm/Refute oracle → Preconditions → Cost → Severity → Stop condition. Work in priority order (§5), look left and right for adjacent bugs.
- HARD STOP: the moment evidence shows an identity/credential/ARN/account belonging to AWS's own service plane (e.g. the Nitro Hypervisor's signing key material, AWS's internal attestation PKI private keys), stop, preserve evidence, flag for AWS-Security disclosure.

## 1. Pentest Objectives
1. Determine whether an attestation-conditioned KMS key policy (`kms:RecipientAttestation:NitroTPMPCR*`) can be satisfied by an attacker who never ran the "trusted" workload — via reproducible reference measurements, under-binding, or key-family confusion.
2. Determine whether the attestation gate fails **closed** on absent/malformed/wrong-mechanism attestation documents, or whether any combination of condition keys / operators produces an effectively-always-true gate.
3. Determine whether a captured Attestation Document can be replayed outside its intended single use (freshness/nonce enforcement).
4. Determine whether a custom (third-party) verifier built strictly from AWS's documented validation steps is exposed to certificate-revocation or algorithm-confusion gaps.
5. Determine whether documented security guarantees ("only trusted software and code can perform cryptographic operations", "measured boot… prove the integrity of the instance's boot software") are actually enforced by a mechanism, or are advisory prose with an unenforced gap.

## 2. Components, Assets, and Design

**Provenance / currency check.** `nitrotpm.html`, `nitrotpm-attestation.html`, and `prepare-attestation-service.html` were fetched live (`.html.md` suffix) and diffed against the offline mirror: identical, including the KMS policy JSON example and condition-key names. **No offline/live drift found** on the pages checked.

**What this cluster is.** NitroTPM is a virtual TPM 2.0 device provided by the AWS Nitro System per-instance. It performs *measured boot*: the bootloader/OS hash every boot binary into Platform Configuration Registers (PCRs). An **Attestation Document** — a CBOR object, COSE_Sign1-signed by the Nitro Hypervisor — carries a snapshot of the PCRs plus an optional caller-supplied `public_key`, `user_data`, and `nonce`. AWS KMS can act as a built-in verifier: a KMS key policy can require specific PCR values via `kms:RecipientAttestation:NitroTPMPCR<0-23>` condition keys on `Decrypt`/`DeriveSharedSecret`/`GenerateDataKey`/`GenerateDataKeyPair`/`GenerateRandom`; on success KMS re-encrypts the plaintext response under the document's embedded public key (`CiphertextForRecipient`). Per `attestation-get-doc.md`, **only RSA public keys are supported** for the `--public-key`/`Recipient` field (ECC EK types exist for `GetInstanceTpmEkPub` but are not accepted here) — so the party that can read a successful response is whoever holds the matching RSA private key named in the document, which is the real binding on the *response*, orthogonal to the PCR gate on the *request* (relevant to the replay analysis in Area 4).

**Processes / tooling:**
- Nitro Hypervisor — issues and signs Attestation Documents (AWS-owned, not customer-reachable directly).
- `nitro-tpm-attest` CLI (installed via `aws-nitro-tpm-tools` RPM, or baked into the AWS sample AL2023 image) — guest-side tool that requests the signed document, optionally with `--public-key`, `--user-data`, `--nonce`.
- `nitro-tpm-pcr-compute` — build-time utility that computes reference measurements from a Unified Kernel Image (UKI) during AMI creation (KIWI NG build).
- AWS KMS — the documented first-class verifier; evaluates `Recipient`-attached documents against key-policy conditions.
- A customer's own third-party verifier (docs explicitly invite this: "If you are attesting to a third-party service, you must build your own custom mechanisms for receiving, parsing, and validating Attestation Documents").

**Accounts/trust zones:** customer account (owns the instance, the AMI, the KMS key policy, and the IAM role used as `Principal`) vs. AWS's Nitro System (root of trust, signs documents) vs. any *other* AWS customer who can independently build and register an AMI (relevant because the reference build recipe is public — see Lead 1).

**Identifiers:**
- `TpmSupport` AMI/instance attribute, value `"v2.0"` — set once at `RegisterImage` time, immutable thereafter, **not shown in the EC2 console** for either AMI or instance (`verify-nitrotpm-support-on-ami.md`, `verify-nitrotpm-support-on-instance.md`).
- Attestation Document `module_id` — format `i-<instance-id>-tpm<...>` (seen in the CloudTrail example in `ct-nitro-tpm.md`) — carries the instance ID, logged, but **not** exposed as a KMS condition key (no `kms:RecipientAttestation:ModuleId` exists in `list_kms.md`).
- PCR values — 32/48/64-byte digests (SHA384), hex-encoded in condition keys, "up to 96 bytes" per `conditions-nitro-tpm.md`.

**ASCII pipeline (KMS integration path):**
```
[Guest OS / app]
   --(nitro-tpm-attest --public-key PK [--nonce N])-->
[Nitro Hypervisor]  -- signs --> AttestationDocument{nitrotpm_pcrs, certificate, cabundle, public_key, nonce?}
   --(app attaches doc as Recipient)-->
[KMS Decrypt/GenerateDataKey/... API]
   -- evaluates kms:RecipientAttestation:NitroTPMPCR<N> conditions in key policy --
   -- on match: encrypts plaintext response under `public_key` from the doc --> CiphertextForRecipient
   -- on no match / absent doc: AccessDeniedException (documented)
```

**Build-time trust chain (separate from the runtime path above):**
```
[Public GitHub recipe: amazonlinux/kiwi-image-descriptions-examples]
   --> KIWI NG build --> raw disk image + pcr_measurements.json (PCR4/PCR7/PCR12)
   --> coldsnap upload --> EBS snapshot --> ec2:RegisterImage --tpm-support v2.0 --> "Attestable AMI"
```
Both an honest customer and an attacker with ordinary EC2 permissions can run this exact pipeline independently and land on the **same PCR4/PCR7/PCR12 values**, because the recipe and the boot binaries it produces are public and the measurement is a pure function of the boot binaries (`nitrotpm-attestation-document-content.md`: "the single boot binary hash can describe exactly what code an instance will execute").

## 3. Trust-Boundary Map

| From (actor/zone) | To (resource/zone) | Crossing mechanism | Breach oracle |
|---|---|---|---|
| Any AWS customer (incl. attacker) with ordinary EC2 permissions | Victim's attestation-gated KMS key | Independently rebuilding the public Attestable-AMI recipe, launching from it, calling `nitro-tpm-attest`, attaching the doc as `Recipient` on `Decrypt`/`GenerateDataKey` | Attacker's self-registered AMI's PCR4/PCR7/PCR12 match the victim's key-policy condition values, and KMS returns plaintext/ciphertext-for-recipient to a principal the AMI author never authorized by identity — **only the IAM `Principal` clause, not the PCR condition, prevented this; if that clause is broad, the gate is void.** |
| Policy-authoring customer | KMS `PutKeyPolicy` schema | Mis-selecting a condition key from the near-identical `kms:RecipientAttestation:PCR<N>` (Nitro Enclaves) vs. `kms:RecipientAttestation:NitroTPMPCR<N>` (NitroTPM) families | `PutKeyPolicy` accepts the wrong-mechanism key with no error/warning; the resulting statement is either permanently inert (silent lockout) or — if combined carelessly with `Null`/`StringNotEquals` operators — permissive in a way the author never intended. |
| Attacker who captures one valid, in-flight Attestation Document | KMS `Decrypt`/`GenerateDataKey` (any later time) | Replay of the CBOR/COSE blob as `Recipient` on a fresh API call; `nonce` is optional and documented as "Not used for attestation with AWS KMS" | KMS honors the replayed document (PCR condition still matches, no TTL/nonce check enforced) and returns a new `CiphertextForRecipient`/plaintext for a request the attacker, not the original attested instance, initiated. |
| Third-party verifier implementer (customer-built, per `nitrotpm-attestation-document-validate.md`'s explicit instruction) | Nitro Attestation PKI trust chain | Following the doc's own Java sample, which sets `setRevocationEnabled(false)` and states "CRL must be disabled when doing the validation" | A certificate AWS has revoked (compromised module/signing key) still validates successfully in a verifier built exactly to spec. |
| Third-party verifier implementer | COSE_Sign1 signature algorithm selection | The 4-step validation process never instructs pinning the algorithm to `-35`/ES384 independent of the document's own `protected` header | A verifier that dispatches on the attacker-supplied `protected: {1: alg}` header rather than hardcoding ES384 is exposed to algorithm-confusion for any forged document claiming a different alg. |
| EC2 console operator | `TpmSupport` ground truth | Console does not surface `TpmSupport` for AMIs or instances (stated twice, once per page) | An operator who audits via console believes NitroTPM/attestation posture is whatever they expect; actual state can only be confirmed via `describe-images`/`describe-instances`/`describe-image-attribute` — a verifiability gap that can mask a mis-provisioned (non-attestable) fleet. |

## 5. Recommended Areas of Focus

### Area 1 — Attestation-conditioned authorization (Lens W) — reproducible-measurement bypass [headline finding]
**Background:** `prepare-attestation-service.md` shows the canonical pattern: a KMS key policy allows `Decrypt`/`GenerateDataKey`/`GenerateRandom` only if `kms:RecipientAttestation:NitroTPMPCR4` and `…PCR12` match reference values from "your Attestable AMI." `attestable-ami.md` + `build-sample-ami.md` show that the reference AMI is built from a **publicly published** KIWI NG recipe (`github.com/amazonlinux/kiwi-image-descriptions-examples`, and `github.com/aws/nitrotpm-attestation-samples` for NixOS), with measurement computed deterministically by `nitro-tpm-pcr-compute` from the built UKI.
**Security Concern:** `nitrotpm-attestation-document-content.md` states the boot-binary hash "can describe exactly what code an instance will execute" — i.e. the measurement is a pure, public function of a public recipe. Nothing in the KMS key-policy mechanism binds the condition to a *specific* AMI ID, account, or instance — only the `Principal` clause does that. If a key policy's `Principal` is any broader than a tightly-scoped role (e.g. a role assumable by many workloads, or a policy that omits/wildcards Principal because the author believed the PCR condition alone was "the" lock), any AWS customer can clone the public recipe, self-register an identical AMI in their own account, launch it, run `nitro-tpm-attest`, and present a document whose PCR4/PCR7/PCR12 match the victim's policy exactly.
**High-level Test Scenarios:**
1. Build the public sample recipe twice, in two different accounts; confirm `pcr_measurements.json` PCR4/PCR7/PCR12 are byte-identical (fully expected per docs — this step just establishes ground truth for the oracle).
2. Author a KMS key policy using the exact example from `prepare-attestation-service.md`, but with the `Principal` set to a role trust policy that is *not* narrowly scoped to one instance/AMI (a realistic customer mistake — the doc's own prose frames the PCR condition as "ensures that only requests from instances launched using the Attestable AMI" and under-emphasizes that `Principal` is still doing the account-binding work).
3. From the second account's self-built clone, assume a role satisfying `Principal`, call `Decrypt` with the clone's attestation document attached as `Recipient`. **Oracle: `Decrypt` succeeds** — proves the gate authenticated "this software", not "this customer's instance."
4. Repeat with `Principal` tightened to a single-account role ARN; confirm denial — isolates exactly how much of the security is PCR vs. Principal, for the writeup.
**Doc evidence:** `nitrotpm-attestation-document-content.md` ¶1–2 (constant/deterministic PCR language); `attestable-ami.md` "Requirements for creating Attestable AMIs" + GitHub links; `build-sample-ami.md` full build steps; `prepare-attestation-service.md` example policy.
**Severity-if-true:** Critical if any real-world key policy relies on PCR conditions with a broad/misconfigured Principal (plausible — the doc's framing nudges authors toward over-trusting the PCR condition).

### Area 2 — Under-binding / unpaired PCR conditions (Lens W variant)
**Background:** `nitrotpm-attestation-document-content.md` states PCR0/PCR1 "will always contain constant values" (same for every instance) and that PCR12 is "**Required in conjunction with PCR4** for standard boot to validate the command line was not modified" — i.e. PCR12 alone proves nothing about command-line tampering.
**Security Concern:** `conditions-nitro-tpm.md` defines each `NitroTPMPCR<0-23>` as an independent, single-valued String condition key with no documented cross-key dependency enforced by KMS. A policy author can satisfy `PutKeyPolicy` schema checks while keying a "secure" policy on PCR0/PCR1 alone (constant across all instances — equivalent to no condition at all) or PCR12 alone (meaningless without PCR4).
> **Confirmed smoking gun — AWS's own canonical example pins PCR12 to all-zeros.** The example policy in `prepare-attestation-service.md` (verified byte-for-byte against the live page) pairs a real hex `NitroTPMPCR4` value with `"kms:RecipientAttestation:NitroTPMPCR12":"000000000000…000"` (96 hex zeros). An all-zero PCR is the TPM's *uninitialized/never-extended* value — i.e. the example gates on "the kernel command line was never measured / is the empty-baseline" rather than on a specific trusted command line. A customer who copies this example verbatim (the documented happy path) ships a policy whose PCR12 half is satisfied by any boot that leaves PCR12 unextended, so the only real discriminator is PCR4. This is the under-binding footgun demonstrated *in AWS's own reference artifact* (Lens U: shipped-sample defect), not merely a hypothetical deviation.
> **Operator case-folding:** the same example uses `StringEqualsIgnoreCase` (not `StringEquals`) for the PCR comparison. Hex digests are case-insensitive so this is benign for well-formed values, but it is worth confirming that `IgnoreCase` + an attacker-influenced value field cannot be combined with any non-hex marker to widen a match; carry as a minor sub-check under Area 3's operator-semantics scenario.
**High-level Test Scenarios:**
1. Author a key policy using only `kms:RecipientAttestation:NitroTPMPCR0` pinned to the known-constant value; confirm `PutKeyPolicy` accepts it without warning.
2. From *any* NitroTPM instance (not just the Attestable AMI), request an attestation doc and call `Decrypt`. **Oracle: success**, because PCR0 is identical on every NitroTPM-enabled instance regardless of what AMI/boot code it runs — the gate is attestation-shaped but has zero discriminating power.
3. Author a policy keyed only on `NitroTPMPCR12` (no PCR4); modify the UEFI boot command line on an otherwise-trusted-looking build; confirm the modified command line still satisfies the policy (PCR12 unchanged scenario) or that no detection path exists absent PCR4.
4. **(From the all-zeros finding)** Launch an instance whose boot leaves PCR12 at the all-zeros baseline (or where the command line is not extended into PCR12) and present its document against a policy copied verbatim from `prepare-attestation-service.md`. **Oracle:** the PCR12 condition is satisfied by the all-zeros value → confirms the example's PCR12 half contributes no command-line integrity binding.
**Doc evidence:** `nitrotpm-attestation-document-content.md` "Important" box + PCR12 bullet; `prepare-attestation-service.md` example policy (`NitroTPMPCR12` = 96 hex zeros, `StringEqualsIgnoreCase`).
**Severity-if-true:** High — this is a configuration footgun AWS's own docs make easy to fall into, and the canonical example itself ships an all-zeros PCR12 (so the "copy the example" path inherits the weakness, not just an off-recipe deviation).

### Area 3 — NitroTPM-vs-Nitro-Enclaves condition-key family confusion (Lens S / Lens U)
**Background:** `list_kms.md` enumerates **two parallel, numerically-overlapping** condition-key families plus a third image-digest key: `kms:RecipientAttestation:PCR0`…`PCR31` (Nitro Enclaves; `conditions-nitro-enclave.md`), `kms:RecipientAttestation:NitroTPMPCR0`…`NitroTPMPCR23` (NitroTPM; `conditions-nitro-tpm.md`), and `kms:RecipientAttestation:ImageSha384` (enclave EIF image hash). The *same index* means something **completely different** per family — e.g. enclave `PCR4` = "ID of the parent instance", NitroTPM `NitroTPMPCR4` = "Boot Manager Code." Each key is documented as "effective only when the `Recipient` parameter … specifies a signed attestation document from" its own mechanism. `ImageSha384` is a *third* name a confused author can reach for when searching "attestation image hash" — it belongs to the enclave mechanism and silently never activates for a NitroTPM document.
**Security Concern:** The EC2 NitroTPM docs (`nitrotpm-attestation.md`, `prepare-attestation-service.md`) never mention the enclave family exists at all — a policy author researching "attestation PCR conditions for KMS" via search/copy-paste from KMS docs has a one-character-prefix (`PCR4` vs `NitroTPMPCR4`) way to silently author a statement gated on the wrong mechanism. Because each family only "activates" for its own document type, the likely failure mode is a silent **lockout** (safe but confusing) rather than an open bypass — but the two mechanisms are not cross-validated by `PutKeyPolicy`, so there is no authoring-time signal that the mechanism doesn't match the use case.
**High-level Test Scenarios:**
1. Author a policy intended for NitroTPM gating but using the bare `kms:RecipientAttestation:PCR4` key (enclave family) instead of `NitroTPMPCR4`; confirm `PutKeyPolicy` accepts it with no mechanism-mismatch warning.
2. Attempt `Decrypt` from a genuine NitroTPM instance with a correctly-formed TPM attestation document attached; confirm the enclave-keyed condition is never satisfied (expected deny) — document this as the "safe but silently broken" failure mode.
3. Check whether any policy evaluation path (e.g., a statement mixing `Null` checks across both families, or an `Allow`+enclave-condition statement alongside a separate permissive `Allow` without any attestation condition) can be authored such that the *presence* of either doc type satisfies an overly broad combined policy.
**Doc evidence:** `list_kms.md` lines enumerating both families back-to-back; `conditions-nitro-tpm.md` vs `conditions-nitro-enclave.md` per-index semantic tables.
**Severity-if-true:** Medium (operational/least-privilege risk) rising to High if scenario 3 yields a real bypass combination.

### Area 4 — Attestation Document replay / freshness (Lens M)
**Background:** `attestation-get-doc.md`: the `nonce` parameter "can be used to set up challenge-response authentication… to help prevent impersonation attacks… **Not used for attestation with AWS KMS**." `attestation-attest.md` describes the KMS integration purely in terms of PCR-match + public-key re-encryption; no TTL/timestamp check is mentioned anywhere in the KMS path.
**Security Concern:** The CDDL spec (`nitrotpm-attestation-document-validate.md`) includes a `timestamp` field, but nothing in AWS's docs states that KMS enforces freshness on it for the `Recipient` attestation path. Combined with no mandatory nonce for KMS, a captured Attestation Document (e.g. sniffed in transit, logged, or retained in an app's memory/disk) appears replayable to KMS indefinitely as long as its PCR values still equal the policy's pinned values and its embedded `public_key` is one the replaying party can decrypt for (or if the replaying party doesn't need the plaintext back, just needs to trigger/observe the authorized side-effect of a successful `Decrypt` call, e.g. for audit-bypass or resource-exhaustion purposes).
**High-level Test Scenarios:**
1. Generate one Attestation Document; call `Decrypt` with it once (baseline success).
2. Replay the identical byte-for-byte document on a second, later `Decrypt` call for a different ciphertext. **Oracle:** does KMS succeed again (no TTL enforced), or reject with a freshness-specific error (undocumented behavior worth confirming either way)?
3. Check whether CloudTrail (`ct-nitro-tpm.md`) distinguishes a replayed document from a fresh one (it logs PCR values and `module_id`, not a nonce/timestamp field) — if not, replay is also **invisible** to the documented audit trail (compounds with Lens O).
**Doc evidence:** `attestation-get-doc.md` nonce paragraph; `attestation-attest.md`; `ct-nitro-tpm.md` CloudTrail field list (no nonce/timestamp field present).
**Severity-if-true:** Medium–High (confirmation needed; this is the strongest "doc silence = lead" item in the set — AWS's docs simply never affirm a freshness check exists for this path).

### Area 5 — Certificate-chain validation guidance disables revocation (Lens Y)
**Background:** `nitrotpm-attestation-document-validate.md` §"Certificate chain validity": **"CRL must be disabled when doing the validation,"** followed by sample Java code calling `validationParameters.setRevocationEnabled(false)`.
**Security Concern:** This is a documented MUST aimed at exactly the audience building custom (non-KMS) verifiers. Any implementer following this guidance faithfully builds a verifier that can **never** honor a revocation of a compromised Nitro Attestation PKI leaf or intermediate certificate. The doc does not explain *why* CRL must be disabled (performance? CRL endpoint unavailability? by design because Nitro doesn't issue CRLs?) or what compensating control (e.g. short cert lifetimes) exists instead — a Lens U doc-vs-mechanism gap: the guarantee "Attestation Documents are signed by the AWS Nitro Attestation PKI" is not accompanied by a revocation story.
**High-level Test Scenarios:**
1. Confirm (via AWS Nitro Enclaves root cert docs / CA practice statement, if published) whether short-lived leaf certs are the actual compensating control, or whether this is a genuine, unmitigated gap.
2. For any custom verifier reference implementation AWS publishes (check `nitro-tpm-attest` GitHub repo and `nitrotpm-attestation-samples`), confirm whether it also disables revocation checking — if the *reference implementation* does, every downstream adopter inherits the gap.
**Doc evidence:** `nitrotpm-attestation-document-validate.md` "Certificate chain validity" section, verbatim CRL note.
**Severity-if-true:** High if no compensating control is documented elsewhere; Informational if short cert lifetimes are confirmed as the mitigation (AWS should then say so in-doc — still a Lens U citable gap either way).

### Area 6 — COSE algorithm pinning not mandated for custom verifiers (Lens FF)
**Background:** The COSE_Sign1 structure's protected header is shown as the literal pair `{1: -35}` (ES384). The 4-step validation process in `nitrotpm-attestation-document-validate.md` is: (1) decode CBOR→COSE_Sign1, (2) extract the document, (3) verify the certificate chain, (4) "ensure that the Attestation Document is properly signed."
**Security Concern:** Step 4 never instructs the implementer to **hardcode** the expected algorithm and reject any other value in the attacker-supplied `protected` header, rather than branching on whatever the header declares. This is the structural precondition for alg-confusion (the JWT `alg:none`/RS256→HS256 bug class, here applied to COSE/CBOR). The doc shows the *expected* value as an example, not as a MUST-pin-and-reject-others instruction.
**High-level Test Scenarios:**
1. Review any reference verifier code AWS publishes (`nitro-tpm-attest` GitHub repo) for whether algorithm selection is hardcoded or header-driven.
2. For a from-scratch implementation following only the prose steps, confirm whether a naive implementer (using a generic COSE library's "verify" call without an explicit algorithm pin) would be vulnerable to a crafted document declaring a different `alg` value paired with attacker-controlled key material of the matching (weaker) type.
**Doc evidence:** `nitrotpm-attestation-document-validate.md` COSE_Sign1 structure + 4-step list.
**Severity-if-true:** Medium (depends entirely on third-party implementation choices AWS doesn't control) — reportable as a documentation-hardening gap (Lens U) regardless of live exploitability.

### Area 7 — Documented-guarantee vs. console/API truth (Lens U)
**Background:** `verify-nitrotpm-support-on-ami.md` and `verify-nitrotpm-support-on-instance.md` both state, verbatim: "The Amazon EC2 console does not display `TpmSupport`" / "the `TpmSupport` field."
**Security Concern:** Every security property in this cluster (measured boot, attestation, isolated-compute-environment claims) is downstream of `TpmSupport` actually being enabled. An operator auditing posture via the console — the default workflow for most EC2 attributes — has no way to see whether NitroTPM is active, creating a blind spot that compounds any of Areas 1–6 (a misprovisioned, non-attestable instance can silently sit behind a policy that assumes attestation is in force).
**High-level Test Scenarios:** Confirm current console behavior still omits the field (doc-only check, since this agent does not touch live accounts); if AWS has since added console visibility, this is resolved drift to report.
**Doc evidence:** both verify-*.md pages, identical sentence.
**Severity-if-true:** Low/Informational standalone; raises severity as an enabler for Areas 1–2.

### Area 8 — TPM-enablement is not *value*-gatable (Lens U/R) — CORRECTED; now a cross-reference to the hub plan
> **This area originally claimed `RegisterImage`/`GetInstanceTpmEkPub` have "zero condition keys." That was WRONG** — it was read off the *condensed per-action summary* table in `list_ec2.md` (blank Condition cell), not the authoritative **Actions** table. Corrected facts below; the EK-tracking and RegisterImage-enablement leads themselves are now **owned by `nitrotpm-attack-research-plan.md` (hub)** and are not re-developed here — this entry survives only to (a) carry the correction and (b) state the one attestation-relevant consequence.
**Background (corrected):** `RegisterImage` = `image*` (aws:RequestTag/aws:TagKeys/ec2:ImageID/ec2:Owner/ec2:Region) + a full `snapshot` resource row; `GetInstanceTpmEkPub` = `instance*` + ~20 condition keys. Both are resource/tag-scopable. What is genuinely absent, verified by whole-file grep of `list_ec2.md`, is any **`ec2:TpmSupport`** condition key anywhere, and `ec2:BootModeOverride` appears only on the image-*creating* actions (`CreateImage`/`CopyImage`/`CreateRestoreImageTask`), **not** on `RegisterImage`.
**Security Concern (the attestation-relevant consequence):** because there is no `ec2:TpmSupport` key, an admin **cannot author an IAM/SCP condition that forbids (or requires) `--tpm-support v2.0` by value** — enablement is all-or-nothing with the `RegisterImage` grant. This is the IAM-side mirror of the attestation guarantee: the whole attestation story assumes the fleet's AMIs are genuinely NitroTPM-backed, yet the one knob that turns that on cannot be pinned by policy. (The *registration-as-attacker-AMI* reproducible-measurement angle is Area 1; the EK-as-identifier angle is the hub plan.)
**High-level Test Scenarios:** `iam:SimulateCustomPolicy` showing a `Deny unless ec2:TpmSupport=v2.0`-style statement is **inert** (the key does not exist → the condition never matches → the Deny is vacuous or the Allow fails closed). No resource created.
**Doc evidence:** `list_ec2.md` RegisterImage (Actions table) + GetInstanceTpmEkPub (Actions table) rows; whole-file grep = 0 hits for `ec2:TpmSupport`.
**Severity-if-true:** Low (enablement-value gap, not a bypass) — reportable only as the Lens-U doc/enforcement observation; the privilege angle belongs to the hub plan.

## 7. Out-of-Scope Risk Categories
- The Nitro Hypervisor's internal signing process and private key custody (AWS service plane — hard stop if ever implicated, not a target to probe).
- AMD SEV-SNP attestation (`snp-attestation.md`) is a **separate** mechanism (VCEK/VLEK, AMD root of trust) covered only for completeness/contrast; no NitroTPM-specific lead was found there and it is not this cluster's primary scope.
- Generic `RegisterImage` abuse unrelated to TPM/attestation (e.g., registering a malicious AMI with no TPM support at all) — that is the ordinary shared-responsibility model already called out explicitly in `nitrotpm-attestation.md`'s "AWS shared responsibility model" section; AWS states the customer owns AMI content.
- Single-tenant self-DoS (e.g., an account locking itself out of its own key by misconfiguring its own PCR condition) — a customer footgun, not a boundary breach.
- UEFI Secure Boot internals beyond their role as a PCR7 input (`uefi-secure-boot.md` subtree) — tracked only as a dependency, not independently re-researched here.
