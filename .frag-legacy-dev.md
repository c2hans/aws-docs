## 3. Ranked, lens-mapped falsifiable leads

### Lead 1 — [Lens N] Deprecated v1 lifecycle API lacks `x-amz-expected-bucket-owner` support that the modern lifecycle API has
**Claim:** A caller using the still-functional deprecated v1 PUT/GET Bucket lifecycle API cannot defend against (or benefit from) the bucket-owner-confusion guardrail that the modern lifecycle API provides, because the v1 API's request/response headers do not include `x-amz-expected-bucket-owner`.
**Mechanism (doc evidence):**
- `v1-rel-RESTBucketPUTlifecycle.md` Request Headers section: "This implementation of the operation uses only request headers that are common to all operations" — table lists only `Content-MD5`. Confirmed verbatim on the live page via WebFetch (`docs.aws.amazon.com/.../v1-rel-RESTBucketPUTlifecycle.html`) on 2026-10-04.
- `v1-rel-RESTBucketGETlifecycle.md`: identical "common headers only" statement for GET.
- Contrast: `/work/aws-docs/docs/AmazonS3/latest/API/API_PutBucketLifecycleConfiguration.md` line 54 and `API_GetBucketLifecycleConfiguration.md` line 48 both show `x-amz-expected-bucket-owner: {{ExpectedBucketOwner}}` as a documented request header, with its own named anchor/description.
- Both old and new API share the exact same IAM actions (`s3:PutLifecycleConfiguration` / `s3:GetLifecycleConfiguration`) per `v1-rel-RESTBucketPUTlifecycle.md` line 19 and `v1-rel-RESTBucketGETlifecycle.md` line 16 — i.e., no IAM-side distinction between the two schemas exists; it is purely a client-chosen request shape against the same authorization surface.
**Confirm/Refute oracle:** Issue the legacy `PUT /?lifecycle` / `GET /?lifecycle` request forms against a bucket where the caller expects to own the bucket but a same-named bucket was deleted and recreated by a different account (classic S3 bucket-name-reuse confusion). The modern API would let the caller pin `ExpectedBucketOwner` and get a clean deny/mismatch error; the legacy API, per docs, offers no such header — confirm whether S3 silently proceeds against the "wrong" bucket when reached via the legacy form.
**Preconditions:** Caller has `s3:PutLifecycleConfiguration`/`s3:GetLifecycleConfiguration` on the bucket name but not on the actual current bucket owner's account; relies on bucket-name reuse/deletion race (same shape as prior public S3 "bucket sniping" incidents).
**Severity-if-true:** Medium–High (confused-deputy-adjacent; the control exists in the newer surface specifically to prevent this class of mistake, and the deprecated-but-still-functional surface documents no equivalent).
**Tier:** This is a **doc-vs-doc parity gap in AWS's own API surface**, not a customer-authored artifact — reportable as a hardening/parity gap if confirmed, independent of Lens R/Tier-2 sample-code framing.

### Lead 2 — [Lens N / S] Deprecated v1 lifecycle API has no `Filter`, object-tag, or object-size condition coverage
**Claim:** The v1 lifecycle API can only scope rules by `Prefix`; it has no `Filter`/`Tag`/`ObjectSizeGreaterThan`/`ObjectSizeLessThan` elements. Any security or cost-control design that relies on tag- or size-based lifecycle scoping (e.g., "only auto-expire objects tagged `Confidential=false`") cannot be expressed or enforced through the legacy API — but the legacy API is still callable and will silently apply the (broader) `Prefix`-only rule instead of refusing the call.
**Mechanism (doc evidence):** `v1-rel-RESTBucketPUTlifecycle.md` element table (lines 117–134) lists only `Prefix`, `Transition`, `Expiration`, `NoncurrentVersion*`, `AbortIncompleteMultipartUpload` — no `Filter`/`Tag`/`ObjectSizeGreaterThan`/`ObjectSizeLessThan`. Contrast: `API_PutBucketLifecycleConfiguration.md` line 18: "A filter identifying a subset of objects to which the rule applies. The filter can be based on a key name prefix, object tags, object size, or any combination of these," with explicit `<Filter>` XML (lines 67–85, 133, 170, 188–201).
**Confirm/Refute oracle:** Author a lifecycle rule intended to be tag-scoped using the legacy PUT form (which has no `Filter`/`Tag` element) and confirm it is accepted as a `Prefix`-only (i.e., broader-than-intended) rule rather than rejected — i.e., does S3 fail closed (reject malformed/ambiguous scoping) or fail open (accept the broader rule silently)?
**Severity-if-true:** Medium (unintended-broadening of a destructive lifecycle action — deletion/transition — rather than a cross-tenant breach).
**Tier:** Doc-vs-doc parity gap (not customer-authored).

### Lead 3 — [Lens R, Tier-2] `PutObjectAcl` CLI example grants public READ via the AllUsers URI group, with no Block Public Access caveat
**Claim:** AWS's own copy-pasteable AWS CLI example for `PutObjectAcl` grants `READ` to the well-known `http://acs.amazonaws.com/groups/global/AllUsers` URI — i.e., a verbatim public-read ACL grant — with no accompanying warning about Block Public Access, bucket ownership considerations, or "don't do this in production" caveat (contrast with the CORS/ListObjectsWeb examples below, which *do* carry such a caveat).
**Mechanism (doc evidence):** `s3_example_s3_PutObjectAcl_section.md` lines 112–120:
```
aws s3api put-object-acl --bucket {{amzn-s3-demo-bucket}} --key {{file.txt}} --grant-full-control {{emailaddress=user1@example.com,emailaddress=user2@example.com}} --grant-read {{uri=http://acs.amazonaws.com/groups/global/AllUsers}}
```
with prose "...and `read` permission to everyone" stated as a factual description, not a security warning.
**Confirm/Refute oracle:** A customer who copies this command verbatim against a bucket with Block Public Access disabled (or an account-level BPA override) makes the object world-readable. Confirm whether this example page or any linked page (`s3_example_s3_Scenario_ManageACLs_section.md`) carries a BPA/production warning anywhere — if not, the gap is "AWS's own example never surfaces the control that would prevent its own demonstrated action from going public."
**Severity-if-true:** Medium (customer self-inflicted exposure, but the *example itself* ships the unsafe grant as the canonical demonstration — Tier-2 because it's AWS-authored and copy-verbatim, not a customer-composed policy).

### Lead 4 — [Lens R, Tier-2] `PutBucketPolicy` CLI example and C++ snippet both demonstrate `"Principal": "*"` bucket-wide public read
**Claim:** The flagship CLI example for `PutBucketPolicy` is a public-read-except-one-prefix policy (`Principal:"*"`, `Action:"s3:GetObject"`, `Resource: bucket/*`, with a `Deny` carve-out only for `MySecretFolder/*`) — i.e., the *default worked example* for this API is "make the whole bucket public except for one folder," not a scoped, principal-specific grant.
**Mechanism (doc evidence):** `s3_example_s3_PutBucketPolicy_section.md` lines 81–113 (CLI section): prose states "This example allows all users to retrieve any object in *amzn-s3-demo-bucket* except those in the *MySecretFolder*," with `"Principal": "*"` appearing twice (Allow and Deny statements). Note the JavaScript (lines 253–278) and SAP ABAP (line 379) examples in the same file instead scope to a specific IAM role ARN/user ARN — i.e., AWS's own examples are internally inconsistent, and the CLI tab (often the first one developers copy) is the public-read one.
**Confirm/Refute oracle:** Confirm this is still the live CLI example on docs.aws.amazon.com (same URL) and check whether any surrounding prose anywhere on the page states a Block-Public-Access or "avoid public buckets" caveat — if absent, the finding stands as written.
**Severity-if-true:** Medium (Tier-2 sample-code insecure default; same class as the 2017-era "S3 bucket policy generator" public-bucket incidents AWS later hardened against with BPA).

### Lead 5 — [Lens R, Tier-2] `PutBucketCors` CLI example pairs wildcard `AllowedOrigins:["*"]` with `AllowedHeaders:["Authorization"]` for GET
**Claim:** AWS's own `PutBucketCors` CLI example's second rule allows **any origin** to issue cross-origin `GET` requests to the bucket while also allowlisting the `Authorization` header in the CORS preflight — meaning any third-party website's script can attach caller-supplied SigV4 `Authorization` headers in a cross-origin `GET` and have the browser-level CORS check pass, with the bucket able to serve the response to that arbitrary origin.
**Mechanism (doc evidence):** `s3_example_s3_PutBucketCors_section.md` lines 55–60:
```
{
  "AllowedOrigins": ["*"],
  "AllowedHeaders": ["Authorization"],
  "AllowedMethods": ["GET"],
  "MaxAgeSeconds": 3000
}
```
Prose at line 40 only frames this as "enables `GET` requests from any domain" — no warning comparable to the explicit "Don't do this in production" comment found in `s3_example_s3_Scenario_ListObjectsWeb_section.md` (Lead 7 below).
**Confirm/Refute oracle:** This is a browser-enforced boundary (CORS), so the "breach" is: does S3 itself (server-side) still enforce normal SigV4 authorization on the request regardless of the CORS headers (likely yes — CORS only governs whether the *browser* exposes the response to the calling script, not S3's own authn/authz)? If so, this specific pairing is lower severity than it first looks (CORS wildcard-origin + GET is a common, lower-risk pattern since the caller still needs valid read permission on the object) — but it is still a documented AWS example that trains customers to pair `AllowedHeaders:["Authorization"]` with `AllowedOrigins:["*"]`, which is a bad habit if copied onto a bucket where `s3:GetObject` is also broadly granted (chains into Lead 3/4). Flag as a **compounding factor**, not a standalone breach.
**Severity-if-true:** Low standalone; Medium when chained with Lead 3/4 (public-read ACL/policy + this CORS rule = any website can display/exfiltrate bucket contents in-browser from any origin).

### Lead 6 — [Lens R/Y, Tier-2] Presigned-URL scenario page: .NET SDK example defaults to a 12-hour expiry for both GET and **PUT** (write) presigned URLs — a clear outlier against every other SDK's example on the same page
**Claim:** Of the ~8 SDK language examples on the single `s3_example_s3_Scenario_PresignedUrl_section.md` page, the .NET example sets `const double timeoutDuration = 12;` (hours) — i.e., 43,200 seconds — and reuses this same 12-hour value for a **PUT** presigned URL (upload/overwrite capability), confirmed identical on the live docs.aws.amazon.com page via WebFetch on 2026-10-04. Every other SDK's example on the same page uses a far shorter default: Java 10 minutes (`Duration.ofMinutes(10)`, three occurrences), JavaScript v3 3600 seconds / 1 hour (two occurrences), PHP 20 minutes (`"+20 minutes"`), SAP ABAP 600 seconds / 10 minutes, and the .NET v4 presigned-POST scenario explicitly comments `// Short expiration for the demo` using 10 minutes. Python and Rust/Go leave the duration as a caller-supplied parameter (not an AWS-chosen default).
**Mechanism (doc evidence):** `s3_example_s3_Scenario_PresignedUrl_section.md` lines 30–31 and 112–113 ("Specify how long the signed URL will be valid in hours" / `double timeoutDuration = 12;`), lines 72 and 182 (`Expires = DateTime.UtcNow.AddHours(duration)` applied to both the GET example at line ~68 and the **upload/PUT** example at line ~177 — `GeneratePreSignedURL` is reused for `UploadUsingPresignedURL`). Compare lines 1052/1205/1370 (Java, `Duration.ofMinutes(10)`), 1459/1566 (JS, `expiresIn: 3600`), 1726 (PHP, `"+20 minutes"`), 2298 (SAP ABAP, 600-second comment), 336 (.NET v4 presigned-POST, `AddMinutes(10)` with explicit "Short expiration for the demo" comment).
**Confirm/Refute oracle:** This is a direct, in-corpus differential: the same page, same vendor, same tutorial purpose, same operation family, yet one language's canonical example is 12x–72x longer-lived than its siblings — and it's the one applied to a **write** capability. No live test needed to establish the differential; a hunter should additionally confirm whether the "Expires" field on a presigned PUT URL, once issued, can be revoked before natural expiry (it generally cannot, short of revoking/rotating the signing credential — a Lens Y "presigned-URL survival past revocation" angle worth testing live).
**Severity-if-true:** Medium (Tier-2 — a 12-hour leaked/logged/referrer-leaked presigned PUT URL gives a 12-hour window to overwrite or plant an object at a chosen key, vs. a 10–60 minute window in every sibling example).

### Lead 7 — [Lens C — presigned POST / presigned URL example scoping] No example in the entire 2314-line scenario page demonstrates pinning conditions on a presigned POST (content-length-range, key prefix, Content-Type, ACL)
**Claim:** AWS's own `CreatePresignedPost`/presigned-URL teaching material (`s3_example_s3_CreatePresignedPost_section.md` and the presigned-POST portion of `s3_example_s3_Scenario_PresignedUrl_section.md`, lines ~192–470) exposes a `conditions`/`Fields` parameter on the API but **never populates it with a concrete security-relevant condition** (no `content-length-range`, no `starts-with $key`, no ACL pin) in any shown example — confirmed by a full-file grep for `condition|content-length-range|starts-with|acl|policy` returning a single incidental hit (a comment noting ACL settings aren't needed because the URL embeds signed query params, not an actual conditions example).
**Mechanism (doc evidence):** `s3_example_s3_CreatePresignedPost_section.md` lines 25–59 (`conditions` parameter accepted but passed through generically, no sample values); full-file grep of `s3_example_s3_Scenario_PresignedUrl_section.md` for the above terms returns only line 1388 (an unrelated comment about query-param-embedded auth).
**Confirm/Refute oracle:** This is a **null-result-as-lead**: the absence itself is the finding. A customer following only these two pages has no AWS-provided template for the single most important hardening step for presigned POST (bounding upload size / key namespace) — contrast with the modern userguide's presigned-POST security guidance if it exists elsewhere (out of this cluster's assigned pages; flag as doc-gap to check `GeneratingPresignedURLsUploadObject`/userguide pages in a future pass).
**Severity-if-true:** Low standalone (an omission, not an active bad default) but amplifies Lead 6's severity — the teaching material shows duration but never shows scoping, so a copy-paste customer gets an unbounded, long-lived upload grant.

### Lead 8 — [Lens Q/R] AWS Amplify browser-upload example's first/default `put` call has no visible access-level scoping; "private" is only the second, opt-in example
**Claim:** `browser-based-uploads-aws-amplify.md`'s first worked example (`Storage.put('test.txt', 'Hello')`) sets no `level` option, and only the second example explicitly opts into `level: 'private'`. Per Amplify's own (external) Storage module semantics, the unspecified level defaults to `'public'` — meaning the page's canonical first example demonstrates a public-storage write by omission, with the private alternative framed as the special case rather than the default.
**Mechanism (doc evidence):** `browser-based-uploads-aws-amplify.md` lines 36–53: first block has no `level`; second block adds `level: 'private'` with prose "shows how to put *private* data" implying the first was something else (public) by contrast.
**Confirm/Refute oracle:** This page alone does not state the Amplify default explicitly — this is a **doc-gap**, not a confirmed claim. Cross-check needed against AWS Amplify's own Storage-module documentation (external to this cluster) to confirm the default level is indeed `'public'` before treating this as more than a plausible lead.
**Severity-if-true:** Low–Medium (Tier-2 if the public-default claim is confirmed, since the page never states what "no level" resolves to).

### Lead 9 — [Lens O, informational] `get-request-ids.md` Ruby wire-logging guidance warns of credential leakage but the general SDK logging guidance does not repeat the warning
**Claim:** The page explicitly warns, only under the Ruby tab: "Wire logging can include sensitive information, such as your access key ID. Sensitive information should be sanitized before sharing it with AWS Support" (line 233–234) and separately warns generically "don't recommend enabling logging in production systems" (line 87–88, performance framing only, not a security framing) — but no equivalent sensitive-data warning appears under the C++, Java, JavaScript, Kotlin, .NET, PHP, or Python tabs, even though verbose/debug logging in those SDKs can equally capture `Authorization` headers, SSE-C keys, or request bodies.
**Mechanism (doc evidence):** `get-request-ids.md` lines 83–96 (generic intro, performance-only caveat) vs. line 233–234 (Ruby-specific sensitive-data caveat) — the security caveat is not repeated across the other 8 SDK tabs on the same page despite the same debug/verbose-logging mechanism applying to all of them.
**Severity-if-true:** Informational/Low — a documentation-completeness gap, not an exploitable control failure; worth noting because it is the only place in this cluster where AWS states outright that its own recommended debugging workflow can leak credentials, and does so inconsistently.

### Lead 10 — [Lens U] S3 Tables object-API: ACL, storage class, and SSE headers are accepted syntactically but silently forced to fixed values
**Claim:** `developing-s3-tables-APIs.md` documents that `PutObject`/`CreateMultipartUpload` accept `x-amz-acl`, `x-amz-storage-class`, and `x-amz-server-side-encryption` headers, but for S3 Tables the values are hardcoded ("the default value is `bucket-owner-full-control` and it can't be changed" / "`STANDARD` and it can't be changed" / "`SSE-S3 (AES256)` and it can't be changed") — i.e., the API surface advertises these as configurable headers but silently overrides any customer-supplied value rather than rejecting the request.
**Mechanism (doc evidence):** `developing-s3-tables-APIs.md` lines 24, 32–33, 58, 74–75.
**Confirm/Refute oracle:** This is a **positive control** (can't be weakened to public ACL or unencrypted), but the open question is whether S3 silently accepts and ignores a conflicting customer-supplied header (e.g., `x-amz-acl: public-read`) with a 200 response, vs. rejecting it with a 400 — silent-ignore is a Lens U doc-vs-behavior integrity question (does the caller get any signal that their requested ACL/encryption was not honored?) even though the net security outcome here favors safety.
**Severity-if-true:** Informational (confirms a hardening behavior, but silent-override-without-error is worth flagging as an integrity/observability gap, not a vulnerability).
