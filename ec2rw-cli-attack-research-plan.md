## 1. Pentest Objectives (boundary-breach goals)

1. Achieve code execution on a **healthy** EC2Rescue rescue host by feeding it a crafted foreign offline volume (invert the tool's safety premise: compromised volume → clean host).
2. Recover a `ResetAccess`-generated local Administrator password for an instance you do **not** own/control from SSM Parameter Store, using only broad `ssm:GetParameter` + default-key decrypt (no attach rights, no origin-instance access).
3. Prove the AWS-authored "least-privilege" sample IAM policy fails closed and that AWS's own adjacent docs push the customer to an account-wide `ssm:*` grant → intra-account escalation enabler.
4. Drive stop/detach/attach/image on an arbitrary instance via the SSM Automation `AutomationAssumeRole` confused-deputy, holding only `ssm:StartAutomationExecution` + a loose `iam:PassRole`.
5. Confirm `/check-only` (documented "makes no modifications") still writes the disk signature by default — a false documented guarantee with integrity impact on a volume the operator asked not to touch.
6. (If pursued) Confirm the admin-run EXE has no published integrity material (hash/Authenticode), making the download+execute chain an unverified supply-chain primitive.

## 2. Components, Assets, and Design

**What it is.** `EC2RescueCmd.exe` (and a GUI) — a downloadable tool run **on** a Windows Server 2012+ EC2 instance to diagnose/fix another (or the same) instance. Two modules: a **data-collector** and an **analyzer** that "parses the data collected against a series of predefined rules" (`Windows-Server-EC2Rescue.md:15`). Three actions: **Collect**, **Rescue**, **Restore**. On start it checks it is running on an EC2 instance.

**Interfaces / entry points.**
- **Local CLI** `/online` — acts on the host instance itself (collect logs, reset local admin password, enable user-data execution).
- **Local CLI** `/offline:<device_id>` — acts on a **foreign root EBS volume detached from an impaired instance and attached to this healthy host** (`ec2rw-cli.md:10-12`; workflow `ec2rw-gui.md:65-77`).
- **Download**: path-style `https://s3.amazonaws.com/ec2rescue/windows/EC2Rescue_latest.zip?x-download-source=docs` (bucket literal name `ec2rescue`), run with Administrator rights (`ec2rw-cli.md:14`, `ec2rw-gui.md:49-54`). TLS-1.2-may-need-enabling note on Win2016-and-earlier (`ec2rw-gui.md:58-63`).
- **SSM Run Command** `AWSSupport-RunEC2RescueForWindowsTool` — "Downloads and verifies" the tool, imports a PowerShell module, runs `EC2RescueCmd`. Commands: `ResetAccess`, `CollectLogs`, `FixAll` (`ec2rw-ssm.md:8-20`).
- **SSM Automation** `AWSSupport-ExecuteEC2Rescue` / `AWSSupport-StartEC2RescueWorkflow` — orchestrates stop → detach root → attach to a helper instance → run → reattach, via an `AutomationAssumeRole`.

**Assets.**
- Local **Administrator password** (generated by Rescue/ResetAccess). Via SSM stored at `/EC2Rescue/Password/<INSTANCE_ID>` (SecureString, default key `alias/aws/ssm`) (`ec2rw-ssm.md:17`).
- **Foreign volume secrets** harvested by Collect: SYSTEM/SOFTWARE registry hives, BCD hive, memory/mini-dumps, SSM InstanceData, SetupAPI logs → zip at `/output:<path>` on the rescue host (`ec2rw-cli.md:36-57`).
- **The EXE itself** (admin-run artifact) and the **AWS-managed SSM documents** and **sample IAM policies** (copy-verbatim artifacts).

**ASCII pipeline (offline mode — the interesting path):**
```
   [IMPAIRED / attacker-influenced instance]
        | root EBS volume detached
        v
   [EBS volume: NTFS + SYSTEM/SOFTWARE/BCD hives, .dmp, .evtx, SetupAPI logs, RegBack]
        | ec2:AttachVolume  (xvdf)
        v
   [HEALTHY RESCUE INSTANCE  --- admin/SYSTEM ---]
      NTFS driver (kernel) --> EC2Rescue collector --> analyzer "predefined rules"
            |                        |                        |
         mount parse            read hives/dumps          write: disk-signature "fix",
                                                          Ec2SetPassword, Ec2HandleUserData,
                                                          LKGC / RegBack restore
        |  /output zip (secrets land on the healthy host)
        v
   (reattach volume -> boot target with attacker-chosen admin pw / boot script)
```

## 3. Trust-Boundary Map

| From (actor / zone) | To (resource / zone) | Crossing mechanism | **Breach oracle** |
|---|---|---|---|
| Impaired/foreign volume content (untrusted) | Healthy rescue host (admin) | NTFS mount + collector/analyzer parse of hives/dumps/evtx | **Any code exec, OOB/UAF, or hang in the rescue-host parser from crafted foreign bytes = breach** (clean host compromised by the volume it was rescuing) |
| Caller with EBS attach/detach on a 2nd instance | Target instance's OS admin | offline Rescue: Ec2SetPassword / Reset Admin Password / Ec2HandleUserData written to the foreign volume | Target boots with attacker-known admin password or runs attacker boot script — **no OS credential/keypair/RDP ever needed** |
| Any account principal with broad `ssm:GetParameter`+decrypt | Another instance's admin password | SecureString at deterministic `/EC2Rescue/Password/<id>`, default key `alias/aws/ssm` (un-scopable) | Plaintext admin password returned for an instance the caller has **no** attach/OS rights over |
| Caller with `ssm:StartAutomationExecution` + loose `iam:PassRole` | Arbitrary instance (stop/detach/attach/image) | `AutomationAssumeRole` assumed by SSM on caller's behalf | Full stop/detach/attach/backup cycle driven under a role the caller could not use directly |
| Operator intent "no modifications" (`/check-only`) | Attached volume integrity | default disk-signature overwrite after offline op | Volume MBR/signature region bytes change despite `/check-only` and no prompt |
| Customer following the doc | AWS-owned `ec2rescue` S3 bucket | path-style download of admin-run EXE, no published hash/signature | **HARD STOP** — any probe of the bucket's ownership/state is service-plane; treat as doc-gap only |
| Any customer surface | AWS's own service plane (AWSSupport doc owner, ec2rescue/awssupport-ssm buckets) | — | **Hard stop; preserve evidence; flag for disclosure** |

## 5. Recommended Areas of Focus (priority order)

### 5.1 Untrusted foreign-volume parsing → code exec on the healthy rescue host  — **[TOP PRIORITY, NEW]**
**Background.** Offline mode exists precisely so a *clean* instance acts on an *impaired* one. The rescue host (admin/SYSTEM) mounts the foreign volume and the analyzer "parses the data collected against a series of predefined rules" (`Windows-Server-EC2Rescue.md:15`; `ec2rw-gui.md:77`) automatically — SYSTEM/SOFTWARE hives, the `HKLM\BCD00000000` hive, `.dmp`/minidumps, `.evtx` event logs, SetupAPI logs, `\Windows\System32\config\RegBack` (`ec2rw-cli.md:36-45`, `ec2rw-gui.md:20-26`).
**Security Concern.** The foreign volume is attacker-influenceable: (a) the impaired instance was compromised before triage and a crafted hive/dump/log was planted; or (b) an operator is socially engineered into attaching an attacker's volume/snapshot. The docs are **silent** on any sandboxing, format validation, hive/dump integrity check, or privilege separation between collector and analyzer — a doc-gap, not a documented mitigation.
**High-level Test Scenarios.**
- **Claim:** a malformed registry hive (bad cell offsets / recursive keys / corrupt security descriptors), BCD store, `.dmp`, `.evtx`, or raw NTFS structure triggers OOB/UAF/hang in `EC2RescueCmd.exe` or a child parser running as admin on the healthy host. **Oracle:** attach a volume crafted at a known registry/evtx/dump parser-bug pattern, run `/collect:all` or an analyzer-invoking action, observe crash/hang/OOB vs clean failure. Requires binary analysis of the EXE (download in an isolated lab).
- **Claim:** the NTFS driver itself (kernel) parses the untrusted filesystem on mount before EC2Rescue reads anything — a crafted NTFS volume is a kernel-parser input regardless of the tool. **Oracle:** mount a fuzzed NTFS image on an isolated rescue host; observe driver fault.
**Doc evidence:** `Windows-Server-EC2Rescue.md:15`, `ec2rw-gui.md:77`, `ec2rw-cli.md:36-45`. **Severity-if-true:** Critical (code exec on clean host inverts the tool's safety premise + yields that host's instance-profile creds); Medium if crash/hang-only (DoS of the incident-response tool). **Stop:** on first reproducible memory-safety signal — capture crash artifact, do not weaponize further.

### 5.2 Cross-principal recovery of ResetAccess admin passwords from Parameter Store  — **[HIGH]**
**Background.** `ResetAccess` resets the local Administrator password and stores it at `/EC2Rescue/Password/<INSTANCE_ID>`, SecureString, default key `alias/aws/ssm` (`ec2rw-ssm.md:17`). Confirmed singular "Password" by a second independent doc (the runbook reference).
**Security Concern.** The path is **deterministic/enumerable** from a public instance ID (`ec2:DescribeInstances`/console/CloudTrail expose IDs with no SSM rights). Decrypt under the default key is gated **only** by the caller's own `kms:Decrypt` because "you cannot establish access control policies for the default `aws/ssm` KMS key" (`secure-string-parameter-kms-encryption.md:227`; decrypt-needs-`kms:Decrypt` at :223). `GetParameter`'s only condition keys are tag-based (`list_ssm.md:1446-1449`) — nothing ties the read to the caller's own instance. The parameter persists after instance termination (`systems-manager-best-practices-delete-resources.md:25`; no auto-cleanup documented).
**High-level Test Scenarios.**
- **Claim:** a principal with broad `ssm:GetParameter*` + `kms:Decrypt` on `Resource:"*"` (a common "SSM read" bundle) reads the plaintext admin password of **another** instance it has no attach/OS rights over. **Oracle:** two instances, `ResetAccess` one, read `/EC2Rescue/Password/<other-id>` from a separate scoped principal; expect plaintext.
- **Claim:** the parameter (and plaintext) survives termination of the rescued instance. **Oracle:** terminate, re-read.
**Doc evidence:** `ec2rw-ssm.md:17`; `secure-string-parameter-kms-encryption.md:223,227`; `list_ssm.md:1446-1449`. **Severity-if-true:** High (break-glass feature becomes a durable, broadly-readable admin-credential store for every rescued instance). **Stop:** on first cross-instance plaintext read in the authorized test account.

### 5.3 AWS-authored sample IAM policy fails closed → doc pushes customer to `Resource:"*"`  — **[HIGH, Lens R/S/U]**
**Background.** `ec2rw-ssm.md` prints **two** sample policies the customer attaches verbatim; prose says write path `/EC2Rescue/Password/<id>` (singular) but both policies' Resource ARNs use `parameter/EC2Rescue/Passwords/<id>` (plural) (`ec2rw-ssm.md:17` vs `:42,:68`).
**Security Concern.** IAM is default-deny and `PutParameter`'s only resource type is the ARN-matched `parameter*` (`list_ssm.md:1647-1651`) — the plural ARN does not match a singular-path write, so the "least-privilege" policy fails closed. AWS's **own** adjacent runbook-reference "Required IAM permissions" grants `ssm:PutParameter`+`kms:Encrypt`+`ssm:SendCommand` on `Resource:"*"` — i.e. the documentation steers a blocked customer to an account-wide grant that (chained with §5.2) exposes every rescued password.
**High-level Test Scenarios.** **Claim:** attaching the verbatim scoped policy and invoking `ResetAccess` yields `AccessDenied` on `ssm:PutParameter` citing the `.../Password/<id>` resource not matching the granted `.../Passwords/<id>`. **Oracle:** `iam:SimulateCustomPolicy` with the published JSON against the singular ARN (no resources touched), then live scoped call with canary.
**Doc evidence:** `ec2rw-ssm.md:17,42,68`; `list_ssm.md:1647-1651`. **Severity-if-true:** High — AWS-authored, copy-verbatim artifact defect that induces an over-broad grant (disclosure set **Tier 2**, route `aws-security`; **not** a customer footgun). **Stop:** once simulate confirms the mismatch denies.

### 5.4 SSM Automation `AutomationAssumeRole` confused deputy  — **[MEDIUM–HIGH, Lens B]**
**Background.** `AWSSupport-ExecuteEC2Rescue` takes an optional `AutomationAssumeRole`; absent it, Automation uses the caller's permissions, otherwise SSM assumes the role on the caller's behalf. The offline/`FixAll` workflow stands up a helper-instance CloudFormation stack and does stop → detach → attach → image → reattach (`AWSSupport-StartEC2RescueWorkflow` steps; actions in `list_ec2.md`: `ec2:AttachVolume`/`DetachVolume`/`CreateImage`/`StopInstances` + VPC CRUD, plus `iam:CreateRole`/`PassRole` and `lambda:CreateFunction`).
**Security Concern.** A caller with only `ssm:StartAutomationExecution` + `iam:PassRole` on an over-provisioned role drives all those privileged actions under the assumed role — not their own. AWS's sample policy scopes IAM/Lambda to the `AWSSupport-EC2Rescue-*` name prefix but leaves EC2/networking + volume attach/detach/stop/image on `Resource:"*"` with no tag/instance condition.
**High-level Test Scenarios.** **Claim:** a principal lacking direct `ec2:StopInstances`/`AttachVolume`/`CreateImage` drives a full stop/detach/attach/backup cycle on an arbitrary instance via the role. **Oracle:** grant only `StartAutomationExecution`+`PassRole` on a loose role; run against a canary instance; observe the cycle.
**Doc evidence:** runbook `AutomationAssumeRole` param; `AWSSupport-StartEC2RescueWorkflow` required-permissions JSON; `list_ec2.md` entries for the named actions. **Severity-if-true:** Medium–High (generic SSM-Automation pattern, but this role is unusually powerful). **Stop:** once the cross-privilege action succeeds on a canary.

### 5.5 `/check-only` writes the disk signature despite "makes no modifications"  — **[MEDIUM, Lens U]**
**Background.** `/check-only` = "generates a report but makes no modifications to the offline volume" (`ec2rw-cli.md:119`), immediately contradicted by the Note: signature collisions are corrected **by default, even with `/check-only`**, unless `/no-fix-signature` is passed (`ec2rw-cli.md:120-121`; also :58-59, :165-166). The write mechanism: overwrite the disk signature with the BCD signature when they differ (`ec2rw-gui.md:12`).
**Security Concern.** When the operator's intent in choosing `/check-only` is to preserve a forensic/evidence or compliance-sensitive volume non-destructively, the silent default write (structural MBR/signature change, no interactive prompt documented) violates the headline guarantee; the override must be discovered and proactively added.
**High-level Test Scenarios.** **Claim:** `/rescue:all /check-only` (no `/no-fix-signature`) on a volume with a mismatched disk/BCD signature writes the signature region. **Oracle:** hash/diff the MBR/signature bytes before and after on a canary volume.
**Doc evidence:** `ec2rw-cli.md:119-121`; `ec2rw-gui.md:12`. **Severity-if-true:** Medium (false documented guarantee + integrity impact; bounded blast radius, disableable). **Stop:** on first confirmed write under `/check-only`. *(Already noted in `Windows-Server-EC2Rescue-attack-research-plan.md` §5.7 — this adds the BCD-vs-disk mechanism; reuse that lead, don't double-count.)*

### 5.6 Admin-run EXE supply-chain / download integrity  — **[MEDIUM now / Critical if bucket ever lapses, Lens EE/Y]**
**Background.** The EXE is fetched path-style from AWS-owned global-namespace bucket `ec2rescue` and run with admin rights; no doc publishes a hash/Authenticode/GPG check (`ec2rw-cli.md:14`; `ec2rw-gui.md:49-54`; S3 global-namespace semantics `bucketnamingrules.md:43,119`). The SSM path claims it "Downloads and verifies" (`ec2rw-ssm.md:11`) but the canonical runbook reference describes a Distributor-package install and never says "verify" — the mitigation claim is unsubstantiated in the docs.
**Security Concern.** Unverified download+admin-execute is a classic supply-chain RCE primitive; the only customer-facing mitigation claim ("verifies") is undefined.
**High-level Test Scenarios.** **Claim (doc-only, confirmed):** no integrity material is published for an admin-run artifact. **Claim (low-risk live, optional):** `aws ssm get-document --name AWSSupport-RunEC2RescueForWindowsTool` PowerShell contains no `Get-FileHash`/`Get-AuthenticodeSignature`. **Oracle:** read the public document JSON (read-only `GetDocument`).
**HARD STOP:** do **not** `HeadBucket`/probe ownership of `ec2rescue` or `awssupport-ssm.*` — those are AWS service-plane buckets; treat purely as a documentation-gap finding, not a takeover. **Severity-if-true:** Medium (missing integrity path); Critical only in the hypothetical bucket-lapse, which is out of scope to test.

### 5.7 Collect = cross-volume secret sprawl  — **[LOW, Lens T/A]**
**Background.** Offline Collect reads SYSTEM/SOFTWARE/BCD hives, memory dumps, SSM InstanceData from the foreign volume into a zip at `/output:<path>` on the **rescue** host (`ec2rw-cli.md:36-57,90-94`).
**Security Concern.** Reaching those bytes requires only attach/detach — already conceded by §5.1/offline-Rescue as a full compromise primitive — so this is **not** a wall-bypass. The genuine (minor) angle: the zip is a new, less-protected copy of another instance's OS secrets resting on a second instance's disk, with no documented at-rest encryption, access-restriction, or cleanup.
**Oracle / Severity:** confirm (checked: none found in `ec2rw-cli.md`/`ec2rw-gui.md`) whether any doc specifies protection/retention for the `/output` zip; if truly undocumented, Low — a one-line data-sprawl doc-gap, not a standalone lead.

## 7. Out-of-Scope Risk Categories (state confidently)

- **Operator rescuing their OWN corrupted (non-adversarial) volume** — intended use; not a finding.
- **"EBS attach/detach == OS admin of the volume's owner" equivalence** — this is a real and powerful primitive (offline Ec2SetPassword / Reset Admin Password / Ec2HandleUserData), **but it is already fully captured** by `ResettingAdminPassword-attack-research-plan.md` §5 [P4] + Chain 4 (High) and `Windows-Server-EC2Rescue-attack-research-plan.md` §5.7 (Ec2HandleUserData). Do **not** re-derive. *The one additive note for a future pass:* name the Ec2SetPassword / Reset-Admin / Ec2HandleUserData triad as a single equivalence class — "`ec2:AttachVolume`+`ec2:DetachVolume` on any second instance is sufficient for OS-admin-equivalent compromise of any instance whose root volume you can detach, with no OS credential ever required." Naming/consolidation only; no new evidence.
- **IMDS on these managed-by-customer hosts, single-tenant self-DoS, product/feature gaps.**
- **Any live probe of the `ec2rescue` / `awssupport-ssm.*` buckets or AWSSupport document-owner account** — AWS service plane, hard stop.
- **The generic SSM-Automation confused-deputy pattern itself** is well-known; in scope here only because EC2Rescue's required role is unusually broad and AWS's sample leaves EC2/networking unscoped (§5.4).
