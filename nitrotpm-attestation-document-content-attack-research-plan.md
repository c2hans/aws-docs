## 1. Pentest Objectives
1. **Verifier-cannot-know-what-it-pins:** demonstrate that an attestation-consumer following AWS documentation cannot reliably determine what any register outside PCR4/7/12 measures, because the two authoritative AWS sources — this User-Guide page and the IAM Service Authorization Reference — assign *contradictory* meanings to the same `NitroTPMPCR` indices (Area 1). An author who pins `NitroTPMPCR16` believing it is "Debug" (this page) is, per the IAM reference, pinning a "custom, user-definable" value with no fixed trust meaning.
2. **"Triad matches" ≠ "trusted runtime":** show that the attestable triad (PCR4/7/12) structurally excludes the OS-, application-, and (per this page) debug-layer registers the document carries, so a boot state matching the triad can carry a compromise measured only in an un-pinned register. (Mechanism-level exploit owned by `create-pcr-compute` A1; this plan contributes the document-semantics mapping.)
3. **PCR1 constant-vs-host-identity:** resolve whether PCR1 is an AWS-controlled *constant* (this page) or includes per-host *serial/model numbers* (IAM reference) — the latter making a freely-generable, shareable attestation document a host-fingerprint / co-residency oracle (Area 2).
4. **Trust-root clarity:** confirm the document is signed by the Nitro Hypervisor (AWS), not a per-instance TPM key — bounds what the document proves (measurement, not identity). HARD-STOP boundary (Area 3).

## 2. Components, Assets, and Design
**What this page describes.** The **Attestation Document** is a CBOR / COSE_Sign1 object generated by the per-instance NitroTPM and **signed by the Nitro Hypervisor**, carrying a snapshot of the instance's PCRs. This page enumerates register semantics; the IAM Service Authorization Reference (`list_kms.md`) independently enumerates the `kms:RecipientAttestation:NitroTPMPCR*` condition-key semantics. **The two disagree** — see the reconciliation table in Area 1.

**Confirmed condition-key facts (`list_kms.md`, 2026-10-15):**
- **`kms:RecipientAttestation:NitroTPMPCR0`–`NitroTPMPCR23`** = 24 keys (NitroTPM family), linked to `conditions-nitro-tpm.html`.
- **`kms:RecipientAttestation:PCR0`–`PCR31`** = 32 keys (**Nitro Enclaves** family, different semantics — e.g. plain `PCR3`="IAM role of parent instance", `PCR4`="parent instance ID"), linked to `conditions-nitro-enclaves.html`. **Same index ≠ same meaning** across families (silent-lockout, owned by `nitrotpm-attestation` A3).
- **`kms:RecipientAttestation:ImageSha384`** = a single key, **grouped with the Nitro-Enclaves link, NOT NitroTPM.** *(Corrects the `create-pcr-compute` sibling note which listed "NitroTPMPCR0-23 + ImageSha384" as if ImageSha384 were a NitroTPM key — it is enclaves-side.)*
- All `RecipientAttestation:*` keys: Type = `String` only; **exact hex length / case-sensitivity is a doc-gap** in the reference. The one example policy uses `StringEqualsIgnoreCase` with 96-hex-char values (SHA-384 / 48-byte digest) → matching is case-insensitive *in AWS's own example*, inferred not specified.
- Keys apply to exactly **5 actions**: `Decrypt`, `DeriveSharedSecret`, `GenerateDataKey`, `GenerateDataKeyPair`, `GenerateRandom`. (`GenerateDataKeyWithoutPlaintext` does **not** carry them.)
- The one official example policy (`prepare-attestation-service.md`) pins **only `NitroTPMPCR4` + `NitroTPMPCR12`(=96 hex zeros)**; `NitroTPMPCR7` appears in prose only. **No official example anywhere uses PCR16/PCR23 or any register outside 4/7/12.**

**Design facts for a hunter (from `…content.md`):**
- Document **signed by the Nitro Hypervisor** (one AWS authority), not a per-instance TPM key → proves "the Nitro platform asserts these PCRs," not "this instance's hardware TPM quoted them." Trust root = AWS service plane (HARD STOP).
- Document **includes all of PCR0–23**; AWS guidance + tooling + the only example pin **only PCR4/7/12** → 21 registers are present-and-checkable but excluded from every AWS example (Area 1 coverage gap).
- **PCR0/PCR1 claimed AWS-controlled constants** ("will always contain constant values") — but see Area 2 (IAM ref says PCR1 includes host serial/model numbers).
- **PCR7 = hash of Secure Boot *policy*** (enrolled certs), not the booted binary → image-independent (owned by `create-pcr-compute` A2 + `enable-nitrotpm-support-on-ami` A2).

### ASCII trust/measurement view


**Security Concern (net-new; no sibling reconciles the two sources — siblings cite one or the other).**
- **(1a) A verifier author cannot determine what it is pinning.** If `NitroTPMPCR16` is "Debug" (this page), pinning it to a known-good value is a meaningful control; if it is "custom, user-definable" (`list_kms`), then its value may be influenced by in-guest software and carries **no fixed trust meaning** — pinning it is either security-theater or, worse, pins an attacker-influenceable field. The same applies to PCR6 and PCR23. **AWS's two authoritative references cannot both be right.** (Lens U doc-defect; AWS-owned; Tier-2-reportable.)
- **(1b) PCR12 scope contradiction.** This page says PCR12 = "the command line passed to the UEFI boot binary." `list_kms` says PCR12 = "kernel command line, **system credentials and system configuration images**." The broader `list_kms` definition means PCR12 commits more than a verifier reading *this* page expects — a verifier pinning PCR12 for "cmdline integrity" may unknowingly also bind (or fail to re-bind) system-credential / config-image state. Combined with the sibling-owned all-zeros-PCR12 example (`nitrotpm-attestation` A2), the uninitialised baseline is even more consequential than "no cmdline binding." (Cross-ref A2; the scope-contradiction half is net-new here.)
- **(1c) PCR8–15 completeness gap.** This page gives a verifier author one vague line ("Static Operating System") for eight registers; `list_kms` reveals they follow systemd/UKI conventions (PCR11 = all UKI components, PCR15 = rootfs encryption key). A verifier built from *this page alone* has no idea PCR11 measures the UKI or PCR15 the disk-encryption key — exactly the registers that would catch OS-layer tamper the triad misses. (Lens U; AWS-owned.)
- **(1d) Triad excludes runtime registers (the "matches ≠ trusted" gap).** All of PCR8–15/16/23 are present in the document but outside PCR4/7/12 and pinned by no AWS example → OS/app/debug state is attestation-invisible on the documented path. **Mechanism-level exploit (rootfs/overlay/runtime not measured) is owned by `create-pcr-compute` A1; this plan contributes the per-register document-semantics mapping that proves *which* classes of compromise fall in the gap.**

### Area 2 — [Lens A / V, SHARPENED by `list_kms`] PCR1 "constant" (this page) vs "host serial and model numbers" (IAM ref) → host-fingerprint / co-residency oracle in a freely-shareable document
**Background.** This page states flatly (`…content.md:9`): "PCR0 and PCR1 … will always contain **constant** values." The IAM Service Authorization Reference describes `NitroTPMPCR1` = "core system firmware data/host platform configuration, **typically including serial and model numbers**." Serial/model numbers are per-physical-host, the opposite of constant. (A parallel contradiction exists for PCR6: this page = "Host Platform Manufacturer Specifics," `list_kms` = "custom/user-defined.")
**Security Concern.** The attestation document is a self-contained object a customer can generate at will and hand to any verifier (including an attacker-controlled one). If PCR1 (or PCR6) is in fact host-variable:
- **Co-residency oracle (Lens V):** two instances on the same physical host share the PCR1 value → an attacker correlates documents from their own fleet to detect co-residency with a target on shared infrastructure.
- **Host-fingerprint disclosure (Lens A):** the document leaks AWS physical-host serial/model identifiers.
And the "constant → safe to pin / safe early-boot updates" rationale on this page would be **false**, misleading anyone who pins PCR1 expecting a stable constant.
**High-level Test Scenarios:**
1. **Claim:** NitroTPMPCR1 differs across physical hosts and is stable per host (i.e. `list_kms` is right, this page's "constant" is wrong). → **Oracle:** launch several canary instances, capture each attestation document, compare PCR1 (and PCR6) across them; correlate with any placement signal. If PCR1 varies, resolve the contradiction toward "host-variable." → **Severity-if-true:** Low–Medium (co-residency inference / host-fingerprint on shared infra). **If PCR1/PCR6 proves to encode anything about AWS's physical fleet beyond coarse class, treat as a service-plane disclosure and apply the HARD STOP.**
**Doc evidence:** `…content.md:9` (constant), `list_kms.md:~2721` (NitroTPMPCR1 serial/model). **This is a confirm-the-surface-first lead** — the contradiction is documented; which source is correct is the empirical question. Likely PCR1 is genuinely a fixed-form constant and the IAM wording is boilerplate inherited from physical-TPM conventions (→ null), but no sibling has examined it, so it is an open lead.
**Severity-if-true:** Low–Medium.

### Area 3 — [Lens U / HARD-STOP boundary, pointer] Signing authority is the Nitro Hypervisor, not a per-instance TPM key
`…content.md:6`: the document is "generated by the NitroTPM and it is signed by the Nitro Hypervisor." One AWS-owned signing authority attests the PCR snapshot → the document binds *measurements*, not *caller/instance identity* (consistent with `enable-nitrotpm-support-on-ami` A2). No offensive scenario here: any probe toward the hypervisor signing key or the Nitro attestation PKI private material is a **HARD STOP** (service plane). Record and route to AWS-Security if ever implicated. **Severity:** N/A (boundary statement).
