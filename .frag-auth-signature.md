# Cluster: AUTHENTICATION & REQUEST SIGNATURE (Legacy S3 Developer Guide)

## 1. Cluster summary

This cluster covers how every S3 REST/POST request establishes identity and integrity: legacy SigV2 (HMAC-SHA1, `Authorization: AWS {key}:{sig}` or query-string `Signature`/`Expires`), SigV4/SigV4A (HMAC-SHA256 / ECDSA-P256, Authorization-header or query-string "presigned URL" variants, plus chunked/streaming upload with optional trailing-checksum chunks), the STS-based temporary-credential family (`GetSessionToken`, `AssumeRole`, `GetFederationToken`), and the four SigV4-specific bucket-policy condition keys (`s3:signatureversion`, `s3:authType`, `s3:signatureAge`, `s3:x-amz-content-sha256`) that let a bucket owner constrain *how* a request may be authenticated. The throughline risk is **coverage mismatch**: multiple mechanisms exist (header vs query-string vs POST vs legacy SigV2 vs SOAP), several condition keys were visibly designed around only a subset of these mechanisms, and the signature itself only ever covers what the signer chose to include (`SignedHeaders`, payload-hash placeholders like `UNSIGNED-PAYLOAD`). Every lead below is therefore of the shape "a stated guarantee is actually scoped more narrowly than the bucket-policy author would assume," not a confirmed exploit — nothing here was tested live.

## 2. API / surface items found

- SigV2 REST Authorization header (`AWS {AccessKeyId}:{Signature}`), HMAC-SHA1 over a fixed-field StringToSign (`RESTAuthentication.md`).
- SigV2 query-string ("presigned") auth variant: `AWSAccessKeyId`, `Signature`, `Expires` as query params (`RESTAuthentication.md`).
- SigV4 Authorization-header auth, single-chunk payload (`sigv4-auth-using-authorization-header.md`, `sig-v4-header-based-auth.md`).
- SigV4 query-string / presigned-URL auth: `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Expires`, `X-Amz-SignedHeaders`, `X-Amz-Signature`, `X-Amz-Security-Token` (`sigv4-query-string-auth.md`).
- SigV4 chunked/streaming upload: seed signature + per-chunk chained signatures (`sigv4-streaming.md`).
- SigV4 streaming with trailing checksum header chunk (`x-amz-trailer`, `x-amz-checksum-crc32c`, trailer-signature) (`sigv4-streaming-trailers.md`).
- `x-amz-content-sha256` value space: real hex digest, `UNSIGNED-PAYLOAD`, `STREAMING-UNSIGNED-PAYLOAD-TRAILER`, `STREAMING-AWS4-HMAC-SHA256-PAYLOAD[-TRAILER]`, `STREAMING-AWS4-ECDSA-P256-SHA256-PAYLOAD[-TRAILER]` (`sigv4-auth-using-authorization-header.md`).
- Bucket-policy SigV4 condition keys: `s3:signatureversion`, `s3:authType` (`REST-HEADER`/`REST-QUERY-STRING`/`POST`), `s3:signatureAge`, `s3:x-amz-content-sha256` (valid value `UNSIGNED-PAYLOAD` only) (`bucket-policy-s3-sigv4-conditions.md`).
- STS temp-credential surfaces: `GetSessionToken` (IAM user/root), `AssumeRole` (IAM role, denies AWS-account-root principal), `GetFederationToken` (requires IAM `Policy` param; permission = intersection with calling IAM user) (`AuthUsingTempSessionToken.md`, `AuthUsingTempFederationToken.md`).
- Anonymous-request fallback when SDK client created without credentials (`AuthUsingAcctOrUserCredentials.md`).
- `x-amz-security-token` header / query param for STS creds and DevPay dual-token (product token + user token) (`RESTCommonRequestHeaders.md`).
- MFA-protected API access via bucket policy requiring MFA-sourced temp credentials (`MakingRequests.md`).
- 15-minute signature/timestamp validity window (both SigV2 `Date` skew check and SigV4 signed-portion replay window) (`RESTAuthentication.md`, `sig-v4-authenticating-requests.md`).

## 3. Lens-mapped falsifiable leads (ranked by severity)

### Lead 1 — `s3:x-amz-content-sha256` condition key is structurally blind to the one auth path where unsigned payload is mandatory [Lens S / Lens Y]
- **Claim:** A bucket policy using `StringEquals: {"s3:x-amz-content-sha256": "UNSIGNED-PAYLOAD"}` with `Effect: Deny` ("deny uploads with unsigned payloads") does not actually block unsigned-payload uploads delivered via presigned (query-string) URLs.
- **Mechanism (doc evidence):** `bucket-policy-s3-sigv4-conditions.md` (verified verbatim against the live `/developerguide/` page): *"Note that this condition key doesn't support the `x-amz-content-sha256` header as a query string parameter."* Combined with `sigv4-query-string-auth.md`: presigned-URL canonical requests *always* use the literal constant `UNSIGNED-PAYLOAD` — "you don't include a payload hash in the Canonical Request... Instead, you use a constant string `UNSIGNED-PAYLOAD`" — this is not a header the caller sets, it's baked into the mechanism itself.
- **Confirm/Refute oracle:** Attach the documented "deny unsigned payload" bucket policy, then issue a presigned PUT URL and upload an object through it. If the upload succeeds, the policy's stated intent ("deny any uploads where payloads are not signed") is refuted for the query-string auth path.
- **Preconditions:** Bucket owner believes the condition key is a blanket unsigned-payload denylist and does not separately restrict `s3:authType != REST-HEADER`.
- **Severity if true:** Medium–High (policy-author false sense of security; data-integrity/tamper-protection control silently inert for an entire, commonly-used auth method).

### Lead 2 — `s3:signatureAge` is a hardcoded constant for SigV2, making signature-age-based deny policies inert against legacy traffic [Lens S]
- **Claim:** A bucket policy denying requests with `NumericGreaterThan: {"s3:signatureAge": N}` (e.g., the documented "deny if older than 10 minutes" example) provides no protection against SigV2-authenticated requests, regardless of how stale the actual signature is.
- **Mechanism (doc evidence):** `bucket-policy-s3-sigv4-conditions.md`, confirmed verbatim online: *"In Signature Version 2, this value is always set to 0."* The online version additionally clarifies this key "works for" Presigned URLs and Presigned POST specifically, with "the most restrictive condition wins" — language not present in the local mirror, i.e. **the local mirror is stale/incomplete relative to the live page for this key's scope statement.**
- **Confirm/Refute oracle:** Apply the "deny if signatureAge > 600000" policy, then submit a SigV2-signed request (header or query-string) with a timestamp far outside any reasonable freshness window. If accepted, the staleness control is confirmed inert for SigV2.
- **Preconditions:** Target region/bucket still accepts SigV2 (see Lead 3) and relies on this condition key as its sole staleness control.
- **Severity if true:** Medium (replay-window widening for an already-legacy, lower-assurance signing mode; compounds with Lead 3).
- **Doc-staleness note:** this is a concrete instance of "local may be stale" — flag for whoever maintains the mirror.

### Lead 3 — Documented permanent carve-out lets SigV2 presigned URLs bypass the "SigV2 fully retired" claim indefinitely [Lens Y]
- **Claim:** Despite `Appendix-Sigv2.md`'s blanket statement that "Amazon S3 will only accept API requests that are signed using Signature Version 4," SigV2 remains permanently valid for presigned URLs that need validity beyond SigV4's 7-day signing-key ceiling.
- **Mechanism (doc evidence):** `specify-signature-version.md`, confirmed verbatim via live fetch: *"If you are using a presigned URL that requires you to sign for more than 7 days, no action is currently needed. You can continue to use AWS Signature Version 2 to sign and authenticate the presigned URL."* This directly contradicts the blanket SigV2-sunset claim made elsewhere in AWS's own docs (`Appendix-Sigv2.md`).
- **Confirm/Refute oracle:** Generate a SigV2 query-string-signed URL with `Expires` set >7 days out against a bucket in a region that otherwise claims SigV4-only enforcement; a successful request confirms the carve-out is live, not just historical documentation residue.
- **Preconditions:** None beyond holding valid long-lived AWS keys; this is a documented, intentional exception, not a bug — but it means any security control predicated on "SigV2 is fully disabled" (e.g., Lead 2's reliance on `s3:signatureversion` to reject `"AWS"`) has a standing, AWS-sanctioned bypass path via long-dated presigned URLs.
- **Severity if true:** Medium (expands the legacy HMAC-SHA1 attack surface — weaker algorithm, inert `signatureAge`, no 15-minute skew check for query-string auth per `RESTAuthentication.md` — on an indefinite basis for a specific, common use case).

### Lead 4 — Presigned URL default signing surface reduces to `host`-only header coverage with structurally mandatory `UNSIGNED-PAYLOAD` [Lens Y / Lens M]
- **Claim:** The minimum valid presigned URL only cryptographically binds the HTTP method, path, and the listed `X-Amz-*` query parameters — the `host` header is the only header required in `X-Amz-SignedHeaders`, and the body is never covered (always `UNSIGNED-PAYLOAD`). Any other header (`Content-Type`, `Content-Disposition`, `Content-Encoding`, custom metadata not prefixed `x-amz-*`) can be freely set by whoever holds the URL without invalidating the signature.
- **Mechanism (doc evidence):** `sigv4-query-string-auth.md`: *"X-Amz-SignedHeaders... The following headers are required... The HTTP host header. Any x-amz-* headers that you plan to add"* — everything else is optional ("For added security, you should sign as many headers as possible," implying by default most are not signed). Worked example literally shows `X-Amz-SignedHeaders=host` with no other headers. Payload is unconditionally `UNSIGNED-PAYLOAD` per the same page.
- **Confirm/Refute oracle:** Take a presigned PUT URL generated with `SignedHeaders=host`; replay it with an arbitrary body and an added `Content-Type`/`Content-Disposition` header not present at signing time. If S3 accepts the request and stores attacker-chosen `Content-Type`/body, the lack of coverage is confirmed exploitable for response-header injection style effects (e.g., stored XSS via `Content-Type` on a public bucket, or cache-poisoning oriented metadata).
- **Preconditions:** Caller possesses any presigned PUT URL (e.g., leaked, intercepted, or legitimately issued for a narrower purpose) and the receiving application trusts uploaded object metadata/content-type.
- **Severity if true:** Medium–High depending on downstream consumer (classic presigned-URL design limitation, not novel, but the doc explicitly confirms the minimal case rather than recommending it as default).

### Lead 5 — STS session token embedded verbatim in presigned-URL query string is a documented logging/leakage surface, with no stated server-side revocation check [Lens C / Lens M]
- **Claim:** A presigned URL built from STS temporary credentials carries the full `X-Amz-Security-Token` as a plain query parameter (loggable in access logs, proxies, Referer headers, browser history), and the docs do not state whether S3 re-validates the underlying STS session's live status (vs. only recomputing the SigV4 signature) at request time — i.e., whether revoking/expiring the STS session invalidates already-issued presigned URLs before `X-Amz-Expires` elapses.
- **Mechanism (doc evidence):** `sigv4-query-string-auth.md` Example 2 shows a ~1KB STS token embedded directly in the URL. No page in this cluster (`sigv4-query-string-auth.md`, `AuthUsingTempSessionToken.md`, `AuthUsingTempFederationToken.md`) states the revocation-check behavior for presigned URLs built on temporary credentials.
- **Confirm/Refute oracle:** Issue a presigned URL using STS creds, then revoke/let the underlying STS session expire (independent of the URL's own `X-Amz-Expires`), and replay the URL before `X-Amz-Expires` elapses. Acceptance despite STS-session revocation would confirm the gap; the docs give no basis to predict either outcome.
- **Preconditions:** Application mistakenly assumes revoking the STS session immediately kills all previously-issued presigned URLs derived from it.
- **Severity if true:** Medium–High (session-revocation bypass window up to the full `X-Amz-Expires`, max 7 days) — **doc-gap, not a confirmed mechanism either way.**

### Lead 6 — SigV4 minimal `SignedHeaders` + explicit 15-minute "unsigned portions may be modified" admission [Lens Y]
- **Claim:** For Authorization-header SigV4 requests, only `host` and any `x-amz-*` headers the signer chooses are mandatory in `SignedHeaders`; everything else (`Content-Type`, `Range`, `Content-Length`, non-`x-amz` custom headers) can be added or altered by a man-in-the-middle/proxy within the 15-minute validity window without breaking the signature.
- **Mechanism (doc evidence):** `sig-v4-header-based-auth.md`: *"the host header and all x-amz-* headers, excluding x-amz-content-sha256, are required [for signing]. However... you should consider including all the headers in the signature calculation."* `sig-v4-authenticating-requests.md`, stated as an explicit AWS caveat (not a lead inference): *"An unauthorized party who has access to a signed request can modify the unsigned portions of the request without affecting the request's validity in the 15 minute window."*
- **Confirm/Refute oracle:** Capture a validly-signed SigV4 request that signs only mandatory headers; replay it through a proxy with an added/modified non-`x-amz` header (e.g., `Range`, `Content-Type`) within 15 minutes. Request succeeding with the attacker-modified header in effect confirms the gap AWS itself documents.
- **Preconditions:** Attacker can intercept/relay a validly-signed in-flight request (classic MITM precondition, mitigated by TLS at transport layer — this is specifically about what the *signature itself* additionally guarantees once intercepted, e.g., via a compromised proxy/CDN that terminates TLS).
- **Severity if true:** Medium (AWS already discloses this; real severity depends on what headers a given application fails to sign, e.g. `Range` manipulation for GET, or metadata headers for PUT).

### Lead 7 — `s3:authType` condition key's documented value set (`REST-HEADER`/`REST-QUERY-STRING`/`POST`) has no listed SOAP value [Lens S / cross-cluster with legacy-SOAP cluster]
- **Claim:** A bucket policy intending to restrict allowed authentication methods via `s3:authType` cannot explicitly target/deny the legacy SOAP endpoint, because SOAP is not among the three documented valid values.
- **Mechanism (doc evidence):** `bucket-policy-s3-sigv4-conditions.md`: *"Valid values: REST-HEADER / REST-QUERY-STRING / POST"* — no fourth value. `MakingRequests.md`/related docs establish SOAP as a legacy, separate request-making path (full depth being analyzed by a parallel cluster run on legacy/SOAP surfaces).
- **Confirm/Refute oracle:** Apply an authType allow-list policy (e.g., `StringNotEquals: {"s3:authType":"REST-HEADER"}` → Deny) against a region/bucket where the SOAP endpoint is still reachable, then issue a SOAP-authenticated request. If it succeeds despite the policy intending to restrict to REST-HEADER only, the condition key has a coverage gap for SOAP traffic specifically.
- **Preconditions:** SOAP endpoint must still be reachable for the target bucket/region (independently uncertain — flagged for correlation with the parallel SOAP-cluster findings).
- **Severity if true:** Medium, contingent entirely on SOAP's actual current reachability (unknown from this cluster's docs alone — explicit doc-gap).

### Lead 8 — Streaming trailer checksum is signature-chained but no page states S3 cross-validates the checksum value against received bytes [Lens CC]
- **Claim:** The trailing-checksum mechanism (`STREAMING-*-TRAILER`, e.g. `x-amz-checksum-crc32c`) cryptographically proves the trailer value came from the holder of the signing key and was sent after the preceding chunk (via signature chaining), but no page in this cluster states whether S3 additionally *recomputes* the checksum server-side and rejects a mismatch — as opposed to merely storing/forwarding a self-reported, correctly-*signed*-but-not-necessarily-*correct* checksum.
- **Mechanism (doc evidence):** `sigv4-streaming-trailers.md` fully specifies the trailer's signature chain (`AWS4-HMAC-SHA256-TRAILER` string-to-sign over `previous-signature` + `hash(trailer-header:value\n)`) but never states a server-side integrity-verification step against actual chunk bytes already received.
- **Confirm/Refute oracle:** Upload a multi-chunk object with a trailer checksum value that is correctly *signed* (valid signature chain) but numerically wrong for the actual chunk data sent; if S3 accepts the upload and later serves the (wrong) checksum as the object's recorded checksum without error, the "trusted upstream" assumption (Lens CC) that signature validity implies data-integrity validity is refuted.
- **Preconditions:** Caller can construct a validly-chained-but-semantically-false trailer signature (requires only the real secret key — this tests S3's own validation logic, not a key-theft scenario).
- **Severity if true:** Low–Medium (checksum field integrity/trust-labeling issue; impact depends on what downstream consumers do with a reported-but-unverified checksum, e.g. integrity assertions to third parties).

## 4. Null hypotheses (lenses checked, no finding)

- **Lens C (session-policy widening via `GetFederationToken`) — holds, not broken.** `AuthUsingTempFederationToken.md` explicitly documents a hard intersection bound: *"The temporary user you create can never get more permissions than the IAM user who requested the temporary security credentials."* No caller-controlled parameter in the documented API is described as able to escape this intersection. Residual risk is purely application-layer (if a backend lets end-users influence the `Policy` param it passes to AWS), not an AWS-mechanism gap. Checked: `AuthUsingTempFederationToken.md`, `AuthUsingTempSessionToken.md`, `MakingAuthenticatedRequests.md`.
- **Lens C (root-account impersonation via `AssumeRole`) — explicitly blocked.** `AuthUsingTempSessionToken.md`: *"you cannot assume the role of an AWS root account; Amazon S3 will deny access."* Checked: `AuthUsingTempSessionToken.md`.
- **Lens M (chunk reordering/truncation in streaming uploads) — mechanism appears sound as documented.** Each chunk's string-to-sign incorporates the previous chunk's signature (`F(chunk_n, signature(chunk_n-1))`), cryptographically enforcing order and binding chunk data; a reordered or substituted chunk would break the chain and (per the mechanism as documented) fail verification. Checked: `sigv4-streaming.md`, `sigv4-streaming-trailers.md`. Caveat: this null hypothesis covers *chunk ordering/substitution* only — it does NOT cover whether the trailer *value* is cross-validated against actual data (that gap is Lead 8, left open, not closed).
- **Lens A (anonymous-request error oracle) — thin documentation, not a confirmed null.** `AuthUsingAcctOrUserCredentials.md` states anonymous (unsigned) requests are possible and that "Amazon S3 returns an error if you send anonymous requests for a resource that is not publicly available," but does not specify whether that error differs (code/body/latency) from the error returned for a resource that does not exist at all — i.e., whether this forms a bucket/object existence oracle. Marked **doc-gap**, not resolved either way. Checked: `AuthUsingAcctOrUserCredentials.md`, `MakingRequests.md`, `RESTCommonRequestHeaders.md`.
- **Lens S (SigV2 15-minute replay-window skew check) — appears limited to Authorization-header SigV2 only, not fully explored for query-string SigV2.** `RESTAuthentication.md` states the 15-minute client/server clock-skew requirement applies to the signed request generally but frames all its worked timestamp-skew language around the header-based flow; it separately notes the query-string (`Expires`-based) variant uses an explicit, caller-chosen expiry instead of the implicit 15-minute window — consistent with Lead 3's broader finding, not a separate break. Checked: `RESTAuthentication.md`.
- **Online cross-check coverage:** Of the 18 assigned pages, 3 were explicitly diffed against the live `docs.aws.amazon.com` `/developerguide/` pages with full verbatim comparison (`specify-signature-version.html`, `bucket-policy-s3-sigv4-conditions.html`, `sigv4-query-string-auth.html`) — the latter two confirmed via the corrected `/developerguide/` URL path after an initial failed attempt against the wrong `/API/` path. One concrete drift was found (Lead 2's `s3:signatureAge` scope clarification present online, absent locally). The remaining 15 pages (`RESTAuthentication.md`, `S3_Authentication2.md`, `MakingAuthenticatedRequests.md`, `MakingRequests.md`, `Appendix-Sigv2.md`, `sig-v4-authenticating-requests.md`, `sig-v4-header-based-auth.md`, `sigv4-auth-using-authorization-header.md`, `sigv4-streaming.md`, `sigv4-streaming-trailers.md`, `sig-v4-examples-using-sdks.md`, `AuthUsingAcctOrUserCredentials.md`, `AuthUsingTempFederationToken.md`, `AuthUsingTempSessionToken.md`, `RESTCommonRequestHeaders.md`) were read only from the local mirror; their online equivalents were not independently diffed in this pass — flagged as residual staleness risk, not as findings.
