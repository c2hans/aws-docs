## 0. How to use this document
- Each lead is a falsifiable claim: **Claim → Mechanism (doc evidence) → Confirm/Refute oracle → Preconditions → Cost → Severity-if-true → Stop condition.** Work in the priority order of §5. Look left and right for adjacent bugs.
- **Prefer the safe oracle first.** The static IAM leads (§5.1) are settleable with `iam:SimulateCustomPolicy` / `iam:SimulatePrincipalPolicy` and read-only reference reads — **no resource created, no Capacity Block purchased.** The cross-account and runtime leads (§5.2–§5.5) need live Capacity Blocks and are **expensive** (Capacity Blocks are prepaid, upfront, and **non-cancellable** — `capacity-blocks-pricing-billing`). Use the **two authorized in-scope accounts** as owner↔consumer, the **smallest purchasable block + shortest duration**, synthetic canary workloads only, and never exceed minimum-PoC capacity. Because Capacity Blocks cannot be cancelled, confirm the test design before purchasing.
- **HARD STOP:** EC2 Fleet runs inside the caller's own account; the in-scope AWS-service-plane identities are the EC2 Fleet SLR `AWSServiceRoleForEC2Fleet` and the CR-Fleet SLR `AWSServiceRoleForEC2CapacityReservationFleet` (hub plan) — treat them read-only. The moment any evidence shows you have reached/assumed/extracted credentials or ARNs belonging to AWS's own fleet/service plane, **stop, preserve evidence, flag for AWS-Security disclosure.**
- **In-scope / reportable (Tier 2):** the static IAM gaps (§5.1) are AWS-owned structural facts of the EC2 authz model (Lens S/U/X) — reportable as a **guardrail-expressibility defect**, because a customer could build a cost/compliance control on a Capacity-Block-targeting guarantee IAM cannot enforce. The cross-account FCFS race (§5.2) is the documented behavior of an AWS multi-account feature — the breach to prove is **targeting a block NOT shared to you** (true cross-account) vs. the owner-adverse-but-documented in-share race (Lens U/AA).
- **Out-of-scope / document-but-don't-report:** self-inflicted single-account cost/availability footguns a customer sets on their own fleet/block with no privilege boundary crossed (see §7).

## 1. Pentest Objectives (concrete breach outcomes to attempt)
1. **Prove the capacity-block *market* guardrail is unexpressible on the fleet path.** Show an admin *cannot* author an IAM/SCP policy that stops a `CreateFleet` caller from provisioning `capacity-block` capacity, because `ec2:InstanceMarketType` (whose value set is exactly `capacity-block | on-demand | spot`, def. offline line 10092) is **absent from the `CreateFleet` action row** (present on `RunInstances`' `instance*` row, line 9591) — and because the market type is baked **inside the launch template**, which `CreateFleet`'s own doc (line 5114) says it cannot scope.
2. **Prove *which Capacity Block* a fleet targets is unpinnable in IAM — on *any* action.** Show that no condition key filtering by a referenced/targeted Capacity-Reservation **ID** exists anywhere in `list_ec2.md` (`ec2:CapacityReservationId` returns zero hits; `ec2:InstanceMatchCriteria` exists but is **not** on `CreateFleet`/`RunInstances` capacity-reservation rows; `ec2:CapacityReservationFleet` scopes only the *Fleet* management ARN, not a consumed block) → an admin cannot write "this team may launch only into Capacity Block cr-X."
3. **Occupy a Capacity Block another account owns and prepaid, by racing it.** Using the two authorized accounts, confirm that a RAM-shared-to consumer who issues the `instant` `CreateFleet` "repeat the call" loop can occupy capacity the owner paid for before the owner launches, incurring **zero reservation cost** (only OS charges) and starving the owner until the consumer terminates or 30 min before expiry.
4. **Falsify the consume-authorization gate.** Determine whether the *only* thing standing between a foreign account and a Capacity Block is the **RAM share** (+ IAM `CreateFleet`), by targeting a Capacity-Block ID that was **not** shared to the caller and recording whether the result is `AccessDenied`, a silent `Insufficient Capacity` (existence-leak oracle), or an actual launch (cross-account breach — hard stop/report).
5. **Redirect a victim fleet's capacity-block target via the launch template.** With only `ec2:CreateLaunchTemplateVersion`/`ModifyLaunchTemplate` (no `CreateFleet`, no `iam:PassRole`), change the `CapacityReservationId`/`MarketType`/`IamInstanceProfile` baked in a template a fleet references, and show the next `instant` `CreateFleet` resolves the attacker-chosen version.
6. **Test the documented validation-exception gates for fail-open.** Submit the four unsupported combinations the page says throw ("`OnDemandTargetCapacity`/`SpotTargetCapacity` + capacity-block default", "`OnDemandOptions::CapacityReservationOptions` + capacity-block default → *An exception will occur*", "multiple Capacity Blocks in one request") and record reject / clamp / silent-accept.
7. **Characterize the error-oracle.** Confirm that "block not yet started" (`Insufficient Capacity Error`) and "request exceeds block limits"/"block full" (`Insufficient Capacity Exception`) are the **same error surface**, and test whether targeting an un-shared/foreign block is distinguishable (enumeration oracle) from a legitimately-full block.

## 2. Components, Assets, and Design

**What the page does.** A CLI/API-only walkthrough: author a launch template that sets `InstanceMarketOptionsRequest.MarketType = capacity-block` and a `CapacityReservationID` pointing at a Capacity-Block reservation, write a `config.json`, and call `aws ec2 create-fleet --cli-input-json file://config.json` to launch GPU/ML instances **into that Capacity Block**. The fleet is `instant`-only. The exact published config (resource IDs are `{{placeholders}}` in the doc):

```json
{
  "LaunchTemplateConfigs": [
    {
      "LaunchTemplateSpecification": { "LaunchTemplateName": "{{CBR-launch-template}}", "Version": "{{1}}" },
      "Overrides": [ { "InstanceType": "{{p5.48xlarge}}", "AvailabilityZone": "{{us-east-1a}}" } ]
    }
  ],
  "TargetCapacitySpecification": { "TotalTargetCapacity": {{10}}, "DefaultTargetCapacityType": "capacity-block" },
  "Type": "instant"
}
```

Note the two security-critical fields (`MarketType=capacity-block`, `CapacityReservationID`) live in the **launch template**, not in this `config.json`. The fleet config carries only `DefaultTargetCapacityType=capacity-block`, a pinned LT `Version "1"`, instance-type/AZ overrides, and `Type=instant`.

**Ownership / trust model (the net-new part).** Unlike the On-Demand and instance-weighting walkthroughs (pure single-account), the Capacity-Block path has a genuine **cross-account / cross-Organization** dimension:
- A Capacity Block is **owned** by the account that purchased it (prepaid, upfront, non-cancellable) and may be **shared via AWS RAM** to specific accounts, an OU, or the whole org **within the owner's AWS Organization** (`capacity-blocks-share`). **UltraServer** Capacity Blocks **cannot be shared** at all. Sharing is unavailable to new / limited-billing-history accounts. A block shared *to* you **cannot be re-shared** (no chaining).
- **First-come-first-served, regardless of ownership** (verbatim, `capacity-blocks-share`): *"Capacity Blocks operate on a first-come, first-served basis for all accounts, regardless of ownership status. When you share a Capacity Block, if a consumer launches instances before the owner, those instances occupy the capacity until the consumer terminates the instances or until 30 minutes before the Capacity Block expires."*
- **Consumer billing:** consumers pay **only OS charges**, **not** the reservation — the owner prepaid it (`capacity-blocks-pricing-billing`). → occupying a shared block is a cost-shift onto the owner.
- **Targeting is purely by ID:** *"To use a Capacity Block, instances must specifically target the reservation ID"* (`ec2-capacity-blocks`). No `InstanceMatchCriteria` applies to Capacity Blocks; no additional owner/consumer authorization is documented beyond standard `CreateFleet`/`RunInstances` IAM **and** the block being shared to that account via RAM.
- **Owner visibility is post-hoc only:** `get-capacity-reservation-usage` lets the owner see which accounts are running how many instances — a **detective**, not preventive, control. Consumers can only see total/available capacity and **cannot** view/modify other accounts' instances.
- **Lifecycle:** `payment-pending → (payment-failed | scheduled) → active → expired`. Instances run until manually stopped/terminated **or** EC2 force-terminates them when the block ends (termination begins 30 min — 60 for UltraServer — before end; an EventBridge event fires 10 min before termination begins). **Only the owner can extend**, which auto-propagates the new expiry to consumers' running instances. **Cancellations are not allowed.**

**Customer-facing interface.** SigV4 `ec2:CreateFleet` (+ `DescribeFleets`/`DescribeFleetInstances`). `instant` type ⇒ **synchronous, single-attempt, immutable** (`instant-fleet`: *"a synchronous one-time request that makes only one attempt… The API response lists the instances that launched, along with errors for those instances that could not be launched"*; *"after you make the API call, you can't modify it"*). No `maintain`-style self-healing/replenishment (`create-ec2-fleet`: health-check replacement is `maintain`-only). Deleting an `instant` fleet terminates all its instances.

**Principals / roles.** Fleet caller (needs `ec2:CreateFleet` + the launch template + the block shared/owned); the EC2 Fleet SLR that issues the actual launches. This page adds no new identity-policy artifact, but it is the **first fleet page where the resource targeted by the launch can be owned by a different account.**

**Identifiers.** Fleet ID; launch-template name + pinned numeric version; **Capacity-Block / Capacity-Reservation ID** `cr-<17 hex>` (e.g. `cr-1234abcd56EXAMPLE`) — not documented as a secret; knowing the ID + IAM + (for non-owners) a RAM share is what's needed to target it. The ID appears **inside the launch template**, not in the fleet request.

```
 Owner account                                 Consumer / foreign account (CALLER)
   │ purchase CB (prepaid, non-cancellable)       │ holds ec2:CreateFleet + LT (MarketType=capacity-block, CapacityReservationID=cr-X)
   │ RAM-share cr-X to accounts/OU/org  ─────────▶│ (share is the ONLY documented consume gate besides IAM)
   ▼                                              ▼
 Capacity Block cr-X  ◀── FCFS "regardless of ownership" ──  instant CreateFleet  (--cli-input-json file://config.json)
   │  (prepaid GPU/ML capacity)                   │  "repeat the call … until all instances are provisioned"  ← race/poll loop
   │                                              │  partial fulfillment + errorSet (instant); NO On-Demand fallback
   │  consumer-launched instances occupy          │
   │  until consumer terminates OR 30m pre-expiry │  consumer pays OS-only; owner prepaid the reservation
   ▼                                              ▼
 No IAM key pins market=capacity-block on CreateFleet, and NO key (any action) pins which cr-ID is targeted
   → an admin cannot IAM-forbid "launch into capacity-block" nor "launch only into MY block"
```

### 5.1 The capacity-block target is doubly unscopable in IAM — **P0 (Lens S / U / X)** — Tier-2 reportable
**Background.** Both security-critical knobs — `MarketType=capacity-block` and the `CapacityReservationID` — live **inside the launch template**. The authoritative `list_ec2.md` `CreateFleet` row (lines 5113–5123) carries an 8-resource-type set whose condition keys **omit** every lever that could gate this:

| Guardrail an admin would want | Key that would express it | Present on `CreateFleet`? | Present elsewhere |
|---|---|---|---|
| "no capacity-block market on fleets" | `ec2:InstanceMarketType` (values `capacity-block\|on-demand\|spot`, def. 10092) | **No** (absent from all rows incl. `instance*` 5118) | `RunInstances` `instance*` (9591) + ~44 instance-lifecycle actions |
| "launch only into Capacity Block cr-X" | `ec2:CapacityReservationId` | **No — key does not exist anywhere** (0 hits) | — (no action has it) |
| "only blocks accepting targeted launches" | `ec2:InstanceMatchCriteria` (def. 10093) | **No** (not on CreateFleet/RunInstances CR rows) | `capacity-reservation` resource type + CR-fleet mgmt actions only |
| "scope which launch template a fleet uses" | `ec2:LaunchTemplate` / `ec2:IsLaunchTemplateResource` | **No** (launch-template row 5119 has only `aws:ResourceTag`/`ec2:Region`/`ec2:ResourceTag`) | `RunInstances` most rows |
| "within my Org only" | `aws:PrincipalOrgID`/`ResourceOrgID`/`ResourceOrgPaths` | **No — zero hits in all of EC2** | — (RAM/SCP-only; hub plan) |

`CreateFleet`'s own description (line 5114, verbatim): *"Resource-level permissions for this action do not include the resources specified in a launch template. To specify resource-level permissions for resources specified in a launch template, you must include the resources in the RunInstances action statement."* — AWS's own acknowledgment that `CreateFleet` cannot IAM-scope the LT-borne `MarketType`/`CapacityReservationId`. And `ec2:CapacityReservationFleet` (def. 10060) scopes only a *CapacityReservationFleet management ARN* (Cancel/Modify/Describe), **not** the block a launch consumes.

**Security Concern.** Three guardrails the walkthrough's own feature implies an operator can set are **structurally impossible to express at the fleet entry point**:
- "This team may not use Capacity Blocks" — no `ec2:InstanceMarketType` on `CreateFleet`; and even the one partial lever (`ec2:InstanceMarketType=capacity-block` Deny) only binds `RunInstances`, which the SLR — not the caller — invokes for the fleet, so it is inert on the fleet path (Lens X asymmetry + the sibling's SLR-non-propagation runtime fact).
- "This team may launch only into our own Capacity Blocks (cr-X), never a block shared from elsewhere" — **no key, on any action, filters by the targeted CR/block ID.** The *only* access control over which block is consumed is the RAM share + whether the caller knows the ID — not IAM (this is the IAM backstop whose absence makes §5.2 un-mitigable).
- "Only within our Organization" — EC2 has no Org condition key at all.

**High-level Test Scenarios.** All settleable with `iam:SimulateCustomPolicy` — **no fleet created, no block purchased:**
- *Claim:* a `Deny CreateFleet` with `Condition{StringEquals{ec2:InstanceMarketType: capacity-block}}` does not deny a capacity-block fleet. → **Oracle:** simulate `CreateFleet`; the key is reported not-applicable / the Deny does not match → confirmed inert. **Severity:** High (defeats a "no Capacity Blocks for this team" cost/governance guardrail).
- *Claim:* no policy on `CreateFleet` (or any action) can restrict the targeted Capacity-Block ID. → **Oracle:** simulate policies referencing `ec2:CapacityReservationId`/`ec2:InstanceMatchCriteria` on `CreateFleet`/`RunInstances`; all ignored/unknown or (for `InstanceMatchCriteria`) not applicable to the launch. **Severity:** High (no IAM backstop for cross-account block selection → enables §5.2).
- *Claim:* the one partial lever `ec2:InstanceMarketType=capacity-block` on `RunInstances` does not reach the fleet-SLR launch. → **Oracle:** simulate the Deny against the caller; show it binds `RunInstances` only, which the caller never calls on the fleet path (cross-ref `ec2-fleet` SLR-non-propagation). **Severity:** confirms inertness.
**Doc evidence:** `list_ec2.md` 5113–5123 (CreateFleet), 5114 (description), 9585–9609 (RunInstances), 10060/10092/10093 (key defs), zero-hit greps for `ec2:CapacityReservationId` + the three Org keys. **Severity-if-true:** High, **in scope** — AWS-owned structural authz gap; a customer building "we restrict Capacity-Block usage/targeting via IAM" relies on a non-enforceable claim.
**Stop condition:** static-reference finding — Simulate confirms with no resource touched; stop at the simulator verdict.

### 5.2 Cross-account / cross-Org Capacity-Block race-and-occupy — **P0 (Lens A / AA / U)** — highest impact
**Background.** `capacity-blocks-share` (verbatim): *"Capacity Blocks operate on a first-come, first-served basis for all accounts, regardless of ownership status. When you share a Capacity Block, if a consumer launches instances before the owner, those instances occupy the capacity until the consumer terminates the instances or until 30 minutes before the Capacity Block expires."* Consumers pay **only OS charges**, not the reservation (`capacity-blocks-pricing-billing`); the owner prepaid it (upfront, **non-cancellable**). Targeting is **purely by ID** — *"instances must specifically target the reservation ID"* — with no documented owner/consumer authorization beyond standard launch IAM + the RAM share. The walkthrough itself hands the attacker the operational tool: *"You can repeat the call to EC2 Fleet again until all the instances are provisioned"* — a tight synchronous `instant`-`CreateFleet` **race/poll loop**. §5.1 proves no IAM key can pin which block a consumer targets, so the owner has **no preventive control**; `get-capacity-reservation-usage` is detective-only.
**Security Concern.** Two sub-boundaries:
- **(a) In-share owner-adverse race (documented but un-preventable):** a consumer the owner RAM-shared the block to can win the FCFS race and occupy the owner's prepaid GPU/ML capacity before the owner's own workload launches — a cost-shift (consumer pays OS-only) and an availability-denial of the owner's prepaid capacity, lasting until the consumer terminates or 30 min before expiry. The owner cannot evict the consumer's instances (consumers' instances are not owner-modifiable) and cannot IAM-restrict the consumer to a sub-portion. This is the AWS-documented FCFS design turned adversarial (Lens U/AA — the share grant has no per-consumer capacity cap or priority reservation for the owner). **In scope to characterize** (impact + the absence of any owner-side mitigation), not a code-defect claim.
- **(b) Un-shared / foreign-block targeting (the true cross-account breach to falsify):** does the EC2 service enforce the RAM share server-side at launch, or is the share merely advisory such that any account that *knows* a `cr-ID` (which is not a secret) and holds `CreateFleet` can target it? If a launch into a **not-shared-to-caller** block ever succeeds → cross-account occupation of a block with no grant at all (Critical; hard-stop/report).
**High-level Test Scenarios** (two authorized accounts = owner A, consumer B; smallest/shortest block; synthetic workload):
- *Claim (b):* B targets A's Capacity-Block ID in an LT **before** A shares it (no RAM share) and `instant` `CreateFleet` launches instances into it. → **Oracle:** `DescribeFleetInstances`/`errorSet` — a launched instance in A's block with no share = **cross-account breach, hard stop, preserve, report**; `AccessDenied` or `Insufficient Capacity` = refuted (and feeds §5.5 oracle). **Severity:** Critical if it launches. **Precondition:** B knows A's `cr-ID` (enumerable? — the ID is `cr-`+17 hex, not secret; test whether B can discover it via any Describe, else assume known).
- *Claim (a):* after A shares the block to B, B's "repeat the call" loop occupies the whole block before A launches; A is then starved and pays the full reservation while B pays OS-only. → **Oracle:** A runs `get-capacity-reservation-usage` and sees B holding the capacity; A's own `CreateFleet` returns `Insufficient Capacity Exception`. **Severity:** High (cross-account cost-shift + prepaid-capacity denial; un-preventable by the owner).
- *Claim:* no per-consumer cap / owner-priority exists on a share. → **Oracle:** inspect the RAM share + CB APIs for any capacity-reservation-for-owner or per-consumer quota knob; absence confirms the owner-adverse design. **Severity:** Medium–High (Lens AA grantee-scope gap).
**Doc evidence:** `capacity-blocks-share` (FCFS quote, consumer-billing, 30-min hold); `ec2-capacity-blocks` ("target the reservation ID"); target page ("repeat the call"); §5.1 (no IAM backstop). **Severity-if-true:** (b) Critical / (a) High, **in scope** (cross-account on an AWS multi-account feature). **Stop condition:** the moment a launch into an un-shared block is confirmed, STOP (service-plane-adjacent cross-account) and report; for (a), one confirmed occupancy + the owner's `Insufficient Capacity` is enough — terminate B's instances immediately (block is prepaid & non-cancellable, so minimize spend).

> **De-dup:** the hub plan (`fleet-tutorials` Area 7) names this FCFS fact; this §5.2 owns the **walkthrough-mechanism development** — the `instant`+"repeat the call" race loop, the share-vs-ID consume-gate falsification, and the zero-reservation-cost cost-shift quantification. Cross-ref the hub for RAM-share mechanics and the CR-Fleet SLR.

### 5.3 Launch-template late-binding redirects the capacity-block target — **P1 (Lens B / E / X)** — intra-account privesc/redirect
**Background.** Because `MarketType=capacity-block` and `CapacityReservationID` are baked in the **launch template**, control of the template version = control of **which block the fleet lands in, which market it uses, and (via `instant` overrides) the instance profile / user-data / AMI**. The sibling `ec2-fleet-instance-weighting-walkthrough` (Area 2) established the `$Latest`/`$Default` late-binding privesc generically; the IAM audit confirms `CreateLaunchTemplateVersion` carries **no `ec2:Attribute`** key (lines 5259–5262) and `ModifyLaunchTemplate`'s `ec2:Attribute` (8940–8943) is only a field-*name* filter (cannot assert "the new `MarketType` must equal X" or "the baked `CapacityReservationId` must equal cr-mine"). So a principal holding only `ec2:CreateLaunchTemplateVersion`/`ModifyLaunchTemplate` on a template (no `CreateFleet`, no `iam:PassRole`) can rewrite its market type / CR-target / instance profile.
**Caveat specific to this page:** capacity-block fleets are **`instant`-only** (no `maintain` self-replenishment), so the sibling's "re-resolves on every replenishment" amplifier does **not** apply — the redirect only takes effect on the **next** `CreateFleet` call. The tutorial pins `Version "1"` (safe), but `instant-fleet`'s own examples idiomatically use `$Latest`; a victim fleet that references `$Latest`/`$Default` (or is re-created by IaC) resolves the attacker's new default version at that call.
**Security Concern.** An LT-editor who cannot launch fleets can still cause the next capacity-block fleet to (i) land in a **different block** (DoS / wrong-capacity, or a block the editor controls), (ii) attach an **attacker-chosen `IamInstanceProfile`** on the `instant` launch (privesc if the fleet creator holds `PassRole` for a role the editor doesn't), or (iii) inject 16 KB of base64 user-data via the `instant` override. Intra-account cross-team.
**High-level Test Scenarios.**
- *Claim:* `CreateLaunchTemplateVersion` with no `ec2:Attribute` key allows writing `MarketType`/`CapacityReservationId`/`IamInstanceProfile` with no field-value restriction. → **Oracle:** `iam:SimulateCustomPolicy` shows no condition can bound the written fields; (live) create a new default version changing the CR-target. **Severity:** Medium–High.
- *Claim:* a fleet referencing `$Latest`/`$Default` resolves the attacker's version on the next `instant` `CreateFleet`. → **Oracle:** set attacker version default; issue `CreateFleet`; `DescribeFleetInstances` shows the attacker-chosen block/profile. **Severity:** High if an instance-profile swap crosses a privilege line (cross-ref `ec2-fleet` §5.1 PassRole bypass).
**Doc evidence:** `list_ec2.md` 5259–5262, 8940–8943, 9967 (launch-template resource key set); `instant-fleet` ($Latest examples, override field list `IamInstanceProfile`/`KeyName`/`MetadataOptions`/SSM-AMI/16 KB user-data); `API_FleetLaunchTemplateSpecificationRequest`. **Severity-if-true:** Medium–High (intra-account privesc/redirect). **Stop condition:** redirect confirmed once; tear down.

### 5.4 `instant`-only: validation-exception gates (fail-open?) + EventBridge detection blind-spot — **P1 (Lens U / O)**
**Background.** The page documents four unsupported combinations, one explicitly throwing (*"An exception will occur"*): `OnDemandTargetCapacity`/`SpotTargetCapacity` with `capacity-block` default; `OnDemandOptions::CapacityReservationOptions` with `capacity-block` default; multiple Capacity Blocks in one request; non-`instant` type. These are **synchronous** validations (consistent with `instant`'s single-attempt nature). Separately, `instant` fleets emit **no EventBridge events** (established by `fleet-monitor`/`monitor-ec2-fleet-using-eventbridge` plans — *"Only fleets of type `maintain` and `request` emit events. Fleets of type `instant` do not emit events"*), so a capacity-block fleet launch is **invisible on the EventBridge channel**. (The capacity-block *end* EventBridge event comes from the Capacity Block, not the fleet.)
**Security Concern.** (U) If any documented-illegal combination is **silently accepted or clamped** rather than rejected, a caller can build a fleet whose capacity mix diverges from the documented constraint (config-integrity / cost). (O) The EventBridge blindness means detection of capacity-block provisioning must rely on CloudTrail `CreateFleet` management events (logged by default) — a SOC keyed on EventBridge fleet events sees nothing; combined with §5.2 this hides a cross-account occupancy from EventBridge-based alerting.
**High-level Test Scenarios.**
- *Claim:* `CreateFleet` with `DefaultTargetCapacityType=capacity-block` **and** `OnDemandOptions::CapacityReservationOptions` is accepted (fail-open) instead of throwing. → **Oracle:** submit; record exact exception vs silent accept. **Severity:** Low–Medium (doc-vs-enforcement). *Use a not-yet-started block or expect `Insufficient Capacity` to avoid real provisioning while testing validation ordering — see §5.5.*
- *Claim:* multiple Capacity Blocks in one request / `OnDemandTargetCapacity` + capacity-block default are silently reshaped. → **Oracle:** submit each; compare to the documented "not supported." **Severity:** Low–Medium.
- *Claim:* the capacity-block fleet launch produces no EventBridge event. → **Oracle:** rule on `aws.ec2fleet`; confirm silence; confirm the CloudTrail `CreateFleet` event still fires. **Severity:** Low (detective-control gap; raises §5.2 severity as an enabler).
**Doc evidence:** target-page Considerations; `fleet-monitor`/`monitor-ec2-fleet-using-eventbridge` plans (instant = no events); `create-ec2-fleet`. **Severity-if-true:** Low–Medium. **Stop condition:** record each validation outcome once.

### 5.5 Error-oracle ambiguity, no On-Demand fallback, partial-fulfillment — **P2 (Lens A oracle / business-logic / availability)**
**Background.** The page states **both** "block hasn't started" and "request exceeds block limits"/"block full" surface as the **same error family** — `Insufficient Capacity Error` vs `Insufficient Capacity Exception` (near-identical). *"For Capacity Blocks, EC2 Fleet will not fallback to launching On-Demand Instances."* And partial fulfillment is expected: *"fulfill as much capacity as it can … repeat the call."*
**Security Concern.** (A-oracle) The collapsed error surface is a **weak enumeration oracle**: a caller probing a `cr-ID` cannot distinguish "not started" / "full" / "exceeds limits" — but conversely, the §5.2(b) test must determine whether targeting an **un-shared/foreign** block returns `AccessDenied` (fail-closed, refutes IDOR) or `Insufficient Capacity` (indistinguishable → an existence/occupancy oracle for foreign blocks the caller shouldn't see). (availability) No On-Demand fallback means a capacity-block fleet silently under-provisions on shortfall — but because the fleet is `instant`, the shortfall **is** surfaced synchronously in `errorSet` (unlike the `maintain` under-ICE blind spot of the on-demand sibling §5.2), so detection here is actually stronger.
**High-level Test Scenarios.**
- *Claim:* targeting a foreign/un-shared `cr-ID` returns `Insufficient Capacity` (not `AccessDenied`) → an occupancy/existence oracle for blocks the caller has no grant on. → **Oracle:** `CreateFleet` against a known-foreign `cr-ID`; compare error vs a bogus `cr-ID` vs a legitimately-full own block. **Severity:** Low–Medium (enumeration oracle; feeds §5.2(b)).
- *Claim:* "repeat the call" with no idempotency token can over-provision beyond intent when callers race their own loops. → **Oracle:** fire two concurrent `instant` loops against one block; sum launched instances vs target. **Severity:** Low (single-account); the cross-account variant is §5.2.
**Doc evidence:** target page (both error sentences, no-fallback, repeat-the-call); `create-ec2-fleet` (`errorSet` examples). **Severity-if-true:** Low–Medium. **Stop condition:** error taxonomy recorded; stop.

### Kill-chain candidates (rate at the end of the chain)
- **§5.1 (no IAM key pins the block ID) → §5.2(a) (in-share FCFS race):** because an admin cannot IAM-restrict which block or sub-capacity a shared-to consumer targets, a consumer runs the `instant` "repeat the call" loop to occupy the owner's entire prepaid GPU block before the owner launches → owner pays the full reservation, gets `Insufficient Capacity`, cannot evict; consumer pays OS-only. End severity: **High** (cross-account cost-shift + prepaid-capacity denial, un-mitigable by the owner).
