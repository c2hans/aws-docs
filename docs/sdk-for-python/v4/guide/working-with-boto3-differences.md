**Developer Preview**: This documentation covers the AWS SDK for Python v4, which is in Developer Preview and intended for evaluation and testing only. Do not use it for production workloads. For production applications, use the [AWS SDK for Python (Boto3)](https://docs.aws.amazon.com/boto3/latest/guide/quickstart.html). To understand the differences between the two SDKs, see [Choosing the right AWS SDK for Python](choosing-sdk.md).

# Key differences
<a name="working-with-boto3-differences"></a>

AWS SDK for Python (Boto3) and the AWS SDK for Python v4 have different Python client interfaces. The AWS SDK for Python v4 also adds asynchronous clients. The following table summarizes the API-model and execution differences that affect your application code. The operation, request, response, streaming, and error rows compare generated AWS SDK for Python v4 clients with Boto3 low-level clients.

| Area | AWS SDK for Python (Boto3) | AWS SDK for Python v4 |
| --- | --- | --- |
| Execution model | Service operations are synchronous and block the calling thread until they complete. | Each service package has a synchronous client and an asynchronous client. Synchronous client operations block the calling thread, like Boto3 operations. Asynchronous client operations yield to the asyncio event loop, so other tasks can run while a call is in flight. |
| Packages and service coverage | Installing boto3 provides access to clients and features for a broad set of AWS services. | Each service client is distributed as a separate package. The Developer Preview covers a subset of AWS services. Its clients don't implement every Boto3 feature yet. |
| Clients and imports | Import boto3 and create clients dynamically, such as boto3.client("dynamodb"). | Install a service package, such as aws-sdk-dynamodb, and import its generated clients from the top-level package, such as DynamoDBClient and AsyncDynamoDBClient from aws\_sdk\_dynamodb. |
| Higher-level features | Provides higher-level abstractions for supported services, including paginator and waiter objects and managed transfer utilities. | The Developer Preview focuses on generated service clients. It doesn't provide paginator or waiter objects or managed transfer utilities yet. |
| Operation and member names | Low-level client operation methods use snake case, such as put\_object, but request parameter names and response keys preserve modeled API casing, such as Bucket, Key, and ETag. | Operation methods, their keyword arguments, and generated output model members use snake case, such as put\_object() with the bucket and key arguments, and the e\_tag output member. |
| Requests | Low-level clients accept modeled request parameters as keyword arguments. Nested structures and unions are dictionaries that use modeled names, such as {"S": "Mary Major"}. | Operations take keyword arguments named after the input members. You can also pass the whole request as one positional argument, either the generated input model or its dictionary form. Pass nested structures and unions as dictionaries that use snake-case member names, such as {"s": "Mary Major"}, or as generated model objects, such as AttributeValueS(value="Mary Major"). |
| Responses | Low-level client operations generally return service responses as dictionaries. Read values by key and check whether optional keys are present. | Operations return generated output models. Read model attributes and check optional members for None. When a member is a union, narrow its generated variant before accessing its value. Event-stream operations, which only asynchronous clients provide, return stream objects. |
| Streaming | Boto3 reads streaming response bodies and output event streams, such as Amazon Bedrock Runtime converse\_stream, synchronously. These reads block the calling thread. Boto3 doesn't support bidirectional event streams. | Both client types support streaming request and response bodies, such as Amazon S3 objects. Event streams are available only in asynchronous clients. Bidirectional event streams use HTTP/2 and require the AWSCRTHTTPClient HTTP client. |
| Errors | Client-side failures use Botocore exception classes. Service errors can be caught as ClientError, which exposes details through its response dictionary. | Modeled service errors use concrete generated exception classes, including errors raised while consuming a stream. |
| Configuration | boto3.client() uses the default Boto3 session. Create a boto3.Session or pass a Botocore Config to customize settings. | Each client type has a generated configuration class, such as DynamoDBConfig. To customize a client, call the class's resolve() method, such as DynamoDBConfig.resolve(region="us-east-1"). Then pass the result to the client. |
