## 0. How to use this document
- Each lead: **Claim → Mechanism (doc evidence) → Confirm/Refute oracle → Preconditions / Cost → Severity-if-true → Stop condition.** Work in priority order (Section 5 clusters are ordered by value); look left and right for adjacent bugs.
- This chapter documents a **fully-managed compute service under the AWS shared-responsibility model.** Much of the security surface here is *customer configuration* (the customer's own least-privilege footguns) rather than a breakable AWS boundary. The plan is explicit in Section 7 about which is which, so a hunter does not burn time on shared-responsibility gaps.
- **HARD STOP:** the moment evidence shows an identity / credential / ARN / account belonging to **AWS's own service plane** (the Nitro controller, IMDS backend fleet, the EC2 control plane, the attestation/KMS signer), stop, preserve evidence, and flag for AWS-Security disclosure. Reading *your own* instance's role credentials from IMDS is expected behavior, not a finding — the finding is crossing to *another* tenant or to AWS's fleet identity.

## 1. Pentest Objectives (boundary-breach goals, as concrete outcomes)
1. **Steal or widen instance role credentials** — reach `iam/security-credentials/<role>` from a context that should not (SSRF through an app on the instance, a proxy with hop-limit>1, a container sharing the host netns) and use the vended SigV4 creds; or obtain creds for a role the instance was not assigned.
2. **PassRole / instance-profile privilege escalation** — attach a higher-privileged role to an instance the attacker controls, or attach a role the caller lacks `iam:PassRole` for, and read that role's creds from IMDS.
3. **Cross-account / cross-tenant reach** — access another account's key pair, security group, AMI-encryption KMS key, or instance-identity data; or reach another tenant's instance via a shared managed access path (EC2 Instance Connect Endpoint).
4. **Forge or replay a trust assertion** — get a verifier (KMS attestation policy, or any consumer of the instance identity document) to accept a forged/replayed Attestation Document or IID for an instance the attacker does not own or that is not running the trusted software.
5. **Break the network boundary** — use EICE / security-group rule evaluation / connection tracking to reach an instance a rule should have denied.
6. **Escape data-plane → control-plane** — reach the Nitro control interface / IMDS backend / attestation signer from inside a customer instance.


## 2. Components, Assets, and Design (chapter-level)
The EC2 security chapter describes a **fully-managed compute service** whose security-relevant seams cluster into four zones. Each zone is deep-dived in Section 5.

**Actors / ownership:**
- **Customer account/VPC** — owns instances, key pairs, security groups, AMIs, KMS keys, IAM roles/policies.
- **In-instance code** — application/agent code running on the guest OS; the primary *untrusted-relay* actor (SSRF, proxies, containers) even though the customer "owns" the instance.
- **EC2 service plane** — the control plane (RunInstances, Associate/ReplaceIamInstanceProfile), the IMDS backend that vends role credentials, the Nitro controller/TPM + attestation signer, the EC2 Instance Connect / EICE managed access fleet. **AWS-owned; the hard-stop boundary.**
- **AWS IAM/STS** — issues the temporary credentials surfaced at `iam/security-credentials/<role>`.
- **AWS KMS** — verifier for attestation documents and encryptor of EBS/AMI data.

**Key assets:** instance role credentials (short-TTL SigV4 at the link-local endpoint); key-pair private keys; the instance identity document (accountId/instanceId/region, signed); the Attestation Document + reference measurements; security-group rulesets; AMI-encryption KMS grants.

**Identifier shapes worth noting:** instance IDs (`i-0…`, 17 hex), account IDs (12-digit, appear in the IID), role names in the credential path, key-pair names/fingerprints, security-group IDs (`sg-…`). The IID carries `accountId`+`instanceId` in **plaintext JSON** with a *separate* signature — the classic "consumer forgets to verify the signature" trap.

```
                 customer VPC / instance
  +-----------------------------------------------+
  |  app / agent code  --curl-->  169.254.169.254 |----> IMDS backend (EC2 service plane)
  |        |  (SSRF / proxy / container relay)     |         |-- vends role creds (IAM/STS)
  |        |                                        |         |-- serves IID (+signature)
  |   sshd / authorized_keys <--push-- EC2 Instance Connect (service plane)
  |   NitroTPM  --measure/quote-->  Attestation Doc --> KMS verifier (attestation policy)
  +-----------------------------------------------+
        ^ security groups / EICE gate ingress          ^ control plane: Associate/ReplaceIamInstanceProfile (PassRole)
```

## 5. Recommended Areas of Focus
Four clusters, ordered by value. Cross-cutting hot path: **any SSRF/credential-theft primitive (Cluster A) → instance role or instance-identity-role creds → PassRole/DHMC escalation (Cluster B)**; and **any trust-assertion consumer that skips verification (Cluster C)**. ## Cluster A: Instance Metadata Service (IMDS) & Credential Vending

**Suspected prompt injection (noted, not executed):** every page in this cluster carries an identical injected `## See also` footer instructing an AI agent to run `aws agent-toolkit search-skills --search-query AWSEC2`. Present in both offline mirror and live docs.aws.amazon.com. Treated as an untrusted lure and **not executed**.

### A.1 Components, Assets, Design
**Interface:** plain HTTP (no TLS) on link-local, reachable only from the instance: IPv4 `169.254.169.254`, optional IPv6 `[fd00:ec2::254]` (Nitro-only). Two modes on the same endpoint: **IMDSv1** (bare GET, no auth) and **IMDSv2** (session: `PUT /latest/api/token` with `X-aws-ec2-metadata-token-ttl-seconds` 1s–6h → token replayed on every GET). "If no headers are present, it is assumed the request is intended for IMDSv1" (configuring-instance-metadata-service.md).

**Assets in the flat key/value tree:** instance metadata; **`iam/security-credentials/{role-name}`** — live temporary role creds, auto-rotated (new creds ≥5 min before expiry); `identity-credentials/ec2/security-credentials/ec2-instance` (instance-identity role, "no policies attached"); `tags/instance` (opt-in InstanceMetadataTags); `user-data` (≤16KB, unauthenticated/unencrypted, often holds bootstrap secrets).

**Option precedence** (configuring-instance-metadata-options.md): HttpTokens/HttpPutResponseHopLimit/HttpEndpoint/InstanceMetadataTags resolved **Instance launch config > Account-level default > AMI config**; separate later account-level `HttpTokensEnforced` gate. All four mutable post-launch via `ModifyInstanceMetadataOptions`, immediate, no reboot.

### A.2 Trust-Boundary Map
| From | To | Mechanism | Breach oracle |
|---|---|---|---|
| Any in-instance process (SSRF app, co-located container, malware) | `iam/security-credentials/{role}` | unauth (v1) or token-gated-instance-side-only (v2) HTTP GET | A process that is not the intended consumer retrieves full-scope role creds — breach = absence of per-caller scoping |
| Remote attacker input → server-side fetcher (SSRF) | IMDS token/cred endpoints | fetcher's outbound request redirected to 169.254.169.254 | A PUT token (or v1 GET) via the vulnerable path returns usable token/creds |
| VPC network appliance w/ src-dst check disabled | Another instance's IMDS | appliance forwards packets to IMDS address | Traffic from outside the target instance's netns completes token PUT/GET |
| IAM principal w/ ec2:ModifyInstanceMetadataOptions | Running hardened instance's IMDS config | ModifyInstanceMetadataOptions --http-tokens optional, immediate | Hardened instance answers unauth v1 GET for creds right after the API call, no code on the box |
| Stolen v1/v2 creds used off-instance | AWS API plane | SigV4 with exfil creds | Call succeeds; absent ec2:RoleDelivery=2.0, v1/v2 creds accepted identically |
| IMDS credential fetch event | CloudTrail | none documented | Theft produces zero CloudTrail record at the point of theft |

### A.3 Falsifiable Research Leads
**A-1 — Default hop-limit=1 as SSRF-relay killswitch.** Claim: a one-hop relay (reverse proxy/LB/container bridge) between an SSRF app and IMDS cannot complete the PUT token exchange when HttpPutResponseHopLimit=1. Mechanism: "the response to PUT requests has a response hop limit (TTL) of 1 at the IP protocol level" (configuring-instance-metadata-service.md). Oracle: from one hop beyond, attempt PUT; TTL drop confirms, returned token refutes. Severity-if-refuted: Critical.
**A-2 — Container hop-limit=2 reopens the SSRF window.** Claim: the documented container fix (raise HopLimit to 2) restores the one-hop relay path A-1 closes. Mechanism: "In a container environment, consider... increasing the hop limit to 2" (instancedata-data-retrieval.md). Oracle: hop-limit=2 instance; one-hop relay completes token PUT and reads creds. Severity: High–Critical.
**A-3 — IMDSv1 reachable by default unless explicitly disabled.** Claim: un-hardened instances answer bare GET for creds. Mechanism: "By default, you can use either IMDSv1 or IMDSv2, or both"; v1 example is a headerless curl (instance-metadata-security-credentials.md). Oracle: filter http-tokens=optional; bare curl returns creds. Severity: Critical.
**A-4 — X-Forwarded-For rejection on PUT is a narrow proxy-signature check.** Claim: the only anti-relay check applies to proxies stamping XFF; raw SSRF where the vulnerable server issues the PUT itself (no XFF) is unaffected. Mechanism: "PUT requests are rejected if they contain an X-Forwarded-For header" — no equivalent for GET or XFF-less PUT (configuring-instance-metadata-service.md). Oracle: SSRF PoC where app performs PUT without XFF → token succeeds. Severity: High.
**A-5 — No intra-instance authz on credential path.** Claim: no scoping between which process should get creds and which asked. Mechanism: "any software running on the instance can view its metadata" (ec2-instance-metadata.md Important). Oracle: two distinct local users both retrieve identical full-scope creds. Severity: High (lateral privilege within shared host / multi-tenant containers).
**A-6 — IMDS credential retrieval produces no CloudTrail record.** Claim: the fetch is a local link-local HTTP call, not an AWS API call; only downstream API use is logged, attributed to the role not the vector. Mechanism: no CloudTrail mention on any cluster page; only aggregate CloudWatch MetadataNoToken/MetadataNoTokenRejected counters (instance-metadata-transition-to-version-2.md). Oracle: post-theft, CloudTrail shows only attacker's later API calls under the role principal. Severity: Low standalone / defeats detection for all other leads.
**A-7 — ec2:RoleDelivery=2.0 is opt-in; v1 creds otherwise indistinguishable.** Claim: without this condition key, v1-vended creds accepted like v2. Mechanism: "by using the condition key ec2:RoleDelivery with a value of 2.0... API calls made with EC2 Role credentials obtained from IMDSv1 will receive UnauthorizedOperation" (transition-to-version-2.md). Oracle: absent the key, A-3 creds succeed against arbitrary APIs. Severity: Critical.
**A-8 — AMI-level ImdsSupport=v2.0 silently overridden by precedence.** Claim: a v2.0-hardened AMI is downgraded when a launch param / account default of optional is in effect (AMI is last in precedence). Mechanism: precedence table (configuring-instance-metadata-options.md). Oracle: launch v2.0 AMI in optional-default account, no override → HttpTokens=optional. Severity: High (silent control regression).
**A-9 — ModifyInstanceMetadataOptions downgrades a running hardened instance instantly.** Claim: a principal with only ec2:ModifyInstanceMetadataOptions flips required→optional in-place, reopening v1. Mechanism: "The change takes effect immediately without needing an instance restart"; "Restrict access to the ModifyInstanceMetadataOptions httpTokens property" (transition-to-version-2.md / configuring-IMDS-new-instances.md). Oracle: call --http-tokens optional then bare v1 curl succeeds, no restart. Severity: High–Critical (control-plane→data-plane escape via mis-scoped IAM).
**A-10 — ASG hardening not retroactive.** Claim: hardened launch template leaves existing ASG members IMDSv1-exposed. Mechanism: "existing instances are not affected" (transition-to-version-2.md). Oracle: after template update, filter http-tokens=optional still returns members. Severity: Medium–High.
**A-11 — User data is an unauthenticated sibling exposure.** Claim: any primitive reaching creds also reaches /latest/user-data. Mechanism: "not protected by authentication or cryptographic methods... should not store sensitive data... as user data" (ec2-instance-metadata.md). Oracle: extend cred-theft PoC to GET /latest/user-data, decode base64 for secrets. Severity: High.
**A-12 — InstanceMetadataTags bypasses ec2:DescribeTags IAM gate.** Claim: with tags in IMDS enabled, tag values retrievable via SSRF path with zero IAM perms. Mechanism: "local processes... can view the instance's tag information directly from the instance metadata" (work-with-tags-in-IMDS.md). Oracle: with tags enabled and no creds, retrieve tags/instance without DescribeTags authz. Severity: Medium.
**A-13 — Own-VPC appliance forwards into another instance's IMDS.** Claim: with src/dst check disabled and no drop rule, VPC traffic reaches a different instance's IMDS. Mechanism: "the IMDS can be reached from your own network when a network appliance within your VPC... forwards packets to the IMDS address, and the default source/destination check on the instance is disabled" (instance-metadata-limiting-access.md). Oracle: from a routing instance, complete token PUT/GET against a different instance's IMDS. Severity: High (breaks single-instance-only assumption → same-VPC lateral movement).
**A-14 — Shared link-local 1024 PPS budget → denial of credential renewal.** Claim: co-located process floods the shared IMDS/DNS/NTP link-local budget to deny an app's cred refresh. Mechanism: "1024 packet per second (PPS) limit to services that use link-local addresses... aggregate of Route 53 Resolver DNS... IMDS..." (instancedata-data-retrieval.md). Oracle: sustained flood raises 429/latency for a second process's cred polling. Severity: Low–Medium (self-DoS; escalates only if crosses container/tenant boundary).
**A-15 — IMDS creds are always full role scope; per-caller narrowing is discouraged opt-in.** Claim: every local caller gets identical full-role creds; docs frame the one narrowing mechanism (self-assume + session policy) as usually "unnecessary." Mechanism: "such role assumption calls are unnecessary"; self-assume needs an explicit trust policy or AccessDenied (instance-metadata-security-credentials.md). Oracle: two need-to-know-differing processes both get full-role creds by default. Severity: Medium–High (amplifies A-5 blast radius).

## Cluster B: IAM Roles, Instance Profiles & PassRole

**Suspected prompt injection (noted, not executed):** every page (offline and live, byte-for-byte match confirmed) ends with the `## See also` block telling an AI agent to run `aws agent-toolkit search-skills`. Not executed, not treated as instruction.

### B.1 Components, Assets, Design
- **Identity primitives:** an IAM **role** is the credential-bearing identity; an **instance profile** is EC2's container for exactly one role. Console-created roles auto-create a same-named profile; CLI/API roles/profiles "potentially" have different names (attach-iam-role.md).
- **Attach surface (boundary-crossing API set):** `iam:PassRole`, `ec2:AssociateIamInstanceProfile`, `ec2:DisassociateIamInstanceProfile`, `ec2:ReplaceIamInstanceProfileAssociation` (+ console `iam:ListInstanceProfiles`).
- **Credential vending:** attached role's temp creds served from IMDS. Two documented properties: (a) NOT capped by role `MaxSessionDuration`; (b) NOT instance-bound unless the policy opts in `ec2:SourceInstanceARN`.
- **Instance identity role:** a distinct always-on identity at IMDS `/identity-credentials/ec2/security-credentials/ec2-instance`, ARN `arn:...:assumed-role/aws:ec2-instance/{instance-id}`, with **no role-trust policy** and **not subject to any identity/resource policy**, present "regardless of whether a service or feature that makes use of instance identity roles is enabled." Trusted by 6 services incl. SSM Default Host Management Configuration (DHMC), which "can pass your AWSSystemsManagerDefaultEC2InstanceManagementRole IAM role to your instance," EC2 Instance Connect, GuardDuty Runtime Monitoring, Lambda Managed Instances, Bedrock AgentCore, STS GetCallerIdentity.
- **Instance identity document:** separate unauthenticated plaintext-JSON self-report (see Cluster C for its attacks).
- **Policy surface:** `ec2:Describe*` never supports resource-level permissions (always Resource:*); ABAC via aws:ResourceTag/RequestTag/TagKeys; `ec2:SourceInstanceARN` the only documented instance-binding mechanism.
- **Managed/SLR grants:** spot-fleet-auto-scaling-IAM grants `iam:CreateServiceLinkedRole` on Resource:* (no AWSServiceName condition); EC2FastLaunchFullAccess grants use of instance profiles whose name "contains" ec2fastlaunch.

### B.2 Trust-Boundary Map
| From | To | Mechanism | Breach oracle |
|---|---|---|---|
| IAM caller | instance's role binding | Associate/Replace/DisassociateIamInstanceProfile | Attach/replace/detach a role on an instance outside caller's resource scope (Resource:* reaching un-owned instances) |
| IAM caller | IAM role as passable credential | iam:PassRole at attach/replace time | A role attached without a specific PassRole grant, or via name-mismatch/substring the caller wasn't meant to match |
| Instance (attacker code) | attached role creds via IMDS | vending, no MaxSessionDuration, no default SourceInstanceARN | Creds valid past role max session duration, or replayed off-instance / after replace/detach |
| Any EC2 instance | instance identity role → services | self-asserted, trust-policy-free identity vended unconditionally | SSM DHMC accepts identity-role creds and passes AWSSystemsManagerDefaultEC2InstanceManagementRole to an instance never explicitly authorized |
| Caller w/ tagging rights | ABAC-gated attach policy | ec2:CreateTags self-tag vs aws:ResourceTag-scoped Associate | Caller self-applies the qualifying tag, then exercises attach it shouldn't qualify for |
| Defender revoking role | continued live access | documented up-to-1-hour propagation delay | Creds/permissions remain effective after the defender believes access was revoked |

### B.3 Falsifiable Leads
**B-1 — Wildcard-resource attach/replace lets a caller hijack un-owned instances.** Claim: Associate/Replace on Resource:* restricted only by PassRole role-name pattern → attach to ANY instance in account. Mechanism: ExamplePolicies_EC2.md "allows users to attach or replace an IAM role for any instance... only... names that begin with TestRole-" with Resource:*. Oracle: Associate against an instance the caller doesn't own, with a TestRole-* profile → success. Severity: High (Critical if TestRole-* is broad).
**B-2 — iam:PassRole Resource:* is a documented direct-to-admin path.** Claim: unscoped PassRole passes any role to a self-controlled instance. Mechanism: permission-to-pass-iam-roles.md "If you specify the resource for iam:PassRole as *, this would grant access to pass any of your IAM roles to an instance." Oracle: attach a privileged role to a caller-launched instance; IMDS vends its creds. Severity: Critical.
**B-3 — Role-name vs instance-profile-name mismatch is a PassRole scoping trap.** Claim: scoping PassRole to the profile name rather than the role name silently over/under-grants. Mechanism: ExamplePolicies_EC2.md "specify the name of the IAM role and not the instance profile (if the names are different)." Oracle: profile TestRole-Foo containing role AdminRole; grant PassRole on role/TestRole-*; attach → IAM evaluates real role ARN. Severity: High (recurring misconfig class AWS flags).
**B-4 — EC2 role creds ignore MaxSessionDuration.** Claim: IMDS creds not subject to the role's max session duration. Mechanism: iam-roles-for-amazon-ec2.md Note verbatim. Oracle: set MaxSessionDuration=1h, confirm IMDS serves valid creds indefinitely while attached. Severity: Medium–High (removes a customer blast-radius cap).
**B-5 — IMDS creds not instance-bound unless ec2:SourceInstanceARN opted in.** Claim: creds from instance A usable anywhere by default. Mechanism: ExamplePolicies_EC2.md SourceInstanceARN example ("the other instance cannot perform any of these actions" implies no restriction without it); "attach the same role to many instances." Oracle: replay A's creds from elsewhere for a role lacking SourceInstanceARN → succeed. Severity: High (SSRF/theft blast-radius multiplier).
**B-6 — Detach/remove-role has up-to-1-hour revocation lag.** Claim: removing a role from a profile persists access up to an hour. Mechanism: iam-roles-for-amazon-ec2.md "we do not recommend removing a role from an instance profile, because there is a delay of up to one hour before this change takes effect." Oracle: detach, reuse cached creds within 60 min → valid. Severity: High during IR.
**B-7 — ABAC self-tagging bypass on attach policies.** Claim: caller with RunInstances + tag-conditioned CreateTags self-applies the qualifying tag, then exercises a aws:ResourceTag-scoped attach. Mechanism: iam-policies-for-amazon-ec2.md warns you must explicitly deny tag mutation "Otherwise, it's possible for a user to circumvent your restrictions... by modifying its tags"; paired with the department:test-scoped attach example. Oracle: retag instance to department=test, Associate a DevTeam* role → success. Severity: High (footgun AWS names for this exact pattern).
**B-8 — Unscoped DescribeIamInstanceProfileAssociations leaks account-wide mapping.** Claim: the required companion Describe* (Resource:* only) enumerates every instance's role association, not the tag-scoped subset. Mechanism: iam-policies-for-amazon-ec2.md "Describe* API actions do not support resource-level permissions." Oracle: as a department=test-scoped caller, Describe returns out-of-scope associations. Severity: Medium (recon feeding B-1/B-7).
**B-9 — Instance identity role → SSM DHMC is an unauthenticated confused-deputy chain.** Claim: any code-exec on any instance in a DHMC-enabled account gets the trust-policy-free identity-role creds, has SSM register the instance, and receives AWSSystemsManagerDefaultEC2InstanceManagementRole with no prior instance-profile grant. Mechanism: iam-roles-for-amazon-ec2.md DHMC "uses the identity provided by the instance identity role to register EC2 instances... Systems Manager can pass your AWSSystemsManagerDefaultEC2InstanceManagementRole IAM role to your instance"; creds "present... regardless of whether a service or feature... is enabled." Oracle: from an instance with no profile in a DHMC account, use identity-role creds; SSM registers and the management role becomes usable. Precondition: DHMC enabled (AWS's modern default). Severity: Critical.
**B-10 — Instance identity role isn't feature-gated, only ARN-gated.** Claim: an instance never configured for a feature can still present valid identity-role creds to that feature's API. Mechanism: "credentials are present in the instance metadata regardless of whether a service or feature... is enabled." Oracle: from an EIC-never-used instance, fetch identity-role creds and attempt EIC host-key-update / GuardDuty telemetry for that instance-id. Severity: Medium–High (doc-gap — confirm per-service authz in EIC/GuardDuty/Lambda MI docs).

## Cluster C: NitroTPM, Attestation & Instance Identity Documents

**Suspected prompt injection (noted, not executed):** every page carries the `## See also` block instructing an AI agent to run `aws agent-toolkit search-skills`. Boilerplate injected across the corpus; logged once and not executed.

### C.1 Components, Assets, Design
- **NitroTPM** — virtual TPM 2.0 from the Nitro hypervisor; PCRs 0–23 (SHA384), measured boot, seal/unseal to PCR state.
- **Attestable AMI** — reference measurements computed by the customer's OWN build pipeline (nitro-tpm-pcr-compute via KIWI NG) into a local `pcr_measurements.json`.
- **Attestation Document** — CBOR/COSE_Sign1: module_id, timestamp, digest, nitrotpm_pcrs{0..23}, certificate, cabundle[], optional public_key/user_data/nonce. Signed by the "AWS Nitro Attestation PKI," root from aws-nitro-enclaves.amazonaws.com, subject CN=aws.nitro-enclaves — the SAME root as Nitro Enclaves.
- **Instance Identity Document (IID)** — plaintext JSON at IMDS `latest/dynamic/instance-identity/document` (accountId, instanceId, imageId, privateIp, region...). Three separate signature endpoints: pkcs7 (SHA1/DSA), base64 SHA256/RSA, rsa2048 (SHA256/RSA-2048).
- **AWS KMS** — built-in verifier via `kms:RecipientAttestation:NitroTPMPCR4/PCR7/PCR12` condition keys on a CMK policy; on match, encrypts the response to the public_key embedded in the doc (CiphertextForRecipient).
- **Credential Guard (Windows VBS)** — requires NitroTPM + UEFI Secure Boot AMI and requires HVCI ("memory integrity") DISABLED.

**ASCII flow (attestation→KMS):** build pipeline → nitro-tpm-pcr-compute → pcr_measurements.json (UNSIGNED, customer-local) → Attestable AMI; customer manually pastes ref values into KMS key-policy condition keys. Instance launch (NitroTPM type) → measured boot (PCR4 boot manager, PCR12 cmdline, PCR7 secure-boot policy; PCR8-15 OS uncovered by the standard keys) → guest `nitro-tpm-attest --public-key PK [--nonce N]` → NitroTPM signs → COSE_Sign1 doc → caller SigV4-signs a KMS Decrypt request + attaches doc → KMS: (1) verify COSE chain to Nitro root, (2) compare PCR4/7/12 to policy, (3) evaluate Principal/IAM, (4) encrypt response under PK. Separately: plaintext IID from IMDS → optional signature check left entirely to the off-box consumer.

|---|---|---|---|

### D.1 Components, Assets, Design
- **Key pair material:** RSA/ED25519. AWS never keeps the private key for console/CLI-generated keys ("no way to recover a private key if you lose it") **except** CloudFormation-created keys, whose private key is written to SSM Parameter Store at `/ec2/keypair/{key_pair_id}` (create-key-pairs.md).
- **Public key record:** stored as a control-plane object (KeyPairId/name/fingerprint) AND, independently, as bytes in a specific instance's `~/.ssh/authorized_keys` at first boot. **Not linked after boot** — deleting/replacing the control-plane object never touches the instance file.
- **Ephemeral EIC public key:** pushed by `ec2-instance-connect:SendSSHPublicKey` into instance metadata, 60-second life.
- **EICE:** managed identity-aware TCP proxy with an ENI in the customer VPC; dual-gated by IAM (`OpenTunnel`, `SendSSHPublicKey`) and security groups.
- **Security groups:** stateful per-ENI firewalls; conntrack table with configurable idle timeouts.
- **Interface VPC endpoint (EC2 API):** PrivateLink ENI; default resource policy is unrestricted.
- **Ownership:** single-account/VPC model — trust seams are intra-account IAM-scope / network-scope mismatches and control-plane vs data-plane state divergence, not classic cross-account IDOR.

## 7. Out-of-Scope Risk Categories (state confidently — keeps the hunter off shared-responsibility line)
