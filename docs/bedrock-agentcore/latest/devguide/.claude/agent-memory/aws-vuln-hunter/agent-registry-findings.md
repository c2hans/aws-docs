AWS **Agent Registry** live-tested 2026-09-04 (run vh-run-id 2026-09-04-1). Control plane `agent-registry-control` (15 ops: Create/Get/Update/Delete Registry[Record], UpdateRegistryRecordStatus, Submit...ForApproval), data plane `agent-registry` (Search/List/BatchGet DiscoverableRegistryRecord — **no InvokeRegistryMcp exists**). Multi-tenant MCP/agent/skill catalog.

**Why this matters:** the upstream recon plan's boundaries mostly HOLD; don't re-run the refuted ones. Record what was confirmed vs refuted so a future pass targets only the residuals.

- **SSRF (descriptor `fromUrl`) — CONFIRMED but bounded.** AWS-managed compute fetches caller-supplied `https://` URLs and reflects the target's HTTP status/error into `GetRegistryRecord.statusReason` (blind-SSRF oracle, sink "service fetches your link"). BUT: IP-literal URLs rejected at validation; hostnames resolving to non-public IPs rejected at fetch time ("resolves to a non-public IP address"); `iam:PassRole` enforced synchronously (cross-account role → AccessDenied). Egress is **public-only** → low/informational, no metadata/cross-tenant reach.
- **IDOR (LEAD 4) — REFUTED.** Cross-account full-ARN → 403 (existing AND non-existent both 403, no ID-enumeration oracle); cross-format "my-registry + foreign-record-ARN" caught by explicit `Registry and record ARN account mismatch`; bare-id cross-account → 404 identical to non-existent. Clean.
- **Curation/state-machine (LEAD 5) — REFUTED.** Forcing internal states (CREATING/CREATE_FAILED/UPDATING) → `Invalid target status`; illegal transitions rejected by a real state machine; cross-tenant writes → 403. Residual: same principal can submit→approve (no submitter-vs-approver condition key) = operator IAM-granularity note, not a service break.
- **Data-plane dual-auth (LEAD 3) — REFUTED/N-A.** No registry resource-policy API exists (so the doc'd "single-Deny fail-open" has no surface). Data-plane discovery is registry-scoped and IAM-enforced cross-account (403/404).
- **Stored injection (LEAD 6) — primitive CONFIRMED, sink untestable.** displayName/description/descriptor `data` stored & returned **verbatim** (incl. `<script>`/prompt-injection) via control+data planes. Downstream LLM (Amazon Quick connector) / curator-console XSS inferred from docs only.
- **Provenance forgery (LEAD 7) — structurally REFUTED.** No `provenance`/`createdByAutoDetection` field exists in this API version.
- **PrivateEndpointOverride (LEAD 2) — REFUTED for descriptor fetch.** It's referenced only by `CustomJWTAuthorizerConfiguration`, not the descriptor path.
- **T-NEW-JWT-SSRF (escalation pass 2026-09-04 — SETTLED: internal reach STILL-INSUFFICIENT, strongly leaning REFUTED).** CUSTOM_JWT `discoveryUrl` IS fetched server-side (fetches arbitrary public HTTPS I control: valid OIDC canary -> registry READY; public 404 -> `Failed to fetch discovery document from:<url>`). Validation inconsistency real: JWT path accepts IP-literal/link-local URLs at API-create where descriptor path rejects them. BUT fetch-layer: forced HTTPS(:443) + timing/error-string differential across link-local(literal+rebind), RFC1918(10.11.12.13), loopback(127.0.0.1), public-blackhole(192.0.2.10 TEST-NET), NXDOMAIN — ALL internal/unreachable targets fail FAST (~3-4.6s) with identical generic `OIDC discovery endpoint is not valid`, INDISTINGUISHABLE from a public-unreachable IP. Only genuinely-connected public hosts emit the distinct `Failed to fetch discovery document` (connected) oracle; NO internal target ever did, and NO content/creds/metadata were EVER returned (no stop-line crossed). Loopback also fast-failed => no localhost HTTP connection. Unprovable sliver: an internal service listening on :443 — cannot test without targeting real AWS-internal endpoints (out of bounds). Net: bounded public-egress SSRF only; no demonstrated internal reach. Don't re-run without a NEW oracle (e.g. an attacker-controlled responder on the fleet's own network, which isn't available here).
- **Env quirks for re-runs:** per-account registry quota = **10** (delete aggressively, hit it during batch testing). Registry create->READY/FAILED async workflow ~60-70s for success, ~3-5s for fast failures. Multiple concurrent vh-runs share the accounts (saw run-2/-3 tagged registries) — ALWAYS filter teardown by your own vh-run-id tag; never delete another run's resources.
