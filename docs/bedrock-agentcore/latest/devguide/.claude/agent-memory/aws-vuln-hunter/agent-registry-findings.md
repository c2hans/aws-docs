AWS **Agent Registry** live-tested 2026-09-04 (run vh-run-id 2026-09-04-1). Control plane `agent-registry-control` (15 ops: Create/Get/Update/Delete Registry[Record], UpdateRegistryRecordStatus, Submit...ForApproval), data plane `agent-registry` (Search/List/BatchGet DiscoverableRegistryRecord — **no InvokeRegistryMcp exists**). Multi-tenant MCP/agent/skill catalog.

**Why this matters:** the upstream recon plan's boundaries mostly HOLD; don't re-run the refuted ones. Record what was confirmed vs refuted so a future pass targets only the residuals.

- **SSRF (descriptor `fromUrl`) — CONFIRMED but bounded.** AWS-managed compute fetches caller-supplied `https://` URLs and reflects the target's HTTP status/error into `GetRegistryRecord.statusReason` (blind-SSRF oracle, sink "service fetches your link"). BUT: IP-literal URLs rejected at validation; hostnames resolving to non-public IPs rejected at fetch time ("resolves to a non-public IP address"); `iam:PassRole` enforced synchronously (cross-account role → AccessDenied). Egress is **public-only** → low/informational, no metadata/cross-tenant reach.
- **IDOR (LEAD 4) — REFUTED.** Cross-account full-ARN → 403 (existing AND non-existent both 403, no ID-enumeration oracle); cross-format "my-registry + foreign-record-ARN" caught by explicit `Registry and record ARN account mismatch`; bare-id cross-account → 404 identical to non-existent. Clean.
- **Curation/state-machine (LEAD 5) — REFUTED.** Forcing internal states (CREATING/CREATE_FAILED/UPDATING) → `Invalid target status`; illegal transitions rejected by a real state machine; cross-tenant writes → 403. Residual: same principal can submit→approve (no submitter-vs-approver condition key) = operator IAM-granularity note, not a service break.
- **Data-plane dual-auth (LEAD 3) — REFUTED/N-A.** No registry resource-policy API exists (so the doc'd "single-Deny fail-open" has no surface). Data-plane discovery is registry-scoped and IAM-enforced cross-account (403/404).
- **Stored injection (LEAD 6) — primitive CONFIRMED, sink untestable.** displayName/description/descriptor `data` stored & returned **verbatim** (incl. `<script>`/prompt-injection) via control+data planes. Downstream LLM (Amazon Quick connector) / curator-console XSS inferred from docs only.
- **Provenance forgery (LEAD 7) — structurally REFUTED.** No `provenance`/`createdByAutoDetection` field exists in this API version.
- **PrivateEndpointOverride (LEAD 2) — REFUTED for descriptor fetch.** It's referenced only by `CustomJWTAuthorizerConfiguration`, not the descriptor path.
- **T-NEW-JWT-SSRF (escalation pass 2026-09-04 — SETTLED: internal reach STILL-INSUFFICIENT, strongly leaning REFUTED).** CUSTOM_JWT `discoveryUrl` IS fetched server-side (fetches arbitrary public HTTPS I control: valid OIDC canary -> registry READY; public 404 -> `Failed to fetch discovery document from:<url>`). Validation inconsistency real: JWT path accepts IP-literal/link-local URLs at API-create where descriptor path rejects them. BUT fetch-layer: forced HTTPS(:443) + timing/error-string differential across link-local(literal+rebind), RFC1918(10.11.12.13), loopback(127.0.0.1), public-blackhole(192.0.2.10 TEST-NET), NXDOMAIN — ALL internal/unreachable targets fail FAST (~3-4.6s) with identical generic `OIDC discovery endpoint is not valid`, INDISTINGUISHABLE from a public-unreachable IP. Only genuinely-connected public hosts emit the distinct `Failed to fetch discovery document` (connected) oracle; NO internal target ever did, and NO content/creds/metadata were EVER returned (no stop-line crossed). Loopback also fast-failed => no localhost HTTP connection. Unprovable sliver: an internal service listening on :443 — cannot test without targeting real AWS-internal endpoints (out of bounds). Net: bounded public-egress SSRF only; no demonstrated internal reach. Don't re-run without a NEW oracle (e.g. an attacker-controlled responder on the fleet's own network, which isn't available here).
## 2026-09-16 re-run (vh-run-id 2026-09-16-1) — NEW 2026-09-16-sync fields (provenance/autodetect/org/KMS/MCP)
The 2026-09-16 docs sync added `provenance`, `createdByAutoDetection`, `createdBy`, `autoDetectionConfiguration{scope=ORGANIZATION,enabled}`, `encryptionConfiguration.kmsKeyArn`, `WorkloadIdentityDetails`, and a real MCP invoke endpoint. All fields NOW EXIST in the deployed `agent-registry-control` 2025-12-01 model. Both test principals are full `AdministratorAccess` (`Action:*`). Results:
- **AREA 1 provenance / createdByAutoDetection forgery — REFUTED (guard holds).** Create+Update both reject a caller-supplied `provenance` (lowercase, model wire-name) with `ValidationException: provenance cannot be set by the caller`. Wire-variant probe (inject post-serialization via `before-sign` hook, set `request.data` not `request.body`): keys `Provenance`/`PROVENANCE` and output-only fields `createdByAutoDetection:true`/`createdBy:"<foreignacct>"` are ACCEPTED-200 but SILENTLY DROPPED — rest-json parse is case-sensitive; readback shows `provenance=null`, `createdByAutoDetection=None`, `createdBy` server-derived to the caller's own acct (NOT the injected value). Nested-under-descriptors also dropped. No forgery, no cross-acct sourceId spoof, no trust-flag spoof.
- **AREA 2 org-scope auto-detection authZ — REFUTED (onboarding guard).** CreateRegistry `scope=ORGANIZATION` (enabled true OR false) → `ValidationException: The caller's AWS Organization is not onboarded to auto-detection. Enable trusted access...`. Identical string for both accounts (both standalone, `organizations:DescribeOrganization`=AccessDenied) → NO enumeration oracle. A fully-ACTIVE cross-account org pull is unreproducible here (no onboarded org); residual for an org-enabled env.
- **AREA 3 RAM cross-account share — REFUTED (tiers enforced, revocation complete).** RAM supports resource type `agent-registry:Registry` w/ 4 managed perms (ReadOnly / Consumer[+InvokeRegistryMcp] / Publisher / Admin). Cross-acct access requires the FULL ARN (bare id → 404 in caller's own acct; note DeleteRegistryRecord is idempotent-200 on a not-found bare id — that's not a cross-acct write). ReadOnly consumer: reads 200, CreateRecord/DeleteRecord → 403 "no resource-based policy allows...", DeleteRegistry → 403 "Cross-account access is not allowed for operation: DeleteRegistry". Foreign admin (`*`) still blocked without the share = resource-policy is the limiter. Revocation: reads stay 200 during RAM `DISASSOCIATING` (~80s eventual-consistency) then flip to AccessDenied exactly when association reaches `DISASSOCIATED` — complete, no stale window.
- **AREA 4 legacy `bedrock-agentcore:*` namespace parity — REFUTED (legacy control already closed).** Legacy twins: control `bedrock-agentcore-control` (signingName bedrock-agentcore, older 2023-06-05 schema, NO provenance field), data `bedrock-agentcore:SearchRegistryRecords`. ALL legacy CONTROL registry actions (Get/List/Create/Delete Registry[Record]) → `AccessDeniedException` SERVICE-SIDE even for a `*` admin (denial is service, not IAM — migration cutoff effectively enforced). Legacy DATA-plane search authorizes but sees a DISJOINT backend (`ResourceNotFoundException` for new registries). No parity gap, no legacy-provenance-injection path (create denied).
- **AREA 5 CMK cross-account / kms:ViaService confused-deputy — REFUTED (caller-access check).** Same-acct key → READY. Cross-acct key with NO grant → `ValidationException: Caller lacks access to the KMS key. KMS ... AccessDeniedException`. Cross-acct key whose policy grants the caller ACCOUNT → registry READY (so docs' "same account and Region required" is NOT structurally enforced — only a caller-access check; consensual, informational doc inaccuracy). Cross-acct key granting ONLY the `agent-registry` SERVICE principal (not the caller acct) → STILL "Caller lacks access" → the service checks KMS AS THE CALLER, never lends its own identity. No confused deputy.
- **AREA 6 / T-NEW-MCP — MCP invoke endpoint EXISTS now (was absent in prior hunt), authz SOLID.** Real endpoint `https://agent-registry.<region>.api.aws/registry/<id>/mcp`, SigV4 signingName `agent-registry`, JSON-RPC 2025-11-25, tools search/list/batch_get. IAM action `agent-registry:InvokeRegistryMcp` + `GetDiscoverableRegistryRecord` exist in RAM perms but have NO modeled SDK op (MCP is HTTP/JSON-RPC). Tests: discoverability gate holds (DRAFT record → `RESOURCE_NOT_FOUND`, only APPROVED returned); cross-acct invoke without share → 403 "no resource-based policy allows agent-registry:InvokeRegistryMcp"; SDK `BatchGetDiscoverableRegistryRecord` `entries` capped at len 1; recordIds resolved WITHIN the entry/URL registry (reg1 share + reg2 recordId → reg2 `RESOURCE_NOT_FOUND`); direct query of unshared reg2 → `AccessDeniedException`. No cross-tenant/cross-registry IDOR.
- **Net 2026-09-16:** every new-field boundary HOLDS. No confirmed vuln. Only informational: (a) provenance guard is exact-lowercase-key presence check w/ benign unknown-field-drop on case variants; (b) KMS same-account doc claim not structurally enforced (consensual cross-acct allowed); (c) `InvokeRegistryMcp`/`GetDiscoverableRegistryRecord` IAM actions unmodeled in SDK. Botocore is now **1.43.95** (env updated from 1.43.73).

- **Env quirks for re-runs:** per-account registry quota = **10** (delete aggressively, hit it during batch testing). Registry create->READY/FAILED async workflow ~60-70s for success, ~3-5s for fast failures. Multiple concurrent vh-runs share the accounts (saw run-2/-3 tagged registries) — ALWAYS filter teardown by your own vh-run-id tag; never delete another run's resources.
