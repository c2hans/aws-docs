# Alarms

Innovation Sandbox deploys Amazon CloudWatch Alarms to alert you to operational issues. By default, none of the alarms have notification actions attached. To receive notifications, subscribe an Amazon SNS topic to the alarm. For guidance, refer to [Acting on alarm changes](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Acting_Alarm_Changes.html).

## Alarms deployed by the solution
<a name="solution-alarms"></a>

| Alarm | Fires when | What to do |
| --- | --- | --- |
|  **Tag resource failure**  | One or more `Organizations:TagResource` calls fail within an hour (across lease approval, cleanup, ejection, or cost-report-group updates). | Check Amazon CloudWatch Logs for entries with `logDetailType` set to `TagResourceFailed`. Common causes: the account reached the 50-tag limit (`TagSpaceExhausted`) or a transient API error (`ApiError`). |
|  **Tag activation workflow failure**  | The tag activation Step Functions workflow fails or times out without successfully activating the ISB cost allocation tag keys. | The ISB tag keys may not be active in the billing console. See [Manually activating cost allocation tags](troubleshooting.md#manually-activating-cost-allocation-tags). |
|  **Assignment processing DLQ**  | One or more lease assignment operations (granting or revoking IAM Identity Center account access) fail after all retries and land on the dead-letter queue. | Investigate the messages on the `Isb-<namespace>-AssignmentProcessingDLQ` SQS queue. Common causes: IAM Identity Center API throttling, permission set not found, or account not in the organization. |
|  **Observability link missing**  | TokenPoll successfully lists links attached to the managed Region’s hub sink but finds no link from a token-monitored lease’s sandbox account during two of three ten-minute periods. | Search the Compute stack’s ISB log group for messages beginning `Observability Link Missing:`. Use the `leaseId`, `awsAccountId`, and `region` fields to identify the failed link. See [Observability link missing in a managed Region](troubleshooting.md#observability-link-missing). |
|  **Observability Region unreadable**  | TokenPoll cannot list attached OAM links or read Bedrock token metrics in a managed Region during two of three ten-minute periods. | Search the Compute stack’s ISB log group for messages beginning `Observability Region Unreadable:`. Use the `region`, `leasesAffected`, `errorName`, and `error` fields to identify the failed operation and cause. See [Observability Region unreadable](troubleshooting.md#observability-region-unreadable). |
|  **Cache sync failure**  | The Principal Cache Sync Lambda function reports errors in two consecutive one-hour periods. Errors can come from principal synchronization, permission-set reconciliation, or event-driven permission-set updates. | Review the function’s logs in the Hub account. See [Investigating cache synchronization failures](troubleshooting.md#cache-sync-failure). |
|  **SES send failure**  | One or more notification emails can’t be sent through Amazon SES within an hour. | Check Amazon CloudWatch Logs for entries with `notificationMetricType` set to `NotificationDeliveryFailed` and `channel` set to `SES`. For common causes, see [Notifications are not delivered](troubleshooting.md#notifications-not-delivered). |
|  **SNS publish failure**  | One or more notifications can’t be published to the SNS integration topic within an hour. | Check Amazon CloudWatch Logs for entries with `notificationMetricType` set to `NotificationDeliveryFailed` and `channel` set to `SNS`. Common causes are changes to the topic’s access policy or to the Compute stack’s KMS key policy. The failed message isn’t delivered to subscribers. |
|  **WAF blocked requests**  | AWS WAF blocks one or more requests to the Innovation Sandbox API. | Review the AWS WAF logs to determine whether the blocked requests are legitimate. A spike may indicate misconfigured WAF rules blocking valid users, or it may indicate an attack being correctly mitigated. |
|  **Sandbox Spaces message DLQ**  | One or more chat messages are on the `ISB-<namespace>-SandboxAgentDLQ.fifo` dead-letter queue in a 5-minute period. A message moves there after three failed processing attempts, and the agent doesn’t answer it. Common causes: the Worker Lambda function crashed or was throttled. | Review the errors and throttles of the Worker Lambda function. The function has a reserved concurrency of 10, so Lambda throttles messages beyond 10 at a time. The agent might have run commands before the failure. Before you purge the queue, use the Worker logs in the Compute stack’s ISB log group and the resources in the affected sandbox account to find out which commands ran. Then purge the queue, and tell the affected users which changes the agent made, so they can decide whether to send their messages again. Don’t redrive the queue, because a redrive can run the same commands again. |
|  **Sandbox Spaces memory write failure**  | The agent runtime fails to save a turn to AgentCore Memory one or more times within 5 minutes. That turn is missing from the conversation history. | Search the agent runtime log group `/aws/bedrock-agentcore/runtimes/<runtime-id>-DEFAULT` for entries with `message` set to `MemoryWriteFailure`. For the log group name, see [Log retention strategy](monitoring-logs-and-tracing.md#log-retention-strategy). |
|  **Sandbox Spaces memory cleanup DLQ**  | Long-term memory cleanup for a terminated lease fails after all retries, and the message lands on the `Isb-<namespace>-SandboxAgentMemoryCleanupDLQ.fifo` SQS queue. The long-term memory records of the lease stay, and they don’t expire. | Search the Compute stack’s ISB log group for entries with `logDetailType` set to `MemoryCleanupFailed`. Use the `leaseId` and `phase` fields to identify the failed cleanup. Fix the cause, and then redrive the dead-letter queue. Cleanup is safe to run again. |
|  **Sandbox Spaces turn metering failure**  | Three or more turns in 15 minutes finish without token usage reported by the agent runtime. The Worker then charges an estimate based on the length of the message. | Search the Compute stack’s ISB log group for entries with `logDetailType` set to `AgentTurnMeteringFailed`. The usage estimates for these turns are approximate. This failure doesn’t affect budget enforcement by the token poll. |
|  **Sandbox Spaces usage recording failure**  | One or more times in 5 minutes, the Worker can’t write the usage of a turn after all retries, so that turn is missing from the per-user usage record. Budget enforcement by the token poll isn’t affected. | Search the Compute stack’s ISB log group for entries with `logDetailType` set to `SandboxSpacesUsageRecordingFailed`, and check the Sandbox Spaces usage table for throttling. |

Both notification alarms use the `NotificationFailed` metric in the `ISB/Notifications` namespace. The `ISBNamespace` and `Channel` dimensions identify the deployment and notification channel (`SES` or `SNS`).

You can configure additional alarms based on metrics reported by the different services within the solution. For example, you might alarm on Lambda error rates, DynamoDB throttling, or SQS dead-letter queue depth.
