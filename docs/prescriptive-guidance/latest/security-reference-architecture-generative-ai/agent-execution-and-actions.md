# Agent execution and actions

An agent can use tools to change records, run code, initiate transactions, or control a device. For example, a service-desk agent might search tickets and propose closing one. The application must authorize the closure, validate the target ticket and parameters, and record the result. Operators also need a way to stop execution or recover from an incorrect or incomplete action.

The following controls cover agent execution and action-capable tools. They also apply to fixed workflows that can make the same changes. Use them with the applicable [model inference](https://apg-library.amazonaws.com/edit/a349f18f-a9fd-43a3-9a48-27534bf6412a#contents?section=model-inference), [data and retrieval](https://apg-library.amazonaws.com/edit/a349f18f-a9fd-43a3-9a48-27534bf6412a#contents?section=data-and-retrieval), and [read-only tool access](https://apg-library.amazonaws.com/edit/a349f18f-a9fd-43a3-9a48-27534bf6412a#contents?section=read-only-tool-access) controls.

## Security considerations
<a name="security-considerations"></a>
+ Injected instructions can cause an agent to misuse otherwise valid tool permissions.
+ Reused sessions or delegated credentials can expose another user's data and authority.
+ Repeated calls, retries, and resumed tasks can exceed spending or operational limits.
+ An agent that can approve its own request, alter approved parameters, or bypass the executor can perform changes outside the intended approval.

## Infrastructure security
<a name="infrastructure-security"></a>

### Isolate agent and tool execution
<a name="isolate-agent-and-tool-execution"></a>

[Amazon Bedrock AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-permissions.html) provides an execution environment with session isolation for hosted agents. The application team configures a dedicated execution role and the network access the workload needs. Bind each session to the authenticated user and reject attempts to resume another user's session, as described in [Runtime security best practices](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html). Service-level session isolation does not establish this ownership.

Set per-user request limits and task limits for duration, model tokens, tool calls, and spending. Measure [representative successful tasks](https://aws.amazon.com/blogs/publicsector/what-does-it-cost-to-answer-one-question-measuring-per-request-cost-in-agentic-workloads/) by task class, then choose limits that meet the required completion rate and maximum task cost. Test difficult legitimate tasks and runaway or retry cases. When a limit is reached, stop additional model and tool work and return an explicit result, or require a separately authorized continuation.

Use [Runtime session limits](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-lifecycle-settings.html) and, when using [Amazon Bedrock AgentCore harness](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-vs-runtime.html), its invocation limits. Use [Amazon Bedrock AgentCore Gateway identity rate limits](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-rate-limits.html) to constrain tool traffic, accounting for their documented fail-open behavior. [Enforce cumulative task budgets outside the agent's control loop](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost07-bp01.html), in trusted application code across retries and resumed sessions. A new invocation must not reset the task's spending authority.

[Amazon Bedrock AgentCore Code Interpreter](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/code-interpreter-tool.html) and [Amazon Bedrock AgentCore Browser](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/browser-tool.html) provide options for managed code execution and browsing. Choose each service's network mode according to its supported configuration. Sandboxing limits process interaction, while credentials and network access determine the resources code can reach from inside the sandbox. Restrict access to data and destinations to limit the consequences of compromised agent code.

For agents and tools on [Amazon Elastic Compute Cloud (Amazon EC2)](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/iam-roles-for-amazon-ec2.html), [Amazon Elastic Container Service (Amazon ECS)](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html), [Amazon Elastic Kubernetes Service (Amazon EKS)](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html), or [AWS Lambda](https://docs.aws.amazon.com/lambda/latest/dg/lambda-intro-execution-role.html), apply the relevant image, patching, isolation, and vulnerability-management controls from the inference baseline. Keep tool permissions separate where actions have different consequences. A single broadly privileged runtime increases the scope of what an injected instruction can influence.

Protect public application APIs with [AWS WAF](https://docs.aws.amazon.com/waf/latest/developerguide/how-aws-waf-works-resources.html) on supported front ends. For inspected [Amazon Virtual Private Cloud (Amazon VPC)](https://docs.aws.amazon.com/vpc/latest/userguide/what-is-amazon-vpc.html) egress, route the intended paths through [AWS Network Firewall](https://docs.aws.amazon.com/network-firewall/latest/developerguide/stateful-rule-groups-domain-names.html) and restrict destinations to reviewed dependencies. Apply the DNS filtering baseline to agent and tool VPCs. Enforce tool authorization independently of these network controls, and verify alternate network and invocation paths as part of the design.

### Configure AgentCore harness
<a name="configure-agentcore-harness"></a>

AgentCore harness runs a managed agent loop inside Runtime. Apply the Runtime isolation and execution-role controls, and review the following configuration:
+ Approve [model providers, endpoints, and credential sources](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-models.html). Check guardrail and logging coverage for the selected endpoint and API, and approve data handling before using an external provider.
+ Validate [caller-supplied configuration](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html) before invocation. Model parameters can change routing, credentials, and Regions. Restrict model and skill overrides, and review skill instructions and scripts from approved [Amazon Simple Storage Service (Amazon S3)](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html) or Git sources.
+ Use inbound OAuth with bearer JSON Web Tokens (JWTs) when downstream tools need the user-scoped credentials from [Amazon Bedrock AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html). Signature Version 4 (SigV4) authentication does not propagate per-user identity through the harness.
+ Restrict direct commands and [interactive shells](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-command-shell.html) to approved operators. For shell access, scope [AWS Identity and Access Management (IAM)](https://docs.aws.amazon.com/IAM/latest/UserGuide/introduction.html) permissions for SigV4 callers and configure the inbound authorizer for bearer-token callers. Review the agent's built-in tool access separately.
+ Set [iteration, token, and time limits](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-operations.html) for each invocation and idle and lifetime limits for sessions. Validate caller overrides. Record harness invocation, command, and shell data events under `AWS::BedrockAgentCore::Runtime` in [AWS CloudTrail](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/enabling-cloudtrail-data-event-logging.html). Shell audit events do not contain terminal input or output.

### Design for containment and recovery
<a name="design-for-containment-and-recovery"></a>

Containment requires coordination between the application owner and the security team. The application owner should be able to disable a tool or agent, and the security team should have an agreed procedure to revoke access and preserve evidence. The procedure must account for active sessions, cached credentials, queued work, and in-progress transactions because blocking new requests might not stop work already running.

For [AWS Agent Registry records](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-record-lifecycle.html), reject a record to temporarily remove it from discovery during investigation; it can be approved again. Deprecation is permanent and cannot be undone. These catalog changes do not revoke access to the underlying tool or stop active sessions, so apply the service's containment controls as well.

Use [Amazon Inspector](https://docs.aws.amazon.com/inspector/latest/user/what-is-inspector.html) for supported compute and container scanning, and [AWS Systems Manager](https://docs.aws.amazon.com/systems-manager/latest/userguide/what-is-systems-manager.html) for approved maintenance and response on managed nodes. Restrict who can run automation and commands, scope their execution roles, and retain operation records. These services manage applicable customer compute; they do not give you access to the hosts underlying serverless AgentCore sessions.

Use the [AWS Security Reference Architecture (AWS SRA) for cyber forensics](https://docs.aws.amazon.com/prescriptive-guidance/latest/security-reference-architecture-cyber-forensics/introduction.html) to align evidence preservation with the organization's incident response architecture. Exercise the containment procedure in a controlled environment and define how to restore service safely.

Automate restoration only through a tested, preauthorized runbook with defined limits. Recheck the current state before acting; [AWS Config automatic remediation](https://docs.aws.amazon.com/config/latest/developerguide/setup-autoremediation.html) can use an outdated compliance snapshot. Restoring an approved endpoint version or enforcement setting can still interrupt work. Require approval when a response introduces permissions or behavior outside the approved baseline, exceeds the runbook's limits, or has uncertain effects on data or transactions.

## Identity and data security
<a name="identity-and-data-security"></a>

### Authorize downstream actions
<a name="authorize-downstream-actions"></a>

In the ticket-closing example, the requesting user and the agent's execution identity are distinct. The downstream system must determine whether the requested closure is permitted, using the originating user and the permissions delegated for the task. Signing in to the agent alone does not authorize the closure.

Dedicated IAM roles define workload permissions. [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html) provides credential brokering where required. Preserve the originating identity across delegated calls and verify which identity and permissions the downstream service uses to authorize the action. [Authenticate peer agents and authorize each delegated task](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec06-bp03.html) at the receiving boundary. Treat messages as untrusted input and restrict outgoing content to the recipient's permissions. Use [message signing](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec06-bp01.html) when integrity or proof of the originating agent must survive intermediaries.

[AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway.html) centralizes tool access. Use [Policy in Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html) to authorize production tool calls. Attach a policy engine to the gateway in `ENFORCE` mode and set each required policy's [enforcement mode](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-test-a-policy.html) to `ACTIVE`. Test rules against permitted and denied requests before release. `LOG_ONLY` mode records decisions without enforcing them. Restrict `bedrock-agentcore:UpdateGateway` to the release role because it can change the gateway to `LOG_ONLY` or remove its policy engine. Define permissions for the caller, requested tool, and permitted action context, and reject requests that lack the identity needed for authorization.

[Gateway policy evaluation](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/use-gateway-with-policy.html) applies to MCP tools. It does not restrict MCP prompts or resources; protect sensitive content exposed through those methods separately.

Use a Cedar tool authorization policy to scope a permit to a trusted caller claim, tool, and gateway. Review all policies for additional permissions, then test missing claims, a different caller, and a different tool. Keep target permissions scoped and prevent alternate invocation paths from bypassing the enforcement point. Apply equivalent authorization in self-hosted tools and the shared IAM review controls.

### Limit permissions and protect stored context
<a name="limit-permissions-and-protect-stored-context"></a>

Grant the agent's normal execution role only the permissions for the resources and actions that its task needs, and keep administrative privileges separate. Protect credentials with [AWS Secrets Manager](https://docs.aws.amazon.com/secretsmanager/latest/userguide/intro.html) or the selected identity service, restrict secret readers, and make rotation part of tool lifecycle management.

Conversation memory and tool results can contain sensitive information. When the application uses [Amazon Bedrock AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-create-a-memory-store.html) for persistent context, configure its authorization and retention controls. [Validate content before it enters or is reused from memory](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec01-bp02.html), including tool results, agent messages, and consolidated records. Apply sensitive-data controls to these paths, retain source provenance, and check memory integrity before use. [Quarantine corrupted records and invalidate dependent context](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec01-bp03.html) before resuming affected tasks. Configure [AWS Key Management Service (AWS KMS)](https://docs.aws.amazon.com/kms/latest/developerguide/overview.html) key policies for resources that accept customer managed keys, and use Transport Layer Security (TLS) for network connections. Runtime, memory, gateway, and log resources have their own encryption options, so review each one individually.

For payment workflows using [Amazon Bedrock AgentCore payments](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments.html), establish the permitted spending scope, expiry, and approval requirements before enabling transactions. Validate the intended merchant and payment destination in trusted application code; do not assume that a spending limit enforces a destination allow list. The x402 payment protocol does not replace the organization's payment authorization policy. Apply the same principle to account changes, external messages, and other consequential operations: define the authority at the target boundary. Model instructions do not enforce that boundary. Payment-capable agents have higher commercial and regulatory impact. Follow the [Amazon Bedrock AgentCore payments security best practices](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-security-best-practices.html) and the relevant human-in-the-loop workflow to help confirm that required security controls are in place. The AWS blog post [Technical deep dive: AgentCore Payments and innovation in agentic commerce](https://aws.amazon.com/blogs/machine-learning/technical-deep-dive-agentcore-payments-and-innovation-in-agentic-commerce/) describes measures to help keep agent spending within defined limits.

## AI application security
<a name="ai-application-security"></a>

### Validate actions outside the model
<a name="validate-actions-outside-the-model"></a>

The model proposes an action; a separate component authorizes and executes it. Expose tools with defined operations, validated parameters, and explicit limits on what they can change. For actions that require human approval, use an independent approval workflow:

1. Record the authenticated requester, exact operation, target resource, parameters, and expiry.

1. Present that request to an authorized approver. Record the authenticated approver, decision, time, and exact request approved. Protect this record from the agent and its tools.

1. At execution, verify that approval covers the unchanged request, remains valid, and has not already been used. Recheck the caller's current authorization.

1. Record the result and reconcile partial failure before retrying.

Determine approval requirements in trusted policy code. Present [independent policy and manipulation warnings](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec07-bp02.html) with the exact request. For the highest-risk actions, require [independent reviewers](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec07-bp03.html) and keep disagreements or expired requests blocked. [Monitor queue age, review time, and decision reversals](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec07-bp01.html); escalate overload and keep requests blocked until review is complete.

An [AWS Step Functions Standard workflow with a callback task](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html#connect-wait-token) can wait for the approval service before invoking the executor. Use a supported callback integration, such as the [Amazon Simple Queue Service (Amazon SQS) callback example](https://docs.aws.amazon.com/step-functions/latest/dg/callback-task-sample-sqs.html); the optimized AgentCore integration cannot use `.waitForTaskToken`. Restrict access to the task token. Explicitly deny `states:SendTaskSuccess` to the agent role and exclude callback operations from roles and tools it can invoke. Callback actions require `Resource: "*"`; the [AgentCore Step Functions connector](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-step-functions.html) cannot restrict them to its configured state machine. Grant completion to the independent approval service only. Test self-approval through every reachable path and completion of an unchanged, authorized request. The application implements the approval binding and replay checks above.

Apply [Amazon Bedrock Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) to the relevant content paths, alongside tool schema validation and target authorization. Where responses must agree with explicit business rules, use [Automated Reasoning checks](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-automated-reasoning-checks.html) and handle their findings in the application before proceeding. A content filter is not an action permission check. Evaluate sequences of actions as well as individual calls: several permitted operations can combine into an unintended outcome. If you use [temporal policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-temporal.html) in AgentCore, review its session and deployment requirements separately from point-in-time Cedar rules.

### Govern configuration changes
<a name="govern-configuration-changes"></a>

Review changes to prompts, model choices, tools, skills, and orchestration as production changes. Require curator approval before making [Registry records](https://dp8l2mfblnx2f.cloudfront.net/architecture/#catalog-approved-agents-and-tools) available for production discovery. Use [Amazon EventBridge notifications](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-eventbridge.html) to connect submissions to the review workflow, which approves or rejects the record after its checks. [Editing an approved record](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry-record-lifecycle.html) creates a draft while the previous approved revision remains discoverable. Review the new revision before approving it.

Evaluate and approve changes proposed by [Amazon Bedrock AgentCore optimization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/optimization.html) before adoption. Preserve the configuration version associated with an action so investigators can reconstruct its context.

Point a named production [AgentCore Runtime endpoint](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agent-runtime-versioning.html) to an approved immutable runtime version. The `DEFAULT` endpoint advances when a new version is created. Restrict endpoint updates to the release role and detect changes to an unapproved version. [Existing microVM sessions retain their original code](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-troubleshooting.html); assess active sessions separately when rolling back or containing an incident.

Review custom orchestration and action-executor code through the [application code review workflow](https://dp8l2mfblnx2f.cloudfront.net/answers/ai-applications/#review-custom-application-code-with-aws-continuum). Include approval callbacks, credential handling, and retry logic. Before releasing a vulnerability fix, test that an agent cannot approve its own action, substitute another user's identity, or repeat an action beyond its authorized scope. Verify that containment and recovery still work.

Apply the [shared configuration checks](https://dp8l2mfblnx2f.cloudfront.net/architecture/#keep-required-settings-enabled) to runtime versions, Gateway policy enforcement, and tool configuration. Configure remediation as a separate, permission-scoped workflow; a compliance result alone does not prevent an agent action.

### Correlate actions and security findings
<a name="correlate-actions-and-security-findings"></a>

Use [Amazon Bedrock AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html) and [Amazon CloudWatch](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/WhatIsCloudWatch.html) to correlate requests, tool calls, and outcomes. Custom code-based evaluators in [Amazon Bedrock AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluators.html) can check captured traces against application rules. Test authorization and recovery in the application as well; sampled traces and quality scores do not establish that access controls work. [AWS Continuum for penetration testing](https://docs.aws.amazon.com/securityagent/latest/userguide/what-is.html) can test application endpoints within an approved scope. Use [separate test memory, tool endpoints, and permissions](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec09-bp04.html) to contain test effects. Supplement automated tests with periodic [human-led exercises](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec07-bp05.html) covering memory poisoning, delegated prompt injection, and approval bypass. Use the results to update detections, response procedures, and regression tests. For a sample implementation of controls such as validating content before memory writes, scoping namespaces to the verified actor, and periodically reviewing and purging memory to help defend against memory poisoning, see the AWS Security Blog post [**Help defend against memory poisoning in Amazon Bedrock AgentCore with multi-layer write validation**](https://aws.amazon.com/blogs/security/help-defend-against-memory-poisoning-in-amazon-bedrock-agentcore-with-multi-layer-write-validation/).

Enable [AWS CloudTrail data events for AgentCore Gateway](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/enabling-cloudtrail-data-event-logging.html) when gateway invocation records are required; CloudTrail does not capture these events by default. Combine supported CloudTrail API events with application traces that record the initiating user, event, schedule, or agent, along with the session, tool and configuration versions, authorization decision, and downstream result. Enable trace propagation across agent and tool services. Preserve an [application correlation ID across asynchronous boundaries](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec05-bp02.html) where a new trace can start. Remove credentials and unneeded prompt or tool content before exporting telemetry. Protect log access and retention. Use [Amazon Athena](https://docs.aws.amazon.com/athena/latest/ug/what-is.html) for approved queries over evidence stored in S3 buckets, and restrict access to the relevant datasets and query results.

Apply the [shared detection controls](https://dp8l2mfblnx2f.cloudfront.net/architecture/#detect-threats-in-ai-workloads). [Baseline normal agent behavior](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentsec07-bp04.html), including data access, tool errors, and inter-agent call patterns, and investigate deviations. Keep application safety events in the tracing or monitoring pipeline unless a supported integration or explicit findings conversion sends them to the security workflow. Use [Amazon EventBridge](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-what-is.html) to route selected events to response workflows. Authenticate event producers, scope target permissions, and apply the [containment and recovery procedure](https://dp8l2mfblnx2f.cloudfront.net/acts/agents/#design-for-containment-and-recovery), including its limits on automatic remediation.

Use [AWS DevOps Agent](https://docs.aws.amazon.com/devopsagent/latest/userguide/about-aws-devops-agent.html) to investigate operational incidents across connected workload accounts and propose mitigation. Connect approved telemetry sources and scope investigation permissions to the workload. AWS DevOps Agent turns off [directed actions](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html) by default. Enable them only for approved response procedures; every directed action requires operator approval. Handle security incidents through the organization's incident response process and retain evidence using the [AWS Security Reference Architecture (AWS SRA) cyber forensics guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/security-reference-architecture-cyber-forensics/introduction.html).

## Design considerations
<a name="design-considerations"></a>
+ Human approval adds a review step, but the action still needs authorization and validation. Include the approval workflow in the architecture review.
+ A task can span several agents, tools, and downstream services. Assess permissions and data exposure across the complete sequence.
+ Some operations cannot be retried or reversed. Define how to reconcile incomplete work, compensate for completed changes where possible, and escalate failures.
+ Role and policy templates, guardrail policies, and logging standards reduce repeated design work. New models, data sources, tool permissions, or Regions still need review against the approved baseline.
+ Agree on who can stop the agent, who investigates its actions, and what evidence is required before it resumes operation.
