# ADVOPS02-BP05 Monitor partner connectivity health and traffic management effectiveness across your advertising network
<a name="advops02-bp05"></a>

 Advertising workloads depend on low-latency connectivity with tens to hundreds of external partners. Monitor the health, latency, and throughput of each partner connection in both your network and application. When traffic management modules such as rate limiting and request filtering are applied in the connectivity path, monitor their effectiveness to validate that controls work as intended and to distinguish between network-generated and application-generated responses.

 **Desired outcome:**
+  You have real-time, per-partner visibility into connection health at both the network and application layers, with latency anomaly detection measured in single-digit minutes rather than tens of minutes.
+  Your dashboards separate network-layer and application-layer metrics for rapid triage, and you can correlate connectivity issues with bid rate changes without cross-referencing disparate tools.
+  Your operations teams can distinguish responses generated by traffic management modules (rate limiters, filters) from responses generated by the bidder application, removing ambiguity in root cause analysis.

 **Common anti-patterns:**
+  Monitoring bid outcomes without monitoring the connectivity path, which obscures the root cause.
+  Treating network-generated no-bids (from filters or rate limiters) and application-generated no-bids (from bidder logic) as a single metric, hiding which component is dropping requests.
+  Relying solely on aggregate metrics across partners.
+  Deploying traffic management rules without A/B testing or holdback measurement.
+  Using application-layer latency percentiles as a proxy for connectivity-layer health.
+  Not accounting for RTB Fabric latency being reported in microseconds.
+  Alarming on a count of discovered endpoints as though it reported endpoint health.
+  Leaving a zero-threshold availability alarm on the default missing-data behavior.

 **Benefits of establishing this best practice:**
+  Proactive detection of partner connectivity degradation before it affects revenue.
+  Isolate whether issues originate in the connectivity path, at the partner endpoint, or within the bidder application.
+  Confirm that rate limiting and filtering rules produce the expected effect on traffic volume and bid outcomes.
+  Distinguish no-bids generated by traffic management modules from no-bids from bidder application logic.
+  Data-driven A/B testing of traffic management configurations using holdback percentages with correlated observability.

 **Level of risk exposed if this best practice is not established:** High

## Implementation guidance
<a name="implementation-guidance"></a>

 *Network observability* covers the connectivity path between your application and external partners, such as per-partner request volumes, forwarding latency, error rates, HTTP status-code distributions, and target endpoint health. These reveal connectivity-specific issues (partner endpoint failures, TLS handshake problems, network-path degradation) invisible to application monitoring.

 *Application observability* covers your bidder application's processing of requests that traverse the path, such as bid request volume, no-bid rates, timeout rates, server errors, throughput, and P90/P95/P99 latency. These reveal bidding-logic errors, database latency, and capacity constraints.

 Correlate network and application observability to identify which layer contains the issue. When traffic management modules filter or rate-limit at the network level, application observability reflects the expected reduction in traffic. If the network shows 95 percent of traffic filtered but the application shows no corresponding drop, you have a configuration or routing issue.

 If application timeout rates rise while network latency stays stable, the issue is internal to the bidder application. For traffic management modules, monitor filter hit rates (what percentage is filtered, by which rules), rate-limiter throttling (volume throttled above configured TPS), and network-layer no-bid responses (generated before requests reach the bidder). At the application level, monitor no-bid reason codes (targeting mismatch, budget exhaustion, pacing), the full no-bid attribution funnel, and holdback effectiveness for A/B testing.

 For workloads using [AWS RTB Fabric](https://docs.aws.amazon.com/rtb-fabric/latest/userguide/what-is-rtb-fabric.html), metrics publish automatically to the AWS/RTBFabric Amazon CloudWatch namespace with per-link granularity:
+  total-request-count
+  success-request-count
+  failure-request-count (Sum, per Link)
+  request-status-count (Sum, per Link and HttpStatusCode),
+  forwarding-latency
+  total-latency (Average, minimum, and maximum, per Link and Statistic, for P90/P95/P99)

 Both forwarding-latency and total-latency are reported in microseconds. Make sure dashboard axes, alarm thresholds, and anomaly-detection band widths account for the unit (a 100 ms threshold is configured as 100,000 microseconds). Several of these metrics, including the request counts and the filter and no-bid metrics, are emitted as multiple data points per minute, so an averaging statistic understates the true volume. The [dimensions reference](https://docs.aws.amazon.com/rtb-fabric/latest/userguide/monitoring-cloudwatch-dimensions.html) scopes GatewayId to the no-bid metrics, so gateway-based alarms are available only where a metric documents that dimension.

 Application log delivery for each link to [Amazon CloudWatch Logs](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/) is both a cost and coverage decision. Error records are low-volume and diagnostic, so capture them in full. Filter records scale with bid volume, so sample them. For workloads with agentic AI in the bid path, consider adding the Amazon Bedrock Agents Time-to-First-Token (TTFT) metric to composite-alarm logic for cross-layer latency correlation across the full bid cycle (network, application, and inference).

 Endpoint discovery and endpoint health are separate signals. target-ip-count reports "The number of target IP addresses discovered in your managed endpoints", which is an inventory count. healthy-target-ip-count reports "The number of target IP addresses that passed Health checks for Managed Endpoints and are receiving traffic", and it publishes only when health checks are enabled on Auto Scaling group managed endpoints. A fleet where every instance is discovered but fails its health check can return a discovery count at a normal value, so alarm on both metrics together (for more detail, see [Creating CloudWatch dashboards for RTB Fabric](https://docs.aws.amazon.com/rtb-fabric/latest/userguide/monitoring-cloudwatch-dashboards.html)).

 When health checks can't determine which resources are healthy, the system doesn't cut off traffic. Instead, it routes to every discovered instance.

### Implementation steps
<a name="implementation-steps"></a>

1.  **Inventory partner connectivity paths:** Identify every managed connectivity link and direct internet connection in your bid path. Document expected baseline latency and throughput per partner, and the failure modes that apply at each layer.

1.  **Instrument application-layer per-partner metrics:** Emit bid request count, no-bid count (reason codes distinguishing application-generated from network-generated), timeout count, server-error count, throughput, and P90/P95/P99 latency, all tagged with partner identity, to Amazon CloudWatch.

1.  **Enable network-layer metric collection:** For AWS RTB Fabric, confirm per-link metrics are publishing to the AWS/RTBFabric namespace. For other managed connectivity services, follow the service-specific metric namespace documentation.

1.  **Configure application log delivery per connectivity link:** For AWS RTB Fabric, deliver errorLog (100 percent) and filterLog (calibrated to volume and cost) to CloudWatch Logs, making sure bidder application logs carry the same link ID dimension.

1.  **Pair the endpoint-availability alarms and build them first:** These are the highest-signal, lowest-false-positive connectivity alarms, because zero is never a valid steady state. Alarm on target-ip-count at zero for a discovery or registration failure, and on healthy-target-ip-count at zero while discovery is non-zero for target endpoints failing health checks. Neither metric documents a dimension, so scope each alarm to the undimensioned aggregate and recognize that on a multi-gateway deployment the aggregate can mask a single gateway. Set both to treat missing data as breaching, since CloudWatch otherwise defaults to missing and parks the alarm in insufficient-data when a gateway stops publishing entirely, per the [missing-data guidance](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-missing-data.html). Use a 1-minute period, the shortest available for standard-resolution metrics in this namespace, and route directly to the on-call engineer.

1.  **Enable anomaly detection on per-link metrics immediately:** Configure CloudWatch anomaly detection on latency, error rates, and request counts per link as soon as each metric begins reporting. The model trains on up to two weeks of data and improves as data accrues, and a full two weeks isn't a prerequisite for enabling it. Expect band accuracy to improve over the first two weeks as time-of-day and day-of-week seasonality is captured, and hold off on paging from anomaly alarms until that baseline exists.

1.  **Build side-by-side dashboards:** Display network-layer (per-link latency, error rates, filtered counts) and application-layer (bid win rate, no-bid rate by reason code, timeout rate) metrics per partner. Include the discovered and healthy endpoint counts together so the gap between them is visible at a glance. Use [CloudWatch cross-account cross-Region dashboards](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cloudwatch_crossaccount_dashboard.html) if partners terminate in different accounts or Regions.

1.  **Create composite alarms for correlated degradation:** Fire only when network-layer degradation correlates with application-layer change (for example, elevated forwarding latency AND elevated timeout rate), reducing noise from independent transient issues.

1.  **Split no-bid attribution using the built-in metrics:** Use filter-transaction broken out by its Reason and ModuleId dimensions for no-bids generated in the connectivity path, and no-bid-external and no-bid-internal for the bid-transaction split. Read all of these with Sum. Derive the network-to-application ratio with metric math against your bidder's own no-bid-reason metrics. Reserve CloudWatch Contributor Insights or Logs Insights for high-cardinality drill-down inside the delivered logs, after you have inspected a sample and confirmed the record fields, and Contributor Insights operates over log groups and bills per matching log event. For A/B testing, use holdback percentages and correlate the holdback cohort against the filtered cohort to measure business impact.

1.  **Review and refine thresholds monthly:** Revisit alarm thresholds, filter configurations, and anomaly baselines monthly based on observed traffic and false-positive rates, and document threshold rationale for future operators.
