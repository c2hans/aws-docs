# Performance efficiency design principles
<a name="perf-design-principles"></a>

 These design principles help you achieve and maintain efficient performance for advertising workloads in the cloud. They extend the [lens-wide design principles](design-principles.md) with guidance specific to using cloud computing resources efficiently to meet system requirements as demand changes and technologies evolve.
+  **Design for data volume and query processing considerations for [AWS Clean Rooms](https://aws.amazon.com/clean-rooms/) collaboration:** Large datasets can impact query performance. Consider data partitioning, aggregations, and filters to reduce result sets. Complex joins across multiple tables and number of collaborators can impact processing time. The optimal design for collaborators uses one-to-many collaboration channels along with optimized pre-compiled query templates. Avoid running unbounded queries against large unpartitioned datasets that hit service limits.
+  **Select architecture based on evidence, not defaults:** The optimal solution for a particular advertising workload varies. Different advertising components, including bid evaluation, user profile storage, ML inference, and analytics pipelines, have widely different resource profiles that require different compute families, storage types, and network configurations. Make architecture decisions based on benchmarks against realistic advertising traffic patterns, not assumptions or general-purpose defaults. An architecture optimized for general web traffic will under-serve or over-provision for advertising-specific access patterns.
+  **Match compute to workload characteristics:** Use purpose-built instance families for each advertising workload type: Compute Optimized for bid evaluation and auction logic, Storage Optimized for real-time user profile databases requiring NVMe access, Trainium for deep learning model training, and Inferentia for inference. Regularly re-evaluate instance selection as new AWS hardware generations and instance types are released, because the performance and cost profile changes meaningfully with each generation.
+  **Move latency-sensitive computation to earlier in the pipeline:** Contextual classification, creative quality validation, and audience segmentation all produce outputs that are known before any individual bid request arrives. Running these computations at content ingest time and caching results removes synchronous ML inference from the bid evaluation path, where it would consume both latency budget and compute energy per impression. Pre-compute where possible, cache aggressively, and retrieve lazily on the critical path.
