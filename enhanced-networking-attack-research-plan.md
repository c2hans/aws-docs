## 1. Pentest Objectives (boundary-breach goals)
1. Prove or refute that an admin **cannot** author an identity policy that forbids/forces the ENA-Express (SRD) enable state on an ENI (`EnaSrdEnabled`/`EnaSrdUdpEnabled`) — i.e. the toggle is IAM-unscopable by value.
2. Prove or refute that a cross-team principal holding only broad `ec2:ModifyNetworkInterfaceAttribute` (or `ec2:AttachNetworkInterface`) can flip a victim-owned ENI's ENA-Express state and thereby silently change its traffic path/characteristics.
3. Determine whether SRD multipath transport **evades in-path network inspection** (Traffic Mirroring, Gateway Load Balancer appliances, firewall-in-path) or degrades VPC Flow Log / mirroring fidelity between two consenting instances.
4. Prove or refute that `ec2:ModifyInstanceAttribute` cannot be scoped to a *single* attribute (enaSupport only, not userData) — i.e. the attribute-modify grant is effectively all-or-nothing.
5. Characterize the **irreversible** `sriovNetSupport`/`enaSupport` enablement as a cross-team availability/bricking primitive against a stopped victim instance.
6. Audit every AWS-authored driver-install / tuning command the docs tell the customer to run verbatim for insecure defaults (Lens R).

## 2. Components, Assets, and Design

**What it is.** Enhanced networking = SR-IOV-based high-performance NIC virtualization. Three enable mechanisms:
- **ENA** (Elastic Network Adapter) — up to 100 Gbps; all Nitro instances + some Xen (H1, I3, G3, m4.16xlarge, P3, P3dn, R4). Gated by the **instance attribute `enaSupport`** (and the AMI attribute `enaSupport`).
- **Intel 82599 VF** (`sriovNetSupport="simple"`) — up to 10 Gbps; C3/C4/D2/I2/M4(non-16xl)/R3. Gated by instance/AMI attribute `sriovNetSupport`.
- **ENA Express** — AWS **Scalable Reliable Datagram (SRD)** transport layered on ENA; per-**attachment** attribute `EnaSrdSpecification{EnaSrdEnabled, EnaSrdUdpSpecification{EnaSrdUdpEnabled}}`. Boosts single-flow bandwidth 5→25 Gbps, same Region, SRD multipaths packets across AWS network paths and does reorder/retransmit in the network layer.

**Identifiers / shapes.** `eni-…`, `i-…`, `ami-…`. ENA Express state lives on the **attachment** (instance↔ENI relationship), read back as `Reservations[].Instances[].NetworkInterfaces[].Attachment.EnaSrdSpecification`.

**How identity/config is established (control plane).**
| Setting | API(s) | Precondition | Default |
|---|---|---|---|
| `enaSupport` (instance) | `ModifyInstanceAttribute --ena-support` / `Edit-EC2InstanceAttribute -EnaSupport $true` | instance **STOPPED** (EBS) | `false` |
| `sriovNetSupport` (instance) | `ModifyInstanceAttribute --sriov-net-support simple` | instance STOPPED | unset |
| `enaSupport`/`sriovNetSupport` (AMI) | `RegisterImage -EnaSupport/-SriovNetSupport`, `ModifyImageAttribute` | n/a | inherited from source instance |
| ENA Express `EnaSrdSpecification` | `ModifyNetworkInterfaceAttribute --ena-srd-specification` **or** `AttachNetworkInterface --ena-srd-specification` | ENI attached to a supported instance | `EnaSrdEnabled=false` |
| read-back | `DescribeInstanceAttribute`, `DescribeImageAttribute`, `DescribeInstances` | — | — |

**Driver layer (guest/OS plane — mostly out of the control-plane trust boundary).** Linux ENA driver on GitHub (`github.com/amzn/amzn-drivers`); Windows ENA driver install pages; Intel `ixgbevf` module. The customer's own instance pulls/builds the driver — a **guest-side** fetch, not a service-plane fetch (see Null hypotheses).

**ASCII pipeline (data plane, ENA Express):**
```
Instance A (EnaSrdEnabled=true) ──SRD──▶ [AWS multipath network fabric] ──SRD──▶ Instance B (EnaSrdEnabled=true)
        │ falls back to standard ENA if either side not enabled / middlebox in path / cross-Region
        └─ no middleware boxes supported on the SRD path  ◀── segmentation/inspection question (Lens V/O)
```

## 3. Trust-Boundary Map

| From (actor / zone) | To (resource / zone) | Crossing mechanism | Breach oracle |
|---|---|---|---|
| Cross-team principal (same account) w/ broad `ModifyNetworkInterfaceAttribute` | Victim-owned ENI attachment | flip `EnaSrdEnabled`/`EnaSrdUdpEnabled` with no value condition key | victim ENI's ENA-Express state changes under a policy the admin believed forbade it |
| Cross-team principal w/ broad `ModifyInstanceAttribute` | Victim **stopped** instance | set `enaSupport`/`sriovNetSupport` (irreversible) / or `userData` | an attribute the admin tried to scope out is still set; or irreversible enablement bricks an incompatible OS |
| Instance A data plane (SRD) | Instance B across AWS fabric | SRD multipath transport, "no middleware boxes" | SRD flow completes while bypassing an in-path inspection/mirroring control the design assumes is unavoidable |
| Instance owner | VPC Flow Logs / Traffic Mirroring | SRD network-layer reorder/retransmit/multipath | flow telemetry misses or misreports SRD traffic (detection blind spot) |
| Any customer surface | AWS's SRD transport fabric / Nitro card | — | **hard stop** — any identity/path belonging to AWS's own fabric |

## 5. Recommended Areas of Focus

### Area 1 — ENA Express (`EnaSrdSpecification`): IAM-unscopable by value + three-path action-family-parity gap [Lens S / X / U] — PRIMARY
**Background.** `EnaSrdSpecification{EnaSrdEnabled, EnaSrdUdpSpecification{EnaSrdUdpEnabled}}` is accepted by **three** APIs (confirmed from `ena-express-configure.md` examples + `list_ec2.md`): `ModifyNetworkInterfaceAttribute --ena-srd-specification`, `AttachNetworkInterface --ena-srd-specification`, and `RunInstances` / launch-template at launch time.
**Security Concern.** An exhaustive grep of `list_ec2.md` returns **ZERO** occurrences of `EnaSrd` / `ec2:Ena*` as a condition key (the 25 `ec2:Ena*` matches are all `ec2:Enable*` *action* names, not keys). So **no IAM condition key binds the ENA-Express enable value** on any of the three paths. Worse, the three paths are **asymmetric** in even their attribute-NAME scoping:
- `ModifyNetworkInterfaceAttribute` `network-interface*` row carries `ec2:Attribute` + `ec2:Attribute/${AttributeName}` (name-scope only — never the boolean value).
- `AttachNetworkInterface` `network-interface*` row (list_ec2 ~L4858–4862) carries **NO `ec2:Attribute` at all**.
- `RunInstances` / launch-template sets EnaSrd with no attribute-level key either.

**This is the sharpest net-new lead: the mitigation the sibling `modify-network-interface-attributes` plan documents — a `Deny` keyed on `ec2:Attribute = "enaSrdSpecification"` against `ModifyNetworkInterfaceAttribute` — gives ZERO protection**, because the identical setting can be pushed via `AttachNetworkInterface` or launch-time `RunInstances`, neither of which exposes `ec2:Attribute`. A policy author who believes they have fenced ENA Express has an open flank on two sibling write-paths (Lens X action-family parity / policy-completeness gap).
**High-level Test Scenarios.**
- *Claim:* a `Deny ModifyNetworkInterfaceAttribute` on `ec2:Attribute StringEquals "enaSrdSpecification"` is fully bypassed by setting EnaSrd via `AttachNetworkInterface` (detach→re-attach the ENI) or via a launch-template at `RunInstances`. → *Oracle:* `iam:SimulateCustomPolicy` shows the Attach and RunInstances calls **Allowed** with that Deny in place.
- *Claim (Lens-S case fail-open):* even against Modify, a Deny on lowercase `enaSrd`/`enaSrdSpecification` is inert if the engine binds the request field's actual casing. → *Oracle:* `iam:SimulateCustomPolicy` with both casings as `ec2:Attribute` context overrides (cross-ref the sibling `ec2:Attribute` casing lead).
- *Claim:* no key can require `EnaSrdEnabled=false`. → *Oracle:* no `ec2:EnaSrd*` key exists in `list_ec2`; confirmed.
**Doc evidence.** `ena-express-configure.md` CLI examples (all three paths); `list_ec2.md` ModifyNetworkInterfaceAttribute (~L8966), AttachNetworkInterface (~L4858). **Severity-if-true:** Medium (least-privilege / policy-completeness gap; AWS-owned — the governing keys do not exist and the write-paths are inconsistent). Report as Lens-U "guarantee has no mechanism" if any AWS doc implies ENA Express is IAM-governable.

### Area 2 — Cross-team flip of a victim ENI's ENA-Express state [Lens S / A intra-account]
**Background.** `ModifyNetworkInterfaceAttribute` on the `network-interface*` resource is scopable only by identity keys (`ec2:NetworkInterfaceID`, `ec2:Subnet`, `ec2:Vpc`, tags, Region) — not by the EnaSrd value.
**Security Concern.** A principal granted broad `ModifyNetworkInterfaceAttribute` (e.g. for routine SG/attribute management, or via a `network-interface/*` wildcard) can toggle `EnaSrdEnabled`/`EnaSrdUdpEnabled` on another team's attached ENI. Flipping it **off** silently drops the victim's traffic to standard ENA (latency/throughput regression under load — a stealthy, non-alarming degradation); flipping it **on** changes the transport path. Because the setting is attachment-scoped, detach/terminate silently resets it (`ena-express.md` Note), making the change ephemeral and hard to attribute.
**High-level Test Scenarios.**
- *Claim:* with only `ModifyNetworkInterfaceAttribute` on `network-interface/*` (no tag scoping), I can set `EnaSrdEnabled=false` on an ENI I don't own. → *Oracle:* under a scoped canary role, call succeeds against a second-team canary ENI; `DescribeInstances … Attachment.EnaSrdSpecification` reflects the change. → *Breach oracle:* performance-affecting state changed on a resource the policy author believed scoped.
**Doc evidence.** `ena-express.md` attachment-lifecycle Note; `list_ec2.md` row. **Severity-if-true:** Medium (intra-account cross-team performance tamper / stealth degradation; no cross-account reach).

### Area 3 — SRD multipath transport vs in-path inspection & flow telemetry [Lens V / O] — HIGH-VALUE, DOC-GAP
**Background.** `ena-express.md`: SRD "distributes packets for each network flow across different AWS network paths" and *"The network path between the instances must not include middleware boxes. ENA Express doesn't currently support middleware boxes."*
**Security Concern.** Two questions the docs leave open: (a) does enabling ENA Express cause traffic between two consenting instances to take fabric paths that **bypass a security appliance / Gateway Load Balancer / Traffic-Mirroring target** that a defender assumes is unavoidably in-path? (The "no middleware boxes" line suggests SRD will *fall back* to standard ENA when a middlebox is present — confirm that fallback is reliable and not attacker-suppressible.) (b) Does SRD multipathing + network-layer reorder/retransmit **degrade VPC Flow Logs / Traffic Mirroring fidelity** (packet/flow accounting, per-path capture, reassembly) so that cross-instance traffic is under-reported or evades inspection?
**CONFIRMED doc-silence (net-new, subagent 1).** A grep sweep across the entire VPC Flow Logs and Traffic Mirroring doc trees — `docs/vpc/latest/userguide/flow-logs-*.md` (all files) and `docs/vpc/latest/mirroring/*.md` (all files) — for `ENA Express` / `EnaSrd` / `SRD` returns **ZERO hits in both directories**. AWS makes **no statement in either direction** about whether Flow Logs or Traffic Mirroring observe SRD-multipathed/reordered/retransmitted traffic the same way they observe standard ENA. `monitoring-network-performance-ena.md`'s "Metrics for ENA Express" section documents only in-guest counters (`ena_srd_mode`, `ena_srd_eligible_tx_pkts`, `ena_srd_tx_pkts`, `ena_srd_rx_pkts`, `ena_srd_resource_utilization`) with no mention of Flow Logs, Traffic Mirroring, or CloudTrail. This elevates (a) from "docs leave open" to "docs are provably silent across the owning service's entire doc tree."
**Fallback-direction note (subagent 1, Lens V/D).** The "no middleware boxes" line is framed purely as an *eligibility* requirement (alongside same-Region / both-ends-enabled / instance-type), never as a security guarantee. The docs do NOT say SRD "falls back safely and still transits the middlebox" **nor** "bypasses the middlebox" — they are silent on behavior when the requirement is violated. The architecture (multipath over AWS's backbone between two *cooperating* ENA drivers, inside the normal socket/TCP-UDP stack, still subject to SG/VPC enforcement per the docs) makes "SRD simply doesn't activate" far more likely than "SRD routes around a customer-placed inline device" — so this is a **weak lead recorded to close it out**, not a predicted bypass. Also note the genuine named segmentation facts: SRD traffic can't be sent in a **Local Zone**, and cross-AZ SRD is unavailable in São Paulo, Bahrain, and UAE — an org pinned to those does not need to threat-model SRD cross-AZ multipath at all.
**High-level Test Scenarios.**
- *Claim:* when a Traffic-Mirroring or GWLB inspection path exists between A and B, enabling ENA Express does NOT route around it (fallback holds). → *Oracle:* mirrored/inspected byte counts match with and without ENA Express; no SRD flow observed bypassing the appliance.
- *Claim:* VPC Flow Logs record SRD flows with the same fidelity as standard ENA. → *Oracle:* flow-log 5-tuple/packet counts for a known SRD-heavy flow match the same flow with ENA Express disabled; specifically check for packet-reordering artifacts, SRD-retransmission duplicate records, or multipath fan-out a signature-based IDS on a Traffic-Mirroring tap might miss or double-count.
- *Preconditions:* two owned supported instances same AZ/Region; an inspection control deployed between them. **This is a data-plane behavioral test — needs owned canary instances; keep strictly within your own account.**
**Doc evidence.** `ena-express.md` "How ENA Express works" + requirements list; confirmed-silence grep of `docs/vpc/latest/{userguide/flow-logs-*,mirroring/*}.md` + `monitoring-network-performance-ena.md`. **Severity-if-true:** inspection bypass between tenants' own hosts is at most intra-account (both ends consenting) → Medium; a cross-tenant or defender-blinding gap would be High. Likely a **detection-fidelity / design-assumption** finding, not cross-tenant. Mark doc-gap — confirm behavior first.

### Area 4 — `ModifyInstanceAttribute` single-attribute scopability + casing fail-open (enaSupport vs userData) [Lens S / B]
**Background.** `enaSupport`/`sriovNetSupport` are set with the *same* `ModifyInstanceAttribute` action that also sets `userData`, `instanceType`, `disableApiStop`, etc. The `instance*` row (list_ec2 ~L8806–8811) carries `ec2:Attribute` (name-only, `String`) + `ec2:Attribute/${AttributeName}` (value) plus many instance keys. Per `iam-policies-for-amazon-ec2.md` L203–265, the value form "supports only properties of a primitive data type ... or complex `AttributeValue` objects that contain only a `Value` property" — `EnaSupport` (`AttributeBooleanValue`) and `SriovNetSupport` (`AttributeValue`) both qualify structurally, so sub-attribute scoping *looks* possible.
**Security Concern — casing fail-open (net-new, subagent 2).** AWS gives exactly **one** worked example of either key form anywhere in the docs: `ec2:Attribute/Description` on `ModifyImageAttribute` — **PascalCase**, matching the *named request parameter* `Description`, NOT the lowercase `description` that appears in that same action's `Attribute` enum. `ModifyInstanceAttribute`'s `Attribute` enum is documented all-lowercase camelCase (`...sriovNetSupport | enaSupport | userData...`, `API_ModifyInstanceAttribute.md` L23). **Nothing in the docs states which string the IAM engine actually binds into the context key** when a caller uses the modern named field (`--ena-support`) vs the legacy generic `Attribute`+`Value` form. Consequence: a Deny written against the lowercase doc enum — `"ec2:Attribute/userData": {"Bool": true}` — **fails open** (a principal believed blocked from `userData` is not) if the real context value is PascalCase `UserData`. An Allow written the same way fails *closed* (safe-but-broken). And `ModifyInstanceAttribute(userData)` is a confirmed PassRole-adjacent live-launch-spec / root-at-next-boot reach (cross-ref `using-eni`/instance plans), so a "let the perf team enable ENA" grant that fails open on `userData` is a privesc.
**Wire-shape note (subagent 2).** `enaSupport`/`sriovNetSupport` are **named request parameters only** (`EnaSupport.Value`, `SriovNetSupport.Value`) — unlike `userData`, they are NOT settable through the legacy generic `Attribute=...&Value=...` pair (the API doc restricts that generic form to `kernel|ramdisk|userData|disableApiTermination|instanceInitiatedShutdownBehavior`). So enaSupport/sriovNetSupport have exactly one wire form; `userData` has two — widening the surface for a casing/wire-form mismatch on the very attribute that matters.
**High-level Test Scenarios.**
- *Claim:* a Deny on `ec2:Attribute/userData` (camelCase, per the doc enum) does NOT block setting `userData` because the engine binds PascalCase `UserData`. → *Oracle:* `iam:SimulateCustomPolicy` — policy A denies on `"ec2:Attribute/UserData"`, policy B on `"ec2:Attribute/userData"`; supply both casings as context overrides and compare `EvalDecision`. No live resource touched; exposes the normalization directly without ever calling EC2.
- *Claim:* `Allow ModifyInstanceAttribute` scoped to `ec2:Attribute = enaSupport` still permits `userData`. → *Oracle:* same simulate harness with `RequestContext ec2:Attribute=userData` — Allowed = fail-open.
**Doc evidence.** `iam-policies-for-amazon-ec2.md` L203–265 (sole example, PascalCase); `API_ModifyInstanceAttribute.md` L23 (lowercase enum); `list_ec2.md` L8806–8811. **Severity-if-true:** Medium if refuted-as-fail-open (silent `userData` privesc via a "perf" grant); Low if IAM normalizes to the shape member name server-side (the more probable outcome, but asserted nowhere in the docs). **This is a genuine documentation gap, not a confirmed bypass** — settle it with the simulate harness before investing.

### Area 4b — Describe\* read oracle: "read enaSupport" grant is actually "read every attribute incl. userData" [Lens O / A] — net-new
**Background.** `sriov-networking.md`'s own verification procedure for `sriovNetSupport` uses `describe-instance-attribute --attribute sriovNetSupport` (the single-attribute call); the `enaSupport` test uses bulk `DescribeInstances/.EnaSupport`.
**Security Concern (net-new, subagent 2).** `DescribeInstanceAttribute` (list_ec2 L6924–6928) and `DescribeImageAttribute` (L6882–6886) carry **NO `ec2:Attribute` condition key at all** — not even the name-only form, and not the "primitive/single-Value" carve-out that at least limits the *write* side. So a grant of `ec2:DescribeInstanceAttribute` on an instance (e.g. to let a compliance tool verify `sriovNetSupport`) **cannot be IAM-restricted to that one attribute**: the identical grant permits `describe-instance-attribute --attribute userData`, returning the full base64 user-data blob — a frequent carrier of bootstrap secrets/credentials. This is the read-side mirror of Area 4, and arguably *more* exploitable because there is zero attribute-scoping key on the read path, full stop.
**High-level Test Scenarios.**
- *Claim:* a principal with unconditioned `ec2:DescribeInstanceAttribute` on an instance can read `userData` as readily as `sriovNetSupport`. → *Oracle:* `iam:SimulateCustomPolicy` requesting both `{"Attribute":"sriovNetSupport"}` and `{"Attribute":"userData"}` context — both evaluate `allowed` identically, confirming the grant cannot distinguish them.
**Doc evidence.** `sriov-networking.md` test section; `list_ec2.md` L6924–6928 / L6882–6886. **Severity-if-true:** Medium (least-privilege read oracle → userData/secret disclosure via a "read ENA state" grant).

### Area 5 — Irreversible enablement as a bricking / availability primitive [Lens L / U / X / integrity]
**Background.** The `sriovNetSupport` irreversibility is a **stronger, independent** hazard from `enaSupport`'s reachability warning, and the two compound (subagent 2):
- `sriovNetSupport` has **no disable API path at all** — confirmed in THREE places: `sriov-networking.md` L128 ("There is no way to disable the enhanced networking attribute after you've enabled it"), `API_ModifyInstanceAttribute.md` L96 ("There is no way to disable enhanced networking with the Intel 82599 Virtual Function interface at this time"), and `API_RegisterImage.md` L113 ("There is no way to disable `sriovNetSupport` at this time.").
- `enaSupport`, by contrast, IS reversible — `modify-instance-attribute --no-ena-support`. Its hazard is reachability only ("might render incompatible instances or operating systems unreachable"), not permanence.

Set requires the instance **STOPPED**.
**Security Concern.** A cross-team principal holding `ModifyInstanceAttribute` + `StopInstances`/`StartInstances` on a victim's **stopped** (esp. PV / driverless) instance can run `--sriov-net-support simple` **once, permanently**: no value-level IAM key gates it (only ownership-style `ec2:InstanceID`/tag keys exist — same unscopability as Area 1, confirmed by the Area-4 key enumeration), there is no confirmation flag, no state-transition-aware condition key ("allow enabling, never re-triggering"), and no API undo. On next boot the PV instance may be **permanently unreachable** (`sriov-networking.md`: "Enabling enhanced networking with a PV instance can make it unreachable"), with the only recovery being restore-from-a-pre-attack-AMI. Uniquely high impact-asymmetry: one low-privilege, innocuous-sounding call → permanent, unrepairable state change + plausible outage.
**AMI-level twin — RegisterImage is an unguarded write-path (Lens X, confirmed).** `RegisterImage` sets AMI `enaSupport`/`sriovNetSupport` and carries **ZERO `ec2:Attribute` condition keys** on either resource row (`image*`, `snapshot`) — confirmed literal in `list_ec2.md` L9317–9321. `ModifyImageAttribute`'s `Attribute` enum is `description | imdsSupport | launchPermission` **only** — it excludes enaSupport/sriovNetSupport entirely, so AMI-level enhanced-networking is settable **only** via `RegisterImage` or source-instance inheritance, and the `ec2:Attribute` keys that *do* exist on `ModifyImageAttribute` are **structurally irrelevant** to governing it. Net: a Deny/SCP targeting `ec2:Attribute/EnaSupport` on `ModifyInstanceAttribute` gives **zero** coverage against a principal with `ec2:RegisterImage` baking `--sriov-net-support simple` into a fresh AMI — same irreversibility, **broader blast radius** (propagates to every instance launched from that AMI).
**High-level Test Scenarios.**
- *Claim:* enabling `sriovNetSupport` on a stopped PV/driverless instance makes it unreachable and cannot be reverted. → *Oracle:* on an owned canary with a deliberately incompatible kernel, set the attribute, start, observe unreachability + `DescribeInstanceAttribute` shows it stuck enabled. **Owned canary only; destructive — do NOT run against any shared/other resource.**
- *Claim:* a Deny on `ec2:Attribute/EnaSupport` for `ModifyInstanceAttribute` does not stop `RegisterImage` from baking enhanced networking into an AMI. → *Oracle:* `iam:SimulateCustomPolicy` for `ec2:RegisterImage` with that Deny present shows Allowed (the key isn't defined on RegisterImage, so it's simply not evaluated).
**Doc evidence.** `sriov-networking.md` L68/L128; `API_ModifyInstanceAttribute.md` L96; `API_RegisterImage.md` L113; `list_ec2.md` L9317–9321. **Severity-if-true:** Medium–High (intra-account cross-team DoS/bricking; irreversible; AMI path has broader blast radius). Note: gated by instance-type support ("You can only enable this attribute on supported instance types").

### Area 6 — AWS-authored driver-install / tuning commands (insecure defaults) [Lens R]
**Background.** The docs instruct customers to download/build the ENA Linux driver from GitHub, install the Windows ENA driver, load the Intel `ixgbevf` module, edit GRUB (`net.ifnames=0`), update `initramfs`/`dracut`, and apply Nitro/Linux tuning. `sriov-networking.md` L356 (Windows): *"The administrator password will reset when you enable the initialize instance EC2 Launch script. You can modify the configuration file to disable the administrator password reset…"*
**Security Concern.** Audit every verbatim command for: driver download over HTTP vs HTTPS; absence of checksum/GPG/signature verification before a privileged `insmod`/install; unpinned "latest" driver fetch (supply-chain / downgrade); any `curl|sh` pattern; the Windows admin-password-reset note (does the documented default weaken credential posture?). These are guest-side, but AWS-authored copy-verbatim steps → in-scope Lens-R if a weak default ships.
**CONFIRMED audit result (subagent 3).**
- *Windows (R-1, fires — Medium):* `ena-adapter-driver-install-upgrade-win.md` Step 2 Option 1 instructs `invoke-webrequest https://ec2-windows-drivers-downloads.s3.amazonaws.com/ENA/**Latest**/AwsEnaNetworkDriver.zip` → `expand-archive` → run `install.ps1`, all **as local Administrator**, with **no documented SHA256/Authenticode/GPG verification** of the zip before extraction/execution. The URL uses the **mutable, unversioned `Latest` alias** (contrast Option 2 and the version-history table, which link pinned paths like `ENA/x64/2.11.0/...`) — the doc's "fastest" path is also the unpinned one. Only integrity-adjacent note on the page is a TLS-1.2-enable transport workaround, not artifact verification. Partially mitigated by platform defaults the docs don't mention (64-bit Windows kernel driver-signature enforcement would reject an unsigned `.sys`; HTTPS transport). **Residual risk is at the `install.ps1`/installer-script layer** — it runs with full admin privilege and is trusted purely on TLS-to-S3-hostname, no secondary check.
- *Linux (R-2, doc-gap):* the in-scope UserGuide pages print **no** Linux `git clone`/`curl`/`make install` sequence — they delegate to `github.com/amzn/amzn-drivers` (an **Amazon-owned** org, so still in-scope Lens R, not a 3P exclusion). The only printed privileged Linux command is `sudo insmod ena.ko enable_frag_bypass=...` (loads an already-built module, no fetch). A follow-on pass should fetch that README/RELEASENOTES and audit whether it instructs GPG-signed-tag verification or bare `git clone + make`.
**High-level Test Scenarios.** *Claim:* `https://.../ENA/Latest/AwsEnaNetworkDriver.zip` ships with no AWS-published checksum/signed manifest the documented workflow references. → *Oracle (pipeline-access only, not live-tamper):* does the package's Authenticode signature chain to a trusted Amazon code-signing cert, and does any `.sha256`/signed manifest exist that the runbook omits? If a checksum exists but the docs never cite it, that omission is the defect.
**Doc evidence.** `ena-adapter-driver-install-upgrade-win.md` Step 2; `ena-driver-releases-windows.md`; `ena-nitro-perf.md` (Linux delegation + `insmod`); `enabling_enhanced_networking.md`, `enhanced-networking-os.md`, `ena-improve-network-latency-linux.md`. **Severity-if-true:** Medium (Windows: copy-verbatim admin install, no integrity step, mutable alias); Linux unrated (doc-gap, follow-on). *[Full audit: `.cache/ena-driver-monitoring-findings.md`.]*

### Area 7 — ENA / ENA-Express metrics as a side-channel / oracle [Lens O / L]
**Background.** `monitoring-network-performance-ena.md` documents per-instance allowance metrics (`bw_in/out_allowance_exceeded`, `pps_allowance_exceeded`, `conntrack_allowance_exceeded`, `linklocal_allowance_exceeded`) and ENA-Express SRD metrics (operating state, SRD-eligible/used packets).
**CONFIRMED analysis (subagent 3).** Metrics are guest-readable via `ethtool -S` (no privilege beyond a shell) and **opt-in** to CloudWatch via the CloudWatch agent — **never cross-account**.
- *(a) Noisy-neighbor side-channel — REFUTED.* `monitoring-network-performance-ena.md` states the `*_allowance_exceeded` ceilings are "based on instance type and size," static and publicly knowable, **not** a function of co-tenant load; `ena-nitro-perf.md` adds the Nitro card is "physically separate from the system main board," shaping against a fixed allowance table, not a contended shared queue. These counters tell you only about *your own* traffic vs *your own* documented maximum → no cross-tenant inference. Evidence-backed null. (Residual doc-gap: does the "maximum" ever dynamically shrink under host contention undisclosed? Nothing on these pages suggests so.)
- *(b) SRD metrics leak host-maintenance — fires, Informational/Low.* `monitoring-network-performance-ena.md` explicitly: a gap between `ena_srd_eligible_tx_pkts` and `ena_srd_tx_pkts` "can also [occur] during **live migrations or live server updates**." A guest tight-polling `ethtool -S eth0 | grep ena_srd` can thus infer AWS is doing live migration/server-update on its host. Squarely in the shared-Nitro/host-infra out-of-scope bucket (AWS already discloses maintenance via scheduled-event APIs), but a genuine *AWS-documented* side-channel worth recording because it's explicit in the text.
- *(c) conntrack / linklocal — cross-ref only.* `conntrack_allowance_exceeded`/`conntrack_allowance_available` are the real-time *oracle* the conntrack-exhaustion sibling plans (`create-network-interface`/`modify-network-interface-attributes`) need — this page is their evidence source, not restated here. `linklocal_allowance_exceeded` is a **per-ENI** PPS cap shared by all processes/containers on the instance that hit 169.254.x (IMDS/DNS/Time-Sync) → a same-instance self-DoS (one noisy container starving siblings' IMDS/DNS); **doc-gap** on whether any AWS-managed multi-tenant-on-one-ENI pattern exists before escalating (cross-ref IMDS/169.254 hub). Not cross-account.
**Doc evidence.** `monitoring-network-performance-ena.md`, `ena-nitro-perf.md`. **Severity-if-true:** Low / Informational (self-DoS signal + documented host-maintenance side-channel; both out-of-scope-leaning). *[Full detail: `.cache/ena-driver-monitoring-findings.md`.]*
