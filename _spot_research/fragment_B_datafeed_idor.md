# Fragment B — Spot Data Feed S3 Trust Model, Spot Request ID IDOR, Launch-Spec Content
Documentation-only analysis. No live AWS calls were made. All claims are grounded in the cited offline-mirror files; none have been confirmed against a live account.

## (A) Spot Data Feed → S3 cross-account trust model

### A1. Revocation incompleteness — stale AWS-data-feed-account grant survives `DeleteSpotDatafeedSubscription`
- **Claim**: After a customer deletes their Spot data feed subscription, the "AWS data feed account" keeps `FULL_CONTROL`-derived read/write ACL grants on the bucket and on every already-delivered `.gz` object. EC2 does not clean this up.
- **Mechanism** (doc evidence): `/work/aws-docs/docs/AWSEC2/latest/UserGuide/spot-data-feeds.md:68`: *"If you delete your data feed subscription, Amazon EC2 doesn't remove the read and write permissions for the AWS data feed account on either the bucket or the data files. You must remove these permissions yourself."* Combined with `spot-data-feeds.md:64`: subscribing *"update[s] the bucket ACL to give the AWS data feed account `FULL_CONTROL` permission"*, and `spot-data-feeds.md:67`: *"Each data feed file has its own ACL... The AWS data feed account has read and write permissions."*
- **Confirm/Refute oracle**: On a real account, subscribe → receive at least one `.gz` file → delete the subscription → fetch the bucket ACL (`GetBucketAcl`) and an object ACL (`GetObjectAcl`). If the "AWS data feed account" grantee is still present with FULL_CONTROL/WRITE after deletion, the claim is confirmed exactly as documented (this is actually AWS's own documented, *expected* behavior, not a hidden bug — it's a leftover-permission footgun, not a boundary violation per se).
- **The real open question** (what would make this a genuine cross-tenant issue rather than self-inflicted): the doc describes a single named grantee, "the AWS data feed account" (singular, canonical AWS principal used to deliver data feeds to all subscribers globally). It does NOT document whether that account's write capability into a *given* customer's bucket is scoped per-subscription (e.g., via a secret/random prefix or STS-vended temporary credential tied to that specific `CreateSpotDatafeedSubscription` call) or whether it is simply "grant this one well-known AWS principal FULL_CONTROL ACL — globally, for every EC2 customer's feed." The doc evidence only establishes the latter (a bucket ACL grant to a named AWS account), which is a *coarse* grant, not a scoped one.
  - If the grant is the same principal for every customer (plausible reading of "the AWS data feed account" as a singular, non-customer-specific principal) then the control that prevents "customer A's bucket being written to by customer B's data feed" is **not** stale-permission-based at all — it is whatever internal addressing EC2 uses server-side to route each account's `.gz` files only to the bucket *that account* subscribed. The ACL grant to the single shared principal is necessary but not sufficient; the actual isolation boundary is an undocumented backend routing control, which the public docs give no detail on and which a hunter cannot verify without AWS-side access. This should be flagged as **not independently confirmable from documentation** — call it an assumption surfaced, not a verified boundary.
- **Preconditions**: Caller must have owned/subscribed a data feed and have bucket-ACL-read permission post-deletion (self-service, no privilege needed).
- **Severity-if-true**: Low-to-Moderate for the customer themselves (self-inflicted residual exposure — they must manually clean up ACLs; the doc explicitly warns them). Would be **Moderate-High** only if the "AWS data feed account" principal is shown to also be reachable/assumable by other *tenants* for write purposes, which the docs do not state and which is out of scope to test live.
- **Lens**: AA (permission/ACL hygiene), T (trust boundary ambiguity).
- **Classification**: Primarily **self-inflicted / known-accepted-risk** per AWS's own docs (the customer is explicitly told to clean up). The only genuinely open cross-tenant question — whether the shared delivery principal is a single global actor whose write path is isolated purely by server-side routing rather than by per-subscription scoped credentials — is a **documentation gap**, not a confirmed vulnerability.

### A2. Bucket-ownership validation gap for `CreateSpotDatafeedSubscription`
- **Claim**: `CreateSpotDatafeedSubscription` only requires the caller's AWS account to have S3 `FULL_CONTROL` permission on the target bucket — not bucket *ownership*. This is explicitly documented as sufficient.
- **Mechanism** (doc evidence): `/work/aws-docs/docs/AWSEC2/latest/UserGuide/spot-data-feeds.md:63`: *"You must have `FULL_CONTROL` permission to the bucket. If you're the bucket owner, you have this permission by default. **Otherwise, the bucket owner must grant your AWS account this permission.**"* The `CreateSpotDatafeedSubscription` API request itself (`/work/aws-docs/docs/AWSEC2/latest/APIReference/API_CreateSpotDatafeedSubscription.md:15-18`) takes only a bare `Bucket` name string and optional `Prefix` — no bucket-owner-account parameter, no ownership proof, no `ExpectedBucketOwner`-style check is mentioned anywhere in either doc.
- **Confirm/Refute oracle**: Account X grants account Y's AWS account ID `FULL_CONTROL` on an S3 ACL for bucket `b` (a legitimate, documented cross-account S3 ACL grant). Account Y then calls `ec2:CreateSpotDatafeedSubscription --bucket b`. If it succeeds, confirmed-as-designed: EC2 performs no additional ownership check beyond what S3's ACL evaluation already enforces when EC2 (using "the AWS data feed account" principal) later tries to write. This is explicitly how the feature is *designed* to work per the docs — it is not a bypass, it's the intended cross-account use case (e.g., centralized billing/log aggregation buckets).
- **Preconditions**: Requires a cooperating bucket owner who already granted FULL_CONTROL — i.e., this is consensual cross-account sharing, not an unauthorized boundary cross. The interesting edge case is whether EC2 revalidates FULL_CONTROL at *delivery* time (hourly) vs. only at subscribe time — undocumented.
- **Severity-if-true**: Informational/Low — this is intentional cross-account support, not a flaw. Flagging it here only because it means the account-id embedded in the delivered file path (see A3) can diverge from the bucket-owning account, which matters for A3.
- **Lens**: T (trust model documentation), A (authorization).
- **Classification**: **Out-of-scope / by design.** Not a vulnerability; included because it's the precondition for A3.

### A3. Predictable/embedded-account-id file path — enumerability
- **Claim**: Data feed object keys embed the subscriber's 12-digit AWS account ID in a predictable, low-entropy format: `{bucket}.s3.amazonaws.com{/prefix}/{aws-account-id}.{YYYY-MM-DD-HH}.{n}.{unique-id}.gz`.
- **Mechanism** (doc evidence): `/work/aws-docs/docs/AWSEC2/latest/UserGuide/spot-data-feeds.md:29-39`, example: `amzn-s3-demo-bucket.s3.amazonaws.com/my-prefix/111122223333.2023-12-09-07.001.b959dbc6.gz`. Only the trailing `{unique-id}` component (`b959dbc6`, 8 hex chars ≈ 32 bits) is high-entropy; account-id, date/hour, and sequence number `{n}` are all either public/guessable or trivially enumerable once the bucket/prefix is known.
- **Confirm/Refute oracle**: This is only exploitable if an attacker already has *some* read access to the bucket (e.g., via an overly permissive bucket policy, or as the cooperating bucket owner in the A2 cross-account scenario) — in which case `ListObjectsV2` already reveals the keys directly, making the "predictability" moot. The oracle for a real finding would be: is there any S3 API or EC2 API that allows blind/unauthenticated *existence* probing of a specific key (e.g., via `HeadObject` behavior differences, or via EC2's `DescribeSpotDatafeedSubscription` leaking the account ID / bucket / prefix to a party who shouldn't see it). Per `/work/aws-docs/docs/AWSEC2/latest/APIReference/API_DescribeSpotDatafeedSubscription.md`-adjacent `SpotDatafeedSubscription` object (`/work/aws-docs/docs/AWSEC2/latest/APIReference/API_SpotDatafeedSubscription.md:23-26`), the response includes `ownerId`, `bucket`, `prefix` — but `DescribeSpotDatafeedSubscription` has no resource-type/ARN entry in `list_ec2.md:7392-7398` (no resource-level IAM scoping — Access level List, Condition keys: only `ec2:Region`), meaning authorization is purely "does this caller's credentials belong to account X", not fine-grained. This is normal (it's an account-singleton resource — "only one Spot data feed per AWS account", `spot-data-feeds.md:15`) so there's no IDOR surface here beyond standard IAM identity-based access.
- **Preconditions**: Requires pre-existing bucket access; the account-id-in-filename pattern by itself is not an exploitable primitive without that access.
- **Severity-if-true**: Low — informational enumerability only, not a standalone finding.
- **Lens**: A.
- **Classification**: **Not a boundary issue** — downgrade to informational/no-finding. Flagging only because it was explicitly asked for.

### A4. One-data-feed-per-account constraint — race/dedup
- **Claim**: "You can create only one Spot Instance data feed per AWS account" (`spot-data-feeds.md:15`; also `API_CreateSpotDatafeedSubscription.md:8`: *"You can create one data feed per AWS account."*).
- **Mechanism**: Singleton resource semantics, enforced server-side (no `SubscriptionId` is ever issued — the resource is addressed implicitly by the caller's account). No idempotency token, no documented `DryRun`-only-collision-check behavior.
- **Confirm/Refute oracle**: Fire concurrent `CreateSpotDatafeedSubscription` calls with different `Bucket`/`Prefix` values from the same account's credentials (same account, two parallel threads/roles). Observe whether the second-writer-wins silently, or whether one receives an explicit "already subscribed" error. Docs do not specify either outcome — a real race-condition question, but entirely intra-account (your own two threads racing your own singleton setting), so even in the worst case it's a self-own, not a cross-tenant bug.
- **Preconditions**: Caller already has `ec2:CreateSpotDatafeedSubscription` on their own account.
- **Severity-if-true**: Informational — intra-account only.
- **Lens**: AA.
- **Classification**: **Out-of-scope** (no cross-tenant implication; at most a UX/idempotency nit).

### A5. SSE-KMS requirement — customer-managed-key-only note
- **Claim**: If the destination bucket uses SSE-KMS, the key MUST be a customer managed key (not an AWS managed key).
- **Mechanism** (doc evidence): `spot-data-feeds.md:69`: *"If you encrypt your Amazon S3 bucket using server-side encryption with a AWS KMS key stored in AWS Key Management Service (SSE-KMS), you must use a customer managed key."*
- **Confirm/Refute oracle**: Subscribe pointing at an SSE-KMS bucket keyed with the AWS-managed `aws/s3` key; observe whether delivery silently fails (files never arrive, and per `spot-data-feeds.md:66` the only officially documented failure mode for ACL problems is "files cannot be written; resubscribe"). No access-boundary implication — this is a service limitation of "the AWS data feed account" principal, which (being a non-customer principal) cannot be granted `kms:Decrypt`/`kms:GenerateDataKey` on an AWS-managed key the way it could on a customer-managed key policy. This actually reinforces that the data-feed-account's write path is permission-gated at the KMS-key-policy layer when SSE-KMS is used — i.e., *some* genuine least-privilege control does exist here, which is reassuring evidence against the worst reading of A1.
- **Preconditions**: None beyond having an SSE-KMS bucket.
- **Severity-if-true**: Informational.
- **Lens**: H (key-management boundary), T.
- **Classification**: **Out-of-scope / reassuring control**, not a vulnerability.

## (B) Spot Instance Request ID IDOR / enumeration

### B1. ID format evolution — low-entropy legacy 8-hex-char IDs vs. 17-hex-char modern IDs
- **Claim**: Older docs/examples show `sir-xxxxxxxx` with only 8 hex characters (~32 bits) of entropy (e.g., `sir-1a2b3c4d`, `sir-df6f405d`, `sir-pwq6nmfp`-style IDs in the data feed example); current UserGuide CLI examples use the longer 17-hex-char form consistent with AWS's 2016 "longer resource IDs" migration (e.g., `sir-0e54a519c9EXAMPLE`).
- **Mechanism** (doc evidence): Legacy format: `/work/aws-docs/docs/AWSEC2/latest/APIReference/API_DescribeSpotInstanceRequests.md:132` (`sir-1a2b3c4d`) and `:59` of `API_CancelSpotInstanceRequests.md` (`sir-1a2b3c4d`); also data feed example `MyBidID` field shows `sir-pwq6nmfp` in `spot-data-feeds.md:148`. Modern format: `/work/aws-docs/docs/AWSEC2/latest/UserGuide/using-spot-instances-cancel.md:37` and `using-spot-instances-request.md:104` both show `sir-0e54a519c9EXAMPLE` (a 17-character hex suffix, matching the same length/format as modern `i-0123456789abcdef0` instance IDs).
- **Confirm/Refute oracle**: Call `DescribeSpotInstanceRequests`/`CancelSpotInstanceRequests` today and observe the actual ID length returned for a freshly created request. If accounts still on legacy short-ID behavior exist (unlikely post-migration — AWS completed this years ago for all new resources), the 32-bit space would be guess-attackable at volume; for the modern ~64-bit random suffix this is computationally infeasible to brute force. This is a **historical** note rather than a live concern — AWS's resource-ID-length migration (2016) applies retroactively to the ID *format* for all new resources, so this is very unlikely to be exploitable today, but it is worth noting the docs still contain stale 8-char examples that could mislead a reader into assuming low entropy is still current.
- **Preconditions**: N/A (would require an account on a legacy ID scheme, which AWS docs give no indication still exists for new requests).
- **Severity-if-true**: Informational/historical.
- **Lens**: A.
- **Classification**: **Likely moot today** — flagged only because the docs are internally inconsistent about ID format and a hunter should verify current ID length live rather than trust the older API-reference examples.

### B2. No resource-level IAM scoping for `Describe*` spot actions — coarse-grained authorization by design
- **Claim**: `DescribeSpotInstanceRequests`, `DescribeSpotPriceHistory`, and `DescribeSpotDatafeedSubscription` have **no resource-type entry** in the IAM Service Authorization Reference — meaning IAM policies can only grant/deny them at `Resource: "*"` granularity; you cannot write an IAM policy that says "describe only `spot-instances-request/sir-X`". `CancelSpotInstanceRequests`, by contrast, **does** support the `spot-instances-request` resource type.
- **Mechanism** (doc evidence): `/work/aws-docs/docs/service-authorization/latest/reference/list_ec2.md`:
  - `DescribeSpotInstanceRequests` (lines ~7416-7421): `Resource types (*required):` *(blank)*, `Condition keys: ec2:Region`, `Access level: List`.
  - `DescribeSpotPriceHistory` (lines ~7422-7427): same — no resource type, only `ec2:Region`.
  - `DescribeSpotDatafeedSubscription` (lines ~7392-7398): same — no resource type, only `ec2:Region`.
  - `CancelSpotInstanceRequests` (lines ~4972-4977): `Resource types (*required): spot-instances-request*`, `Condition keys: aws:ResourceTag/${TagKey}, ec2:Region, ec2:ResourceTag/${TagKey}`.
  - Resource-type ARN definition: (line ~10000) `spot-instances-request | arn:${Partition}:ec2:${Region}:${Account}:spot-instances-request/${SpotInstanceRequestId}`.
- **Why this matters as an IDOR-shaped question**: Because `DescribeSpotInstanceRequests` cannot be resource-scoped in IAM, the *only* thing stopping caller A (account 111111111111) from passing `SpotInstanceRequestId.1=sir-<account-B's-id>` and getting account B's request details back is the EC2 *service-side* authorization check (cross-account ownership filtering done by the API implementation itself, not by IAM policy evaluation) — because IAM literally has no resource ARN to evaluate here. The docs state the request supports arbitrary `SpotInstanceRequestId.N` values (`API_DescribeSpotInstanceRequests.md:81-84`) and filters (including `spot-instance-request-id` as a `Filter.N` value, line 58) but never explicitly document that the service filters by "resources owned by the caller's account" — this is assumed/implicit AWS backend behavior, universal across EC2 Describe* APIs, but **not asserted in this specific doc page**.
- **Confirm/Refute oracle**: From account A, call `DescribeSpotInstanceRequests --spot-instance-request-ids sir-<valid-but-foreign-id-from-account-B>`. Two possible outcomes define the oracle:
  - Error `InvalidSpotInstanceRequestID.NotFound` (or empty result set) → confirms per-account ownership filtering is enforced server-side (expected, secure behavior — matches how `DescribeInstances`, etc. behave for EC2 generally).
  - Returns account B's request details → confirmed IDOR (would be severe, cross-tenant data disclosure including `launchSpecification` contents — AMI ID, key pair name, security group IDs, subnet ID, and base64 `UserData` per `API_RequestSpotLaunchSpecification.md`).
  - A third, subtler oracle: **error-message/oracle differential** between "ID well-formed but belongs to another account" vs. "ID malformed" vs. "ID does not exist at all" — if EC2 returns a *different* error type or message for foreign-but-valid IDs vs. truly nonexistent IDs, that differential itself is an account-existence/resource-existence oracle (enumeration primitive), independent of whether the full object is disclosed. Docs do not document distinct error codes for these cases (`API_DescribeSpotInstanceRequests.md` Errors section just defers to `CommonErrors.md`), so this must be tested live to characterize, not something verifiable from documentation alone.
- **Preconditions**: Attacker needs a syntactically valid foreign `sir-` ID (a non-trivial precondition today given 17-hex-char entropy — see B1 — unless leaked via another channel, e.g., shared logs, the data feed `MyBidID` field at `spot-data-feeds.md:148`, CloudTrail events visible to the wrong principal, or a support ticket).
- **Severity-if-true**: **High** if full cross-account disclosure is confirmed (leaks `UserData`, AMI ID, key pair name, network config of another tenant's workload) — this would be a genuine cross-tenant boundary break, not self-inflicted. **None/not-applicable** if (as expected, consistent with AWS's general multi-tenant EC2 isolation model) the service enforces caller-account ownership filtering server-side regardless of IAM's lack of a resource-type entry.
- **Lens**: A.
- **Classification**: **This is the one genuine candidate cross-tenant boundary question in this whole fragment that is not resolvable from documentation alone** — the IAM reference's omission of a resource-type for the three `Describe*` actions is a real, documented asymmetry (contrast directly with `CancelSpotInstanceRequests`, which does have one), and it is exactly the shape of gap that has historically preceded real-world EC2 Describe-API IDOR reports elsewhere in AWS's history. Flag for live verification (by an authorized hunter, in their own two test accounts) rather than treated as confirmed.

### B3. `CancelSpotInstanceRequests` resource-level permission exists, but condition keys don't include an explicit "owner" check
- **Claim**: Unlike Describe*, `CancelSpotInstanceRequests` *does* support IAM resource-level permissions scoped to `spot-instances-request` ARNs (`list_ec2.md` ~4972-4977), with condition keys limited to `aws:ResourceTag`/`ec2:ResourceTag`/`ec2:Region`. There is no condition key analogous to an "owner" or "requester" check — tag-based conditions are the only fine-grained control offered.
- **Mechanism** (doc evidence): same `list_ec2.md` rows cited in B2, plus the ARN template `arn:${Partition}:ec2:${Region}:${Account}:spot-instances-request/${SpotInstanceRequestId}`. Note the ARN itself embeds `${Account}` — meaning a correctly written IAM policy (`Resource: arn:aws:ec2:*:111111111111:spot-instances-request/*`) *does* inherently scope to the caller's own account, because IAM resource-matching requires the account segment in the ARN to match. So the resource-level support that exists for Cancel is actually a *stronger* control than Describe's `Resource: "*"`-only model — this cuts the other way from B2's framing: Cancel is the safer-by-IAM-design action; Describe is the weaker-by-IAM-design one.
- **Confirm/Refute oracle**: A customer-authored IAM policy scoping `ec2:CancelSpotInstanceRequests` to `Resource: arn:aws:ec2:*:<their-account>:spot-instances-request/*` cannot, by IAM ARN-matching semantics, ever match a foreign account's request ARN, regardless of what ID value is supplied in the API call — so if the *identity policy* is written this way, cross-account cancellation is structurally impossible at the IAM layer (defense works as designed). The open question is only for principals holding `Resource: "*"` (common in practice, e.g. managed policies, legacy roles): for those, cross-account ownership enforcement again falls entirely to the EC2 service backend, not IAM — same backend-trust-assumption caveat as B2, just for Cancel instead of Describe.
- **Preconditions**: Only relevant to accounts whose policies grant `Resource: "*"` for this action.
- **Severity-if-true**: High if backend ownership enforcement were ever found missing (would allow a foreign, unauthorized account to cancel/DoS another tenant's Spot request) — but this would be a severe, basic multi-tenancy regression that is very unlikely given EC2's maturity; flagged for completeness/oracle-definition only.
- **Lens**: A.
- **Classification**: Genuine boundary *shape* exists in principle (same backend-trust caveat as B2) but lower prior likelihood than B2 because Cancel at least has the option of a correctly-scoped IAM policy as a real mitigating control that Describe* structurally cannot offer.

### B4. `DescribeSpotPriceHistory` — no account-specific data, minimal info-leak surface
- **Claim**: `DescribeSpotPriceHistory` returns market-wide pricing data (by instance type/AZ/product), not account-specific records — so despite also lacking a resource-type entry in IAM (`list_ec2.md` ~7422-7427), there is no cross-tenant data to leak via this API.
- **Mechanism** (doc evidence): `/work/aws-docs/docs/AWSEC2/latest/APIReference/API_DescribeSpotPriceHistory.md` request parameters are all market filters (`AvailabilityZone`, `InstanceType.N`, `ProductDescription`, time range) — no `SpotInstanceRequestId` or account-identifying parameter exists in this API at all.
- **Confirm/Refute oracle**: N/A — reading the parameter list is sufficient; there is no account-scoped identifier accepted or returned by this action per the docs.
- **Preconditions**: N/A.
- **Severity-if-true**: None.
- **Lens**: A.
- **Classification**: **No finding** — included to close out the item the task asked about; this API is public/market-data by design and out of scope.

## (C) Launch-specification content (`RequestSpotLaunchSpecification`)

### C1. `BlockDeviceMapping`/`EbsBlockDevice` — snapshot/encryption/KMS confusion surface
- **Claim**: The Spot launch spec lets the requester specify an arbitrary `SnapshotId` (no account-scoping or ownership proof enforced *in the schema* — authorization for snapshot access is deferred entirely to EBS/KMS permission checks at launch time) plus independent `Encrypted` and `KmsKeyId` fields, with a documented mutual-exclusion rule between snapshot-sourced volumes and specifying encryption state.
- **Mechanism** (doc evidence):
  - `/work/aws-docs/docs/AWSEC2/latest/APIReference/API_RequestSpotLaunchSpecification.md:19`: *"You can't specify both a snapshot ID and an encryption value. This is because only blank volumes can be encrypted on creation. If a snapshot is the basis for a volume, it is not blank and its encryption status is used for the volume encryption status."*
  - `/work/aws-docs/docs/AWSEC2/latest/APIReference/API_EbsBlockDevice.md:38-46` (`Encrypted` field): spells out the same rule in more detail, including: *"If you are creating a block device mapping from an existing encrypted or unencrypted snapshot, you must omit this parameter. If you include this parameter, the request will fail..."*
  - `API_EbsBlockDevice.md:61-65` (`KmsKeyId`): *"Identifier... of the customer managed KMS key to use for EBS encryption. This parameter is only supported on `BlockDeviceMapping` objects called by `RunInstances`, `RequestSpotFleet`, and `RequestSpotInstances`."* — confirms `RequestSpotInstances` is an explicitly supported caller for KMS-keyed volume creation.
  - `API_EbsBlockDevice.md:73-76` (`SnapshotId`): bare string, no ownership/account constraint documented in this field's description.
- **Analysis**: Cross-account snapshot use (launching a Spot Instance from a snapshot shared to you by another account) is a long-standing, *intended* EC2 feature — not a vulnerability by itself; authorization is enforced by EBS snapshot permissions (`CreateVolumePermission`) at the time EC2 attempts to create the volume, which is outside this API's own validation and outside this fragment's doc set. The "KMS key confusion" angle (Lens H) the task asked about would be: does the Spot launch path allow a requester to supply a `KmsKeyId` belonging to a *different* account than the snapshot's encryption key, and if the snapshot is itself encrypted (where `Encrypted`/`KmsKeyId` on the *request* must be omitted per the doc above), does `RequestSpotInstances` silently ignore a supplied `KmsKeyId` in that case, or error? The doc text implies EC2 should reject conflicting/redundant encryption parameters on snapshot-sourced volumes, but does not spell out behavior if `KmsKeyId` alone (without `Encrypted`) is supplied alongside a `SnapshotId` that is already encrypted with a *different* key — this exact permutation is undocumented and would need live testing to characterize, not something resolvable from the docs.
- **Confirm/Refute oracle**: Submit a `RequestSpotInstances` launch spec with `SnapshotId=<encrypted snapshot keyed with KMS key K1>` and `EbsBlockDevice.KmsKeyId=K2` (a different, caller-owned key) with no `Encrypted` field set. Per the docs the expected behavior is that "its encryption status is used for the volume encryption status" (i.e., K1 wins, K2 is ignored) — if instead K2 is silently applied, or the call errors ambiguously, that's a documentation-vs-behavior gap worth capturing, but not inherently a security boundary break since both K1 and K2 would need to be keys the *same* caller already has access to use.
- **Preconditions**: Caller needs pre-existing read access to the source snapshot (via its own account or a cross-account share) and `kms:*` permissions on any KMS key referenced — both are independent, already-gated permission boundaries; this API does not appear to offer a way to bypass either.
- **Severity-if-true**: Low as scoped by documentation alone (no boundary bypass is evidenced in the docs; genuine risk would only appear if live testing found the API accepting a `KmsKeyId` or `SnapshotId` the caller does NOT have permission to use and EC2 performed the permission check too late/incorrectly — out of scope for this doc-only pass).
- **Lens**: H (KMS key confusion), G.
- **Classification**: **Accepted-risk / standard EBS cross-account sharing model.** No boundary bypass identified in documentation; flagging the undocumented K1-vs-K2 precedence behavior as a gap worth a live hunter's attention, not a confirmed finding.

### C2. `ImageId` — raw identifier only, no name-based resolution in this API (name-confusion N/A here)
- **Claim**: Confirmed from the model: `RequestSpotLaunchSpecification.ImageId` is a plain `String` field (`API_RequestSpotLaunchSpecification.md:34-37`: *"The ID of the AMI. Type: String."*) with no corresponding `ImageName`/filter-based lookup parameter anywhere in this structure. This differs from APIs like `DescribeImages` that accept name-pattern filters.
- **Mechanism**: Absence of a name-based resolution parameter in the schema. The legacy `RequestSpotInstances` launch-spec path requires the caller to already know/resolve a concrete `ami-xxxxxxxx` ID before calling — there is no server-side "find AMI by name" step inside this API that could be confused/hijacked (the whoAMI-style name-confusion attack class, where an attacker publishes a public AMI whose *name* collides with a victim's expected pattern and the victim's tooling resolves by name rather than ID, requires a name-resolution step that simply does not exist inside `RequestSpotInstances`/`RequestSpotLaunchSpecification` itself).
- **Confirm/Refute oracle**: N/A — directly confirmed by absence of any name-pattern parameter in the schema; no live test needed to establish this for *this specific API*. (Name confusion could still occur one layer up, in whatever external tooling/script resolves a human-readable AMI name to an `ami-` ID before calling this API — but that resolution step lives outside `RequestSpotInstances` and is out of scope for this fragment.)
- **Preconditions**: N/A.
- **Severity-if-true**: N/A — this is a negative/confirmatory finding (ruling the class out for this specific API), not a vulnerability.
- **Lens**: Q (AMI/name resolution), ruled out.
- **Classification**: **Confirmed not applicable to this API.** Name-confusion risk, if any, sits entirely in caller-side tooling that resolves AMI names before invoking this API — outside this fragment's scope.

### C3. `UserData` → instance boot → IMDS/instance-profile credential retrieval
- **Claim**: The launch spec accepts a base64-encoded `UserData` blob (max 16 KB) that is delivered to the instance at boot and is retrievable by anything running on that instance via the Instance Metadata Service, and if an `IamInstanceProfile` is also attached to the Spot launch spec, the instance can additionally retrieve temporary role credentials from IMDS.
- **Mechanism** (doc evidence): `/work/aws-docs/docs/AWSEC2/latest/APIReference/API_RequestSpotLaunchSpecification.md:91-94` (`UserData`): *"The base64-encoded user data that instances use when starting up. User data is limited to 16 KB."*; `:29-32` (`IamInstanceProfile`): *"The IAM instance profile. Type: IamInstanceProfileSpecification object."*
- **Analysis**: This is the standard EC2 instance-metadata/IAM-instance-profile trust model, applying identically to Spot and On-Demand launches — **not** specific to the legacy Spot API and **not** a boundary issue by itself.
