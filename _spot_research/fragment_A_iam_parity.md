## 1. Resource-type / condition-key delta: RequestSpotInstances vs RunInstances

Confirmed directly from `list_ec2.md`. `RequestSpotInstances` (L9477–9487) declares exactly 8 resource types: `image`, `key-pair`, `network-interface`, `placement-group`, `security-group`, `snapshot`, `spot-instances-request*` (the only required one), `subnet`. It has **no** `instance` resource type and **no** `volume` resource type at all. `RunInstances` (L9585–9609) declares 14+ resource types including `instance*` (L9591) and `volume` (L9603), each carrying a long list of condition keys that simply do not exist anywhere in the `RequestSpotInstances` entry.

Even where both actions share a resource type (`network-interface`), the condition-key set differs: `RunInstances`'s `network-interface*` (L9595) includes `ec2:AssociatePublicIpAddress`; `RequestSpotInstances`'s `network-interface` (L9481) does not carry `ec2:AssociatePublicIpAddress` at all — only `AuthorizedUser`, `AvailabilityZone`, `ManagedResourceOperator`, `NetworkInterfaceID`, `Permission`, `Region`, `Subnet`, `Vpc`.

| Condition key | On RunInstances? | On RequestSpotInstances? | Guardrail it enforces (on RunInstances) | Bypass obtained via Spot path |
|---|---|---|---|---|
| `ec2:InstanceProfile` | Yes (`instance*`, L9591) | **No** | Restricts which IAM instance-profile ARN may be attached to the launched instance | Caller can attach any instance profile their `iam:PassRole` grant covers, regardless of the profile an admin tried to pin on `RunInstances` |
| `ec2:InstanceType` | Yes (L9591) | **No** | Restricts allowed instance type/size (cost or capability control) | Any instance type can be requested via Spot regardless of a `RunInstances`-scoped allow-list |
| `ec2:Tenancy` | Yes (L9591) | **No** | Pins dedicated/host/default tenancy | Spot request can pick a tenancy the admin tried to forbid on `RunInstances` (note: Spot tenancy options are limited by the Spot market itself, but the IAM control is still absent) |
| `ec2:MetadataHttpTokens` | Yes (L9591) | **No** | Enforces IMDSv2 (`required`) vs allowing IMDSv1 (`optional`) | No IAM lever exists to require IMDSv2 for Spot-launched instances. Compounded by product gap: the legacy `RequestSpotLaunchSpecification` model (per the lead analyst's context) has no `MetadataOptions`/`HttpTokens` field at all, so the instance's IMDS posture falls back entirely to account/region "Instance Metadata Defaults" (a separate, non-IAM setting), not to any launch-time parameter or policy |
| `ec2:MetadataHttpEndpoint` | Yes (L9591) | **No** | Enforces IMDS endpoint enabled/disabled | Same as above |
| `ec2:MetadataHttpPutResponseHopLimit` | Yes (L9591) | **No** | Limits PUT hop count (SSRF/container-pivot mitigation) | Same as above |
| `ec2:InstanceMetadataTags` | Yes (L9591) | **No** | Controls whether instance tags are exposed via IMDS | Not enforceable on Spot path |
| `ec2:CpuOptionsAmdSevSnp` | Yes (L9591) | **No** | Requires/forbids AMD SEV-SNP confidential computing | Not enforceable on Spot path |
| `ec2:RootDeviceType` | Yes, on both `instance*` (L9591) and `image*`/`image` (L9590/9479, 9590) | On `image` only (L9479) — **not on an `instance` resource because none exists** | Restricts root device type (ebs vs instance-store) of the *launched instance* | Image-level filter still applies, but there's no independent instance-level check |
| `ec2:Encrypted` | Yes (`volume`, L9603) | **No** (no `volume` resource type at all) | Requires EBS volume encryption at launch | A Spot-launched instance's attached volumes cannot be constrained to "must be encrypted" via IAM; inherited only from snapshot/AMI defaults or account-level EBS encryption-by-default |
| `ec2:VolumeSize` / `ec2:VolumeType` / `ec2:VolumeIops` / `ec2:VolumeThroughput` | Yes (`volume`, L9603) | **No** | Caps volume size/type/performance (cost control) | No IAM-level cap on volumes attached via Spot BlockDeviceMapping |
| `ec2:AssociatePublicIpAddress` | Yes (`network-interface*`, L9595) | **No** (network-interface condition-key list at L9481 omits it) | Blocks/forces public IP assignment on the primary ENI at launch | Caller can set `NetworkInterface[].AssociatePublicIpAddress: true` in the Spot `LaunchSpecification` with no IAM guardrail, even if `RunInstances` is locked down to forbid public IPs |
| `ec2:PlacementGroup` | Yes (`instance*`, L9591) | **No** (Spot only has the separate `placement-group` resource type with `PlacementGroupName`/`Strategy`, L9482) | Restricts which placement group an instance joins, referenced from the instance side | Marginal — the `placement-group` resource type still exists for Spot, so this delta is weaker than the others; noted for completeness |

Net: of the ~15 condition keys tied to `instance`/`volume`/the `AssociatePublicIpAddress` network-interface key, **all are structurally unavailable to any policy author trying to scope `ec2:RequestSpotInstances`**, because the resource types that carry them (`instance`, `volume`) do not appear in the action's resource-type list at all. This isn't a narrower version of the same control — it is a total absence; there is no condition key an admin can write against `RequestSpotInstances` that inspects anything about the instance or its volumes.

## 2. Modern-path parity check: RequestSpotFleet / CreateFleet

`RequestSpotFleet` (`list_ec2.md` L9465–9475): resource types `image`, `key-pair`, `launch-template`, `placement-group`, `security-group`, `snapshot`, `spot-fleet-request*`, `subnet`. Same structural gap as `RequestSpotInstances` — no `instance`, no `volume`, no `network-interface` resource type at all (not even the weaker Spot-Instances-style `network-interface` entry). The `launch-template` resource type it does carry (L9469) only exposes `ManagedResourceOperator`/`Region`/tag keys — not any instance/volume semantics.

`CreateFleet` (the modern, launch-template-centric fleet action, L5113–5123) **does** restore `instance*` (L5118, with `ec2:InstanceProfile`, `ec2:InstanceType`, `ec2:Tenancy`, `ec2:CpuOptionsAmdSevSnp`, `ec2:EbsOptimized`, `ec2:PlacementGroup`, `ec2:RootDeviceType`) and `volume` (L5122, with `ec2:Encrypted`, `ec2:KmsKeyId`, `ec2:VolumeIops/Size/Throughput/Type`). This confirms the gap is legacy-specific rather than inherent to "Spot" as a pricing model — the modern fleet action was explicitly re-plumbed to carry instance/volume condition keys that the legacy Spot actions never got.

Two caveats on `CreateFleet`, both documented:
1. Its `instance*` condition-key list (L5118) is still missing `ec2:MetadataHttpTokens`, `ec2:MetadataHttpEndpoint`, `ec2:MetadataHttpPutResponseHopLimit`, `ec2:InstanceMetadataTags`, `ec2:InstanceAutoRecovery`, `ec2:InstanceMarketType`, `ec2:ProductCode`, `ec2:AvailabilityZone` relative to `RunInstances`'s `instance*` (L9591) — i.e. the modern path closes the PassRole/Tenancy/volume-encryption gaps but **not** the IMDSv2-enforcement gap.
2. `CreateFleet`'s own description (L5114) states explicitly: *"Resource-level permissions for this action do not include the resources specified in a launch template. To specify resource-level permissions for resources specified in a launch template, you must include the resources in the RunInstances action statement."* AWS is telling policy authors they must write a parallel `ec2:RunInstances` statement to cover launch-template-sourced resources (image, instance, network-interface, etc.) for a `CreateFleet` call. **`RequestSpotFleet`'s entry has no equivalent note** (verified: no "launch template" / "does not include" text anywhere near L9465–9475) — AWS never documented a companion mechanism for the legacy Spot Fleet path, even though `RequestSpotFleet` also supports `LaunchTemplateConfigs`. This is further evidence the legacy action was simply never updated for the condition-key model introduced for `RunInstances`/`CreateFleet`.

## 3. iam:PassRole analysis (instance profile passed to the Spot instance)

`spot-fleet-prerequisites.md` L90–91 (the "Important" box) states, in the admin-facing example policy: *"If you specify a role for the IAM instance profile in the launch specification or launch template, you must grant the user the permission to pass the role to the service. To do this, in the IAM policy include `arn:aws:iam::*:role/{{IamInstanceProfile-role}}` as a resource for the `iam:PassRole` action."*

This confirms: (a) `RequestSpotInstances`/`RequestSpotFleet` do require the caller to hold `iam:PassRole` on whatever role is referenced by `IamInstanceProfile`, same as `RunInstances`; (b) the *only* scoping mechanism offered is the `Resource` ARN(s) in the caller's own `iam:PassRole` statement — there is no EC2-side condition key equivalent to `ec2:InstanceProfile` that can be attached to the Spot action itself, because (per section 1) the `instance` resource type that carries `ec2:InstanceProfile` is absent from `RequestSpotInstances`'/`RequestSpotFleet`'s resource-type list. `iam:PassedToService` (an IAM-side condition, not an EC2 one) can restrict passing to `ec2.amazonaws.com` generically, but cannot restrict *which* profile is attachable per-launch-API the way `ec2:InstanceProfile` could.

Consequence: if an admin's intended control is "RunInstances callers may only attach `low-priv-profile`, enforced via `Condition: {StringEquals: {ec2:InstanceProfile: arn:...low-priv-profile}}` on the `ec2:RunInstances` statement" — and the same principal separately holds a broader `iam:PassRole` grant (e.g., `Resource: arn:aws:iam::*:role/*` or several role ARNs, which is common because `iam:PassRole` is often granted more broadly than any single launch action needs, or because the admin granted PassRole for the Spot Fleet tagging role plus other roles in the same statement) — **that principal can pass any role covered by their PassRole grant via `RequestSpotInstances`/`RequestSpotFleet`, because the Spot action has no `ec2:InstanceProfile` condition to intersect against.** The `ec2:InstanceProfile` pin only ever applied to `RunInstances`; it was never a property of the role or the PassRole grant itself. So yes — a caller with broad `iam:PassRole` can pass any passable role through the Spot path even where an admin pinned `ec2:InstanceProfile` on `RunInstances`.

## 4. Service-linked-role / tagging-role audit

### (a) AWSServiceRoleForEC2Spot — StopInstances/StartInstances scope
`service-linked-roles-spot-instance-requests.md` L15–18 lists the permissions as plain bullet prose: `ec2:DescribeInstances`, `ec2:StopInstances`, `ec2:StartInstances`, each annotated only with a human-readable gloss ("Stop Spot Instances", "Start Spot Instances"). **No IAM policy JSON, resource ARN pattern, or condition key is shown anywhere in this document for the SLR's actual permissions policy** — unlike the managed-policy pages (e.g. `AmazonEC2SpotFleetTaggingRole.md`) which show the full JSON. The "Spot Instances" scoping is asserted in prose only; the doc gives no evidence of a technical restriction (e.g., no `ec2:InstanceLifecycle` / tag condition shown) limiting the SLR's Stop/Start calls to Spot-flagged instances specifically versus any instance in the account. This is a doc-vs-enforcement gap (Lens U): the document does not substantiate the "Spot Instances only" claim with policy evidence.

### (b) KMS grant CreateGrant operation
Both `spot-fleet-prerequisites.md` L205–209 and `service-linked-roles-spot-instance-requests.md` L63–67 show the identical recommended `aws kms create-grant` command granting `AWSServiceRoleForEC2SpotFleet` / `AWSServiceRoleForEC2Spot` the operations: `Decrypt`, `Encrypt`, `GenerateDataKey`, `GenerateDataKeyWithoutPlaintext`, `CreateGrant`, `DescribeKey`, `ReEncryptFrom`, `ReEncryptTo`. `CreateGrant` lets the SLR itself mint further grants on the CMK — i.e. it is not merely a *use* permission but a *delegation* permission. AWS's own documented recipe grants this to a service-linked role whose trust policy restricts assumption to the EC2 Spot/Spot Fleet service principal, which bounds the blast radius to "whatever EC2's spot/spotfleet service does with it" — but the doc gives no narrower grant constraints (no `GrantConstraints` / `EncryptionContextSubset` shown in the example), so as documented the SLR can grant Decrypt/Encrypt/GenerateDataKey etc. on the CMK to any grantee it chooses, bounded only by its own trust policy.

### (c) aws-ec2-spot-fleet-tagging-role / AWSServiceRoleForEC2SpotFleet grants, and name-prefix PassRole scoping
- `AWSServiceRoleForEC2SpotFleet` (`spot-fleet-prerequisites.md` L141–150): grants `ec2:RequestSpotInstances`, `ec2:RunInstances`, `ec2:TerminateInstances`, `ec2:DescribeImages`, `ec2:DescribeInstanceStatus`, `ec2:DescribeSubnets`, `ec2:CreateTags`, plus two `elasticloadbalancing:Register*` actions.
- `aws-ec2-spot-fleet-tagging-role` is documented (L217–223) as granting tag permission on the fleet request/instances/volumes, and AWS explicitly recommends using the `AmazonEC2SpotFleetTaggingRole` managed policy for it (L223). That managed policy's actual JSON (`AmazonEC2SpotFleetTaggingRole.md` L34–88) shows:
  ```
  { "Effect":"Allow", "Action":["ec2:DescribeImages","ec2:DescribeSubnets","ec2:RequestSpotInstances",
    "ec2:TerminateInstances","ec2:DescribeInstanceStatus","ec2:CreateTags","ec2:RunInstances"], "Resource":["*"] },
  { "Effect":"Allow", "Action":"iam:PassRole",
    "Condition":{"StringEquals":{"iam:PassedToService":["ec2.amazonaws.com","ec2.amazonaws.com.cn"]}},
    "Resource":["*"] },
  ...
  ```
  **This is a wildcard `iam:PassRole` (Resource `*`) scoped only by `iam:PassedToService = ec2.amazonaws.com`.** The only thing stopping this role from passing *any* role in the account to EC2 is the `PassedToService` condition (service, not target-role identity) — there is no resource-ARN narrowing at all.

  This role is itself only assumable by `spotfleet.amazonaws.com` via `sts:AssumeRole`, and AWS's confused-deputy guidance (L245–313) recommends scoping that trust policy with `aws:SourceArn`/`aws:SourceAccount` tied to `spot-fleet-request/sfr-*`. Critically, **this confused-deputy hardening is opt-in** ("We recommend that you use...") — if an admin skips it, any entity able to invoke `RequestSpotFleet` with this `IamFleetRole` can cause the service to assume a role with blanket cross-account-unrestricted PassRole(*)-to-EC2, in that account.

- **Name-prefix PassRole bypass**: the admin-facing least-privilege example in `spot-fleet-prerequisites.md` L59–63 grants the *end user* (not the service) `iam:PassRole` scoped as:
  ```
  "Resource": "arn:aws:iam::*:role/aws-ec2-spot-fleet-tagging-role"
  ```
  This is an exact-literal-name match (the `*` wildcard covers only the account-ID segment of the ARN, not the role name). The doc also lists, as "Optional IAM APIs" an admin may grant end users (L103–111): `iam:CreateRole`, `iam:AttachRolePolicy`, `iam:CreateInstanceProfile`, `iam:AddRoleToInstanceProfile`, `iam:GetRole`, `iam:ListPolicies` — "to enable a user to create roles or instance profiles using the IAM console." **If both grants coexist** (common, since the doc presents them as a normal pairing for self-service onboarding), a user can: (1) `iam:CreateRole` a role literally named `aws-ec2-spot-fleet-tagging-role` with a trust policy trusting `spotfleet.amazonaws.com`; (2) `iam:AttachRolePolicy` any managed/inline policy of their choosing onto it (the doc shows no restriction on *which* policy may be attached); (3) pass that self-created role as `IamFleetRole` via their exact-name-scoped `iam:PassRole` grant; (4) have `RequestSpotFleet` cause the service to assume their role and exercise whatever permissions they attached to it, limited only by what the `spotfleet.amazonaws.com` service principal actually calls (per the fixed action list in (b)) during the fleet's lifecycle — not a direct admin-privilege grab, but a path to smuggle attacker-chosen extra permissions (e.g., broader `iam:PassRole`, or write access beyond EC2) into a role that gets assumed by an AWS service under the user's indirect control, independent of whatever the admin intended that name to mean.

## 5. Findings (lead format)

### Lead 1 — Legacy Spot launch path has no IAM lever over the launched instance or its volumes
- **Claim**: `ec2:RequestSpotInstances` cannot be scoped by `ec2:InstanceProfile`, `ec2:InstanceType`, `ec2:Tenancy`, `ec2:Encrypted`, `ec2:VolumeSize/Type`, `ec2:AssociatePublicIpAddress`, or any IMDS-related key, even though `ec2:RunInstances` can.
- **Mechanism (doc evidence)**: `list_ec2.md` L9477–9487 (`RequestSpotInstances` resource types: image/key-pair/network-interface/placement-group/security-group/snapshot/spot-instances-request/subnet — no `instance`, no `volume`) vs L9585–9609 (`RunInstances` resource types include `instance*` L9591 and `volume` L9603, carrying those keys). Network-interface key delta confirmed at L9481 (no `AssociatePublicIpAddress`) vs L9595 (has it).
- **Confirm/Refute oracle**: In a test account, attach a policy that `Allow`s `ec2:RunInstances` only when `ec2:AssociatePublicIpAddress=false` (and separately `Allow`s `ec2:RequestSpotInstances` with `Resource:*`, no condition). Issue `RequestSpotInstances` with `NetworkInterface[0].AssociatePublicIpAddress=true`. If it succeeds while the equivalent `RunInstances` call is denied, the gap is confirmed live. `iam:SimulatePrincipalPolicy` with `ActionNames=["ec2:RequestSpotInstances"]` and `ContextEntries` for `ec2:AssociatePublicIpAddress` should also show the key is not recognized/evaluated for that action.
- **Preconditions**: caller has `ec2:RequestSpotInstances` (commonly broad/unconditioned, since admins rarely think to restrict the legacy action) plus ordinary launch prerequisites (subnet, security group, AMI access).
- **Severity if true**: High — silently defeats public-IP, IMDSv2, tenancy, and EBS-encryption guardrails that an org believes are enforced account-wide via `RunInstances` conditions.
- **Lenses**: S (condition-key semantics), X (legacy-action parity), U (doc-vs-enforcement).

### Lead 2 — PassRole + missing ec2:InstanceProfile on Spot path = instance-profile pinning bypass
- **Claim**: An org that pins allowed instance profiles via `ec2:InstanceProfile` on `ec2:RunInstances` gets no protection against the same principal attaching a different, more-privileged profile via `ec2:RequestSpotInstances`/`RequestSpotFleet`, as long as their `iam:PassRole` grant covers that other role.
- **Mechanism (doc evidence)**: `spot-fleet-prerequisites.md` L90–91 (PassRole is the only documented scoping mechanism for the Spot path's instance profile); `list_ec2.md` confirms `ec2:InstanceProfile` exists only under `RunInstances`'s/`CreateFleet`'s `instance*` resource type (L9591, L5118), never under `RequestSpotInstances`/`RequestSpotFleet`.
- **Confirm/Refute oracle**: Grant a principal `iam:PassRole` on two roles, `low-priv` and `high-priv`; grant `ec2:RunInstances` conditioned on `ec2:InstanceProfile = arn:...low-priv` only, and grant unconditioned `ec2:RequestSpotInstances`. Attempt `RunInstances` with `high-priv` (expect Deny) then `RequestSpotInstances` with `high-priv` (expect Allow). The instance then exposes `high-priv` credentials via IMDS.
- **Preconditions**: broad-enough `iam:PassRole` grant (common misconfiguration — PassRole is frequently granted at a coarser scope than any single launch action strictly needs) plus unconditioned (or less-conditioned) `ec2:RequestSpotInstances`/`RequestSpotFleet`.
- **Severity if true**: High / potential privilege escalation — direct path to instance-profile-mediated credential acquisition for any PassRole-reachable role.
- **Lenses**: B (PassRole), E (privesc), S (condition-key semantics), X (legacy-action parity).

### Lead 3 — aws-ec2-spot-fleet-tagging-role name-prefix PassRole + self-service IAM APIs = attacker-controlled service-assumed role
- **Claim**: The commonly-documented pairing of (exact-name-scoped PassRole to `aws-ec2-spot-fleet-tagging-role`) + (self-service `iam:CreateRole`/`iam:AttachRolePolicy`/`iam:CreateInstanceProfile`) lets a user create their own role under that exact name, attach arbitrary permissions, and have it assumed by `spotfleet.amazonaws.com` as the fleet's `IamFleetRole`.
- **Mechanism (doc evidence)**: `spot-fleet-prerequisites.md` L59–63 (`iam:PassRole` Resource = literal `arn:aws:iam::*:role/aws-ec2-spot-fleet-tagging-role`) presented alongside L103–111 ("Optional IAM APIs" incl. `iam:CreateRole`, `iam:AttachRolePolicy`, `iam:CreateInstanceProfile`) in the same walkthrough; `AmazonEC2SpotFleetTaggingRole.md` L53–67 shows the role AWS recommends for this purpose already carries wildcard `iam:PassRole` (`Resource:*`) gated only by `iam:PassedToService`; confused-deputy trust-policy hardening (`spot-fleet-prerequisites.md` L245–313) is presented as a recommendation, not a default.
- **Confirm/Refute oracle**: In a test account, grant a principal exactly the policy shown in L41–75 of `spot-fleet-prerequisites.md` plus the optional IAM APIs from L103–111. Have that principal `iam:CreateRole` a role named `aws-ec2-spot-fleet-tagging-role` trusting `spotfleet.amazonaws.com`, attach a broad policy to it, then call `RequestSpotFleet` with `IamFleetRole` set to that role's ARN. Observe (via CloudTrail `AssumeRole`/subsequent calls) whether the service assumes the attacker-authored role and whether its attached permissions take effect during the fleet lifecycle.
- **Preconditions**: admin grants both the exact-name PassRole statement and the "optional" self-service IAM role-creation APIs from the same doc page's walkthrough — a realistic, documented-as-normal combination for teams onboarding Spot Fleet via CLI/API rather than console.
- **Severity if true**: Medium-High — contingent on what `spotfleet.amazonaws.com` actually does with the assumed role's permissions beyond its fixed action list, and on whether `iam:PassedToService`/trust-policy hardening is in place; still a clear IAM-artifact-naming-convention-as-security-boundary anti-pattern (Lens R).
- **Lenses**: R (IAM-artifact audit), B (PassRole), E (privesc), U (doc-vs-enforcement — the doc treats a role *name* as if it were an access-controlled identity).

### Lead 4 (supporting / lower confidence) — SLR Stop/Start scope asserted only in prose
- **Claim**: `AWSServiceRoleForEC2Spot`'s `ec2:StopInstances`/`ec2:StartInstances` grant is documented only as acting on "Spot Instances," with no policy JSON or condition key shown to substantiate that scope.
- **Mechanism (doc evidence)**: `service-linked-roles-spot-instance-requests.md` L15–18 — bullet list, prose only, no JSON (contrast with `AmazonEC2SpotFleetTaggingRole.md` which does show full JSON for a comparable role).
- **Confirm/Refute oracle**: Would require inspecting the actual SLR policy document in a live account (`aws iam get-role-policy` / `list-attached-role-policies` for `AWSServiceRoleForEC2Spot`) to see if a resource/tag condition restricts Stop/Start to Spot-flagged instances, or if it's `Resource:*` with no condition (trust-boundary-only enforcement). Documentation alone cannot resolve this — flagged as a doc-vs-enforcement gap requiring live verification, not a confirmed finding.
- **Preconditions**: N/A (informational).
- **Severity if true**: Low-Medium by itself (the SLR's trust policy restricts assumption to the EC2 Spot service, bounding exposure), but worth confirming given the CreateGrant/KMS delegation noted in Lead 3's sibling finding (4b above).
- **Lenses**: U (doc-vs-enforcement), R (IAM-artifact audit).

## Summary of confirmed deltas (for the lead analyst)

1. **Resource-type delta is total, not partial**: `RequestSpotInstances`/`RequestSpotFleet` carry zero `instance`/`volume` resource types in `list_ec2.md`, so every condition key that normally lives on those resource types for `RunInstances` (InstanceProfile, InstanceType, Tenancy, MetadataHttpTokens/Endpoint/HopLimit, InstanceMetadataTags, CpuOptionsAmdSevSnp, Encrypted, VolumeSize/Type/Iops/Throughput) is structurally unenforceable against the Spot path. The `network-interface` resource type is present for `RequestSpotInstances` but missing `ec2:AssociatePublicIpAddress`.
2. **The gap is legacy-specific, not Spot-inherent**: `CreateFleet` (modern) restores `instance*`/`volume` condition keys (minus the IMDS-metadata keys) and documents a companion-`RunInstances`-statement pattern for launch-template-sourced resources. `RequestSpotFleet` has neither the resource types nor that documented companion-statement guidance, despite also supporting launch templates.
3. **PassRole is the sole, insufficient scoping control** for the IAM instance profile on the Spot path — confirmed by `spot-fleet-prerequisites.md`'s own admin guidance, with no `ec2:InstanceProfile`-equivalent available to supplement it.

## Top 3 leads (by priority)
1. **Lead 2** — `ec2:InstanceProfile` pinning on `RunInstances` is bypassable via `RequestSpotInstances`/`RequestSpotFleet` for any PassRole-reachable role (clean privesc path, strong doc evidence, cheap to verify live).
2. **Lead 1** — Public-IP / IMDSv2 / EBS-encryption / tenancy guardrails built on `RunInstances` conditions have zero coverage on the legacy Spot path (broad blast radius, affects every org treating `RunInstances` conditions as a universal EC2 launch guardrail).
3. **Lead 3** — `aws-ec2-spot-fleet-tagging-role` name-literal PassRole scoping, combined with commonly-granted self-service IAM role-creation permissions and the AWS-authored `AmazonEC2SpotFleetTaggingRole` managed policy's wildcard PassRole, is a naming-convention-as-security-boundary anti-pattern worth live verification.
