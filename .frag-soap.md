# Cluster: SOAP API (deprecated, still live over HTTPS) — legacy protocol parity

Source of leads: local mirror `/work/aws-docs/docs/AmazonS3/latest/developerguide/{APISoap,SOAPAuthentication,SOAPAccessPolicy,SOAPErrorResponses,SOAPCreateBucket,SOAPDeleteBucket,SOAPListAllMyBuckets,SOAPListBucket,SOAPBucketsOps,SOAPServiceOps,SOAPPutObject,SOAPPutObjectInline,SOAPGetObject,SOAPGetObjectExtended,SOAPCopyObject,SOAPDeleteObject,SOAPObjectsOps,SOAPGetBucketAccessControlPolicy,SOAPSetBucketAccessControlPolicy,SOAPGetObjectAccessControlPolicy,SOAPSetObjectAccessControlPolicy,SOAPGetBucketLoggingStatus,SOAPSetBucketLoggingStatus}.md`, cross-checked against the live `docs.aws.amazon.com` pages for `APISoap.html` and `SOAPAccessPolicy.html` (byte-identical content, confirming the mirror is current and the omissions below are real doc omissions, not mirror staleness). Status: documentation-derived hypotheses only; nothing tested against a live account.

Every page in this cluster carries the same banner: *"SOAP APIs for Amazon S3 are not available for new customers, and are approaching End of Life (EOL) on August 31, 2025."* The core thesis: the SOAP surface is a 2006-vintage code path (`xmlns="https://doc.s3.amazonaws.com/2006-03-01"` on every operation) that predates Block Public Access (2018), S3 Object Ownership / ACLs-disabled (2021), bucket policies (2011), SigV4 (2014), and STS-based temporary credentials becoming the recommended default — "new features are not added to SOAP" per AWS's own framing elsewhere in this doc set. Every one of those later controls is a *retrofit* onto the REST/IAM path. Nothing in any of the 23 pages below ever mentions "Block Public Access," "Object Ownership," "bucket policy," "condition key," "CloudTrail," or "SigV4" — not once, in any page. That silence, across the service's entire SOAP corpus, is itself the finding this cluster is built around: either those controls are transparently enforced underneath the legacy API shim (undocumented but safe), or the SOAP code path only ever evaluates the legacy ACL/ownership model it shipped with in 2006 and never reaches the newer gates at all (undocumented and a boundary breach). The docs do not resolve this either way — it is marked as the top null-hypothesis / doc-gap below, and it is the single most consequential question this cluster can hand to a live hunter.

## 2. REST/SOAP control-parity table

|---|---|---|---|

Doc only says `WRITE_ACP` rights are required; `SOAPAccessPolicy.md`'s own worked example sets `Group URI http://acs.amazonaws.com/groups/global/AllUsers` + `READ` with no caveat about BPA | A `SetBucketAccessControlPolicy`/`PutObjectInline` call carrying an `AllUsers:READ` (or `WRITE`/`FULL_CONTROL`) grant **succeeds** on a bucket/account that has Block Public Access enabled, where the REST twin (`PutBucketAcl`) would return `AccessDenied` |
| same ops | **S3 Object Ownership = BucketOwnerEnforced** (ACLs entirely disabled on the bucket; REST `PutBucketAcl`/`PutObjectAcl` and any ACL on `PutObject` fail with `AccessControlListNotSupported`) | Not mentioned anywhere in the cluster | A SOAP ACL-setting call **succeeds** (and a non-default grant takes effect) on a bucket whose Object Ownership is `BucketOwnerEnforced`, where REST would hard-fail |
| every op (whole cluster) | **Bucket policies** and **`s3:` condition keys** (`s3:x-amz-acl`, `s3:x-amz-server-side-encryption`, `aws:SecureTransport`, `aws:SourceIp`, `aws:sourceVpce`, `s3:signatureversion`) — REST/SDK calls are evaluated against the bucket policy and SCPs in addition to the legacy ACL | Never referenced. All 16 operation pages describe authorization purely in terms of the five-value ACL permission set or raw bucket ownership | A SOAP request that a bucket-policy explicit **Deny** should block (e.g. "deny unless `aws:SecureTransport`", "deny unless VPC endpoint X", "deny `PutObjectAcl` with public grant") still **succeeds**, because the SOAP legacy authorizer only consults the ACL/ownership model it shipped with, never the policy-evaluation engine the REST path added in 2011+ |
| `GetBucketLoggingStatus`/`SetBucketLoggingStatus` | REST `GetBucketLogging`/`PutBucketLogging` are IAM-permission actions (`s3:GetBucketLogging`/`s3:PutBucketLogging`) that can be **delegated** to any principal via an identity or bucket policy, independent of "ownership" | Doc hard-codes "**Only the owner** of a bucket is permitted to invoke this operation" — a literal ownership check, not an IAM-permission check | Two directions are each a parity break: (a) a delegated non-owner principal who legitimately holds `s3:PutBucketLoggingStatus` via IAM cannot use it over SOAP (functional gap, not a security hole) — **or**, more importantly, (b) if "owner" resolves only to the account's canonical/root identity and the SOAP authorizer never resolves the caller down to a specific IAM principal, an explicit bucket-policy **Deny** aimed at a *specific IAM user/role* (not the root account) may not bind to a SOAP call made with that same IAM user's long-term access key, because SOAP's authorization decision isn't the policy engine at all |
| all authenticated ops | **STS temporary credentials / MFA-enforced access** — modern guidance (and many customer SCPs) require session tokens or `aws:MultiFactorAuthPresent` | `SOAPAuthentication.md`: **"temporary security credentials are not supported"** — only long-term `AWSAccessKeyId`+Secret works | A customer SCP/IAM policy written as `"Condition": {"Bool": {"aws:MultiFactorAuthPresent": "false"}}` (missing an explicit `BoolIfExists`/null-check) is the textbook MFA-enforcement footgun: the condition key is only ever populated by STS. A SOAP request, which never goes through STS, presents **no** `aws:MultiFactorAuthPresent` key at all — not `false`, simply absent — so a `Bool`-keyed Deny statement does not match and the request is allowed through, exactly where an equivalent unauthenticated-MFA REST call using the same static key would also pass (so this isn't SOAP-specific per se) **except** that SOAP is the one path that structurally cannot ever satisfy an MFA-required Allow, yet still offers full read/write/ACL/logging control to any account that still has one un-rotated long-term IAM user key — a legacy-credential amplifier |
| `CreateBucket`, `DeleteBucket`, `ListBucket`(MaxKeys=0) | REST error-oracle hardening (generic `AccessDenied` without existence hints is the modern default guidance) | `SOAPCreateBucket.md` **explicitly documents** the oracle: *"use `ListBucket` and set `MaxKeys` to 0. A `NoSuchBucket` response indicates that the bucket is available, an `AccessDenied` response indicates that someone else owns the bucket, and a Success response indicates you own it or have permission."* | This is a **confirmed-by-docs** (not merely plausible) global bucket-existence/ownership enumeration oracle — AWS's own text instructs using it. Severity is bounded by the fact it's long-published guidance, but it is a real Lens A oracle that still works today over the SOAP path and reveals bucket-ownership information REST increasingly tries to mask |
| `DeleteObject` | REST `DeleteObject`: idempotent, 204 regardless of prior existence (no oracle) | `SOAPDeleteObject.md`: "If you delete an object that does not exist, Amazon S3 will return a success (not an error message)" | Parity holds — no divergence, listed as a confirmed null result |
| `CopyObject` | REST `CopyObject`/`x-amz-copy-source`: ACL reset to private on copy unless overridden | `SOAPCopyObject.md`: "the ACL is not preserved and is set to `private`... unless you specify a new ACL" | Parity holds |
| All signed ops | SigV4 canonical-request signing binds the signature to the full request (headers, resource path, body hash) | `SOAPAuthentication.md`: signature = `HMAC-SHA1("AmazonS3" + OPERATION + Timestamp)` — **the Bucket name, Key, AccessControlList, Data/metadata, and every other body element are explicitly excluded from the signed material** | See Lens Y lead below — this is the highest-severity transport finding in the cluster |

## 3. Ranked lens-mapped falsifiable leads

### Lead 1 — [Lens Y, Critical if true] Signature does not bind to resource or body — forgery/tamper surface
**Claim:** A valid SOAP signature for one request can be replayed, with its body substituted, to perform a *different* action against a *different* resource, because the signature never covers the resource or payload.
**Mechanism (doc evidence):** `SOAPAuthentication.md`: *"Signature: The RFC 2104 HMAC-SHA1 digest of the concatenation of 'AmazonS3' + OPERATION + Timestamp, using your AWS Secret Access Key as the key."* The worked example states the signed value for a `CreateBucket` call is literally the string `"AmazonS3CreateBucket2009-01-01T12:00:00.000Z"` — bucket name `quotes` and the `Acl` element are not part of it. Every operation page (`SOAPCreateBucket.md`, `SOAPPutObject.md`, `SOAPSetBucketAccessControlPolicy.md`, etc.) reuses the identical `AWSAccessKeyId`/`Timestamp`/`Signature` triple pattern with no additional per-request binding element.
**Confirm/Refute oracle:** Capture one valid signed SOAP request for `OPERATION=X` at `Timestamp=T` (replay window is 15 minutes per the same page). Resubmit the identical `AWSAccessKeyId`/`Timestamp`/`Signature` triple with every other element of the body changed (different `Bucket`, `Key`, `AccessControlList`, `Data`) within the 15-minute window. If accepted, the signature confirmed to be purely `OPERATION`+`Timestamp`-scoped, independent of body — a forgeable-by-substitution oracle for anyone who observes one wire-captured request (SOAP must be over SSL per `APISoap.md`, so this requires a MITM/log-leak precondition, but any proxy/debug log capturing the plaintext triple post-TLS-termination defeats it).
**Preconditions:** Observe one valid signed request to the same `OPERATION` name (operation name is the only part of the signed material that must match). Cost: trivial once a sample is captured. **Severity:** High–Critical — turns a single captured legacy-credential request into an all-fields-attacker-controlled forgery for that operation.

### Lead 2 — [Lens X / Lens S, Critical if true] SOAP ACL-setting ops as the un-gated twin of REST `PutBucketAcl`/`PutObjectAcl`
**Claim:** `SetBucketAccessControlPolicy`, `SetObjectAccessControlPolicy`, and the ACL-at-write-time path (`CreateBucket`, `PutObject`, `PutObjectInline` with an inline `AccessControlList`) do not consult Block Public Access or Object-Ownership (`BucketOwnerEnforced`) the way their REST/IAM twins do.
**Mechanism (doc evidence):** `SOAPAccessPolicy.md` worked example sets `Grantee xsi:type="Group" URI=.../groups/global/AllUsers` with `Permission=READ` with zero caveats. `SOAPSetBucketAccessControlPolicy.md`/`SOAPSetObjectAccessControlPolicy.md` state only "You must have `WRITE_ACP` rights" — no mention of account-level or bucket-level BPA settings, nor of Object Ownership. None of the 23 pages in this cluster contain the strings "Block Public Access," "BlockPublicAcls," or "Object Ownership" (checked by direct read of every assigned page).
**Confirm/Refute oracle:** On a bucket/account with all four BPA settings enabled (or Object Ownership = BucketOwnerEnforced), issue `SetBucketAccessControlPolicy` (or `PutObjectInline`) with an `AllUsers:READ`/`WRITE` grant. REST parity says this must fail (`AccessDenied`/`AccessControlListNotSupported`); if the SOAP call returns the documented `200 OK` success body instead, the legacy ACL authorizer has bypassed a control that postdates it by 12+ years.
**Preconditions:** Any account with one long-term IAM credential and `WRITE_ACP` on a BPA-protected bucket. **Severity:** Critical — direct re-enablement of public bucket/object exposure through a control customers believe is a hard account-wide gate.

### Lead 3 — [Lens S, High if true] Bucket-policy Deny statements and `s3:`/`aws:` condition keys may never be evaluated on the SOAP path
**Claim:** The SOAP authorizer evaluates only the legacy ACL permission set (`READ`/`WRITE`/`READ_ACP`/`WRITE_ACP`/`FULL_CONTROL`) and bucket ownership, and never evaluates the bucket's resource policy or any `Condition` block, so a protective bucket-policy Deny (`aws:SecureTransport`, `aws:SourceIp`, `aws:sourceVpce`, `s3:x-amz-acl`) is silently inert against SOAP calls.
**Mechanism (doc evidence):** Every one of the 16 operation pages' "Access Control" sections frames authorization exclusively in ACL-permission or ownership terms (see table in §1). The phrase "bucket policy" appears nowhere in the cluster; the phrase "condition key" appears nowhere in the cluster. `SOAPAccessPolicy.md` even states a resource "created with a default access policy" meaning the legacy ACL default, not an IAM/bucket policy.
**Confirm/Refute oracle:** Attach a bucket policy with an explicit `"Effect":"Deny"` statement gated on a condition key (e.g. deny all actions unless `aws:SecureTransport=true`, or deny `s3:PutObjectAcl`/ACL-setting unless `s3:x-amz-acl` is not public) to a bucket. Issue the SOAP equivalent operation (which per `APISoap.md` is always sent over SSL already, so pick a condition the SOAP request would otherwise violate, e.g. a source-IP restriction naming an IP range excluding the test host, or a Deny on public-ACL grants). If the SOAP call still succeeds where the identical-intent REST call is denied, the bucket policy's condition-key coverage does not extend to SOAP.
**Preconditions:** A bucket policy using a condition key relevant to the operation under test; a long-term credential with the matching legacy ACL grant. **Severity:** High (Critical if chained with Lead 2's public-ACL re-enablement, since a bucket-policy Deny is often the *only* remaining defense once BPA/Object-Ownership are themselves confirmed bypassed).

### Lead 4 — [Lens C/E, Medium-High] SOAP structurally cannot carry STS session context — MFA/temporary-credential-only policies fail open against it
**Claim:** Because SOAP "temporary security credentials are not supported" (long-term keys only), any customer control that depends on STS-populated condition keys (`aws:MultiFactorAuthPresent`, `aws:TokenIssueTime`, `aws:RoleSessionName`) cannot be enforced against SOAP calls using a long-term IAM user access key, and a Deny statement not written with an explicit null-check (`BoolIfExists`) fails open.
**Mechanism (doc evidence):** `SOAPAuthentication.md`: *"When making authenticated SOAP requests, temporary security credentials are not supported."*
**Confirm/Refute oracle:** With an IAM user that has an active long-term access key and is also subject to an org SCP/identity policy of the common shape `Deny * unless aws:MultiFactorAuthPresent=true` (without `IfExists`), issue any SOAP operation using that key. If it succeeds, the MFA-required policy failed open for the SOAP path specifically because the condition key was never populated (absent, not false).
**Preconditions:** An org that still has not rotated away from long-term IAM user keys, and an MFA-enforcement policy using `Bool` (not `BoolIfExists` + explicit deny-on-null). **Severity:** Medium–High — this is a pre-existing IAM policy-authoring footgun (Lens S "null/absent-key resolution asymmetry") that SOAP specifically keeps exploitable long after an org believes it has closed off static-key, non-MFA access by migrating everything else to SSO/STS.

### Lead 5 — [Lens F/Q, doc-gap, severity unknown] XML parser hardening (XXE / entity expansion) is undocumented
**Claim:** The SOAP body is raw XML parsed by a (likely 2006-vintage, "no new features added") XML stack; none of the 23 pages state whether DTD processing / external entity resolution is disabled.
**Mechanism (doc evidence):** Absence — no page in the cluster mentions DTDs, external entities, XXE, or XML parser hardening. `APISoap.md` only states the WSDL location and the SSL-transport requirement.
**Confirm/Refute oracle:** Submit a SOAP body (e.g. a `PutObjectInline`/`CreateBucket` request) containing a DOCTYPE with an external or parameter entity referencing a local file path or an internal network URL, and observe whether the parsed `Bucket`/`Key`/`Metadata` values reflect the resolved entity, or whether the fault response otherwise leaks file contents/SSRF behavior.
**Preconditions:** None beyond SSL transport (required for any SOAP request). **Severity:** unresolved by docs — High–Critical if XXE/SSRF confirmed live, but this cluster can only flag it as an untested, undocumented gap; no AWS doc page confirms or denies hardening.

### Lead 6 — [Lens A, confirmed-by-docs, Low-Medium] Bucket-existence/ownership global enumeration oracle
**Claim:** AWS's own SOAP docs instruct using `ListBucket` with `MaxKeys=0` against any bucket name to determine, from the response's fault/success type, whether that global bucket name is available, owned by someone else, or owned/accessible by you.
**Mechanism (doc evidence):** `SOAPCreateBucket.md`: *"To determine whether a bucket name exists, use ListBucket and set MaxKeys to 0. A NoSuchBucket response indicates that the bucket is available, an AccessDenied response indicates that someone else owns the bucket, and a Success response indicates that you own the bucket or have permission to access it."*
**Confirm/Refute oracle:** Already self-confirmed by the doc text — this is a documented, intended three-way oracle, not a hypothesis. Flagging because it's a cross-tenant existence/ownership side channel against the *global* S3 bucket namespace, reachable without any IAM grant on the target bucket, that still works over the legacy SOAP path right up to EOL.
**Severity:** Low–Medium (it's long-standing, AWS-endorsed behavior and the global-bucket-namespace oracle equivalent exists on REST too via `HeadBucket`; listed for completeness and because the SOAP fault-code granularity, per Lead 7, makes the distinction explicit by name rather than by status code alone).

### Lead 7 — [Lens A, Low] SOAP fault granularity as a richer error oracle than REST's generic responses
**Claim:** SOAP faults always carry a specific `Faultcode` of the form `Client.<SpecificErrorName>`/`Server.<SpecificErrorName>` plus a `Detail` block echoing the offending identifier (e.g. the `Key` that didn't exist), which is a more consistent, highly structured error oracle than some REST error-suppression hardening aims for.
**Mechanism (doc evidence):** `SOAPErrorResponses.md`: *"the SOAP fault code is comprised of a standard SOAP 1.1 fault code ... concatenated with the Amazon S3-specific error code. For example: 'Server.InternalError' or 'Client.NoSuchBucket'"*; worked example shows a `Client.NoSuchKey` fault with `<Detail><Key>Fred</Key></Detail>` for a delete of a nonexistent object.
**Confirm/Refute oracle:** Compare SOAP fault specificity against the REST error response for the same failure case on the same resource, looking for cases where REST has been hardened to a generic `AccessDenied`/404 while SOAP still returns the differentiated legacy code (e.g., `NoSuchBucket` vs `AccessDenied` distinctions already enumerated in Lead 6).
**Severity:** Low — informational enumeration-oracle delta, not a direct access-control break.

### Lead 8 — [Lens U, Low/Informational] "Owner-only" logging-status gate is a hard-coded ownership check, not an IAM-permission evaluation
**Claim:** `GetBucketLoggingStatus`/`SetBucketLoggingStatus` restrict access by literal bucket ownership ("Only the owner of a bucket is permitted to invoke this operation"), not by the `s3:GetBucketLogging`/`s3:PutBucketLogging` IAM actions that REST's equivalents use, meaning delegated non-owner principals (a common modern IAM pattern) cannot act over SOAP, and — more importantly for threat-modeling — any bucket-policy Deny or Allow targeting a *specific* non-root IAM principal for this capability may be structurally unreachable by the SOAP authorizer's ownership check.
**Mechanism (doc evidence):** `SOAPGetBucketLoggingStatus.md` and `SOAPSetBucketLoggingStatus.md`, identical line: "Only the owner of a bucket is permitted to invoke this operation."
**Confirm/Refute oracle:** As a non-owner IAM principal explicitly granted `s3:PutBucketLoggingStatus`/`s3:GetBucketLoggingStatus` via bucket policy, attempt the SOAP operation with that principal's long-term key. If denied despite the explicit grant, the ownership check is a separate, non-policy-driven gate (consistent with the doc wording) — functional gap, not itself a vulnerability. The inverse question (whether the owner's root/account key can bypass an explicit policy Deny aimed only at a sub-principal) is the security-relevant half and folds into Lead 3.
**Severity:** Informational on its own; feeds Lead 3's severity if the ownership check turns out to bypass policy evaluation entirely.
