## 0. How to use this document
- Each lead is: **Claim → Mechanism (doc evidence) → Confirm/Refute oracle → Preconditions → Cost → Severity → Stop condition.** Work in priority order; look left and right for adjacent bugs.
- **HARD STOP:** the moment evidence shows an identity/credential/ARN/account belonging to AWS's own service plane (e.g. the EC2Rescue distribution bucket's backing identity, an AWS-owned automation role you can assume), STOP, preserve evidence, flag for AWS-Security disclosure. Do not exploit beyond existence.
- This is a **runbook / IAM-artifact** target, not a network service. The "attack surface" is: (a) the IAM authorization model behind the documented steps, (b) the AWS-authored tooling/automation the runbook tells the customer to trust, and (c) the within-account data boundary the workflow crosses. Most leads are **customer-controlled-blast-radius** questions (what can a mis-scoped-but-plausible policy do) plus **AWS-owned** supply-chain/automation questions.

## 1. Pentest Objectives (boundary-breach goals, concrete)
1. **Offline root-volume theft within an account:** prove that a principal holding only "operational" EC2 permissions (stop/detach/attach) can read another workload's **unencrypted** root EBS volume offline — SAM hashes, DPAPI master keys, app secrets — bypassing all OS access control, by replaying the runbook's detach→attach-to-my-instance move against a volume it does not own.
2. **"Restore to original instance only" is unenforceable:** demonstrate that no IAM condition key binds a volume to the instance it was detached from, so a least-privilege policy *intended* to limit the reset to the owner's own instance cannot actually express that constraint.
3. **SSM-mediated local-admin takeover:** prove `ssm:SendCommand` to a managed Windows instance (via the `AWSSupport-ResetAccess` automation or the EC2Rescue Run Command path) escalates "can run SSM commands" into "local Administrator / RDP" without the instance owner's consent.
4. **Supply-chain trust in EC2Rescue:** establish whether the runbook directs an operator to download-and-run-as-admin an unverified binary (`EC2Rescue_latest.zip`) with a victim volume mounted, and whether any integrity control exists.
5. **PassRole / over-broad artifact:** audit every AWS-authored IAM artifact in the automation path statement-by-statement for unconditioned `PassRole`, `Resource:"*"`, or self-escalation.

## 2. Components, Assets, and Design

### Customer-facing interface
- EC2 control-plane API / console: `StopInstances`, `DetachVolume`, `AttachVolume`, `StartInstances`, `CreateImage`, `RunInstances`, `CreateKeyPair`, `TerminateInstances`, `GetPasswordData`.
- SSM: `AWSSupport-ResetAccess` Automation document; `ec2rw` SSM Run Command path (re-enable local admin).
- On-host tool: **EC2Rescue for Windows Server** (`EC2Rescue.exe`), downloaded from `https://s3.amazonaws.com/ec2rescue/windows/EC2Rescue_latest.zip`; **EC2Launch v2** agent (generates the new password).

### Assets
- **Windows SAM / registry hive** on the root EBS volume (local Administrator password hash). The whole runbook exists to overwrite this offline.
- **DPAPI master keys, machine keys, cached domain creds, application secrets** co-located on that root volume — all exposed to anyone who mounts it offline.
- **The new administrator password**, generated by EC2Launch v2 and (per the EC2 model) encrypted to the instance key pair's public key, retrievable via `GetPasswordData`.
- The EC2 key pair private key(s) created along the way.

### Processes / trust zones
- **Victim instance** (stopped) — owns the root volume with the secrets.
- **Operator's "temporary instance"** — the runbook's own term; an instance the operator controls, in the **same AZ** as the victim (hard requirement — the volume can only attach within its AZ), running a **different** Windows version (to avoid disk-signature collision). This is where the victim volume is mounted as `xvdf` and EC2Rescue runs in **Offline instance** mode.
- **EC2Rescue.exe** — AWS-authored binary, run as admin, writes to the mounted hive.
- **AWSSupport-ResetAccess** automation — AWS-owned runbook that can perform these steps programmatically under an automation assume-role.

### ASCII pipeline
```
[victim instance] --StopInstances--> stopped
       | DetachVolume (root)                         IAM checks: volume* + instance (independent)
       v
  [EBS root volume: SAM + secrets]  <-- AZ-locked
       | AttachVolume to  --------->  [OPERATOR temp instance]  (same AZ, diff Win ver)
       |                                    |
       |                             run EC2Rescue.exe (admin) "Offline instance" -> edit SAM
       |  DetachVolume                      |   (no check the volume is owned by operator)
       v                                    v
  AttachVolume back to /dev/sda1 --> [victim instance] --StartInstances--> GetPasswordData
```
> **The security-relevant observation:** the volume is the asset, and once detached it carries *no binding to its owner*. Every OS-level control on the victim is irrelevant once its volume is mounted on a host the operator controls. The runbook is the sanctioned instance of a general offline-data-theft primitive.

## 5. Recommended Areas of Focus
Priority order for a hunter: **Area 2 (AWS-authored IAM artifact — privesc) and Area 1 (offline-volume theft)** first — both are confirmed-from-docs and reportable; Area 2a/2c are the highest-severity leads. **Area 3** (supply chain + key-less credential acquisition) next. **Area 4** (EBS Direct API parity) is a cheaper adjacent check.

### Area 1 — EBS volume attach/detach: "restore to original instance only" is IAM-unenforceable (Lens U + S + A) — **PRIORITY 1**

**Background.** The runbook's security-critical step is `DetachVolume` from the victim then `AttachVolume` to an operator-controlled temporary instance. The whole point is to access the Windows SAM on a volume *while the owning OS is offline*. AWS frames the reattach step as "reattach the volume to the original instance" — a human convention, not an enforced constraint.

**Security Concern.** The Service Authorization Reference (`list_ec2.md`) shows that both `ec2:AttachVolume` (lines ~4870–4874) and `ec2:DetachVolume` (lines ~7740–7744) take **two independently-scoped required resource types** — `instance` and `volume` — and the available condition keys bind each resource's **own** attributes only:
- `instance`: `aws:ResourceTag`, `ec2:ResourceTag`, `ec2:InstanceID`, `ec2:InstanceType`, `ec2:Region`, `ec2:AvailabilityZone`, … — **no `ec2:Owner`, no cross-resource key.**
- `volume`: `aws:ResourceTag`, `ec2:ResourceTag`, `ec2:VolumeID`, `ec2:Encrypted`, `ec2:ParentSnapshot`, `ec2:Region`, `ec2:AvailabilityZone`, … — **no owner key, no "attached-to" key.**

There is **no condition key** that expresses "this volume may only be attached to the instance it was detached from" or "the volume's owner must equal the target instance's owner." AWS's own IAM guide states the mechanism explicitly (`iam-policies-for-amazon-ec2.md:144`): *"`AttachVolume` attaches an Amazon EBS volume to an instance, so a user must have permissions to use the volume **and** the instance."* — the two resources are authorized **conjunctively but independently** (an AND of two unrelated checks), never **relationally**. `ec2:Owner` exists only on `image`/`snapshot` resource types (shared/public), not on `instance`/`volume`. Worse, for **`DetachVolume` the `instance` resource is not even marked required** (`list_ec2.md:7742` shows `[instance]`, no `*`, vs `[volume*]`) — a valid least-privilege detach statement can reference the volume alone and no instance at all. The AZ requirement the runbook stresses is availability-driven, not a security control (the operator simply launches the temp instance in the victim's AZ; `ec2:AvailabilityZone` narrows *candidates*, never *owner*). Therefore a policy that *intends* to scope the reset to a team's own instances can only approximate it with tags the holder may be able to set, and **cannot** prevent a volume from being moved onto an attacker-chosen instance.

**High-level Test Scenarios (falsifiable):**
1. **Claim:** A principal granted `ec2:StopInstances` + `ec2:DetachVolume` + `ec2:AttachVolume` scoped by a *shared* tag (or `Resource:"*"`, as many ops roles are) can detach the root volume of an instance owned by another team and attach it to its own instance, then read the filesystem offline. → **Mechanism:** `list_ec2.md` AttachVolume/DetachVolume rows — no ownership-pairing condition key. → **Oracle:** in a test account, from role A, successfully attach role-B's root volume to role-A's instance and read a canary file placed on B's volume. → **Pre/Cost:** two workloads, loose-but-plausible tag scoping; minutes. → **Severity:** **High** (intra-account cross-workload data/credential theft; Critical if it reaches an admin's instance secrets). → **Stop:** once one canary byte is read.
2. **Claim:** No IAM policy can restrict `AttachVolume` so that volume V only re-attaches to its origin instance. → **Mechanism:** absence of a relationship condition key. → **Oracle:** attempt to author a policy enforcing "origin instance only"; show it is inexpressible (or that any tag-based approximation is defeated by the holder's `CreateTags`). → **Severity:** **Informational/Low** as a doc-vs-enforcement gap, **but it is the enabling precondition for scenario 1** — a guarantee the runbook's "reattach to the original instance" wording implies but IAM cannot keep.
3. **Claim (Lens S variant — self-widen):** If the ops policy keys `AttachVolume`/`DetachVolume` on `ec2:ResourceTag/<k>` and the same principal holds `ec2:CreateTags` on volumes, it can tag a victim volume into scope and then move it. → **Oracle:** confirm `CreateTags` is grantable on a foreign-but-accessible volume, tag it, then attach. → **Severity:** High.
4. **Claim (Lens H):** If the victim root volume is encrypted with a CMK the operator cannot use, the offline-mount fails (mitigating). Is `AttachVolume` of an encrypted volume gated by `kms:CreateGrant`/`Decrypt` on the target principal/instance, or only on the default `aws/ebs` key where any same-account principal can decrypt? → **Oracle:** repeat scenario 1 with a volume on the default EBS key vs a restrictive CMK; the default-key case succeeding is the real-world exposure. → **Severity:** Medium–High. **This is the single most important mitigation to characterise** — SSE-EBS with a scoped CMK likely neutralises the primitive.
5. **Claim (Lens S — silently-inert condition footgun):** A policy author who adds `"Condition":{"StringEquals":{"ec2:Owner":"<account>"}}` to an `AttachVolume`/`DetachVolume` statement believing it scopes to owned resources gets a statement that is **syntactically accepted but never evaluated** — `ec2:Owner` is not wired to the `instance`/`volume` resource types (only `image`/`snapshot`). → **Oracle:** author the statement, run `iam:SimulatePrincipalPolicy`/Access Analyzer; show the condition has no effect on the authorization. → **Severity:** Medium–High (operators believe they scoped by ownership and did not).
6. **Claim (Lens A — DryRun recon oracle):** `DryRun=true` on `AttachVolume`/`TerminateInstances` across guessed ARNs returns a three-way signal (`DryRunOperation` / `UnauthorizedOperation` / `Invalid*.NotFound`) usable to enumerate resource existence and the caller's authorization shape — **not** an ownership check (`iam-policies-for-amazon-ec2.md:378`). → **Oracle:** tabulate the three responses across existent/nonexistent IDs under a scoped role. → **Severity:** Low–Medium standalone; a recon accelerant for scenarios 1–3.

**Doc evidence:** `list_ec2.md` lines 4870–4874 (AttachVolume), 7740–7744 (DetachVolume); `ec2:Owner` absent on instance/volume. **Severity-if-true:** High (core), with Medium–High KMS-dependent mitigation.

### Area 2 — SSM `AWSSupport-ResetAccess` automation & EC2Rescue Run Command (Lens R / B / E / T / A) — **PRIORITY 1 (AWS-authored artifact)**

**Background.** The target runbook's Note points customers to the SSM Automation that "automatically applies the manual steps." The reference chain is: `AWSSupport-ResetAccess` and `AWSSupport-ExecuteEC2Rescue` are thin wrappers over **`AWSSupport-StartEC2RescueWorkflow`**, which deploys a CloudFormation stack + helper instance, stops the target, detaches its root volume, attaches it to the helper, runs a caller-supplied `OfflineScript`, then reattaches. AWS **publishes an inline IAM policy** for this (printed on `automation-ec2reset.html` and the `AWSSupport-StartEC2RescueWorkflow` reference) that customers attach verbatim — so weak defaults in it are **AWS's defect, in scope, Tier 2, route `aws-security`**.

**Security Concern.** Statement-by-statement audit of the AWS-published policy surfaces two over-broad statements and the automation's authorization model surfaces a third issue:

**2a — Unconditioned IAM role self-service → admin privesc (Lens R, Critical).** Statement 3 grants `iam:CreateRole`, `iam:PutRolePolicy`, `iam:AttachRolePolicy`, `iam:PassRole`, `iam:CreateInstanceProfile`, `iam:AddRoleToInstanceProfile` on `role/AWSSupport-EC2Rescue-*` + `instance-profile/AWSSupport-EC2Rescue-*`, with **no `iam:PolicyARN`, `iam:PermissionsBoundary`, or `iam:PassedToService` condition keys.** A principal holding only this policy can create `AWSSupport-EC2Rescue-<x>`, attach `arn:aws:iam::aws:policy/AdministratorAccess`, wrap it in an instance profile, and `PassRole`/launch — a textbook non-admin→admin escalation satisfying only a name-prefix the holder controls.
- **Claim → Oracle:** under a scoped role holding *only* the published policy, `iam:SimulatePrincipalPolicy` for `iam:AttachRolePolicy{PolicyArn=…/AdministratorAccess, RoleName=AWSSupport-EC2Rescue-poc}` → if Allow, confirm live with canary role in a sandbox. → **Severity: Critical.** → **Stop** at the first Allow (do not actually assume admin).

**2b — Account-less S3 ARN → template/bucket confusion (Lens EE/R, High-if-exploitable).** Statement 2 allows `s3:GetObject` on `arn:aws:s3:::awssupport-ssm.*/*.template` and `*.zip` — an S3 ARN with **no account/owner component**, matching the glob `awssupport-ssm.*` in *any* account. If the `AWSSupport-StartEC2RescueWorkflow` document fetches its CloudFormation template by a name an attacker's `awssupport-ssm.*`-named bucket could satisfy, an attacker-controlled template could be deployed into the victim's elevated `CreateStack`.
- **Claim → Oracle:** `aws ssm get-document --name AWSSupport-StartEC2RescueWorkflow` and inspect whether the template/zip S3 URL is hardcoded to an AWS-owned bucket or parameter-influenced. Hardcoded ⇒ Informational; influenceable ⇒ Critical supply-chain. → **doc-gap until the document JSON is read.**

**2c — Automation has no per-target-instance authorization (Lens A/X, High).** `ssm:StartAutomationExecution` is authorized on the **document ARN**, while `InstanceId` is a plain *parameter* consumed by `aws:changeInstanceState`/`aws:executeAwsApi` steps — unlike `ssm:SendCommand`, which AWS lets you condition on the target instance. So a holder of document-level start permission plus the published policy may force-stop, root-volume-mount (`OfflineScript` = arbitrary code against the offline disk), and password-reset **any instance in the account**, regardless of tag/ownership.
- **Claim → Oracle:** grant `ssm:StartAutomationExecution` scoped only to the `AWSSupport-ResetAccess` document ARN; target an instance the principal has no EC2 resource-level rights to; supply a benign canary `OfflineScript` that writes a marker to the mounted volume. Marker lands ⇒ confirmed. → **Severity: High** (Critical via the `OfflineScript` arbitrary-code primitive on a foreign instance's disk).

**2d — `ssm:SendCommand` ResetAccess → durable, broadly-readable admin credential (Lens T, High).** The `ec2rw-ssm` Run Command `ResetAccess` resets the local Administrator password and **stores it in SSM Parameter Store at `/EC2Rescue/Password(s)/<instance-id>`** (prose says `Password`, the printed IAM policy says `Passwords` — resolve before building an oracle), encrypted under `alias/aws/ssm` or a caller key. The write permission lives on the **target instance's own role** (`ssm:PutParameter`), not the caller's. A principal with only `ssm:SendCommand` to an instance whose profile already has a broad `ssm:PutParameter` grant can mint an admin credential that then rests at a **predictable path** readable by any *disjoint* principal holding `ssm:GetParameter`+`kms:Decrypt` on `parameter/EC2Rescue/*`.
- **Claim → Oracle:** principal A (`ssm:SendCommand` only) runs ResetAccess; principal B (`ssm:GetParameter`+`kms:Decrypt` on `/EC2Rescue/*` only, never touched SSM) reads the password and RDPs in. B obtaining admin ⇒ confirmed. → **Severity: High** (credential decoupled from the action that created it; the actual logon bypasses SSM session audit). The Linux twin writes an SSH key to `/ec2rl/openssh/<instance-id>/key` — same shape.

**2e — Persistent backup / password-enabled AMIs (Lens T/AA, Medium).** The Automation leaves `AWSSupport-EC2Rescue:<InstanceID>` backup and password-enabled AMIs in the account ("these AMIs remain"); anyone with broad `ec2:CopyImage`/`RunInstances` not scoped to the `AWSSupport-EC2Rescue-*` convention gets the target's full disk image. → **Oracle:** confirm default launch-permission scope and whether an out-of-convention principal can launch them. → **Severity: Medium.**

**Doc evidence:** `automation-ec2reset.md`; `systems-manager-automation-runbooks/.../automation-awssupport-startec2rescueworkflow.md` (required-IAM JSON, Stmts 2–4); `ec2rw-ssm.md` lines 16–17, 25–47. **Doc gaps:** `AmazonSSMAutomationRole` managed-policy JSON was not printed anywhere (the inline policy is explicitly "in addition to" it — pull via `iam:GetPolicyVersion` for the full picture; it almost certainly carries the `ec2:StopInstances`/`AttachVolume`/`DetachVolume`/`CreateImage`/`ssm:SendCommand` grants conspicuously absent from the inline policy); the SSM document source JSON (needed to settle 2b/2c) is not in the docs.

### Area 3 — EC2Rescue supply chain + EC2Launch v2 password exposure (Lens EE / Y / Q / M / F) — **PRIORITY 2**

**Background.** Step 3 of the target runbook tells the operator to download `https://s3.amazonaws.com/ec2rescue/windows/EC2Rescue_latest.zip`, extract, and **run `EC2Rescue.exe` as admin** on the temporary instance that has the victim's root volume mounted, in "Offline instance" mode.

**Security Concern & findings:**

**3a — Unverified admin-run binary (Lens Y/EE, High) — supply-chain doc-gap CONFIRMED.** Corpus-wide grep across `Windows-Server-EC2Rescue.md`, `ec2rw-gui.md`, `ec2rw-cli.md`, `ec2rw-ssm.md` for `sha256|checksum|hash|gpg|signature|signed|verify|authentic` returns **zero** integrity hits. The runbook instructs only `Invoke-WebRequest … -OutFile …` + run. This is **asymmetric within AWS's own corpus**: the Linux sibling (`ec2rl_install.md`) documents a full GPG public-key + `.sig` + SHA256 verification chain with explicit "authenticate the publisher … do not run if altered" guidance; the Windows zip has no equivalent. The URL is unversioned (`_latest`), so the artifact isn't reproducible against any known-good hash. Even the SSM path *claims* `AWSSupport-RunEC2RescueForWindowsTool` "Downloads and verifies" the tool (`ec2rw-ssm.md:11`) but never says what "verifies" means — and that verification is invisible to the manual operator.
- **Claim → Oracle:** confirm (doc-only, already strong) no checksum step exists; to settle whether the SSM "verifies" has real logic, read the `AWSSupport-RunEC2RescueForWindowsTool` document JSON for a pinned hash. No pin ⇒ the prose "verifies" is unsupported. → **Severity: High** (tampered binary runs as admin with a victim volume mounted = offline-disk RCE; **hard-stop + disclose** if the `ec2rescue` bucket's backing identity is AWS's service plane — do not probe the live bucket).

**3b — Global bucket-name trust anchor (Lens EE, Informational/structural).** Every download link in the corpus hardcodes path-style global buckets (`s3.amazonaws.com/ec2rescue/…`, `…/ec2-downloads-windows/…`) with no ownership assertion/canary/fallback — the "this is really AWS's tool" trust anchor is the bucket-name string alone. Explains *why* 3a is consequential. Do **not** test against the live bucket (out of scope / possible service-plane).

**3c — Key-less admin-credential acquisition branch (Lens M/A, Critical).** `ResettingAdminPassword_EC2Launchv2.md` Step 2's "(Optional) if you have the private key … otherwise …" branch walks the operator through creating a **new** key pair, imaging the stopped instance, and launching a **replacement** instance under that new key pair — using only the instance's existing IAM/metadata, **no possession of the victim's original private key**. Combined with the reset, this yields an admin password the operator can decrypt themselves, gated only by `ec2:CreateImage`/`RunInstances`/`AttachVolume`/`GetPasswordData` — never by the victim's key material.
- **Claim → Oracle:** enumerate the exact IAM for this branch from `ExamplePolicies_EC2.md`; check whether any of these actions is scoped looser in common AWS-managed policies than the attach/detach set already assumed. → **Severity: Critical** (admin credential without the owner's key).

**3d — Offline-mode has zero ownership check (Lens Q, reinforces Area 1).** EC2Rescue GUI/CLI offline mode operates on whatever device is at `xvdf`/`/offline:<dev>`; the only step is a UI "confirm the disk selection" — no check the volume belongs to the operator. It reads/writes the SYSTEM/SOFTWARE/SAM hives. This is the on-host half of the Area-1 attach primitive: whoever can attach the volume, EC2Rescue will happily rewrite its admin password with no additional gate.

**3e — EC2Launch password channel ambiguity (Lens T, doc-gap).** The GUI/CLI offline "Reset Administrator Password" action (`ec2rw-cli.md:114`) never documents *where* the new password lands — vs the SSM path which explicitly writes to Parameter Store. If the offline action logs the password into an EC2Rescue collected log group (`ec2launch` logs are collected), it would be readable by anyone who can read those logs, bypassing the `GetPasswordData`+key-pair gate. → **Oracle:** inspect EC2Rescue log output for the generated credential (needs tool artifacts). → **Severity: High if confirmed.**

**3f — Silent victim-volume signature rewrite (Lens L/integrity, Medium).** EC2Rescue auto-corrects a disk-signature collision **by default even under `/check-only`**, requiring `/no-fix-signature` to suppress (`ec2rw-cli.md:118–123`). An operator who ignores the "use a different Windows version" guidance (or an attacker wanting to stay read-only) still triggers an **unprompted on-disk write to the victim volume** — an integrity/availability side effect even in "inspect only" mode.

**Doc evidence:** `ec2rw-gui.md`, `ec2rw-cli.md` (lines 114, 118–123), `ec2rw-ssm.md:11,17`, `ec2rl_install.md` (Linux contrast), `ResettingAdminPassword_EC2Launchv2.md` Step 2, `ec2launch-v2-settings.md`, `connect-rdp.md:35`.

### Area 4 — EBS Direct API twin-authorization parity (Lens X)

**Background/Concern.** The runbook reaches volume *bytes* via attach. A hunter should check the adjacent path: snapshot the root volume, then read via `ebs:GetSnapshotBlock`/`ebs:ListSnapshotBlocks` (separate `ebs` service prefix, `list_ebs.md`). If an ops role is denied `ec2`-level snapshot copy/share but allowed the `ebs:*` data-plane actions (common in least-privilege drift), it may read snapshot contents the control-plane would refuse.
- **Claim:** `ebs:GetSnapshotBlock` on a snapshot of a foreign-but-same-account volume returns bytes where the `ec2` control-plane path (`CopySnapshot`/`CreateVolume`) is denied. → **Oracle:** diff the two authz paths on one snapshot under a scoped role. → **Severity:** Medium–High. → Note the embedded-ownership/encryption caveat (encrypted snapshots still need KMS).

## 7. Out-of-Scope Risk Categories
- **Shared responsibility / managed-host internals:** IMDS behaviour on managed Windows hosts, the EC2 hypervisor, the EBS backend fabric.
- **A legitimate account admin resetting their own instance's password** — the intended use; only *cross-workload* or *privilege-crossing* reuse is in scope.
- **Single-account self-DoS** (disk-signature collision corrupting one's own volume) — availability footgun, note only.
- **Customer-authored least-privilege mistakes** are footguns, NOT findings — *except* where the weak default ships in an **AWS-authored** managed policy / sample policy / SSM runbook the customer copies verbatim (then it is in scope, Tier 2, route `aws-security`).
- Any lead whose evidence points at AWS's own service plane — **hard stop + disclose**, do not exploit.
