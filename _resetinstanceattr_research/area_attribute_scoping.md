# EC2 `ec2:Attribute` / `ec2:Attribute/${AttributeName}` scoping — asymmetry analysis for the `ResetInstanceAttribute` research track

Scope: documentation-only analysis. No live AWS calls were made. All claims are grounded in the offline doc mirror at `/work/aws-docs/docs`; exact file paths and quoted sentences are cited per hypothesis. Nothing here is confirmed against a live account — that is explicitly deferred to a downstream hunter with two authorized test accounts.

- `/work/aws-docs/docs/AWSEC2/latest/UserGuide/iam-policies-for-amazon-ec2.md` — `#attribute-key` section (lines 203–266), condition-key-case-sensitivity note (line 155), `...IfExists` warning (line 196), `DryRun`/authorization-check-only semantics (lines 374–378).
- `/work/aws-docs/docs/AWSEC2/latest/UserGuide/ExamplePolicies_EC2.md` — lines ~1738–1766, the only example in the mirror that actually uses `ec2:Attribute/${AttributeName}` against a real attribute-setting action (`ModifyInstanceMetadataOptions` / `HttpTokens`).
- `/work/aws-docs/docs/AWSEC2/latest/APIReference/API_ModifyInstanceAttribute.md` (full), `API_ResetInstanceAttribute.md` (full), `API_DescribeInstanceAttribute.md` (full), `API_ModifyImageAttribute.md` (Attribute/Description/LaunchPermission fields).
- `/work/aws-docs/docs/service-authorization/latest/reference/list_ec2.md` — action rows for `ModifyInstanceAttribute` (line 8806), `ResetInstanceAttribute` (line 9513), `DescribeInstanceAttribute` (`DescribeInstanceAttribute` entry, `Access level: List`), and the condition-key definition table rows for `ec2:Attribute` / `ec2:Attribute/${AttributeName}` (lines 10051–10052).

## What the docs establish as fact (not hypotheses)

1. **Key definitions** (`list_ec2.md` lines 10051–10052):
   - `ec2:Attribute` = "Filters access by an attribute of a resource" (String).
   - `ec2:Attribute/${AttributeName}` = "Filters access by an attribute being set on a resource" (String).
   Both link to the same UserGuide anchor, `iam-policies-for-amazon-ec2.html#attribute-key`.

2. **Condition key *names* are documented as case-insensitive; values are not addressed.** `iam-policies-for-amazon-ec2.md` line 155: "Condition keys are not case-sensitive." This sentence is about the *key* (`ec2:Attribute` vs `EC2:ATTRIBUTE`), not the *value* compared by the operator (`StringEquals`, which IAM defines as an exact, case-sensitive match unless `StringEqualsIgnoreCase` is used). The doc never states whether the value placed into `ec2:Attribute` at evaluation time is case-normalized.

3. **The only two worked examples of `ec2:Attribute`/`ec2:Attribute/${AttributeName}` in the entire mirror are NOT for `ModifyInstanceAttribute`:**
   - `iam-policies-for-amazon-ec2.md` lines 217–263: both examples are against `ModifyImageAttribute` (resource `image/ami-*`), using `ec2:Attribute/Description` and `ec2:Attribute: "Description"`.
   - `ExamplePolicies_EC2.md` lines 1748–1766: against `ModifyInstanceMetadataOptions` (resource `instance/*`), using `ec2:Attribute/HttpTokens`.
   There is **no documented example anywhere in the mirror of `ec2:Attribute` or `ec2:Attribute/${AttributeName}` used against `ModifyInstanceAttribute`** — i.e., no worked example denying `userData`, `groupSet`, `disableApiTermination`, etc. This is itself a finding: the mechanism the IAM reference *lists* as available for `ModifyInstanceAttribute` is never demonstrated for it.

4. **A concrete, citable casing discrepancy exists in AWS's own example.** `API_ModifyImageAttribute.md` (lines 21–23 per local read) documents the `Attribute` request parameter's `Valid values` as: `description | imdsSupport | launchPermission` — **lowercase**. But the IAM doc's worked Deny example (`iam-policies-for-amazon-ec2.md` lines 247–263) writes `"ec2:Attribute": "Description"` — **capitalized**. One of these two AWS-authored strings does not match the literal wire value the other documents. This is the single clearest, already-in-the-docs demonstration that the exact string populated into `ec2:Attribute` is not obviously derivable from the API reference's `Valid Values` list, and that AWS's own example may itself be inert if `StringEquals` is value-case-sensitive and the runtime value is actually lowercase `description`.

5. **`ec2:Attribute/${AttributeName}` observed casing matches the PascalCase *request field name*, not the lowercase enum.** The one real-world example (`ec2:Attribute/HttpTokens` for `ModifyInstanceMetadataOptions`) uses `HttpTokens` — the literal structured request parameter name for that action — not a lowercase `httpTokens`. By analogy, if the same population rule holds for `ModifyInstanceAttribute`, the per-attribute suffix would likely be the PascalCase structured field name (`UserData`, `GroupId`, `DisableApiTermination`, `BlockDeviceMapping`, `SourceDestCheck`, `InstanceType`, `Kernel`, `Ramdisk`, `EbsOptimized`, `EnaSupport`, `SriovNetSupport`, `InstanceInitiatedShutdownBehavior`) — **not** the lowercase strings in the `Attribute` parameter's own `Valid Values` enum (`userData`, `groupSet`, `disableApiTermination`, …). But `ModifyInstanceMetadataOptions` has no generic `Attribute`/`Value` pair at all, so this analogy is not proof for `ModifyInstanceAttribute`, which uniquely has *both* a generic `Attribute`/`Value` pair *and* per-attribute structured fields (see next point). This remains a doc-gap for `ModifyInstanceAttribute` specifically.

6. **`ModifyInstanceAttribute` has two disjoint, overlapping-but-not-identical request shapes, and the generic `Attribute`/`Value` pair cannot reach every attribute it claims to cover.** From `API_ModifyInstanceAttribute.md`:
   - The `Attribute` parameter's `Valid Values` (line 23) lists 14 names: `disableApiTermination | instanceType | kernel | ramdisk | instanceInitiatedShutdownBehavior | blockDeviceMapping | userData | sourceDestCheck | groupSet | ebsOptimized | sriovNetSupport | enaSupport | nvmeSupport | disableApiStop | enclaveOptions`.
   - But the `Value` parameter (line 107) states: "Use only with the `kernel`, `ramdisk`, `userData`, `disableApiTermination`, or `instanceInitiatedShutdownBehavior` attribute." — only **5 of the 14**.
   - The remaining 9 (including the two most security-sensitive, `groupSet` and `blockDeviceMapping`) are documented as reachable **only** through their dedicated structured parameters: `GroupId.N` (for `groupSet`) and `BlockDeviceMapping.N` (for the `DeleteOnTermination` sub-attribute of block device mapping), plus `EbsOptimized`, `EnaSupport`, `SriovNetSupport`, `DisableApiStop` as their own typed objects.
   - This means a real `ModifyInstanceAttribute` call that changes an instance's security groups is made with `GroupId.N=sg-xxx` and (per the doc) likely never populates the generic `Attribute` string field with `groupSet` at all. Whether `ec2:Attribute`/`ec2:Attribute/${AttributeName}` is populated identically regardless of which of the two request shapes (generic `Attribute`/`Value` vs. structured per-field parameter) was used is **not stated anywhere in the mirror**.

7. **`ResetInstanceAttribute` and `DescribeInstanceAttribute` do not list `ec2:Attribute` or `ec2:Attribute/${AttributeName}` in their condition-key sets** (`list_ec2.md`, `ResetInstanceAttribute` row line 9513–9517; `DescribeInstanceAttribute` row, `Access level: List`), confirming the asymmetry stated in the task. `ResetInstanceAttribute`'s `Attribute` parameter (`API_ResetInstanceAttribute.md` line 20) is narrower than `ModifyInstanceAttribute`'s — only `kernel | ramdisk | sourceDestCheck` — but none of the three can be scoped by attribute name via IAM. `DescribeInstanceAttribute`'s `Attribute` parameter (`API_DescribeInstanceAttribute.md` line 19) is the widest of the three — `instanceType | kernel | ramdisk | userData | disableApiTermination | instanceInitiatedShutdownBehavior | rootDeviceName | blockDeviceMapping | productCodes | sourceDestCheck | groupSet | ebsOptimized | sriovNetSupport | enaSupport | enclaveOptions | disableApiStop` — explicitly including `userData` and `groupSet`, i.e. the read side can retrieve the literal user-data payload and the security-group membership of any instance the caller can `Describe`, with zero attribute-level IAM scoping available.

8. **`DryRun` is explicitly documented as an authorization-only probe, not an attribute- or ownership-aware oracle.** `iam-policies-for-amazon-ec2.md` lines 374–378: "the call completes the authorization check, but does not complete the operation… the request returns `DryRunOperation` [if authorized]; otherwise… `UnauthorizedOperation`." Nothing in `DryRun`'s documented behavior differentiates *which* attribute would have been read/set/reset, or evaluates resource ownership beyond what IAM/Deny already decides. This matters directly for Lens S/X below: a hunter cannot use `DryRun` to observe whether `ec2:Attribute` was populated, matched, or ignored for a given call shape — `DryRun` only tells you pass/fail of the overall IAM decision, not the condition-key evaluation trace.

## Hypotheses

Each hypothesis: **Claim → Mechanism → Confirm/Refute oracle → Preconditions/Cost → Severity-if-true.**

---

### H1 (Lens X — action-family parity break). Per-attribute Deny protecting `ModifyInstanceAttribute` has no equivalent for `ResetInstanceAttribute`, so `kernel`/`ramdisk`/`sourceDestCheck` resets are unconstrained by any attribute-scoped Deny that an operator wrote believing it covered "instance attribute changes" broadly.

- **Mechanism:** `list_ec2.md` lists `ec2:Attribute` and `ec2:Attribute/${AttributeName}` as valid condition keys for the `instance` resource under `ModifyInstanceAttribute` (line 8808) but omits both from the `instance` resource's key list under `ResetInstanceAttribute` (line 9516). The two actions share an overlapping attribute surface (`kernel`, `ramdisk`, `sourceDestCheck` are settable by both), so a policy author who writes `Deny ec2:ModifyInstanceAttribute` with `StringEquals "ec2:Attribute": "sourceDestCheck"` (intending to block disabling source/dest checks, e.g. to prevent turning an instance into a NAT/router) gets zero protection against the same outcome being reached via `ec2:ResetInstanceAttribute` with `Attribute=sourceDestCheck`, because that action's grant/deny evaluation has no `ec2:Attribute` key to match against at all — the Deny statement is simply inapplicable to that action, regardless of whether it's permitted through a separate `Allow ec2:ResetInstanceAttribute` statement.
- **Confirm/Refute oracle:** IAM policy simulator (`iam:SimulateCustomPolicy`) against a synthetic policy containing (a) `Allow ec2:ModifyInstanceAttribute, ec2:ResetInstanceAttribute` on `instance/*`, and (b) `Deny ec2:ModifyInstanceAttribute` `StringEquals ec2:Attribute=sourceDestCheck`. Simulate `ec2:ModifyInstanceAttribute` with context key `ec2:Attribute=sourceDestCheck` (expect Deny) vs. simulate `ec2:ResetInstanceAttribute` with the same context key (expect: key not applicable / Allow, since Reset has no such key to evaluate). A canary-account live call (`ResetInstanceAttribute --attribute sourceDestCheck` against a disposable instance under this policy) would be the live confirmation, deferred to the hunter.
- **Preconditions/Cost:** Needs a principal with `ec2:ResetInstanceAttribute` granted (common in "instance admin" roles that also get `ModifyInstanceAttribute`) and a two-account/two-role setup to compare simulator output under identical context keys. Zero cost to run in the simulator; a canary call against one disposable stopped instance for live confirmation.
- **Severity if true:** Medium–High. Breaks a documented, intended access control — a NAT/router-disable Deny silently has a back door via `ResetInstanceAttribute`. Blast radius is scoped to whichever principals hold both actions, which is a common pairing in "EC2 instance operator" roles.

---

### H2 (Lens X — read-side has no equivalent at all). `DescribeInstanceAttribute` can read `userData` and `groupSet` for any instance the caller has `Describe` rights to, and IAM has no `ec2:Attribute` lever to carve those two fields out, even though the exact same fields *are* carve-outable on the write side via `ModifyInstanceAttribute`.

- **Mechanism:** `API_DescribeInstanceAttribute.md` line 19 lists `userData` and `groupSet` among the `Attribute` parameter's valid values, and the response elements (lines 61–64, 105–107) return them in full (`groupSet` as an array of `GroupIdentifier` objects, `userData` as the raw `AttributeValue`). `list_ec2.md`'s `DescribeInstanceAttribute` row has no `ec2:Attribute`/`ec2:Attribute/${AttributeName}` key at all. An operator who grants `ec2:DescribeInstanceAttribute` on `instance/*` to a support/monitoring role, intending only to let it read things like `instanceType` or `disableApiTermination`, has no IAM-native way to exclude `userData` (which routinely carries secrets, bootstrap tokens, or cloud-init scripts) or `groupSet` (security group membership, useful recon for a lateral-movement path) from that same grant. The only available knob is the coarse `Attribute` *value itself* is not condition-key-filterable — so the choice is all-14-attributes-or-none for that action.
- **Confirm/Refute oracle:** Policy simulator: attempt to construct ANY policy that allows `ec2:DescribeInstanceAttribute` on `instance/*` but denies it specifically when `Attribute=userData`. Confirm there is no condition key in the `DescribeInstanceAttribute` row of `list_ec2.md` capable of matching the `Attribute` request parameter value (the row's key list has none of `ec2:Attribute*`) — this is already confirmed from docs alone (doc fact #7 above), so this hypothesis is largely pre-confirmed by documentation; the *live* oracle is simply calling `DescribeInstanceAttribute --attribute userData` as a scoped-down canary principal that is allowed `DescribeInstanceAttribute` generally, to verify no implicit server-side narrowing occurs beyond what IAM evaluates (i.e., rule out a non-documented service-side attribute ACL).
- **Preconditions/Cost:** Trivial — one scoped IAM role, one disposable instance with non-secret canary user-data, one `DescribeInstanceAttribute` call per attribute value. No destructive action.
- **Severity if true:** High for the specific case of `userData` exposure (frequently contains credentials in the wild despite AWS guidance not to put secrets there) — this is a read-only information-disclosure primitive with no attribute-level IAM mitigation, which is a stronger, more directly exploitable claim than the write-side Reset gap in H1.

---

### H3 (Lens S — case/value-population ambiguity makes `ec2:Attribute` Deny statements for `ModifyInstanceAttribute` potentially inert, independent of the Reset/Describe gap). Even where `ec2:Attribute`/`ec2:Attribute/${AttributeName}` IS listed as available (`ModifyInstanceAttribute`), the exact string AWS populates into the key at evaluation time is not reliably derivable from the docs, and AWS's own worked example for the sibling action `ModifyImageAttribute` uses a value (`Description`, capitalized) that does not match that action's own API-reference `Valid Values` enum (`description`, lowercase).

- **Mechanism:** Compare `API_ModifyImageAttribute.md`'s `Attribute` parameter `Valid values: description | imdsSupport | launchPermission` against `iam-policies-for-amazon-ec2.md` lines 247–263's `"StringEquals": {"ec2:Attribute": "Description"}`. `StringEquals` in IAM is an exact-match operator; `iam-policies-for-amazon-ec2.md` line 155 only says condition *key names* are case-insensitive, it never says condition *values* are normalized or compared case-insensitively. If the runtime-populated value is the literal wire-format lowercase `description` (matching the API reference), AWS's own published example Deny — the only worked `ec2:Attribute` example in the entire corpus — would never match any real `ModifyImageAttribute` call and would be permanently inert (fail-open), silently granting what the policy author believed was denied. If instead AWS normalizes the value server-side to a canonical capitalized form before condition evaluation, the example is correct but the API reference's `Valid Values` field (which every policy author would naturally consult to choose a match string) is actively misleading. Either resolution is a defensive-relevant documentation defect; the mirror does not disambiguate which is true.
- **Confirm/Refute oracle:** Canary-account test (deferred to hunter): apply the exact Deny from `iam-policies-for-amazon-ec2.md` lines 247–263 to a disposable AMI, then attempt `ModifyImageAttribute --attribute description --value "x"` as the restricted principal. If the call succeeds (returns success, not `UnauthorizedOperation`/`AccessDenied`), the Deny is confirmed inert — `ec2:Attribute` was populated with something other than the capitalized `Description` the policy checks for (most likely lowercase `description`, i.e. the literal wire value passed through unmodified). If the call is denied, repeat the oracle using IAM Access Analyzer / `GenerateServiceLastAccessedDetails` or CloudTrail's `errorCode`/`requestParameters` on a denied call to see whether the recorded context reflects `Description` or `description`. Policy-simulator step (no live cost): simulate `ec2:ModifyImageAttribute` supplying context key `ec2:Attribute=description` (lowercase) against the published Deny policy — if the simulator reports "Allowed" (condition not triggered) for the lowercase value, that is strong pre-live evidence the example as published is broken by case mismatch.
- **Preconditions/Cost:** One disposable AMI owned by the test account, one scoped test principal, one `ModifyImageAttribute` dry-run-then-live call pair. Low cost, fully reversible (image description edits).
- **Severity if true:** High for anyone who copy-pasted AWS's own documented example verbatim expecting it to block description changes — a textbook "the control is inert" fail-open, and it undermines confidence in the *mechanism* generally (if AWS's flagship example for this condition key may not even work as documented, the `ModifyInstanceAttribute` case — for which no worked example exists at all, cf. doc fact #3 — is even less trustworthy). This generalizes directly to the `ec2:ResetInstanceAttribute`/`DescribeInstanceAttribute` story: it shows the attribute-scoping mechanism family is fragile even on its best-documented case, reinforcing that operators should not trust it as a compensating control for the actions (Reset/Describe) that don't even expose the key.

---

### H4 (Lens X — generic-vs-structured request-shape bypass, specific to `ModifyInstanceAttribute`'s own internal asymmetry). For the 9 of 14 `ModifyInstanceAttribute` attributes that cannot be set via the generic `Attribute`/`Value` pair (notably `groupSet` via `GroupId.N` and `blockDeviceMapping` via `BlockDeviceMapping.N` — doc fact #6), it is undocumented whether `ec2:Attribute`/`ec2:Attribute/${AttributeName}` is populated at all, and if so with what value, meaning a Deny written against the generic key may not apply to the two most security-sensitive sub-attributes even on the one action where the key is nominally supported.

- **Mechanism:** `API_ModifyInstanceAttribute.md` line 107 restricts the generic `Value` parameter to 5 of the 14 `Attribute` enum values; `groupSet` (security groups — direct network-exposure control) and `blockDeviceMapping`'s `DeleteOnTermination` (data-persistence-on-terminate control) must go through `GroupId.N`/`BlockDeviceMapping.N`. The `#attribute-key` doc's own scoping note (`iam-policies-for-amazon-ec2.md` line 208) says the key "supports only properties that are of a primitive data type… or complex `AttributeValue` objects that contain only a `Value` property… can't be used with complex objects that contain multiple properties, such as the `LaunchPermission` object." `InstanceBlockDeviceMappingSpecification` (used by `BlockDeviceMapping.N`) is a multi-property object (device name + EBS spec + `NoDevice` + `VirtualName`), structurally analogous to the explicitly-excluded `LaunchPermission` object — so by the doc's own stated rule, `ec2:Attribute/BlockDeviceMapping` plausibly *cannot* be used the same way `ec2:Attribute/Description` is used for images. `GroupId.N` is "Array of strings" (doc fact in `API_ModifyInstanceAttribute.md` line 59-62) — closer to a primitive array, so it's ambiguous whether it qualifies.
- **Confirm/Refute oracle:** Policy simulator: construct `Deny ec2:ModifyInstanceAttribute` with `StringEquals "ec2:Attribute/GroupId": "*"` (or `"ec2:Attribute": "groupSet"`) and simulate against a context representing a `GroupId.N`-shaped call; separately simulate against an `Attribute=groupSet&Value=...`-shaped call (noting the latter is not actually achievable per doc fact #6, since `Value` doesn't support `groupSet` — this itself may make the whole generic-key path moot for this attribute). Live canary: as a principal under such a Deny, attempt `ModifyInstanceAttribute --group-id sg-xxxx` (structured path) against a disposable instance and observe whether the Deny triggers.
- **Preconditions/Cost:** One disposable instance, one scoped test principal, one non-destructive security-group-swap call (using two throwaway SGs). Low cost.
- **Severity if true:** High — this is the most directly actionable instance-takeover-adjacent primitive in the whole family (attaching/removing security groups changes network reachability), and if confirmed it means the condition key is doubly unreliable: not just absent for Reset/Describe (as stated in the task framing) but potentially non-functional for the specific sub-fields of Modify that matter most for security groups and EBS delete-on-termination.

## Lens U (documented-guarantee vs. enforcement) — explicit check

No page in the mirror states or implies that `ec2:Attribute`/`ec2:Attribute/${AttributeName}` provides attribute-level scoping for `ResetInstanceAttribute` or `DescribeInstanceAttribute` — the IAM reference simply omits the keys from those two actions' rows, and the UserGuide's `#attribute-key` section only ever illustrates the mechanism against `ModifyImageAttribute`/`ModifyInstanceMetadataOptions`. So there is no "documented guarantee that is false" for the Reset/Describe gap specifically — it's an *silent omission*, not a *false claim*. The closer-to-a-false-claim candidate is H3: the worked Deny example for `ModifyImageAttribute` is presented without qualification as something that "denies all requests that attempt to modify an image's description" (`iam-policies-for-amazon-ec2.md` line 240) — an unconditional claim of enforcement — while the casing mismatch against the API reference's `Valid Values` makes that enforcement claim unverified-by-the-docs-themselves. This is the one place documentation arguably overclaims relative to what it establishes elsewhere in the same corpus.

**The concrete operator-facing breach to state plainly (per the task framing):** An operator who reasons "I'll grant `ec2:ResetInstanceAttribute` and `ec2:DescribeInstanceAttribute` to this role, and if I ever need to restrict which attributes it can touch, I'll just add an `ec2:Attribute` condition like I did for `ModifyInstanceAttribute`" is wrong — the key does not exist for those two actions per `list_ec2.md`, and any such condition clause would make the whole statement either non-evaluable for that action (if written without `...IfExists` and mixed into a multi-action statement, per the `...IfExists` warning at line 196, this can even flip to **fail-closed accidentally** — a different direction of bug worth noting for completeness, though less interesting defensively than the fail-open direction) or simply ignored.

## Doc-gaps — explicitly unresolved, confirm surface first

- **G1.** The exact runtime string(s) populated into `ec2:Attribute` / `ec2:Attribute/${AttributeName}` for `ModifyInstanceAttribute` calls (PascalCase field name vs. lowercase `Attribute`-enum value vs. something else) — not stated for this action anywhere in the mirror. (Feeds H3/H4.)
- **G2.** Whether `ec2:Attribute`/`ec2:Attribute/${AttributeName}` is populated at all when a `ModifyInstanceAttribute` call uses a structured field (`GroupId.N`, `BlockDeviceMapping.N`, `DisableApiTermination`, etc.) rather than the generic `Attribute`/`Value` pair. (Feeds H4.)
- **G3.** Whether `StringEquals` against `ec2:Attribute` is value-case-sensitive at runtime (standard IAM semantics say yes; AWS's own example appears to possibly violate this, per H3) or whether EC2 normalizes the value before IAM evaluation.
- **G4.** Whether any non-IAM, service-side authorization layer (undocumented) narrows `DescribeInstanceAttribute`'s `userData`/`groupSet` exposure — the docs give no indication of one, but absence of documentation is not proof of absence.
- **G5.** Whether AWS has silently added `ec2:Attribute` support to `ResetInstanceAttribute`/`DescribeInstanceAttribute` since this mirror was synced (doc mirrors can lag; the task explicitly allows trying the live `.html` pages for exactly this reason — not done in this pass due to the documentation-only, no-network-call constraint on this task. If the orchestrating workflow does have working `WebFetch` to `docs.aws.amazon.com`, re-checking `list_ec2.md`'s live equivalent for these two actions before the hunter spends live-account budget is cheap and worthwhile.)
