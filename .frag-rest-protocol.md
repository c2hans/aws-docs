## 1. Cluster summary

This cluster covers the mechanics of how a bare REST HTTP request reaches, and is routed/validated by, the S3 fleet before any object-level authz semantics apply: hostname/addressing-style construction (virtual-hosted vs path-style vs dual-stack/IPv6), DNS-based facility routing and 3xx redirects, CORS preflight (OPTIONS), the REST error-response vocabulary (XML `<Error>` body + HTTP status + request-id pair), and the S3 Select wire protocol (event-stream SQL-over-object-content). The common thread across every lead below is: **S3 exposes multiple syntactically different ways to name the same bucket/object (Host header vs path, IPv4 endpoint vs dual-stack, legacy vs regional endpoint), and multiple layers (DNS, redirect logic, CORS evaluation, IAM policy condition keys) that may not canonicalize or validate those names identically.** This is the textbook trigger set for Lens BB (canonicalization/parser differential) and Lens V (network/endpoint reachability vs IP-based policy conditions), with secondary signal for Lens A (403-vs-404 enumeration oracles), Lens DD (CORS/cache), the open-redirect/SSRF angle under Lens G, and Lens F (SQL-injection-adjacent) for S3 Select.

No live testing was performed. All leads below are falsifiable hypotheses to be confirmed/refuted against a real S3 endpoint.

## 3. Ranked lens-mapped falsifiable leads

### Lead 1 — Host-header addressing-style confusion vs path-keyed security controls (Lens BB, Lens CC)
**Claim:** A WAF, CloudFront behavior, or bucket policy/IAM `Condition` written to key off the **path** (e.g., `s3:prefix`, a path-based WAF rule, or a reverse proxy in front of S3) can be bypassed or double-matched by switching between virtual-hosted-style (`examplebucket.s3.us-west-2.amazonaws.com` + path `/puppy.jpg`) and path-style (`s3.us-west-2.amazonaws.com` + path `/examplebucket/puppy.jpg`) addressing for the identical object, because the two forms place the bucket name in different request components (Host vs path).
**Mechanism (doc evidence):** RESTAPI.md, "Virtual hosted‐style and path‐style requests" — shows the identical `DELETE /puppy.jpg` object reachable via two structurally different requests (bucket in `Host` vs bucket in path), both currently supported ("Amazon S3 supports both virtual-hosted–style and path-style URL access in all AWS Regions"). RESTCommonRequestHeaders.md's `Host` row documents the same duality explicitly.
**Confirm/Refute oracle:** Put a security control (edge WAF rule, CloudFront behavior, custom auth proxy) in front of an S3-compatible path that inspects only the URL path for a bucket/key pattern; issue the equivalent virtual-hosted-style request with the bucket moved into `Host` and an empty/different path, and see whether the control's decision diverges from S3's own eventual resource resolution (i.e., the control allows/denies based on a parse that disagrees with what object S3 actually serves).
**Preconditions:** A security layer sitting in front of S3 (not S3 itself) that parses path/Host independently of S3's own bucket resolution — this is a customer-architecture risk more than an S3-intrinsic one, but S3's dual-support of both styles is the documented enabler.
**Severity-if-true:** Medium–High (auth/WAF bypass to a protected object; depends entirely on the surrounding architecture, since S3 itself resolves both forms consistently per its own docs).

### Lead 2 — Temporary-redirect target trust and credential-forwarding (Lens G, open-redirect)
**Claim:** S3's temporary-redirect (307) mechanism hands clients a `Location` pointing at a **service-generated**, request-specific hostname (e.g. `quotes.s3-4c25d83b.amazonaws.com`) that the client is expected to blindly re-issue the *same signed request* against; if that hostname-generation logic (the `-xxxxxxxx` suffix) were ever influenceable by request content (bucket name, region, or other caller-controlled field) rather than purely server-side state, a client's Authorization header/credentials would be forwarded to an attacker-influenced host.
**Mechanism (doc evidence):** RESTRedirect.md's example response: `Location: http://quotes.s3-4c25d83b.amazonaws.com/nelson.txt?rk=8d47490b` plus explicit text: "It is generally safe to follow redirects generated by Amazon S3 automatically, **as the system will issue redirects only to hosts within the amazonaws.com domain** and the effect of the redirected request will be the same as that of the original request." UsingRouting.md's "Important" note: "Don't reuse an endpoint provided by a previous redirect response... it might provide unpredictable results."
**Confirm/Refute oracle:** Determine whether the redirect-target hostname fragment (`s3-4c25d83b`) is deterministic from caller-supplied input (bucket name, region, or request path) vs. purely internal routing state. If any caller-controlled value influences the resulting redirect host beyond the `amazonaws.com` suffix, that is the lead; if it is proven to always resolve within `amazonaws.com` and is non-attacker-influenceable, this is refuted per the doc's own safety claim.
**Preconditions:** Would require finding a case where redirect-target construction incorporates untrusted input (e.g., a custom header, a bucket alias, Transfer Acceleration, or Multi-Region Access Point naming) in a way that escapes the `*.amazonaws.com` constraint.
**Severity-if-true:** Critical if ever provably redirect-off-domain (credential/Authorization-header forwarding to attacker infra); as documented, this is a **null hypothesis** — AWS's own doc explicitly asserts the domain constraint, so without evidence of an escape this should be recorded as low-confidence/no-finding, not claimed.

### Lead 3 — Permanent-redirect error disclosure (region/location enumeration oracle) (Lens A)
**Claim:** `IllegalLocationConstraintException`, `PermanentRedirect`, `IncorrectEndpoint`, and `AuthorizationHeaderMalformed`/`InvalidRequest`'s "ListBuckets request made to a Regional endpoint different from `bucket-region`" error paths allow a caller with **no credentials or wrong credentials** to learn a target bucket's **AWS Region** and existence, purely from unauthenticated/misrouted request behavior (400-class responses that differ from a generic 403), because the permanent-redirect error "does not contain a Location HTTP header" but does include the bucket's actual endpoint in the XML `<Error>` body (per UsingRouting.md's permanent-redirect description) and RESTRedirect.md's example XML includes an `<Endpoint>` element naming the correct facility.
**Mechanism (doc evidence):** UsingRouting.md, "Permanent request redirection": "this type of redirect does not contain a Location HTTP header... Consult the resulting XML error document for help using the correct Amazon S3 endpoint." ErrorResponses.md: `IllegalLocationConstraintException` ("You are trying to access a bucket from a different Region than where the bucket exists"), `IncorrectEndpoint` ("The specified bucket exists in another Region. Direct requests to the correct endpoint.").
**Confirm/Refute oracle:** Compare the error-body/status-code signature for (a) a bucket that exists but in the wrong region vs (b) a bucket that does not exist at all vs (c) a bucket that exists and caller is denied — if (a) is reliably distinguishable from (b)/(c) pre-auth, that is a bucket-existence + region-enumeration oracle via error responses alone.
**Severity-if-true:** Low–Medium (existence/region info leak, standard S3 enumeration-oracle shape; consistent with Lens A's "distinct error responses form an enumeration oracle" variant). Not novel — this class is widely known for S3 — but worth stating as a documented mechanism for completeness.

### Lead 4 — NoSuchKey/NoSuchBucket vs AccessDenied as a cross-tenant existence oracle (Lens A)
**Claim:** S3's error vocabulary deliberately collapses `NoSuchKey` and `NoSuchBucket` onto the same HTTP 404 (confirmed explicitly by ErrorBestPractices.md), while access-without-permission returns 403 `AccessDenied` — this three-way split (404 object-absent / 404 bucket-absent / 403 exists-but-denied) is a documented, intentional enumeration primitive: a caller can distinguish "object doesn't exist" from "object exists but I can't read it" by status/code alone, enabling private-bucket content/key enumeration via a scripted probe of candidate keys.
**Mechanism (doc evidence):** ErrorBestPractices.md: "HTTP status codes are less expressive... For example, the `NoSuchKey` and `NoSuchBucket` Amazon S3 errors both map to the HTTP 404 Not Found status code... use the Amazon S3 error code instead of the HTTP status code." ErrorResponses.md's code table: `NoSuchKey`→404, `NoSuchBucket`→404, `AccessDenied`→403, `AllAccessDisabled`→403, `InvalidAccessKeyId`→403.
**Confirm/Refute oracle:** For a bucket with a restrictive policy, request a key that exists (expect 403 AccessDenied) vs. a key that does not exist (expect 404 NoSuchKey) as an unauthorized/anonymous caller; confirm the differential is observable without any valid credentials.
**Severity-if-true:** Low–Medium per the catalog's standard framing (existence-oracle, not data access) — this is the well-known S3 403-vs-404 behavior; documented here as the exact mechanism/citation rather than a novel claim.

### Lead 5 — CORS preflight as a pre-auth bucket-config/existence oracle (Lens DD, Lens A)
**Claim:** An unauthenticated `OPTIONS` request against any object path reveals, without any credentials, whether the target bucket has a `cors` subresource configured at all (200 OK + CORS headers vs 403 Forbidden with no CORS headers), and — when CORS is configured — which **origins** are permitted (`Access-Control-Allow-Origin` echoes the matched origin, or returns the literal `'*'` if the bucket's CORS rule allows all origins per RESTCommonResponseHeaders.md's note that `'*'` is echoed verbatim instead of the caller's origin). This is a config-disclosure + potential cross-origin-read primitive: if a sensitive bucket's CORS rule is misconfigured to `AllowedOrigin: *` combined with credentialed requests, cross-origin read becomes possible from any web origin.
**Mechanism (doc evidence):** RESTOPTIONSobject.md: "If `cors` is not enabled on the bucket, then Amazon S3 returns a `403 Forbidden` response." Also: "If the origin in your request is not allowed, Amazon S3 will not include this [`Access-Control-Allow-Origin`] header in the response" — i.e., presence/absence of the header is itself an origin-allowlist oracle, probeable one origin at a time, pre-auth. RESTCommonResponseHeaders.md: "If the request origin matches `'*'` in the CORS configuration's allowed origins then the `'*'` is returned in this response header instead of the original origin" and "If the `Access-Control-Allow-Origin` request header is set to `'*'`... the `Access-Control-Allow-Credentials` response header will be omitted" (i.e., AWS's own docs flag the wildcard-vs-credentials interaction as a defined, not accidental, behavior — the known CORS wildcard-origin over-match concern).
**Confirm/Refute oracle:** Send OPTIONS with a battery of candidate `Origin` values against a target bucket/object; observe whether `Access-Control-Allow-Origin` is returned (and whether it's `*` literally or echoes the origin) to map the full allowed-origin set pre-auth; separately confirm whether CORS-enabled-vs-not is itself distinguishable (403 vs 200) regardless of origin matching, which discloses "this bucket has CORS configured" as metadata.
**Severity-if-true:** Medium (origin-allowlist disclosure + config fingerprinting) escalating to High if a specific target bucket is found with `AllowedOrigin: *` AND serves credentialed/sensitive content (chains into actual cross-origin data read — the chain-to-the-end-of-kill-chain framing from Step 5 of the method).

### Lead 6 — IPv6/dual-stack endpoint bypass of IPv4-only `aws:SourceIp` bucket-policy conditions (Lens V)
**Claim:** A bucket policy or IAM policy that restricts access via `aws:SourceIp` using only IPv4 CIDR ranges does **not** block access for a caller using IPv6 over a dual-stack endpoint, because policy evaluation of `aws:SourceIp` against an IPv6-sourced request is a distinct address family from the configured IPv4 ranges; the directional risk the docs call out is actually the inverse (IPv6 traffic being unintentionally *denied* if the admin forgot to add IPv6 ranges) — but the same gap, read the other direction, means a policy intended as an **allowlist keyed on IPv4** (`Allow` if source matches CIDR) does not inadvertently grant IPv6 callers access (fails closed, good) — EXCEPT in the inverse case where the policy is a **Deny-based blocklist** keyed only on IPv4 ranges intended to block a set of IPv4 attacker ranges: an attacker switching to IPv6 (via a dual-stack endpoint) would evade an IPv4-only Deny condition, since `aws:SourceIp` with only IPv4 CIDRs never matches an IPv6 source, so the Deny never triggers and the request falls through to any broader Allow.
**Mechanism (doc evidence):** ipv6-access.md, "Using IPv6 addresses in IAM policies": "If you use source IP address filtering in your AWS Identity and Access Management (IAM) user or bucket policies, you need to update the policies to include IPv6 address ranges. IP address filtering policies that are not updated to handle IPv6 addresses may result in clients incorrectly losing or gaining access to the bucket when they start using IPv6." (AWS's own doc explicitly names **both directions** — "losing or **gaining** access" — as a documented risk class.) The sample policy shown allows only `54.240.143.0/24` and the doc states plainly: "Since all IPv6 addresses are outside of the allowed range, this policy prevents IPv6 addresses from being able to access `examplebucket`" for an Allow-style policy — but the doc's own "gaining access" phrase implies the inverse Deny-blocklist case is the live risk for a Deny-style IP-restriction policy that AWS did not fully spell out with an example.
**Confirm/Refute oracle:** Construct (in a test account) a bucket policy that **Denies** `s3:*` when `aws:SourceIp` is NOT in an IPv4-only allowed CIDR list (common "allowlist via Deny-NotIpAddress" pattern), then access the bucket over the IPv6 dual-stack endpoint (`bucket.s3.dualstack.{region}.amazonaws.com`) from an address outside any IPv4 concern entirely — confirm whether the `NotIpAddress` condition (which only lists IPv4 CIDRs) evaluates as "true" (not in the list) for an IPv6 source, correctly denying it (fails closed, expected), vs. a misconfigured **positive** `IpAddress` Allow-only policy mixed with a separate broader statement, where IPv6 callers may land on a different, unintended statement. The precise bypass shape requires testing the exact condition-operator semantics (`IpAddress` vs `NotIpAddress`) for non-matching address families — this is exactly the "documented condition-key gap" the task description flags and the doc explicitly warns of both-directions failure.
**Preconditions:** Dual-stack/IPv6 access must be reachable for the bucket (not blocked by VPC-endpoint-only access); the bucket policy must use IP-based conditions as a primary control without an explicit IPv6 CIDR entry.
**Severity-if-true:** High if a Deny/blocklist-style IP restriction can be evaded by switching address family (effectively an access-control bypass for a documented "secondary" control); Medium if only the "accidentally over-broad Allow" direction is confirmed (self-inflicted customer misconfiguration, lower severity per the catalog's "customer footgun" framing) — AWS's doc frames this as a **customer configuration responsibility** ("you need to update the policies"), so ultimate severity ownership is shared/customer-side, but the underlying condition-key semantics gap is AWS's documented mechanism.

### Lead 7 — S3 Select SQL dialect as an injection/exhaustion surface over object content (Lens F, Lens L)
**Claim:** S3 Select's SQL-over-object-content allows arbitrary caller-supplied SQL expressions (per the SELECT error-code list showing CAST, LIKE, aggregate functions, GROUP BY, scalar sub-expressions) to be evaluated server-side against the targeted object; the error-code enumeration (`EvaluatorInvalidArguments`, `MaxOperatorsExceeded` "try reducing complexity", `ExpressionTooLong` capped at 256 KB, `IllegalSqlFunctionArgument`) suggests both (a) a non-trivial SQL evaluator with a function surface broad enough for logic errors/edge-case exploitation, and (b) explicit resource-exhaustion guardrails (expression length cap, "MaxOperatorsExceeded... reduce number of operators") implying the service anticipated and bounded a DoS vector via expression complexity.
**Mechanism (doc evidence):** ErrorResponses.md's "List of SELECT Object Content Error Codes" table — specifically `ExpressionTooLong` ("maximum byte-length for an SQL expression is 256 KB"), `MaxOperatorsExceeded` ("Failed to parse SQL expression, try reducing complexity"), `IllegalSqlFunctionArgument`, `IncorrectSqlFunctionArgumentType`, `EvaluatorInvalidArguments`, `ParseMalformedJoin` ("JOIN is not supported"), `ParseExpectedWhenClause` ("CASE is not supported") — the dialect is explicitly restricted (no JOIN, no CASE) but still has a function-call surface and CAST/type-coercion path (`CastFailed`, `InvalidCast`, `NumberFormatError` "caused by underflow or overflow of integers"). RESTSelectObjectAppendix.md documents the binary event-stream framing (prelude + CRC32 + headers + payload) the response is wrapped in — a custom binary protocol parser is itself attack surface per Lens F's "native memory-safety of parsers" variant (length-prefixed fields, nested CRC-checked sections) though no local SDK/parser code is in-scope here, only the wire format description.
**Confirm/Refute oracle:** (1) Injection/logic: craft SQL expressions using documented functions/CAST paths to attempt reading data outside the targeted object's declared schema (e.g., scalar subquery-like constructs, path traversal in `InvalidKeyPath`-adjacent syntax) — confirm the dialect is strictly confined to the single object's rows/columns with no cross-object or catalog-leak primitive. (2) Resource exhaustion: submit an expression near the 256 KB cap with maximal operator nesting below `MaxOperatorsExceeded`'s threshold against a large compressed object, and measure service-side cost/duration to assess whether per-request limits meaningfully bound compute cost given S3 Select is billed by data scanned (cost-based DoS/billing-abuse angle, not availability DoS). (3) Parser: send malformed/truncated event-stream frames (bad prelude length, mismatched CRC) to the extent reachable via documented request-shaping (InputSerialization/CompressionType mismatches) and observe whether error handling (`TruncatedInput`, `CSVParsingError`) degrades gracefully or produces inconsistent partial responses.
**Severity-if-true:** Medium (bounded by AWS's documented single-object scope and explicit complexity/length caps — most likely refuted as "well-bounded" rather than confirmed as injection, since this is a mature, long-shipped feature now closed to new customers); escalate to High only if a cross-object or metadata-leak path is found, which the docs give no indication of (no `FROM` targets beyond the one object; `ParseSelectMissingFrom` and lack of any multi-table/JOIN syntax strongly support containment).

### Lead 8 — Request-ID / Host-ID (x-amz-id-2) leakage as an internal-topology side channel (Lens A, Informational)
**Claim:** `x-amz-id-2` ("host-id") is described as helping "AWS troubleshoot problems" and is returned on every response including errors and anonymous/pre-auth OPTIONS responses (per RESTOPTIONSobject.md's sample response showing `x-amz-id-2` on a 200 OK preflight with no `Authorization` header involved) — while the value itself is designed to be opaque, its consistent presence pre-auth means any pre-auth probe (including the CORS preflight oracle in Lead 5, or the error-oracle in Lead 3/4) also harvests a durable identifier usable for AWS Support correlation, and inconsistencies in its format/length across request types could theoretically fingerprint internal routing (unconfirmed; no doc detail on internal structure).
**Mechanism (doc evidence):** get-request-ids.md: "Request IDs come in pairs, are returned in every response that Amazon S3 processes (even the erroneous ones)." RESTCommonResponseHeaders.md: `x-amz-id-2` "is used together with the x-amz-request-id header to help AWS troubleshoot problems."
**Confirm/Refute oracle:** No actionable oracle beyond noting this is low-severity informational metadata; mark as a null/low-priority lead unless a format-fingerprinting pattern is independently found.
**Severity-if-true:** Informational — included only because Lens A instructs explicitly checking whether request-id/host-id leaks anything; the docs give no evidence of sensitive content in the opaque identifiers themselves.

## 4. Null hypotheses / doc gaps (pages checked, no trigger found or explicitly refuted by the doc text)

- **Permanent redirect as an open-redirect primitive (Lens G):** N/A as a cross-domain open redirect — UsingRouting.md states explicitly that permanent redirects do **not** include a `Location` header at all ("this type of redirect does not contain a Location HTTP header... Consult the resulting XML error document"), so there is no client-followed-automatically redirect target to manipulate for permanent redirects; only *temporary* redirects (Lead 2) carry a `Location`, and that is explicitly constrained by AWS's own doc text to the `amazonaws.com` domain. Checked: RESTRedirect.md, UsingRouting.md in full.
- **Attacker-influenceable temporary-redirect host suffix (part of Lead 2):** no doc evidence that the `s3-xxxxxxxx` suffix is derived from anything caller-controlled; treated as a null hypothesis pending live confirmation, not claimed as broken. Checked: RESTRedirect.md (both the generic topic page and the worked example), UsingRouting.md's redirect-example section.
- **CORS preflight on a bucket that doesn't exist / existence oracle via OPTIONS (sub-case of Lead 5):** the doc text only states the 403-vs-200 behavior keys off whether `cors` is configured, not explicitly on bucket existence; whether a nonexistent-bucket OPTIONS returns a distinguishable error (404 vs 403) is a **doc gap** — RESTOPTIONSobject.md does not describe behavior for a missing bucket/object, only "cors not enabled" → 403. Mark doc-gap, not N/A; would need the general error-handling precedence rules (bucket-existence check vs CORS check order), which are not stated anywhere in this cluster.
- **S3 Select cross-object/catalog leakage (part of Lead 7):** refuted at the documentation level — no `FROM`-clause target other than the single invoked object is described anywhere in RESTSelectObjectAppendix.md or the SELECT error-code list (`ParseSelectMissingFrom`, `ParseMalformedJoin: "JOIN is not supported"`, `MultipleDataSourcesUnsupported: "Multiple data sources are not supported"`); treat the cross-object angle as a documented null hypothesis, with only the complexity/DoS and type-coercion edge-case sub-leads remaining open.
- **Trusted-upstream-header injection (Lens CC) for `X-Forwarded-*` / proxy-asserted identity:** this cluster's pages (RESTCommonRequestHeaders.md, RESTCommonResponseHeaders.md) document no `X-Forwarded-For`/`X-Forwarded-Host`/custom authorizer-context header consumed by S3 itself — S3's own REST layer authenticates via SigV4 `Authorization`/`x-amz-security-token`, not a trusted upstream-asserted identity header. This lens is **N/A for S3's own REST endpoint**; it would only become relevant for a customer-operated reverse proxy in front of S3 (out of scope for this doc cluster). Checked: RESTCommonRequestHeaders.md, RESTCommonResponseHeaders.md in full — no `X-Forwarded-*` or `X-Amzn-*` identity-assertion header appears in either table.
- **Attestation-conditioned authorization (Lens W):** no trigger anywhere in this cluster (no KMS Recipient/PCR/enclave material in header, redirect, routing, CORS, error, or Select pages). N/A — checked all 12 pages in the cluster, no attestation-related terms present.
- **Cache-key vs authorization-key divergence (Lens DD) beyond the CORS Access-Control-Max-Age caching behavior already covered in Lead 5:** RESTCommonResponseHeaders.md documents `Vary` and `Access-Control-Max-Age` as present only on *successful* CORS evaluations, but no edge/CDN caching layer (CloudFront behavior, authorizer-result TTL) is described anywhere in this cluster's pages — S3's own REST responses are the origin, not a cache. Treated as N/A for the S3-REST-origin layer itself; would only resurface if a CloudFront distribution sits in front (out of scope doc-wise here). Checked: RESTCommonResponseHeaders.md, RESTOPTIONSobject.md.
