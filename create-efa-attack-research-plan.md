## 1. Pentest Objectives (boundary-breach goals, concrete outcomes)
1. **Attach an OS-bypass/RDMA device via a path the admin forgot to lock down** — demonstrate that each of the page's **four** create/attach paths (standalone create, attach-to-stopped, inline-at-launch, launch-template) independently yields an `efa`/`efa-only` interface with **no IAM condition that could have blocked it**, and that the launch-template path spawns such devices **through downstream services (AWS Batch / ParallelCluster)** under a different identity and with no re-check.
2. **Set an un-gateable connection-tracking posture at ENI birth** — create an EFA whose idle-connection-tracking timeouts (5-day TCP default) no SCP/identity policy could constrain, and show the knob is absent from the IAM schema.
3. **Mutate the "mandatory" wide SG on a live EFA** — change the security group on an existing EFA post-create (the Considerations bullet invites it) in a way an `ec2:Attribute`/`ec2:SecurityGroupID` policy cannot distinguish from a benign change (swap the self-ref all-traffic SG in or out).
4. **Exploit the stopped-only attach/detach constraint operationally** — show that EFA attach/detach forces an instance **stop**, a disruption lever and a window where state changes.
5. *(Routed to hub Area 4, HARD STOP)* Any cross-tenant SRD/RDMA effect that the device created here enables — **confirm-the-mechanism-first, do not break a live fabric.**

## 2. Components, Assets, and Design (page-specific)

**What this page is.** The create/attach CRUD surface for an EFA. EFA is **not a distinct API**; it is the value `efa` / `efa-only` of the `InterfaceType` parameter (`--interface-type` on `create-network-interface`; `InterfaceType=efa` inside `--network-interfaces` on `run-instances`; `InterfaceType=efa` inside a launch template's `NetworkInterfaces`). The **device type is the privilege boundary** (OS-bypass + SRD + RDMA vs ordinary IP).

**The four creation/attachment paths this page documents (the page's distinctive structure):**
```
(a) Standalone create     : create-network-interface --interface-type efa|efa-only            → an eni- you later attach
(b) Attach-to-stopped     : attach existing EFA eni- to a STOPPED instance (running not allowed)
(c) Inline-at-launch      : run-instances --network-interfaces "...,InterfaceType=efa,..."     → NEW EFA minted at launch
(d) Launch-template       : LT NetworkInterfaces[InterfaceType=efa]  ──consumed by──►  run-instances │ AWS Batch │ AWS ParallelCluster
```
Paths (c) and (d) **mint a brand-new EFA**; the `InterfaceType=efa` field is a plain request parameter on each. Path (d) is the only one whose consumer is a **separate AWS service** resolving the LT (possibly `$Latest`/`$Default`) at a later time.

**Per-ENI knobs settable at create on this page (beyond `InterfaceType`):**
- **Security group(s)** — must be the self-referencing all-traffic SG to enable OS-bypass (links to `efa-start.md#efa-start-security`); changeable later via `ModifyNetworkInterfaceAttribute`.
- **IP / EIP / IPv6 / prefix delegation** — **EFA-with-ENA only**; "You can't assign an IP address to an EFA-only network interface." Primary-IPv6 (GUA) and IPv4/IPv6 prefix delegation (with "AWS verifies it is not already assigned to another resource").
- **Idle connection tracking timeout** — TCP established **Min 60 / Max 432000 (5 days) / Default 432000**; UDP Min 30 / Max 60 / Default 30; UDP stream Min 60 / Max 180 / Default 180. Links to `security-group-connection-tracking.md#connection-tracking-timeouts`. **This knob appears on no other EFA page.**

**State / topology constraints (EFA-specific).** An EFA is created in one subnet, **cannot be moved** to another subnet, and is attachable **only to STOPPED instances in the same AZ**; it **cannot be attached to or detached from a `running` instance** (unlike a plain ENI). SRD traffic can't cross AZ/VPC and is non-routable (fabric property, hub Area 4).

**Identity.** Control-plane: SigV4 IAM on `CreateNetworkInterface` / `AttachNetworkInterface` / `RunInstances` / `CreateLaunchTemplate` / `ModifyNetworkInterfaceAttribute`. Path (d) adds the **downstream service's** launch identity (Batch SLR / ParallelCluster role). Data-plane: none (OS-bypass; no per-RDMA-op IAM check — hub Area 4).

## 5. Recommended Areas of Focus (ranked)

### Area 1 — [HEADLINE] Four independent create/attach paths each bypass InterfaceType scoping; the launch-template path spawns EFA via downstream services (Lens S / U / X / B-late-binding)
**Background.** The hub (Area 1) establishes that no `ec2:InterfaceType` condition key exists, so EFA attachment cannot be denied by IAM. This page is where that gap becomes **four concrete, separately-authorized paths** to the same OS-bypass device — and admins typically lock down one path (e.g. `RunInstances`) while leaving others open.
**Security Concern.**
- **Path multiplicity:** `CreateNetworkInterface` (standalone), `AttachNetworkInterface` (to a stopped instance), `RunInstances` inline, and `CreateLaunchTemplate(Version)` consumed by `RunInstances`/Batch/ParallelCluster all accept `InterfaceType=efa`/`efa-only` with **zero** interface-type condition key on any resource row (verified §4; whole-doc grep = 0 for `InterfaceType`/`interface-type`/`rdma`/`SRD`/`OsBypass`). A policy that denies EFA on one action does nothing on the other three. This is the **Lens-X "action-family parity"** shape: the capability has four doors and the lock fits none.
- **Launch-template late-binding (Lens B/X, highest-value sub-lead — downstream-service research COMPLETE, see Area 1 addendum):** `CreateLaunchTemplate`'s condition-key cell is **empty** in `list_ec2.md`; the LT body — including `NetworkInterfaces[InterfaceType=efa]`, the SG, and the AMI — is opaque to IAM. A principal holding only `ec2:CreateLaunchTemplateVersion`/`ec2:ModifyLaunchTemplate` (no `RunInstances`, no `iam:PassRole`) can inject an `efa` interface (and swap SG/AMI) into a version that **downstream services resolve at launch time**. The page explicitly invites this: *"You can leverage launch templates to launch EFA-enabled instances with other AWS services, such as AWS Batch or AWS ParallelCluster."* If the LT reference uses `$Latest`/`$Default`, every future Batch job / ParallelCluster scaling event picks up the injected device — the EFA-specific instance of the fleet-cluster `$Latest` late-binding privesc.
**High-level Test Scenarios.**
- *Claim:* a principal allowed ordinary-ENI create/launch can always also mint `efa`/`efa-only` via **each** of the four paths → *Oracle:* `SimulateCustomPolicy` with every plausible interface-type condition (there is no key to name) returns Allow on all four actions; a scoped live `create-network-interface --interface-type efa` and a scoped `run-instances …InterfaceType=efa` both succeed. *Severity:* **Medium** (AWS-owned enforcement gap, Tier-2 reportable).
- *Claim:* editing an LT version flips future **Batch/ParallelCluster** launches to EFA with no consumer-side re-check → *Oracle (RESOLVED from docs — Area 1 addendum):* neither service re-validates `InterfaceType`; the LT editor **is** the control point. *Severity:* **Medium–High** (cross-service, intra-account privesc of network capability).
- *Adjacent:* can a plain ENI be converted to EFA post-hoc via `ModifyNetworkInterfaceAttribute`? (Type appears fixed at create — confirm; if convertible, `ec2:Attribute` gating becomes relevant and this is a 5th path.)
**Doc evidence:** `create-efa.md` (all four path sections + "other AWS services" sentence); `list_ec2.md` grep=0 for interface-type; `CreateLaunchTemplate` empty condition cell (line 565–566). **Severity-if-true:** Medium (paths), Medium–High (LT→downstream).

#### Area 1 addendum — Downstream-service LT consumption (AWS Batch / AWS ParallelCluster), documentation-confirmed 2026-10-15
Research of the Batch and ParallelCluster docs settles the previously-open consumer-side questions. **All five sub-findings strengthen the Area-1 claim that the LT editor is the un-gateable control point:**
1. **Batch re-resolves `$Latest`/`$Default` on every infrastructure update, not just at CE creation.** `API_LaunchTemplateSpecification.md`: *"During an infrastructure update, if either `$Default` or `$Latest` is specified, AWS Batch re-evaluates the launch template version, and it might use a different version … even if the launch template isn't specified in the update."* `infrastructure-updates.md` lists `launchTemplate` among the settings that trigger such an update. **Consequence:** a principal who can move `$Default` (via `ec2:ModifyLaunchTemplate`) or add a new default version (`ec2:CreateLaunchTemplateVersion`) gets a malicious LT version adopted by an **existing** Batch compute environment at the next infra update — no need to touch the CE itself. This is the EFA-specific, cross-service realization of the fleet-cluster `$Latest`/`$Default` late-binding privesc already in the plan corpus.
2. **No LT ownership/authenticity gate in either service — it is pure IAM.** No Batch/ParallelCluster doc asserts any check on who created the referenced LT. `BatchServiceRolePolicy` scopes `ec2:RunInstances`/`CreateLaunchTemplate`/`DeleteLaunchTemplate` only by `aws:RequestTag`/`aws:ResourceTag` `AWSBatchServiceTag`, **not** by LT creator identity. Whoever holds LT-write permission on the referenced template controls every future launch. (Absence-of-control finding; no sentence disclaims it.)
3. **No `InterfaceType` re-check at the consumer.** Batch's `launch-templates.md` publishes an explicit "ignored fields" list (instance type, instance role, NI subnets, market options, disable-API-termination) — `InterfaceType` is **not** on it, so it flows straight from the LT. ParallelCluster's `LaunchTemplateOverrides` only restricts the override LT to the `NetworkInterfaces` block *as a whole* (*"validates the launch template and prevents overriding other parameters"*) and its own tutorial example sets `"InterfaceType":"efa-only"` inside that permitted block. **Neither service exposes an admin control to forbid `efa`/`efa-only`.**
4. **Launch identity differs — and neither carries an InterfaceType condition (confirming none exists).** Batch launches under the SLR **`AWSServiceRoleForBatch`** / `BatchServiceRolePolicy` (no network-interface-type key anywhere in the policy). ParallelCluster has **no** such SLR: the **customer head-node / Slurm-resume role** calls `ec2:RunInstances`/`ec2:CreateFleet` directly, documented with `"Resource":"*"`. Either way the OS-bypass device is minted with no interface-type gate.
5. **ParallelCluster makes EFA a one-line flag and auto-builds the wide SG.** `Efa/Enabled: true` on a `ComputeResource`; from 3.15.0 it *"automatically configures EFA-only network interfaces."* By default it *"creates and configures security groups that allow all traffic between cluster nodes"* — i.e. it auto-provisions the exact self-referencing all-traffic SG the hub (Area 2) flags; with a **custom** SG the all-traffic-to-self requirement is pushed onto the admin (reiterated in `efa-v3.md`/`Scheduling-v3.md`). **This means the hub-Area-2 wide-SG surface is reproduced automatically by ParallelCluster, outside this page's console/CLI flow.**
**Net effect on severity:** the LT→downstream path is the sharpest lead on the page — **Medium–High**, intra-account, cross-service, and settleable entirely with `iam:SimulateCustomPolicy` + reading the two services' managed policies (no live fabric risk). Downstream hunter: the control point to test is **`ec2:CreateLaunchTemplateVersion`/`ec2:ModifyLaunchTemplate` on an LT referenced by a Batch CE using `$Default`/`$Latest`.**

### Area 2 — [HEADLINE, net-new to this page] Idle connection-tracking timeout is IAM-unscopable and set at ENI birth with a 5-day TCP default (Lens S / L / U)
**Background.** This page is the **only** EFA doc that exposes the **Idle connection tracking timeout** settings, configurable at create: TCP established **Min 60 / Max 432000s (5 days) / Default 432000**, UDP 30/60/30, UDP stream 60/180/180. It links to `security-group-connection-tracking.md#connection-tracking-timeouts`.
**Security Concern.**
- **No condition key exists** for connection tracking anywhere in EC2: a full grep of `list_ec2.md` returns **0** matches for `ConnectionTracking`/`connection-tracking`/`conntrack`/`ConnectionTrackingSpecification`. On `CreateNetworkInterface` the `ConnectionTrackingSpecification` is a plain sub-struct with **no gate** — an admin cannot write a policy that forbids a 5-day idle timeout, nor require the AWS-recommended "less than 432000 seconds." (The `ena-nitro-perf` sibling records the same `ConnTrackSpec`-IAM-value-unscopable fact for the ENA path; this page is where it is set at EFA birth with the EFA-specific 5-day default.) This is the Lens-S "a condition key that does not exist → cannot deny by it" shape, parallel to the `ec2:InterfaceType` gap.
- **5-day default + mandatory wide SG = conntrack-table amplifier.** The default idle TCP-established timeout is the **maximum** (5 days). On an **EFA-with-ENA** interface, the ENA/IP path is connection-tracked, and the AWS-mandated self-referencing **all-traffic** SG (hub Area 2) means every TCP/UDP flow between every cluster peer is a tracked entry that lingers for up to 5 days idle. The Nitro per-ENI/per-instance conntrack table has a finite ceiling; a long default timeout slows reclamation. **Exhaustion-DoS depth is owned by `ena-nitro-perf` / `monitoring-network-performance-ena`** — this plan's net-new contribution is that the knob is (a) un-gateable and (b) defaulted to the worst value precisely on the interface type AWS also tells you to pair with an all-traffic SG.
- **EFA-only nuance (doc-gap):** `efa-only` ENIs have no IP; whether SG/conntrack applies to them at all is undocumented (ties hub Area 7 "SG-on-efa-only-may-be-vestigial"). If conntrack is IP-path-only, the knob is inert on `efa-only` → confirm which interface types it actually governs.
**High-level Test Scenarios.**
- *Claim:* no IAM/SCP condition can restrict the EFA's connection-tracking timeouts → *Oracle:* `SimulateCustomPolicy` with any attempted conntrack condition (no key to name) returns Allow; a scoped `create-network-interface … --connection-tracking-specification TcpEstablishedTimeout=432000` succeeds under a policy that "should" cap it. *Severity:* **Low–Medium** (AWS-owned schema gap; Tier-2 reportable as a hardening gap).
- *Claim:* 5-day idle timeout + all-traffic self-ref SG on EFA-with-ENA slows conntrack reclamation → *Oracle (defer to `ena-nitro-perf`):* on a canary, measure tracked-flow accumulation; do not drive a shared component to exhaustion. *Severity:* self-DoS Low; **cross-tenant only if a shared NIC is confirmed (routes to efa-acc-inst-types Area 2 doc-gap) — otherwise OOS.**
**Doc evidence:** `create-efa.md` Idle-connection-tracking block (verbatim min/max/default); `list_ec2.md` conntrack grep=0; `security-group-connection-tracking.md`. **Severity-if-true:** Low–Medium (schema gap); DoS deferred.

### Area 3 — [net-new to this page] Post-create SG mutability on a live EFA: breadth is un-gateable (Lens S / V, chains to hub Area 2)
**Background.** The "Considerations" bullet states plainly: *"You can change the security group that is associated with an EFA … in the same way that you change the security group that is associated with an elastic network interface,"* linking to `modify-network-interface-attributes.md`. EFA additionally *requires* that SG be the self-referencing all-traffic one for OS-bypass.
**Security Concern.** `ModifyNetworkInterfaceAttribute`'s `network-interface*` row carries `ec2:Attribute` + `ec2:Attribute/${AttributeName}` and the `security-group` row carries `ec2:SecurityGroupID` (§4). So a policy can gate **which attribute** is modified (`groupSet`) and **which specific SG** is attached — but **nothing expresses SG *breadth***. Two consequences:
- **Widen:** a principal permitted to set `groupSet` to an *allowlisted* SG id can still attach the wide self-ref all-traffic SG if that SG is on the allowlist (it must be, for EFA to work) → the "mandatory" rule guarantees the broad SG is a legitimate target, so the gate is defeated by design.
- **Strip (griefing / self-DoS):** the same permission lets an attacker **remove** the self-ref SG from a victim's live EFA, breaking OS-bypass for that cluster member — an availability hit on an HPC/ML job. Because EFA SG changes are "the same as" plain ENI, there is no EFA-aware guard.
This is distinct from the hub (which owns the SG's *existence* as a lateral-movement surface) and from the ENI sibling (which owns the generic attribute matrix): the net-new point is **the required-broad-SG + un-gateable-breadth interaction on a device whose whole security story is that SG.**
**High-level Test Scenarios.**
- *Claim:* an `ec2:Attribute=groupSet` + `ec2:SecurityGroupID`-scoped policy cannot prevent attaching the all-traffic self-ref SG → *Oracle:* `SimulateCustomPolicy` shows the broad SG passes the same gate as a narrow one; confirm no key encodes rule breadth. *Severity:* **Low–Medium.**
- *Claim:* the same permission strips the self-ref SG from a peer's EFA → *Oracle:* on a canary, `modify-network-interface-attribute --groups <narrow>` on a victim EFA removes the self-ref SG; observe OS-bypass break (self-contained canary only). *Severity:* **Medium** (intra-account availability).
**Doc evidence:** `create-efa.md` Considerations bullet; `list_ec2.md` ModifyNetworkInterfaceAttribute rows (8966+). **Severity-if-true:** Low–Medium.

### Area 4 — [net-new, lower] EFA-with-ENA vs EFA-only IP/EIP/IPv6/prefix asymmetry (Lens U / AA — mostly cross-ref)
**Background.** The page: EFA-with-ENA takes an EIP/IPv4/IPv6 "in the same way as" a plain ENI; **"You can't assign an IP address to an EFA-only network interface."** Primary-IPv6 (GUA) and IPv4/IPv6 **prefix delegation** are offered, with *"AWS verifies that it is not already assigned to another resource."*
**Security Concern.** Two net-new slivers (full IP/EIP depth is owned by the IP/EIP cluster plans — defer):
- **Enforcement of the EFA-only no-IP rule:** is "can't assign an IP to efa-only" enforced at `CreateNetworkInterface`/`AssignPrivateIpAddresses`/`AssociateAddress`, or only in the console? If a later IP-assign API accepts an IP on an `efa-only` ENI, that's a validation-vs-prose gap (Lens U). *Oracle:* attempt `assign-private-ip-addresses`/`associate-address` on a canary `efa-only` ENI; expect reject.
- **Prefix-delegation pre-emption:** the "AWS verifies it is not already assigned" check is the subnet-CIDR-reservation cross-tenant pre-emption/griefing surface already owned by `work-with-prefixes` / `ec2-prefix-eni`. On an EFA this is just another ENI consuming prefixes — **[POINTER]** to those plans; no EFA-specific delta beyond the device living on a cluster-placement-group host.
**High-level Test Scenarios.** *Claim:* the efa-only no-IP rule is API-enforced → *Oracle:* IP-assign APIs reject on `efa-only`. *Severity:* **Informational–Low** (validation parity).
**Doc evidence:** `create-efa.md` Considerations + console step 6. **Severity-if-true:** Informational–Low.

### Area 5 — [net-new, doc-fact] Stopped-only attach/detach is an EFA-specific disruption lever (Lens L / U)
**Background.** *"EFAs can't be attached to or detached from an instance in a `running` state"* and *"you can only attach it to stopped instances in the same Availability Zone."* Plain ENIs support hot (running) attach/detach.
**Security Concern.** This is a documented **constraint**, not a vuln by itself, but it is a lever: any operation that must add/remove an EFA (incl. remediating a mis-attached EFA, or an operator responding to Area 3's stripped SG) requires **stopping the instance** → induced outage of an HPC/ML node, and a state-transition window (stopped) during which other `stopped`-gated changes (user-data, instance-profile, AMI via LT late-binding) can be made. Also an availability asymmetry attackers can weaponize: forcing a stop to "fix" an EFA is more disruptive than a plain-ENI hot-swap. The subnet-immovability (`"You can't move the EFA to another subnet after it's created"`) similarly bakes placement at create with no later correction except delete+recreate.
**High-level Test Scenarios.** *Claim:* EFA lifecycle changes force an instance stop → *Oracle:* confirm `attach-network-interface` of an EFA to a `running` canary is rejected and only succeeds when `stopped`. *Severity:* **Low** (availability/operational; raises blast radius of Area 3). *Adjacent:* the stopped window overlaps the `ModifyInstanceAttribute(userData)` / instance-profile late-binding privesc shape (cross-ref fleet-cluster Lens B/E variant) — a forced stop to attach an EFA opens that window.
**Doc evidence:** `create-efa.md` intro + "Attach an EFA to a stopped instance" + "Create an EFA" subnet-immovability. **Severity-if-true:** Low.
