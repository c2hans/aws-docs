# EC2 "Identity and Access Management" (security-iam) — Attack Research Plan

**Target cluster:** `security-iam` (child of EC2 Security chapter), https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-security.html
**Method:** AWS internal "Researcher Training Material" reconstruction (security-questionbuilder skill), applied against the offline documentation mirror only.
**Hard constraint honored throughout:** documentation-only. No AWS API call, console action, or account was touched to produce this plan. All claims are traceable to a specific doc page or line range cited inline.

---

## 0. How to use this plan

This is a lead list for a hunter who *will* touch a live, authorized AWS account. Every lead below gives: the claim, the doc evidence, a non-mutating first oracle (prefer `iam:SimulatePrincipalPolicy`/`SimulateCustomPolicy`), and what a mutating confirmation would look like if the simulation is ambiguous. Start with Lens R leads — they are AWS-authored artifacts, so a confirmed finding here is an AWS defect report, not a customer-config gap. Do not escalate to a mutating test before the Sim oracle has run and been reviewed. `DryRunOperation`/`UnauthorizedOperation` is **not** an ownership oracle (it fires before resource resolution) — use it only to confirm caller-side IAM evaluation, never as proof a resource-scoping condition works.

## 1. Pentest objectives

1. Prove or refute that an AWS-managed/service-linked-role policy in the EC2 IAM surface permits **self-escalation**: a principal holding only that policy can attach an arbitrary role/instance-profile to a new or existing instance (`iam:PassRole` + `ec2:RunInstances`/`AssociateIamInstanceProfile`) and then retrieve that role's credentials via IMDS.
2. Prove or refute that a non-PassRole EC2 action can be used to **reach the credentials of a role already attached to an instance by someone else** (confused-deputy via `ec2:ModifyInstanceAttribute` on `userData`, then reboot/stop-start to execute).
3. Audit every printed condition-key example in the id-based-policy-examples page for silently-skipped or trivially-satisfiable conditions (Lens S).
4. Determine whether the new "Instance Identity Role" (no trust policy, not subject to any identity/resource policy) has any documented bound on who can rely on it, or whether its "Supported services" list is enforced anywhere beyond prose (Lens C/U).
5. Record every lens that did not fire, with the pages checked, so a follow-on hunter does not have to re-derive scope.

## 2. Components, assets, and design

**Customer-facing interface:** EC2 control-plane API (`ec2.amazonaws.com`, SigV4), console (which calls additional undocumented-combination APIs per `iam-policies-ec2-console.md`), and the per-instance **IMDS** HTTP endpoint (`169.254.169.254`, IMDSv1 unauthenticated-on-the-wire / IMDSv2 token-based), reachable only from inside the instance's own network namespace.

**Processes/roles behind it:**
- EC2 control plane (resource creation/mutation, policy evaluation).
- IAM (PassRole evaluation, service-linked-role creation, STS credential vending).
- Per-instance **IMDS credential vendor** — serves temporary credentials for (a) the classic instance-profile role at `/latest/meta-data/iam/security-credentials/{role-name}}`, and (b) per `iam-roles-for-amazon-ec2.md`, a new **Instance Identity Role** at `/identity-credentials/ec2/security-credentials/ec2-instance`, auto-created per instance, ARN `arn:{{partition}}:iam::{{account}}:assumed-role/aws:ec2-instance/{{instance-id}}`, **no trust policy**, **not subject to any identity or resource policy**. Documented consumers: AgentCore, EC2 Instance Connect, GuardDuty Runtime Monitoring, Lambda Managed Instances, STS `GetCallerIdentity`, Systems Manager Default Host Management.
- Several **service-linked roles** that act on the customer's behalf with EC2-granted permissions baked into AWS-managed policy JSON (Fleet, Spot Fleet, Spot, Fast Launch, Capacity Reservation Fleet, Capacity Manager, Instance Connect Endpoint, Declarative-Policies reporting, VSS snapshots).

**Accounts/ownership:** Single customer account per the docs read; no multi-tenant shared fleet described in this cluster (contrast with e.g. DocumentDB). The trust-relevant split here is principal-vs-role, not account-vs-account, except where PassRole's `Resource:"*"`/`arn:aws:iam::*:role/*` wildcards admit **cross-account** role ARNs in theory (worth testing: does `iam:PassRole` with `Resource:"arn:aws:iam::*:role/*"` actually permit passing a role in another AWS account, or is PassRole implicitly same-account? — recorded as an open lead below, Lens B).

**Resource identifiers:** instance ARNs (`arn:aws:ec2:region:account:instance/i-...`), role/instance-profile ARNs, launch-template ARNs, association IDs (`iam-instance-profile-association-...`) for `ReplaceIamInstanceProfileAssociation`/`DisassociateIamInstanceProfile`.

**Identity establishment:** SigV4 IAM for the control-plane API; for the instance's own code, IMDS token (IMDSv2) or unauthenticated path (IMDSv1) exchanged for temporary STS creds; **self-assumption** of a role from inside an instance that already holds that role requires the role's trust policy to allow the role to assume itself (`instance-metadata-security-credentials.md`).

**Where untrusted data enters and is later trusted:** `userData` on `RunInstances`/`ModifyInstanceAttribute` is customer/attacker-controlled, executed by the guest OS at boot/reboot — this is the transform boundary for Finding #2.

**ASCII summary of the key kill chain (Finding #1):**
```
[Principal holding ONLY EC2FastLaunchFullAccess]
        | iam:PassRole (Resource: instance-profile/*, role/*;
        |               Condition: iam:PassedToService=ec2.amazonaws.com only)
        v
   ec2:RunInstances (unconditioned Sid "EC2LaunchInstance";
                      Sid "EC2LaunchInstanceWithVolAndInstance" gated only by
                      aws:RequestTag/CreatedBy="EC2 Fast Launch" — caller-supplied)
        v
   [New EC2 instance, any role/instance-profile in the account attached]
        v
   IMDS credential retrieval (/latest/meta-data/iam/security-credentials/{role})
        v
   [Attacker holds credentials of the passed role — up to full admin]
```

## 3. Trust-boundary map

| From (actor/zone) | To (resource/zone) | Crossing mechanism | Breach oracle |
|---|---|---|---|
| Principal holding an EC2-scoped IAM policy only | Any IAM role/instance-profile in the account | `iam:PassRole` on `RunInstances`/`AssociateIamInstanceProfile`/`ReplaceIamInstanceProfileAssociation` | Principal can attach a role to an instance that it could not call `sts:AssumeRole` on directly, and later retrieve that role's live credentials via IMDS. |
| Caller-controlled request tag (`aws:RequestTag/*`) | A policy `Condition` meant to scope a privileged action | Tag-based ABAC gate on `RunInstances`/`CreateTags` where the tag key/value is supplied in the same API call it gates | The "gate" is satisfied by the caller simply including the tag in the request — no independent verification that the action is actually AWS-service-orchestrated. |
| Instance's own guest-OS code (anyone who can write `userData` or SSH in) | The instance-profile role's STS credentials | `ec2:ModifyInstanceAttribute` (attribute=`userData`) → reboot/stop-start → guest executes injected payload → reads IMDS | A principal with only EC2 full-access-style permissions (no PassRole, no AssumeRole on the target role) obtains the credentials of a role it never had rights to assume, by rewriting and executing code on an instance that already carries that role. |
| Any code running inside an EC2 instance | STS / downstream AWS services, via the new **Instance Identity Role** | IMDS path `/identity-credentials/ec2/security-credentials/ec2-instance`, documented as having **no trust policy** and **not subject to any identity or resource policy** | Any process on the instance — not just the "Supported services" (AgentCore, EC2 Instance Connect, GuardDuty, Lambda Managed Instances, SSM) — can retrieve and use these credentials, because no policy mechanism is documented to restrict who/what on the instance may call that IMDS path. |
| Customer with Spot/Fleet/FastLaunch SLR-equivalent policy knowledge | `iam:PassRole` to **any** role, scoped only by `iam:PassedToService` | AWS managed policies `AWSEC2FleetServiceRolePolicy`, `AWSEC2SpotFleetServiceRolePolicy`, `AWSEC2SpotServiceRolePolicy`, `EC2FastLaunchServiceRolePolicy` — SLR policies, not customer-attachable, but establish the *pattern* AWS itself uses | Confirms AWS's own baseline for "safe" PassRole scoping is `PassedToService` alone; relevant as a defense-in-depth baseline, not independently exploitable since these are SLR-only (service-assumed), listed here for completeness/comparison. |
| Caller with `iam:PassRole` Resource `arn:aws:iam::*:role/*` wildcard | A role in a **different AWS account** | Untested: does PassedToService-scoped PassRole with an account-wildcard ARN actually succeed cross-account, or does IAM silently require same-account? | Successfully passing a role whose ARN account-id differs from the caller's account. |
| Console-only caller | Underlying API surface not exposed as a single documented policy | `iam-policies-ec2-console.md`: "The console uses additional API actions... these policies may not work as expected" | A console action succeeds using API calls/permissions not listed in any single documented example policy, indicating the console's effective privilege surface is broader/different than the printed examples suggest. |

## 5. Recommended areas of focus (lenses that fired)

### Lens R — AWS-authored IAM-artifact audit (PRIMARY, FIRED — Critical)

Audited statement-by-statement, by reading the **actual printed JSON** (not prose), for all 14 EC2-related AWS managed/SLR policies reachable from `security-iam-awsmanpol.md`:
`AmazonEC2FullAccess`, `AmazonEC2ReadOnlyAccess`, `AmazonEC2ImageReferencesAccessPolicy`, `AWSEC2CapacityReservationFleetRolePolicy`, `AWSEC2FleetServiceRolePolicy`, `AWSEC2SpotFleetServiceRolePolicy`, `AWSEC2SpotServiceRolePolicy`, `AWSEC2VssSnapshotPolicy`, `DeclarativePoliciesEC2Report`, `EC2FastLaunchFullAccess`, `AWSEC2CapacityManagerServiceRolePolicy`, `EC2FastLaunchServiceRolePolicy`, `Ec2InstanceConnect`, `Ec2InstanceConnectEndpoint`.

**Finding #1 (HEADLINE, Critical).** `EC2FastLaunchFullAccess` (customer-attachable to users/groups/roles **and** instance profiles per `security-iam-awsmanpol.md`: "You can attach the `EC2FastLaunchFullAccess` policy to your instance profile or other IAM role") contains:
```json
{"Sid":"IAMSLRPassRole","Effect":"Allow","Action":"iam:PassRole",
 "Resource":["arn:aws:iam::*:instance-profile/*","arn:aws:iam::*:role/*"],
 "Condition":{"StringEquals":{"iam:PassedToService":["ec2.amazonaws.com","ec2.amazonaws.com.cn"]}}}
```
```json
{"Sid":"EC2LaunchInstance","Effect":"Allow","Action":["ec2:RunInstances"],
 "Resource":["arn:aws:ec2:*:*:subnet/*","arn:aws:ec2:*:*:network-interface/*","arn:aws:ec2:*::image/*",
   "arn:aws:ec2:*:*:key-pair/*","arn:aws:ec2:*:*:security-group/*","arn:aws:ec2:*:*:launch-template/*",
   "arn:aws:license-manager:*:*:license-configuration:*"]}
```
(no `Condition` block at all)
```json
{"Sid":"EC2LaunchInstanceWithVolAndInstance","Effect":"Allow","Action":["ec2:RunInstances"],
 "Resource":["arn:aws:ec2:*:*:volume/*","arn:aws:ec2:*:*:instance/*"],
 "Condition":{"StringEquals":{"aws:RequestTag/CreatedBy":"EC2 Fast Launch"}}}
```
`aws:RequestTag/CreatedBy` is a **caller-supplied** tag on the very `RunInstances` call it is meant to gate — it is not independently verified to have originated from the Fast Launch service. Combined with the unconstrained PassRole (any role/instance-profile ARN in — per the `::*:` wildcard — any account, gated only by the near-universal `PassedToService=ec2.amazonaws.com`), a principal holding **only this one AWS-managed policy** can: launch a brand-new instance, attach any IAM role/instance-profile in the account to it (by simply tagging the RunInstances call `CreatedBy=EC2 Fast Launch`), then pull that role's credentials from IMDS. This is a complete non-admin→admin privilege-escalation primitive contained in a single AWS-managed, customer-attachable policy.

**Doc-vs-artifact drift corroborating this finding (Lens U overlap):** The live page (`security-iam-awsmanpol.md`, confirmed via WebFetch of the online twin — see §Online-twin check below) describes this policy's IAM grant as: *"IAM – Access is granted to get and use instance profiles **whose name contains `ec2fastlaunch`** to create the EC2FastLaunchServiceRolePolicy service-linked role."* The actual JSON's `IAMSLRPassRole` statement has **no name restriction at all** — it is `Resource:["arn:aws:iam::*:instance-profile/*","arn:aws:iam::*:role/*"]`. AWS's own prose describes a narrower, safer policy than what is actually shipped. This is independent evidence the unconstrained scope is unintended, strengthening a defect report rather than a "working as designed" dismissal.

**Finding #1b (Critical, same pattern, SLR variant).** `EC2FastLaunchServiceRolePolicy` (the SLR counterpart, not customer-attachable but worth citing as AWS's own template) has an even broader PassRole: `"Sid":"AllowPassRole","Resource":"*"` (no instance-profile/role path restriction at all), same `PassedToService` condition only. Confirms the unconstrained-PassRole pattern is systemic to the Fast Launch feature's IAM design, not a one-off typo in the customer-facing policy.

**Finding #1c (Medium, same family, narrower blast radius).** `AWSEC2FleetServiceRolePolicy` and `AWSEC2SpotFleetServiceRolePolicy` (SLR-only) both carry `iam:PassRole` on `Resource:["*"]` scoped only by `iam:PassedToService`. These are not customer-attachable, so exploitation requires the SLR itself to be tricked into passing an attacker-chosen role — lower priority than Finding #1, but worth testing whether `RequestSpotInstances`/Fleet-create APIs let a customer specify an arbitrary `IamInstanceProfile` that the SLR then passes on their behalf outside the customer's own PassRole grant (i.e., does the SLR's broader PassRole let a customer bypass their *own*, narrower, PassRole restriction by routing the launch through Fleet/Spot Fleet instead of direct RunInstances?). **Positive contrast noted:** `AWSEC2SpotServiceRolePolicy` has an explicit `Deny` on `RunInstances` creating non-spot instances (`StringNotEquals ec2:InstanceMarketType: spot`) — AWS hardened that one; Fleet/SpotFleet have no equivalent deny, worth checking if they should.

**Finding #1d (Low, scoping gap, not currently chainable to credentials).** `AWSEC2VssSnapshotPolicy`: `CreateSnapshotsAccessVolume` on `arn:aws:ec2:*:*:volume/*` and `DescribeImages`/`DescribeSnapshots` on `*` are unconditioned, while sibling statements correctly self-scope via `ec2:SourceInstanceARN: arn:aws:ec2:*:*:instance/${ec2:InstanceId}`. An instance holding this policy can snapshot **any** volume in the account, not just its own attached volumes — a data-exfiltration lead (clone another instance's volume via snapshot→new-volume) rather than a credential-escalation lead.

**Finding #1e (Low).** `Ec2InstanceConnectEndpoint` (SLR): `ec2:ModifyNetworkInterfaceAttribute` on `arn:aws:ec2:*:*:security-group/*` is unconditioned while every sibling statement is tag-scoped to `eice-*`. Minor — the SLR could in principle be used to attach/detach security groups beyond its own ENIs; low confirmed impact without further chaining.

**Null/clean results recorded (pages checked):** `AmazonEC2ReadOnlyAccess` (`Describe*` only, no PassRole) — clean. `AWSEC2CapacityReservationFleetRolePolicy` — `ArnLike` scoped to `crf-*`, clean. `AWSEC2CapacityManagerServiceRolePolicy` (newest, created October 15 2025 per the authoritative online managed-policy changelog) — Organizations read-only actions, no EC2 actions, no PassRole — clean but flagged as newest/least-reviewed surface, recommend re-check on next policy revision. `DeclarativePoliciesEC2Report` — pure read-only account-posture Describe/Get actions — clean. `Ec2InstanceConnect` — `DescribeInstances`+`SendSSHPublicKey` only — clean. `AmazonEC2ImageReferencesAccessPolicy` — read-only, flagged under Lens T below, not a PassRole issue.

**Oracle (safe, first):** `aws iam simulate-custom-policy --policy-input-list <EC2FastLaunchFullAccess JSON> --action-names iam:PassRole ec2:RunInstances --resource-arns <any role ARN in the test account>` and confirm `allowed`. No live resource is touched. If allowed, a mutating confirmation (in an authorized/synthetic account only) would be: attach only `EC2FastLaunchFullAccess` to a disposable test principal, `RunInstances` with `IamInstanceProfile` pointing at a high-privilege instance profile and tag `CreatedBy=EC2 Fast Launch`, confirm instance launches with that profile attached, then retrieve creds via IMDS from that instance.

### Lens B / E — Confused deputy / PassRole & non-PassRole credential reach (FIRED — Critical)

**Finding #2.** `AmazonEC2FullAccess` grants `ec2:*` on `Resource:"*"` with **no `iam:PassRole` statement at all** (confirmed by full read of the policy JSON) — so its holder cannot attach a *new* privileged role via PassRole. But `ec2:*` includes `ec2:ModifyInstanceAttribute`, which `list_ec2.md`'s detailed resource table (~L8800-8824) shows **can** be scoped by `ec2:Attribute`/`ec2:Attribute/${AttributeName}` — a scoping AWS's own `AmazonEC2FullAccess` does not apply. A holder of only `AmazonEC2FullAccess` can therefore: find any running instance that already has a privileged instance-profile attached (by someone else, e.g. an admin), rewrite its `userData` attribute, then `StopInstances`/`StartInstances` (or wait for a scheduled reboot) to force the guest OS to execute the injected payload, which calls IMDS and exfiltrates the attached role's live credentials — reaching a role the attacker was never granted `sts:AssumeRole` or `iam:PassRole` on. This is the skill's confirmed Lens B/E exemplar, verified present and unmitigated in this specific AWS-managed policy.

**Oracle:** `iam:SimulatePrincipalPolicy` for `ec2:ModifyInstanceAttribute` against a representative instance ARN under `AmazonEC2FullAccess`, confirming no `ec2:Attribute` condition narrows it. Mutating confirmation (authorized/synthetic account only): attach a role with a canary IAM policy to a test instance; from a second principal holding only `AmazonEC2FullAccess`, call `ModifyInstanceAttribute(userData=...)`, stop/start, confirm the canary role's temp credentials appear reachable from the rewritten boot script.

**PassRole cross-account question (open lead, untested, no doc answer found):** `permission-to-pass-iam-roles.md` warns `Resource:"*"` on `iam:PassRole` "grants permission to pass any role," without stating whether this is implicitly same-account. `EC2FastLaunchFullAccess`'s `arn:aws:iam::*:instance-profile/*` wildcard uses `*` for the account segment. Recommend testing (via Simulate first) whether PassRole with an account-wildcarded resource ARN can target a role in a **different** account, which would upgrade Finding #1 from account-contained privesc to a cross-account primitive. No page read states IAM blocks this; recorded as doc-gap, not a null.

### Lens C — Credential vending / session scope (FIRED — High, doc-only lead)

**Finding #3.** `iam-roles-for-amazon-ec2.md` documents a new **Instance Identity Role**, auto-created per instance, served at IMDS path `/identity-credentials/ec2/security-credentials/ec2-instance`, with the explicit properties "no trust policy" and "not subject to any identity or resource policy." The doc lists specific "Supported services" (AgentCore, EC2 Instance Connect, GuardDuty Runtime Monitoring, Lambda Managed Instances, STS `GetCallerIdentity`, Systems Manager Default Host Management) as consumers, but **no mechanism is documented that restricts retrieval of these credentials to those services** — the restriction, if any exists, is not stated to be enforced by IAM policy (the doc explicitly says it is *not* subject to any policy). This reads as "any process able to reach the instance's own IMDS can retrieve this role's credentials, and the 'Supported services' list is a usage expectation, not an access control." Needs confirmation: what *does* bound who can call `sts:AssumeRole`-equivalent via this path, if not a trust policy? Is it IMDS-session-scoped only (i.e., no stronger than classic instance-profile creds), or does it carry some other latent restriction (permissions boundary, session policy) not mentioned in this page?

**Oracle:** Read-only — fetch `GET /identity-credentials/ec2/security-credentials/ec2-instance` from a test instance (with IMDSv2 token) and inspect the returned credential's attached permissions via `sts:GetCallerIdentity` + `iam:SimulatePrincipalPolicy` using the vended credentials. This touches only the test instance's own metadata endpoint — no cross-account or production resource is touched. Confirm whether the vended identity can call anything beyond the "Supported services'" needs (e.g., can it call arbitrary `ec2:Describe*` or other services' APIs?).

### Lens S — Condition-key scoping semantics (FIRED — Medium, multiple leads)

Audited every printed example policy in `ExamplePolicies_EC2.md` and `iam-policies-for-amazon-ec2.md` for silent-skip or trivially-satisfiable conditions:

**Finding #4.** `ExamplePolicies_EC2.md` documents that the **`spot-instances-request` resource** in a `RunInstances` policy statement is **only evaluated by EC2 if the caller tags the Spot request at creation time** — if untagged, that resource's IAM clause is silently skipped entirely (not denied, not evaluated). Any policy author who added a `spot-instances-request` ARN condition believing it always applies has a false sense of scoping whenever a caller simply omits the tag. This is exactly the skill's "condition silently ignored" variant.

**Finding #5 (CORRECTED by Finding #F8 in §5A — read both).** The IMDSv2-enforcement example policies (`ExamplePolicies_EC2.md`, "Work with instance metadata") are all **`Deny`-based gates on `RunInstances`/`ModifyInstanceMetadataOptions`**, not `Allow`-based. AWS's own doc states (L1804): *"there are currently no fine-grained access controls (conditions) for the ModifyInstanceMetadataOptions API"* for the "Limit who can modify instance metadata options" example. **This statement is factually wrong** — the ExamplePolicies deep-dive (F8) proves `ModifyInstanceMetadataOptions` DOES support `ec2:MetadataHttpTokens`/`ec2:MetadataHttpEndpoint`/`ec2:MetadataHttpPutResponseHopLimit`/`ec2:Attribute*` condition keys (`list_ec2.md:8864`), and the same page uses `ec2:Attribute/HttpTokens`+`Null` on that very action 40 lines earlier (L1748-1766). The residual true risk persists regardless: combined with Finding #2's `AmazonEC2FullAccess` holding unconditioned `ec2:*`, a holder of that policy can freely call `ModifyInstanceMetadataOptions` to downgrade any instance to IMDSv1 or raise the hop limit, undermining any org-wide IMDSv2-enforcement SCP that relies on `RunInstances`-time conditions alone (those SCPs gate instance *launch*, not later *modification*, unless the "Deny opt-out of IMDSv2" statement is also deployed — worth checking whether orgs commonly deploy only the launch-time Deny and miss the modify-time Deny). The *new* angle F8 adds: because the doc wrongly tells implementers no conditions exist, they default to coarse role-allowlisting (`ec2-imds-admins`) instead of the available `ec2:MetadataHttpEndpoint`-based ABAC that could allow hop-limit tuning while denying endpoint-disable.

**Finding #6.** `iam-policies-for-amazon-ec2.md`'s ABAC section (`aws:ResourceTag/environment`) explicitly warns customers to *also* deny tag mutation (`CreateTags`/`DeleteTags`) to prevent circumvention of tag-based scoping — i.e., AWS's own docs flag that ABAC conditions in this service are self-widenable by default unless the author separately locks tag-write. Confirmed this warning is **not** itself enforced by any of the audited AWS-managed policies (none of them pair a `ResourceTag`-scoped grant with a corresponding tag-mutation Deny) — this is a customer-configuration risk the docs correctly flag but which is easy to miss; worth a quick grep of real-world example policies for presence/absence of the paired Deny.

**Finding #7 (confirmed-clean, included as positive design reference).** The launch-template lockdown examples (`ExamplePolicies_EC2.md` L900-1019) correctly combine `NotResource` + `ArnLike(ec2:LaunchTemplate)` + `Bool(ec2:IsLaunchTemplateResource:"true")` to prevent parameter-override outside the template — no silent-skip or self-widening issue found here; recorded as a null for this specific example (checked: full statement text, both example variants).

### Console + identity-policy pages (Lens R / S / U / X)

- **C1 (Medium, recon).** Every console sample policy on `iam-policies-ec2-console.md` that includes any `ec2:Describe*` grants account/region-wide enumeration regardless of stated "view only these" intent. The page admits it (L57: *"The … `ec2:Describe*` API actions do not support resource-level permissions"*). Confirmed via `list_ec2.md`: `DescribeInstances`(6996), `DescribeImages`(6906), `DescribeSecurityGroups`(7362), `DescribeAddresses`(6576), `DescribeSnapshots`(7386), `DescribeTags`(7446) etc. all have **blank required-resource-type** and only `ec2:Region` as a key — the "scope to a subset" framing (L28-30) narrows resource *category*, never specific resources. Oracle: `iam:SimulateCustomPolicy` any Describe + any ARN → `allowed` account-wide. Standalone recon primitive (instance IDs, SG rules, EIP associations, tags) that the grantor believed was scoped.
- **C2 (Low, Lens R insecure-default).** `iam-policies-ec2-console.md` ships write actions on `Resource:"*"` that *do* support scoping: `AssociateAddress` (L393-408; supports `elastic-ip`/`instance`/`network-interface` + `ec2:ResourceTag`, `list_ec2.md:4712`) and `ModifyReservedInstances` (supports `reserved-instances*`+`aws:ResourceTag`, `list_ec2.md:8986`) are granted unscoped. Teaches the broadest-available pattern. (Contrast: `PurchaseReservedInstancesOffering` genuinely has blank resource types — the page's L417 "can't set resource-level perms" is accurate *for that one action* but bundled misleadingly with the scopable `ModifyReservedInstances`.)
- **C3 (Medium, Lens X console-vs-API).** The page *instructs* admins to grant console-only companion `Describe*`/`CreateSecurityGroup`/`CreateKeyPair` on `"*"` purely so the UI renders (L10, L93, launch-wizard block L111-138) — strictly broader than an API-only `ec2:RunInstances` policy needs. The "let users launch instances" intent silently drags in full instance/VPC/subnet/SG/key-pair enumeration. This is the concrete realization of the task's "console effective surface ⊋ printed policy" trust-boundary row.
- **C4 / S3 (Medium, ABAC self-widen — extends Finding #6).** Both pages state the `ec2:CreateTags` self-widen hazard in **prose only** with no enforcing JSON anywhere: `iam-policies-ec2-console.md` L147-148 and `iam-policies-for-amazon-ec2.md` L355 (*"you must consider explicitly denying users the ability to add those tags"*). Sharp U-lens contrast on the identity page: L351's "must" (Describe needs a separate unconditioned statement) **is** mechanically enforced (true IAM constraint, see C1), while L355's "must consider … denying" is advisory with no sample Deny shipped. The flagship SG-ABAC example (console L272-313) gates `AuthorizeSecurityGroupIngress` on `aws:ResourceTag/Department=Test` but leaves `ModifySecurityGroupRules` on `security-group-rule/*` **unconditioned** and never denies `CreateTags` — so a holder who also has `CreateTags` (which the launch-wizard section tells them to add) retags any SG `Department=Test` and gains modify rights. Oracle: `SimulateCustomPolicy` {SG-ABAC + CreateTags} → `CreateTags` on a foreign SG = allowed, then gated action = allowed.
- **S1 (Medium, condition-key footgun).** `iam-policies-for-amazon-ec2.md` L270-311 documents the `ec2:{{Resource}}ID` key family (`ec2:ImageID`, `ec2:InstanceID`, `ec2:SecurityGroupID`, `ec2:VpcID`, …) that **silently resolve to `*` at runtime** — *"If you specify a different value, the condition always resolves to `*`"* (L270-271) — and AWS recommends avoiding 13 listed action/key pairs (`ec2:ImageID`-`CopyImage`/`CreateImage`/`RegisterImage`, `ec2:InstanceID`-`RunInstances`, `ec2:SecurityGroupID`-`CreateSecurityGroup`). A policy author pinning a specific created-resource ID with these keys is silently wrong (the condition is a no-op, never a block). Classic U-lens "looks restrictive in JSON, is a no-op." Oracle: `SimulateCustomPolicy` `StringEquals ec2:ImageID=ami-specific` on `CopyImage` → satisfied for any image.
- **S2 (Low, condition-key coverage gap).** `ec2:Attribute`/`ec2:Attribute/${AttributeName}` **cannot gate `ModifyImageAttribute`'s `LaunchPermission`** (the AMI public/private-sharing attribute) — L206-208 says the key only works for primitive/single-`Value` attributes, explicitly not multi-property objects like `LaunchPermission`. `list_ec2.md:8800` confirms `ModifyImageAttribute`'s keys (`ec2:Attribute*`, `ec2:ImageID`, `ec2:Owner`, `ec2:Public`, `ec2:ResourceTag`, `ec2:RootDeviceType`) include no attribute-content key reaching the act of flipping `LaunchPermission`. The page teaches `ec2:Attribute` as a general attribute-control mechanism but it excludes the one attribute (AMI sharing) most worth gating — Resource-ARN scoping is the only lever. Disclosed accurately (L208), so informational, but AMI-sharing misconfig is a classic exposure vector.

### IAM-roles / instance-profile / IMDS-vending pages (Lens C / U / M / A)

- **N-1 (Medium–High, same-account only).** The Instance Identity Role's "no policies attached … no additional permissions" guarantee (and `iam-roles-for-amazon-ec2.md:66` "not subject to any identity or resource policy") is a claim about **identity-based** attachment only. Any **resource-based** policy in the *same account* that names the ARN, wildcards `Principal`, or grants account-root (common for S3/KMS/SQS/SNS) still honors calls signed by this identity — same-account resource-policy evaluation needs no identity-based allow. Inflates the blast radius of *every* SSRF-reachable instance, including ones with **no instance profile** (see N-2). Oracle: `iam:SimulatePrincipalPolicy` for `assumed-role/aws:ec2-instance/<id>` against an action governed by a `Principal:root`/`*` resource policy; or read-only sweep of account resource policies for broad-principal patterns. Caps below Critical (same-account), but materially widens Finding #3.
- **N-2 (Medium → High, extends Finding #3).** The identity role turns "no IAM role attached" from a *null* SSRF credential surface into an *always-on* one: creds are *"present in the instance metadata regardless of whether a service or feature that makes use of instance identity roles is enabled"* (`iam-roles-for-amazon-ec2.md:64`) — i.e. **100% of EC2 instances**, including those deliberately run role-less as hardening, now expose an AWS-signed SigV4 identity via SSRF. The `ec2-instance-metadata.md` category rows show version `2018-05-23` (same vintage as classic `iam/security-credentials/`), suggesting the path has existed silently since 2018 and is only now documented (timeline speculative; falsifiable via AWS What's-New history, not offline). Oracle: read-only `GetCallerIdentity` signed with creds from a role-less test instance's `/identity-credentials/ec2/security-credentials/ec2-instance`. Standalone Medium (STS GetCallerIdentity is inert); High wherever N-1 or the six consumer services apply.
- **N-3 (High, scoping-model confusion).** *"You can include an IAM role in multiple instance profiles"* (`iam-roles-for-amazon-ec2.md:48`). Any defense scoping `ec2:AssociateIamInstanceProfile`/`Replace` via the optional `ec2:NewInstanceProfile` condition key (an instance-**profile**-ARN allowlist, `list_ec2.md:4752`) rather than `iam:PassRole` (a **role**-ARN allowlist) is bypassable: a caller with IAM-side `CreateInstanceProfile`+`AddRoleToInstanceProfile` wraps an already-privileged role in a *new* profile ARN not on the EC2 allowlist, pointing at the same role. The action's only required resource type is `instance*` — nothing pins role↔profile 1:1. The doc states the many-profiles-per-role fact without flagging it next to `ec2:NewInstanceProfile`. Oracle: policy-logic review / `SimulatePrincipalPolicy` of any `ec2:NewInstanceProfile`-only gate against a second profile ARN wrapping the same role.
- **N-4 (High during IR).** The only quantified revocation-lag guarantee — *"up to one hour before this change takes effect"* (`iam-roles-for-amazon-ec2.md:50`) — is scoped to the IAM-side `RemoveRoleFromInstanceProfile` on the **profile object**, NOT to the EC2-side `DisassociateIamInstanceProfile`/`ReplaceIamInstanceProfileAssociation` (`attach-iam-role.md:88,149-204`), which are the *recommended* detach/replace path. Neither page states the lag (if any) for the EC2-level ops, nor whether already-vended creds cached on the instance survive the association change. Undermines "replace to contain" as an IR action. Oracle (read-only on test instance): cache vended creds, `disassociate-iam-instance-profile`, retry `sts:GetCallerIdentity` at T+0/+5m/+30m to empirically bound the pre-existing session's STS validity. Distinct from, and sharper than, the earlier B-6/B-11 role-removal-lag note.
- **N-5 (Medium, Lens R sample-coupling fragility).** `AssociateIamInstanceProfile`/`Replace`/`Disassociate` have **no `instance-profile` resource type at all** (`list_ec2.md:4749,7915,9401`) — only `instance*`. The entire "which profile can be attached" restriction is delegated to the `iam:PassRole` statement; AWS's own documented example (`permission-to-pass-iam-roles.md:17-46`) pairs a correctly-scoped `iam:PassRole` with `Resource:"*"` on the three EC2 actions. Functionally safe *only* while the PassRole ARN pattern is never independently widened — a maintenance footgun since the two statements are visually/operationally decoupled in the JSON. Distinct from B-1/B-2: this is about the *sample policy's own internal coupling*, not a hypothetical customer misconfig.
- **N-9 (High if unconfirmed-gated; else doc-gap).** `configuring-instance-metadata-options.md` / `instance-metadata-limiting-access.md` describe `HttpTokens`/`HttpPutResponseHopLimit` as properties of the IMDS **service as a whole** (`169.254.169.254`), never scoped per metadata path. Neither states whether `/identity-credentials/ec2/security-credentials/ec2-instance` is gated by the same `HttpTokens=required`/hop-limit hardening as `/iam/security-credentials/{role}`, or is exempt. **If the always-on identity path is NOT subject to IMDSv2/hop-limit enforcement, that enforcement — deployed specifically to kill SSRF→creds — has a sibling path that silently reopens it on every instance (N-2).** Oracle (read-only, test instance with `HttpTokens=required`): bare no-token `GET` of the identity-credentials path.
- **N-8 (Low direct / Medium doc-gap, Lens M).** ARN `assumed-role/aws:ec2-instance/{instance-id}` embeds a guessable ID, but IMDS has no "fetch creds for instance X" parameter — a caller only ever retrieves its *own* instance's identity creds, so instance-id predictability alone gives no cross-instance impersonation (**direct impersonation refuted, Low**). Open doc-gap (**Medium**): whether any of the six consumer services authorizes purely by server-side ARN string-match vs. cryptographically binding the SigV4 session to the originating instance — unstated in this page set; carried as the six-service follow-up question.
- **N-6, N-7 (nulls, recorded).** N-6: association-ID guessing is moot — the documented workflow always resolves the ID via `describe-iam-instance-profile-associations` (unscopable Describe, prior-plan B-8), so ID entropy is not the controlling factor. Both out of scope going forward.
